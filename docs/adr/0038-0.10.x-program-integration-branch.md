# ADR 0038: Integrate the 0.10.x maintainability program through a non-release program branch

- Status: Accepted on 2026-07-25
- Owners: Product owner, architecture owner, release owner
- Risk: R3 release sequencing; owner-approved and release-owner human-gated
- Amends: [ADR 0033](0033-ci-owned-stable-release-promotion.md) for the bounded `0.10.x` program only

## Context

The `0.10.x` maintainability program contains ordered baseline, canonical-data,
headless migration, retirement, and deferred Presentation slices. Treating each
subordinate stage as an independent release branch to `main` would run release
workflow before the program integration gate. Sending every feature directly
to one long-lived branch would instead remove the review boundary and bounded
scope of exact-version stages such as `0.10.1`.

Existing candidate PRs were created from an earlier `0.10.1` line. Their commits
are useful evidence, but their old target and ancestry cannot become authority
for the owner-approved program.

## Decision

Create one long-lived, non-release program integration branch named `0.10.x`
from a verified `origin/main` SHA.

An owner-bounded stage may create an exact-version subordinate branch, such as
`0.10.1`, from the current reviewed `0.10.x` head. Independently reviewable
features branch from and target that subordinate stage. After its bounded scope,
tests, exact-head review, and CI pass, the subordinate stage merges by reviewed
PR into `0.10.x`.

A program-wide governance or integration slice may use
`feature/0.10.x/<topic>` and target `0.10.x` directly. Every mutable surface
still has one writer, and all normal risk, evidence, Polytail, independent
review, and exact-head CI gates apply.

Neither a feature PR nor a subordinate-stage PR into `0.10.x` starts release
workflow, creates or moves a tag, publishes a package, or creates a GitHub
Release. Only the final owner-approved `0.10.x` integration PR targets `main`
and enters release workflow. Tagging and publication remain separate,
owner-approved actions after that integration passes its release gates.

Candidate commits from an older lineage must be replayed or rebased onto the
current authoritative branch, re-admitted, re-tested, and reviewed at their new
exact head. Branch names and earlier green checks do not transfer authority.

## Rejected options

### Release every subordinate stage directly to main

Rejected because it would run release policy for internal refactor stages and
make the final cross-ticket integration gate optional.

### Merge every feature directly into 0.10.x

Rejected because it would make bounded stage scope harder to review and would
increase mutable-surface contention on the long-lived program branch.

### Merge the existing 0.10.1 candidate branches unchanged

Rejected because their ancestry predates the authoritative `0.10.x` branch and
their review/CI evidence applies only to their old exact heads.

## Consequences

- `main` remains stable and release-capable while internal stages integrate.
- `0.10.1` can be a bounded baseline stage without being a published release.
- Feature and stage PRs retain normal review and CI; no gate is waived.
- The final `0.10.x` to `main` merge is larger than an individual stage, so the
  program integration tests and ticket #197 remain mandatory.
- Release tooling must distinguish PRs targeting `0.10.x` from the final PR
  targeting `main`.

## Migration and verification

1. Record the verified `origin/main` SHA used to create `0.10.x`.
2. Merge the governance slice into `0.10.x`.
3. Create each subordinate stage from the current reviewed `0.10.x` head.
4. Replay only admitted candidate commits; exclude obsolete release-policy or
   Presentation changes.
5. Run phase-local tests, Polytail, the risk-appropriate complete verifier, and
   exact-head review before each integration.
6. Permit the final `0.10.x` to `main` PR only after ticket #197 and all
   firmware, golden, clean-Windows, packaging, protected-CI, and release-owner
   gates are satisfied.

This ADR changes branch authority and release sequencing only. It changes no
firmware range, byte operation, processor authority, support status, or golden
evidence.
