## Measurement authority

`scripts/code_size_policy.py` owns the UTF-8 trimmed-nonblank physical-source
metric. Full production counts C# and AXAML under `src/`. Runtime production
counts non-Presentation C# plus the CRC worker. The four runtime slices now
allocate every runtime line; the desktop composition root is explicitly part
of the Bootstrap + CLI host slice.

Generated output, tests, documentation, profiles, fixtures, line compaction,
and movement to an uncounted directory never count as production reduction.

## What was retired

The frozen inventory identified 13,768 nonblank Bootstrap lines across
authoring/planning/session projections, catalog and route resolution,
execution/delivery/report conversion, inspection/memory/naming, and Workbench
shells. It also identified 775 Application lines in the old Workbench models
and experience-port transport. That **14,543-line figure was gross retirement
surface, never promised net savings**.

At the terminal implementation boundary:

- production contains no `Workbench*`, `CanonicalCapabilityRuntime`,
  `CompositionPlanningAdapter`, `CompositionExperienceAdapter`,
  `FirmwareInspectionAdapter`, `LegacyCombinerPostbuildPlanner`,
  `ICompositionAuthoringExperience`, `ICompositionAuthoringSession`, or
  `WorkbenchRunResult` path;
- Bootstrap contains only composition-root wiring, lifetime/disposal, external
  processor selection, and runtime dependency readiness leasing;
- Presentation has no Bootstrap dependency; CLI owns parsing/rendering and
  calls the same focused Application contracts;
- catalog publication, accepted sessions, inspection/readiness, memory,
  naming, execution, reporting, delivery, and compiled processor plans each
  have one production owner and no compatibility fallback;
- Desktop directly owns exactly six isolated sessions without grouping-only
  session wrappers, and CtrlRAM region/input discovery publishes one coherent
  `MemoryLayoutProjector` result instead of separate Infrastructure projections;
- the retained `LegacyCombinerPostbuildProfile`/processor names describe a
  required external protocol adapter, not the deleted runtime planner.

The old files and symbols were deleted rather than renamed. The replacement
code is the minimum canonical implementation needed to preserve the supported
product behavior and fail-closed evidence contracts.

## Why the planning estimate was too low

The pre-implementation estimate expected a 7,800–10,200 net reduction and a
runtime near 60,000 lines. The implementation disproved that estimate. It
overstated the duplicate share for four concrete reasons:

1. Large Bootstrap files mixed forwarding shells with unique bundle trust,
   profile materialization, fixed/dynamic route, CtrlRAM/General admission,
   report, delivery, and external-tool semantics. Those semantics could not be
   deleted; they had to move intact to Application or Infrastructure.
2. Removing parallel routes required explicit accepted execution-plan,
   immutable artifact, revision, publication-token, capability-fingerprint,
   compilation-fingerprint, and stale-state contracts. Those checks replace
   implicit Workbench coupling and are required for one safe path.
3. UI and CLI could not keep the old DTO transport. Typed client contracts,
   client-owned parsing/rendering, and exact readiness/diagnostic states were
   required to preserve observable behavior without a new facade.
4. Firmware bytes, supported workflows, profiles, diagnostics, report wire,
   delivery behavior, processor protocols, and existing golden evidence were
   deliberately not deleted to meet a line target.

Therefore the reasonable post-retirement size is the measured result:
approximately **67,400 runtime lines** and **96,000 full-production lines**.
This is larger than the old planning point but still smaller than the frozen
predecessor, with the legacy semantic layer removed. A 25,000-line whole
runtime remains incompatible with the retained product scope.

No further line target is imposed on LAR completion. Detail simplification and
performance work after `v0.10.3` must begin from these exact ratchets, prove a
real net reduction or measured benefit, and preserve the one-path boundary.

## Release stop condition

`v0.10.3` is not created from this measurement alone. LAR-00 completes only
when the final frozen diff has:

1. exact lowered runtime and slice ratchets with slice-sum closure;
2. all available golden complete BIN bytes and SHA-256 values unchanged;
3. structure, architecture, UI/CLI, full verifier, and scoped Polytail green;
4. reviewed residual inventory showing no legacy production path or renamed
   equivalent facade;
5. release package, SBOM/provenance, and clean-Windows evidence;
6. owner review, merged PR, and green post-merge CI.

Only then may the release owner create `v0.10.3` and begin the separately
planned detail-optimization milestone.
