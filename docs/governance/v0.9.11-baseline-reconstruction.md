## Decision

The current `0.9.11.10` head was created from the pre-release performance branch
instead of the final protected `v0.9.10` release. It is not a valid release
successor and must not be merged or published as-is.

Reconstruction starts from the final `v0.9.10` tree and replays the reviewed
`0.9.11.10` intent on a separate candidate branch. Official `v0.9.10` safety
semantics win every firmware, Application, Bootstrap, processor, output, and
release-policy conflict. Current `0.9.11.10` UI, startup, DP/LDC, packaging
representation, and spatial-layout intent is then reapplied without weakening
those semantics.

The existing `0.9.11.10` branch is not rewritten or pushed during reconstruction.
Replacing that integration ref, merging to `main`, tagging, or publishing remains
an explicit owner action after all local and GitHub review gates pass.

## Overlap and conflict policy

The 29 shared paths cover `SPEC.md`, release/code-size documents and scripts,
MainWindow XAML/resources/styles/ViewModels, and architecture/bootstrap/UI tests.
They are resolved by rule, never by whole-file `ours`/`theirs` selection:

1. Domain, Application, Profiles, Bootstrap execution, external-processor
   authority, package allowlists, immutable input snapshots, output verdicts,
   and atomicity use the final `v0.9.10` semantics.
2. DP/LDC profile additions are reapplied through the existing V2 compiler and
   deny-by-default policy. No UI-owned range or processor rule is allowed.
3. Startup and package-representation changes may optimize loading/JIT/bundling
   but cannot remove a profile, processor, report, validation, evidence payload,
   or self-contained dependency.
4. Tests are unioned. A stable safety test is not deleted or inverted to match
   the premature branch. Changed assertions require an explained contract change
   and the relevant owner gate.
5. Final `v0.9.10` Changes behavior remains. The capability-driven viewport and
   its renderer contracts stay in the `0.9.12` backlog.
6. The stable Build Completed behavior, the current bottom-right rail, and the
   owner-required spatial control are composed into one UI result.
7. Documentation reflects product version `0.9.11`; `0.9.11.10` remains only
   an integration branch identifier.

## Recoverable Git procedure

Before reconstructing:

1. Create `backup/0.9.11.10-pre-v0.9.10-reconstruction` at `22debe69` and push
   that backup ref without changing the original integration ref.
2. Create an external Git bundle containing the backup, `v0.9.10`, and their
   reachable histories. Store it outside the repository and run
   `git bundle verify`.
3. Create `feature/0.9.11.10/reconstruct-from-v0.9.10` at the original head and
   commit this reviewed M0 plan on that candidate only.
4. On that candidate only, run:

   ```text
   git rebase --onto b0266f312a67d644475731153b1af82f7eadcc95 \
     795f313cab88295f8dc9f922fea555aba72e875b
   ```

5. Resolve each conflict using the preceding semantic rules. If conflict
   density prevents independent review, abort the rebase and replay three
   explicit slices: DP/LDC R3, startup/package, then UI/layout.

Required lineage evidence after reconstruction:

```text
git merge-base --is-ancestor b0266f312a67d644475731153b1af82f7eadcc95 HEAD
git rev-list --count b0266f312a67d644475731153b1af82f7eadcc95..HEAD
git range-diff 795f313c..22debe69 b0266f31..HEAD
git diff --check
```

The original implementation mapping must remain 31/31 in `range-diff`. Because
the reviewed M0 plan is committed before the candidate rebase, the expected
post-rebase count is 32: the 31 original patches plus that one M0 documentation
commit. Every missing or materially changed original patch receives a ledger
entry before M1 passes.

## M5 — post-release branch and version governance

M5 begins only after the approved `v0.9.11` release exists. It is a separate
reviewable documentation/governance phase before any branch deletion.

1. Inventory every local and remote branch by owner, release, merge state,
   reachability, last update, open PR, unique commits, and retention reason.
2. Propose keep/archive/delete sets. Archive or delete no remote ref until the
   owner approves the exact list and protected branches are verified.
3. Define multi-agent ownership: one version integration branch, one owner per
   independently reviewable feature, explicit file responsibility, no shared
   uncommitted edits, phase commits, distinct reviewer, and exact merge target.
4. Add predecessor gates that reject a version branch when the required stable
   tag is not its ancestor. Record `Base-Tag` and `Base-SHA` at branch creation.
5. Define SemVer entry criteria:
   - patch: compatible defect, safety, performance, evidence, or UI correction
     with no new supported workflow/profile contract;
   - minor: backward-compatible user capability or supported IC/mode/profile
     expansion with its complete evidence and migration story;
   - major: incompatible public/profile/report/protocol behavior, removal, or a
     support contract requiring coordinated migration.
6. Define version capacity and freeze: each version has one coherent product
   outcome, explicit non-goals, bounded R3 review capacity, a feature-freeze
   date, no unresolved P0/P1, complete declared evidence, and rollover rules for
   work that misses its gate. Commit count or elapsed time alone never selects a
   version number.
7. Update `SPEC.md`, `AGENTS.md`, development tags, execution workflow, and PR
   template so the rules are executable repository policy rather than a
   one-release note.

The M5 document and any branch operation require their own review and commit.
