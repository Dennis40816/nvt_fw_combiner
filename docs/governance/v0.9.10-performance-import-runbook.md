# v0.9.10 Performance and UI Safe-Import Runbook

Status: prepared framework; no final `0.9.9` SHA has been supplied.

Prepared: 2026-07-18 from
`feature/0.9.10/replace-performance-baseline` at

This runbook lets an integration owner import the reviewed `v0.9.10` process
and UI performance work after establishing the final `0.9.9` predecessor. It
does not perform or require a rebase, does not ask `0.9.9` to know about

## 1. Ownership and one-way dependency

```text
final reviewed 0.9.9 SHA
  -> clean integration worktree owned by the integration owner
  -> v0.9.10 import units in this runbook
  -> authoritative node C and final verification
```

`0.9.9` never imports, cites, or adapts to this branch. The only required input
from outside this line is the final reviewed `0.9.9` SHA, supplied by the total
integration owner. This agent owns the `v0.9.10` patch/evidence framework and
post-import validation, not the operation used to establish the predecessor.

The source branch is a reviewable evidence stack, not a branch that may be
merged wholesale. Its merge base is
`7e18cfa0b10e005307b4ec57fdb5039786ff71fe`; final `0.9.9` will have different
workflow, support, UI, ADR, and size-ratchet state.

## 2. Non-negotiable invariants

Every import unit preserves all of these conditions:

- one shared Application composition use case and one Domain engine;
- Automatic Build performs one authoritative composition run and one output
  commit, never reuses a stale Preview artifact;
- immutable source/reference artifacts and a host-owned mutable work buffer;
- sequential Legacy Combiner commands with exact argv, order, tool binding,
  timeout, and per-command failure attribution;
- one final host readback plus independent diff and allowed-write-range
  validation; selective tail handling is limited to `MERGE_MODE`;
- complete report JSON, output SHA-256, mutation records, changed ranges,
  warnings, processor trace, naming, and atomic-failure semantics;
- a UI inspection snapshot is display authority only; Build always reads and
  hashes its own immutable inputs;
- progress comes only from typed Application phases and never from filenames,
  operation ids, reason text, IC labels, elapsed time, or animation frames;
- no byte percentage or remaining-time estimate without a reviewed contract;
- support exposure, IC families, firmware ranges, processor commands, golden
  outputs, and promotion remain owned by final `0.9.9` plus their normal
  R2/R3 evidence gates.

No performance result authorizes removing hashes, reports, independent diff,
range checks, golden evidence, accessibility, cancellation, or atomic output.

### `P2` Legacy Combiner readback

For a non-merge plan with `C` commands, require exactly:

```text

C output-existence/length metadata checks
1 final complete firmware read
0 intermediate complete firmware reads
```

A plan with `M` `MERGE_MODE` commands adds `M` selective tail reads and appends
only when output is actually short. Staged immutable-artifact reads remain
separate and must be reported.

Run Infrastructure tests plus the NT51926 Common FW 1.4.1 cascade TP-base
full-output case `nt51926-cascade-tp-base-self-regression-20260717`. The
13-command case proves count/order only and must not be represented as
full-output golden parity. Stop for firmware-owner review before accepting this
R3 unit.

### `A1`, `U1`, and `U4/U5` progress and responsiveness

Application owns only these ordered applicable phases:

```text
preparing
reading-inputs
executing-composition
running-external-processor
validating-output
committing-output
preparing-report
```

Preview omits commit; a plan without a processor omits processor. UI shows the
current applicable step and lifecycle ordinal, not byte completion. Required
evidence includes exact feed order, at most seven events, input failure,
cancellation, validation rejection, commit failure, progress-before-worker,
off-dispatcher execution, stale-run rejection, English/Traditional Chinese,
accessible live status, high contrast, and reduced motion with unchanged text
and state.

Run Application, UiSmoke, and Architecture tests after the final wiring.

### `U2a` through `U2c` report scalability

The complete JSON and export are the authority. Initial UI materialization is
bounded, review-required content sorts first, byte previews are bounded, and
detail is created only for the requested page.

Required deterministic checks include:

- `1,000` differences / `40` sections: `0` detail rows at summary, `24` after
  first expansion, `25` after requesting the section's final row;
- loading additional group headers does not materialize their detail;
- escaped labels, full raw JSON, history/save/export, counts, classifications,
  and shared row identity remain exact;
- report projection and parsing stay off the dispatcher.

Run UiSmoke and Architecture tests after each report unit. Run `T1` under
identical B/C conditions before and after `U2c`.

### `U3` immutable inspection snapshot

Require at most one full-file read for one selected display identity/hash,
including facts, mismatch guidance, context suggestion, metadata, coverage,
slots, and postbuild readiness. Re-select/content change invalidates the old
snapshot; cancellation or a newer selection rejects stale results. Context
reprojection may decode again but may not reopen the file. Build performs its
own authoritative reads/hashes and never consumes the UI snapshot.

Run Bootstrap snapshot tests, UiSmoke selection tests, and Architecture tests.

## 7. Fail-stop conditions

Stop the current import unit and retain the last accepted commit when any of
these occurs:

- predecessor SHA or worktree identity is uncertain;
- final `0.9.9` tests are not green before runtime import;
- a conflict touches support exposure, family/evidence status, profile ranges,
  processor commands, base acceptance, or report classification without the
  owning reviewer;
- output bytes, SHA-256, name, mutations, argv/order, warnings, or atomic-failure
  behavior drifts without declared evidence;
- a process becomes visible, commands run in parallel, or staging confinement
  weakens;
- UI progress/report/inspection state is inferred from firmware-facing text;
- saved/exported report JSON becomes incomplete;
- a golden expected output is regenerated to match implementation;
- the source-size ratchet fails. Reconcile ownership and remove genuine
  duplication; do not raise the ratchet or delete safety/evidence merely to
  proceed;
- a retry repeats without a material code, input, command, or environment
  change.

After node C is captured:

1. run Polytail separately for `P1`, `P2`, and the combined UI/progress/report

2. obtain an independent R2 architecture/UI review;
3. obtain firmware-owner review and full-output golden approval for `P2`;
4. verify no real firmware, private evidence, generated performance JSON,
   secrets, or release artifacts are staged;
5. run `git diff --check` and then `python scripts/verify.py --all` once as the
   canonical final local gate;
6. update the final ADR numbers, B/C evidence summary, roadmap, verification
   report, and PR notes in one reviewed documentation phase.

The final PR targets the owner-selected `0.9.10` integration branch, not
`main`. It must identify every accepted unit, exact tests, firmware/profile/
protocol/release impact, missing private evidence, R2/R3 reviewers, and the
final `0.9.9` predecessor SHA.

## 9. Alternatives and consequences

Rejected approaches:

- merge the whole provisional branch: imports stale 0.9.9 documents, ADR
  numbers, size ratchets, and UI/support assumptions;
- squash all performance changes: hides which process/UI boundary caused a
  regression and prevents unit-level rollback;
- optimize only UI animation: leaves duplicate composition, process launches,
  staging reads, report allocation, and inspection fan-out;
- use timing thresholds as CI authority: machine noise would replace
  deterministic parity/count evidence;
- drop report or independent diff evidence: performance would weaken firmware
  safety and auditability.

The selected unit stack costs more review steps but gives the fastest safe
path: each accepted commit has one owner, one narrow gate, a clear rollback
point, and no need for `0.9.9` to know about later work.
