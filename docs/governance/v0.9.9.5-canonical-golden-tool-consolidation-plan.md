## Canonical physical layout

所有 direct golden 移到：

```text
testdata/golden/canonical/
  manifest.json
  README.md
  <IC>/<workflow>/<variant-or-version>/<topology>/<case-id>/
    inputs/
    expected/
    provenance/
```

規則：

1. `<IC>` 使用大寫 `NT519xx`。
2. `<workflow>` 使用 `standard-merge`、`ab-merge`、`dp-replace` 或
   `ctrlram-replace`，不以來源 archive 名稱分類。
3. `<variant-or-version>` 優先使用 manifest 已證明的 Common FW version；沒有
   firmware version fact 時使用既有 variant（例如 `gen-flash`、`flashmap`、
   `dp-256k`），不得由檔名猜版本。
4. `<topology>` 使用已證明的 `single`、`cascade-<count>`；workflow 未宣告
   topology 時使用 `topology-unscoped`，避免推論 topology-independent support。
5. `<case-id>` 保留既有 case／Jira identity；缺 case id 的 Standard Merge case
   使用穩定的 `<ic>-<variant>` id。
6. `inputs/` 只放 immutable composition／postbuild inputs；`expected/` 只放
   owner-approved expected output；`provenance/` 放 BAT、owner notes、source
   archive facts與先前 manifest facts。
7. 每個 physical payload 由 canonical manifest 鎖定 path、role、size、SHA-256、
   source classification、approval 與 legacy path。不得重新生成或修改 expected。

## Alias 與重複 intake

Canonical manifest 的 alias 必須包含：alias case id、target IC、workflow、
variant/version、topology、source direct case id、允許共用的精確 fact、evidence refs、
以及 `directGolden: false`。Alias 不建立第二份 expected BIN，也不讓 alias IC 冒充
direct product golden。

第一批既有 fact scopes：

- Standard Merge：NT51917 → NT51927、NT51919 → NT51929。
- AB Merge：NT51919／NT51932 → NT51929；NT51951 → NT51950 workflow logic。
- CtrlRAM Replace：NT51917 的 exact single／2-chip／3-chip → 對應 NT51927
  direct facts；NT51919 exact single → NT51929；NT51928 non-NB exact 2-chip
  只引用已核准 NT51927-family fact，不引用成相同 output bytes。
- DP Replace：只引用既有 Standard Merge FlashCode／DP control 的 exact case；
  不藉 alias 擴大 project、capacity 或 support scope。

2026-07-17 與 2026-07-18 若為相同 direct case、相同 artifact role、相同 SHA，合併
成一個 physical artifact並保留兩個 legacy path／source intake refs。不同 case 或不同
role 即使 SHA 相同也不自動合併。

## Diagnostics 分離

下列資料不是 expected golden，移到 repository-only：

```text
testdata/diagnostics/golden-evidence/
  owner-handoff/
  ctrlram-replace/
```

- `owner-handoff` 的收件說明、`.keep`、歷史 missing-evidence directories；
- `real_sample/51927_nf_replace_single`、derived experiment 等 diagnostic controls；
- comparison／difference observations若不是 owner expected，必須標成 diagnostic。

Diagnostics 不得由 canonical golden tests 當 expected 讀取，也不進 release
`reference/`。若 diagnostic artifact 是某 direct case 的合法 immutable input，該 input
只在 canonical case 保存一次，diagnostic record以 manifest reference指向它。

## Manifest、consumer 與 release migration

遷移以同一 deterministic mapping table完成，並依序關閉：

1. 建立 canonical manifest validator，拒絕 path escape、未列 payload、size／SHA
   mismatch、alias cycle、alias scope缺件、diagnostic path混入 expected。
2. 搬移 physical files；比較遷移前每個 logical artifact的 size／SHA與遷移後
   physical path或alias target。
3. Golden／Bootstrap／fixture tests只能由 canonical inventory定位case，不得依
   dated sibling path或 filename guessing。
4. `validate_repository.py`、AB／CtrlRAM validators 與 package reference allowlist改讀
   canonical manifest；legacy roots必須不存在。
5. Release只複製 canonical manifest宣告且 release-approved 的 Standard Merge
   reference artifacts；CtrlRAM private inputs、diagnostics與owner-handoff不進 package。
6. `RELEASE-MANIFEST.json`／`SHA256SUMS.txt`仍列出每個實際 shipped path與hash。

## External-tool consolidation

External-tool package records統一具備 logical id、tool/version、platform、runtime status、
release status、payload path/role/size/SHA、argv/working-directory status與provenance。
Legacy Combiner維持現有 runtime registration與release inclusion；DiffNFMerge只補齊
repository/package/deployment identity測試，維持 not-registered／release-excluded；
CRC Worker維持generated package artifact。不得把 recovered NT51930／NT51931
Combiner或 golden archive內 executable納入 repository/runtime/release。
