# v0.10.4 simplification and ownership audit

Status: implementation candidate; final frozen-diff verifier and owner review pending
Measured: 2026-08-11
Release baseline: `v0.10.3` (`6e028261ef7c235c60c1400045c8d9da3160bb2c`)
Implementation branch base: `571554a924e8e950e34931db0eb4a30c9d6d63d3`

## Outcome

The audit keeps the six canonical workflows and their firmware semantics
unchanged. It removes remaining zero-production-caller planning, report,
selector, startup, and test-shortcut code; moves firmware file identity and
stability checks behind the Application inspection port; and keeps live report
projection typed while retaining the durable JSON compatibility path.

The result is not claimed to be the mathematical minimum. The stop condition is
that another full production caller scan finds no unused internal type and no
unused production method except two explicit deterministic test seams, while
the remaining larger candidates are either durable compatibility paths,
cross-scope contract changes, or disproportionate to their measured benefit.

## Next performance stage: read-only TEST parallelization plan

No verifier or test scheduling code changes in this audit. The repository
already overlaps at most three top-level verifier lanes; the dominant test tail
is instead Bootstrap static catalog publication plus the large UI and
Architecture test classes. The reviewed next-stage order is:

1. Capture clean-SHA TRX/binlog timing, peak memory, test inventory, skips, and
   current-auto versus three-worker/four-worker/jobs-one baselines.
2. Isolate Bootstrap catalog publication state so unrelated catalog tests can
   leave the nonparallel collection.
3. Split the Architecture and UI mega-classes by independent state ownership;
   keep package-trust MSBuild, process-kill, XAML/App initialization,
   performance-observation, coverage merge, and golden/private evidence serial.
4. Add a bounded project scheduler only if the first three steps leave a real
   queue gap. Keep it only for at least 10% solution-test or 5% complete .NET
   lane improvement on the same SHA, with no more than 25% peak-memory growth.

The next stage must preserve the exact eight project inventory, existing skip
count, coverage pairs, complete golden bytes/hashes, cleanup, and absence of
orphan processes or stale catalog state.

### Follow-on test-parallelization execution record

The clean T0 baseline is commit `b71c3b74`, GitHub Actions run
`31488645668`. The canonical .NET lane took 468.2 seconds, including 169.7
seconds for the solution test command. Its eight executable test projects
reported Domain 404, Application 526, GoldenRegression 17, Infrastructure 403
with two declared platform skips, ProfileContract 387, Bootstrap 925,
Architecture 213, and UI smoke 444. The project durations were respectively
0.9, 2, 12, 28, 2, 89, 46, and 67 seconds; the solution command already
scheduled several projects concurrently.

T1 is the test-only commit `cc7f27c5`. It replaces the process-wide Bootstrap
catalog serialization collection with per-test host graphs for all 31 cases
that replace a catalog publication. The residual shared Bootstrap test host is
query-only: 52 source files and 264 references retain zero publication reload
calls. Bootstrap discovery remains 925 and Architecture discovery remains 213.
The focused 60 cases passed, the full Bootstrap project passed repeatedly, and
the first independent Polytail review found no remaining P0-P3 issue. Local
warm project timings of 33.7 to 35.2 seconds are recorded only as race and
directional evidence; they are not compared directly with the 89-second CI T0
because the runners differ.

T2 is the test-only commit `1323bb51`. It decomposes the former 211-case
`RepositoryBoundaryTests` partial mega-class into nine ownership classes while
retaining the separate two-case project-dependency suite. The 16 package-trust
cases remain in one MSBuild collection and therefore stay serial with each
other; the collection does not disable parallel execution for the other 197
read-only cases. Fact, Theory, InlineData, skip, and 213-case discovery
inventories are unchanged. Independent runs completed all 213 cases in 29.5
to 31.2 seconds, compared with 35.6 seconds immediately before T2 on the same
local tree. This local delta is accepted as layout evidence; the clean CI
comparison remains the release performance authority.

T3 is the test-only commit `acc6ea03`. It decomposes the 319-case
`ShellViewModelTests` mega-class into 12 state-owned groups. Ten groups use
independent class-fixture host graphs; six external-golden cases remain serial
with one another; and the three process-wide Shell observation cases plus the
sole Avalonia `App.Initialize()` resource case remain assembly-exclusive. UI
smoke discovery remains 444 with the same 388 methods, Fact, Theory, InlineData,
MemberData, skip, assertion, and normalized data-case identity inventories.
Three isolated full-project runs completed in 30.6 to 35.5 seconds with a
32.1-second median, compared with the 60.1-second pre-change median. A separate
clean process-tree A/B measured 55.3 to 35.6 seconds (-35.6 percent), while
peak working-set/private memory fell from 1012.7/771.8 MiB to 848.8/663.9 MiB.
Independent R2/Polytail review found no P0-P3 issue.

T1 through T3 add 297 nonblank test-harness lines after helper consolidation;
they add no production line and change no profile, schema, golden expectation,
fixture BIN, external-tool payload, or report wire.

The scheduler audit rejects a custom per-project runner. The single solution
command already owns project-level scheduling, while the canonical verifier
owns coverage aggregation, cancellation, and cleanup. On the same T3 tree and
exact coverage command, the default completed in 100.7 seconds with
4592.0/2782.3 MiB peak working-set/private memory.
`-m:6` completed in 119.5 seconds and was 18.7 percent slower. `-m:8` took
112.0 seconds and exposed one Application test failure; that test immediately
passed under the default scheduler. Neither experiment meets the admitted
10-percent solution-test or 5-percent complete-lane improvement threshold.
The canonical verifier therefore remains unchanged.
