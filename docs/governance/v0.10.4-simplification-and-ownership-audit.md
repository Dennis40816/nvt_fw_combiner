# v0.10.4 simplification and ownership audit

Status: implementation candidate; final frozen-diff verifier and owner review pending
Measured: 2026-08-11 through 2026-08-12
Release baseline: `v0.10.3` (`6e028261ef7c235c60c1400045c8d9da3160bb2c`)
Implementation branch base: `571554a924e8e950e34931db0eb4a30c9d6d63d3`

## Outcome

The audit keeps the six canonical workflows and their firmware semantics
unchanged. It removes remaining zero-production-caller planning, report,
selector, startup, and test-shortcut code; moves firmware file identity and
stability checks behind the Application inspection port; and keeps live report
projection typed while retaining the durable JSON compatibility path.

The result is not claimed to be the mathematical minimum. The stop condition is
that another full production caller scan finds no unused internal type and no
unused production method except two explicit deterministic test seams, while
the remaining larger candidates are either durable compatibility paths,
cross-scope contract changes, or disproportionate to their measured benefit.

## Next performance stage: read-only TEST parallelization plan

No verifier or test scheduling code changes in this audit. The repository
already overlaps at most three top-level verifier lanes; the dominant test tail
is instead Bootstrap static catalog publication plus the large UI and
Architecture test classes. The reviewed next-stage order is:

1. Capture clean-SHA TRX/binlog timing, peak memory, test inventory, skips, and
   current-auto versus three-worker/four-worker/jobs-one baselines.
2. Isolate Bootstrap catalog publication state so unrelated catalog tests can
   leave the nonparallel collection.
3. Split the Architecture and UI mega-classes by independent state ownership;
   keep package-trust MSBuild, process-kill, XAML/App initialization,
   performance-observation, coverage merge, and golden/private evidence serial.
4. Add a bounded project scheduler only if the first three steps leave a real
   queue gap. Keep it only for at least 10% solution-test or 5% complete .NET
   lane improvement on the same SHA, with no more than 25% peak-memory growth.

The next stage must preserve the exact eight project inventory, existing skip
count, coverage pairs, complete golden bytes/hashes, cleanup, and absence of
orphan processes or stale catalog state.

### Five-minute required .NET check convergence

The owner accepts five minutes as the target for the complete required
`dotnet / build-test` check. The earlier three-minute number applies only to
the single solution `dotnet test` command; it is not an end-to-end CI target.
The first implementation kept one stable job and one canonical verifier
invocation. That restriction was useful for rejecting an unmeasured custom
scheduler, but the owner superseded it on 2026-08-12 after the bounded
single-runner candidates missed the five-minute gate. The stable required-check
name and canonical verifier authority remain mandatory; evidence-producing work
may now run in the closed DAG defined by ADR 0027.

Two measured duplications are removed:

1. `dotnet format` now verifies whitespace only. On the same restored base and
   machine, the full formatter took 65.573 seconds and the whitespace formatter
   took 11.165 seconds. This does not remove style or analyzer enforcement: the
   Release solution build retains `EnforceCodeStyleInBuild`, `AnalysisLevel`, analyzer
   warnings, and `TreatWarningsAsErrors`. Characterization probes proved that
   whitespace drift fails the formatter, while an `IDE0161` style violation
   and a `CA1062` analyzer violation pass whitespace verification but fail the
   Release build.
2. The 15 package-trust counterfactual materialization cases retain their
   existing Theory/Fact identities and per-case diagnostics, but share one
   bounded `dotnet msbuild -m:1 -nr:false` host. The batch uses isolated
   workspaces, explicit begin/end/result/completion markers, asynchronous
   output drains, process-tree termination, and final cleanup. A missing case,
   unexpected success, incomplete batch, timeout, or diagnostic mismatch still
   fails its original test. The complete Architecture project remains 213
   cases and improved locally from 47.0 seconds to 14.456 and 14.645 seconds in
   two complete runs; the focused 15 cases completed in about three seconds.

The first frozen single-runner candidate, `43afe0da`, passed its functional,
coverage, golden, fixture, and cleanup gates in Actions run `31516164870`, but
its required check took 378 seconds and therefore failed the 300-second gate.
The bounded `d4078b52` follow-up let the solution test own the initial build

A same-tree local scheduler screen then compared the unchanged solution

server-first readiness handshake. No retry, skip, coverage reduction, golden
change, or production behavior is accepted as a timing fix.

The approved R2 stacked ticket implements one full Release-build producer,
three closed Windows test shards, and one always-run evidence finalizer. The
canonical map in `scripts/verify.py` assigns Bootstrap 925, UI 444, and a core
set of Domain 404, Application 526, Infrastructure 405 with two skips,
ProfileContract 387, GoldenRegression 17, and Architecture 213: exactly eight
projects, 3,321 tests, and two skips. Each project produces one TRX and one
paired JSON/Cobertura report. The workflow contains no `.csproj` path and no
coverage merge implementation.

The finalizer keeps the required name `dotnet / build-test` and accepts only
the exact source SHA, SDK `10.0.301`, disjoint project set, counters, hashes,
paths, producer success, and file inventory. It then copies the eight validated
coverage pairs into the existing canonical coverage owner, runs the unchanged
CtrlRAM fixture-manifest gate followed by coverage policy, and uploads only the
merged coverage evidence. Each producer first copies declared regular evidence
into a clean allowlisted upload root; the finalizer keeps the four downloaded
artifact roots separate until exact ownership and collision checks pass.
Build/test logs and intermediate TRX/coverage artifacts are retained for three
days; no build output, firmware payload, private fixture, profile, schema, or
golden expectation is transferred.

Implementation is not performance acceptance. It must pass the local frozen
verifier and scoped R2 review, then two fresh same-SHA workflow runs must each
reach the finalizer verdict within 300 seconds. The first miss stops this DAG;
it does not authorize another shard, retry, skip, filter, or weaker gate.

The repaired stacked base `1d972880` passed PR #358 Actions run `31548842206`:
