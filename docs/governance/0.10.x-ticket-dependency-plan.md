# 0.10.x Ticket Dependency Plan

Status: owner-approved dependency graph. GitHub issues and PRs are the sole live
execution-state records.

This document anchors the reviewed GitHub issue inventory for the `0.10.x`
maintainability program so the repository can be reviewed without reconstructing
planning dependencies from GitHub. It does not duplicate open/closed,
completion, review, or current-frontier state. If an edge or approved outcome
changes, update the issue and this table in the same planning phase.

`ready-for-agent` means that a ticket is sufficiently specified for agent
execution. It does not override a listed blocker, evidence gate, branch rule,
review requirement, or owner approval. A ticket is on the executable frontier
only when every listed blocker is complete and its own intake gates are
satisfied.

Dependency depth is a topological planning aid, not a release number. Tickets
at the same depth may run independently only when they do not contend for the
same files, ownership seam, private evidence, or human reviewer. The owner
allocates dependency-ready tickets to an actual later `0.10.x` release; this
plan does not assign `0.10.1`, `0.10.2`, or any other version.

## Stable execution ordering

Live completion and dependency-ready frontier state are queried from GitHub;
they are not committed here. File ownership and the one-writer rule still
govern which dependency-ready tickets may run concurrently. #221 is an early
removal ticket, not a late compatibility cleanup: it must close before #177
migrates remaining metadata families, before #187 migrates remaining TP Header
families, and before #194 closes headless convergence.

The ordering deliberately keeps the headless data/Application/CLI migration
ahead of Presentation work:

1. #173 establishes the canonical seam.
2. #221 removes retired routes while #174-#194 migrate metadata, sessions,
   firmware routes, mapping, readiness, naming, and only the remaining admitted
   headless consumers.
3. #182, #185, #191, #192, #207, #208, and #214 consume those frozen contracts
   in the deferred UI wave.
4. #195 and #196 delete compatibility and legacy runtime owners.
5. #230 freezes the Core semantic seam; #231 and #232 may then proceed in
   parallel with disjoint writers; #233 removes remaining Bootstrap/CLI
   duplication; #229 closes the four-slice hard gate.
6. #197 is the final integration/release gate.

#183 precedes #180; it is not blocked by #180. #194 has no Presentation
dependency. These two rules prevent the former readiness cycle and keep UI
work from delaying headless convergence.

#183 may therefore use one named CtrlRAM compiled-route bridge with
`AuthoringRevision(0)` while #180 still owns the session migration. The bridge
must carry the existing admitted route into the shared readiness gate, bind
runtime results to an explicit environment generation, and extract only
processor/tool references already present in the compiled plan. #180 replaces
the revision-zero input; #194 deletes the bridge when CtrlRAM resolves from the
canonical capability catalog. It is never an alternate firmware, evidence, or
publication owner.

## Family and FirmwareConfig allocation

ADR 0039 and ADR 0041 distinguish the strong perfect-family invariant from one
typed, fact-scoped partial-sharing contract:

- #175 defines the one all-IC FirmwareConfig General Parameters structure and
  pilots map-bound locators through NT51927/NT51928 without making the global
  definition a TP-family fact. It also freezes their
  Initial-Code-shared and TP-shared author vocabulary, but does not create
  dedicated runtime relationship subclasses or migrate their DPCMI runtime
  binding.
- #176 binds the same global FirmwareConfig structure for NT51950/NT51951
  topology prerequisite without creating another field table.
- #177 owns the remaining metadata bindings. Its slices include the
  family-owned NT51919/NT51929/NT51932 perfect-like DPCMI migration,
  NT51917/NT51927 perfect-family plus NT51917/NT51927/NT51928 shared-part
  bindings, and NT51923/NT51926 exact-reference consumers.
  NT51950/NT51951 retain only their TP-region relationship; FirmwareConfig and
  DPCMI remain global definitions with map-specific locator bindings.
- #221 removes NT51920/NT51925/NT51930/NT51931 before #177/#187/#194. Their
  former locators, including NT51920 `0x3E014` and NT51931 `0x3E018`, remain
  historical traceability only and are not migration input, runtime authority,
  or a reason to retain a compatibility route.

The #177 deployed evidence matrix therefore covers NT51919/29/32 as one
perfect-like family, NT51917/27/28 as Initial-Code/TP shared parts, and
NT51923/26 as exact-reference consumers. Consumer-wide workflow convergence
remains #194 and is not a reason to duplicate these family facts.

No later slice may redefine FirmwareConfig fields, duplicate perfect-like
firmware semantics per member, or treat shared TP/Initial Code as authority for
another artifact part.

## NT51928 dual-capacity allocation

- #239 owns one NT51928 Standard Merge capability and one DP Replace capability
  with declared `0x40000` shared Initial-Code/TP and `0x80000` LDC variants.
  It consumes the already accepted `initial-code-shared` and `tp-shared`
  `SharedFactRelationship` scopes; it cannot promote NT51927/NT51928 to a
  perfect family or copy their shared geometry.
- For Standard Merge, LDC absence selects the `0x40000` candidate; supplied
  LDC selects the `0x80000` candidate and must then pass structural validation.
  Failure blocks and never falls back to absence. DP Replace selects its variant
  from the accepted Reference length. Neither mechanism infers IC identity or
  creates another route/Support Matrix row.
- #239 owns the canonical replacement selection group, conditional operation
  materialization, warning-only non-uniform Initial Code/DP/LDC validation, and
  headless Application/CLI/report evidence. It is ordered after #219 to avoid
  concurrent ownership of shared profile/compiler integration surfaces.
- #194 consumes #239 during remaining route convergence. #182 later presents
  its typed LDC `PendingInput`/`NotApplicable`/Optional and Warning states
  without deriving capacity or firmware validity in Presentation.

## DiffDLM and Diff NF allocation

The 2026-07-27 owner correction supersedes any interpretation of a legacy
DiffDLM outer envelope as one contiguous writable range:

- Every profile whose canonical DiffDLM record composition includes Diff NF
  must bind explicit writable DLM and preservation-mask subranges whose
  non-overlapping union covers each complete active target record. Missing, `unknown`,
  overlapping, or incomplete mask authority blocks compilation; it is not a
  warning or compatibility fallback. A DiffDLM filename or outer envelope alone
  does not trigger this contract; DLM-only routes retain their separately
  declared write geometry.
- #219 owns the canonical full-stride-source-to-masked-target contract for the
  NT51919/NT51929/NT51932 perfect family. It pilots the owner-confirmed
  NT51932 4-IC geometry (`0x0B90` DLM bytes in a `0x1400` source/target stride,
  with the `0x0870` Diff NF tail preserved) and binds cascade IC Count `N` to
  exactly `N - 1` active DLM subranges.
- #219 must prove that preview, execution, and mutation audit preserve every
  NF byte, ignore invalid source NF filler, and reject any required DLM
  subrange that is entirely one repeated byte. Validation covers every required
  record. AE records after the active `N - 1` prefix are inactive dummy content:
  they are not copied, cannot enlarge the compiled DiffDLM source/read or
  scatter/write set, and leave inactive target records identical to the
  reference before postbuild. For this family, postbuild owns FWConfig Backup
  placement; runtime compares the marker-derived actual start with
  `AlignUp(0x2D100 + (N - 1) * 0x1400, 0x1000)`. An in-authority mismatch is a
  typed Build Report warning, while missing/ambiguous or out-of-authority
  placement fails closed. Its affected DiffDLM
  authoring route keeps independent NF selection unavailable until a separate
  NF-mode/`DiffNFMerge.exe` contract is approved.
- #188 owns the NT51950/NT51951 migration using the independent owner-confirmed
  2-IC geometry: target `0x33200`, stride `0x1400`, writable Diff CtrlRAM
  `[+0x000,+0x910)`, and preserved Diff NF `[+0x910,+0x1400)`. Their declared
  End Flag `0x36FFC` fixes the canonical FWConfig Backup start at `0x36000`;
  postbuild copies the primary FWConfig from `0x22200` to that destination.
  No implementation may reuse NT51932's split, wider IC Counts, or
  count-derived Backup placement formula by analogy. Direct expected-output
  and exact processor mutation evidence remain promotion gates.
- #194 migrates remaining consumers only after #219/#188 expose this behavior
  through the canonical compiled plan. #184/#194 project DiffDLM as one
  renderer-neutral segment with typed preservation details; #208 presents the
  compact hover/focus summary and lateral kept-range details. Presentation
  never owns the byte mask.

## Change control

Any dependency change must preserve all of the following:

1. the issue body and this repository anchor agree;
2. no ticket is moved ahead of its characterization, evidence, or ownership
   prerequisite;
3. a dependency depth change is not presented as an automatic release
   allocation;
4. `ready-for-agent` remains a specification-readiness label rather than a
   bypass for blockers; and
5. the final integration gate remains downstream of coverage, verifier,
   compatibility-owner deletion, legacy-runtime retirement, and #229 Canonical
   Core Convergence.
