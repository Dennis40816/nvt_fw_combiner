# 0.10.x Ticket Dependency Plan

Status: owner-approved; synchronized with the closed design grill and GitHub
issues on 2026-07-27.

This document anchors the reviewed GitHub issue inventory for the `0.10.x`
maintainability program so the repository can be reviewed without reconstructing
planning state from GitHub. GitHub issue bodies remain the live execution
records. If an edge changes, update the issue and this table in the same
planning phase.

`ready-for-agent` means that a ticket is sufficiently specified for agent
execution. It does not override a listed blocker, evidence gate, branch rule,
review requirement, or owner approval. A ticket is on the executable frontier
only when every listed blocker is complete and its own intake gates are
satisfied.

Dependency depth is a topological planning aid, not a release number. Tickets
at the same depth may run independently only when they do not contend for the
same files, ownership seam, private evidence, or human reviewer. The owner
allocates dependency-ready tickets to an actual later `0.10.x` release; this
plan does not assign `0.10.1`, `0.10.2`, or any other version.

## Execution frontier at publication

The completed baseline is #170, #171, and #172. The open executable frontier
after the 2026-07-27 synchronization is #173 plus the independent retirement
ticket #221. #173 freezes the canonical catalog, route identity/fingerprint,
shared UI/CLI availability, explicit reload/LKG, and NT51929 Standard Merge
tracer. #221 removes four withdrawn capabilities before later migrations can
mistake their transitional facts for target data.

The ordering deliberately keeps the headless data/Application/CLI migration
ahead of Presentation work:

1. #173 establishes the canonical seam.
2. #221 removes retired routes while #174-#194 migrate metadata, sessions,
   firmware routes, mapping, readiness, naming, and only the remaining admitted
   headless consumers.
3. #182, #185, #191, #192, #207, #208, and #214 consume those frozen contracts
   in the deferred UI wave.
4. #195 and #196 delete compatibility and legacy runtime owners; #197 is the
   final integration/release gate.

#183 precedes #180; it is not blocked by #180. #194 has no Presentation
dependency. These two rules prevent the former readiness cycle and keep UI
work from delaying headless convergence.

## Family and FirmwareConfig allocation

ADR 0039 and ADR 0041 distinguish the strong perfect-family invariant from one
typed, fact-scoped partial-sharing contract:

- #175 defines the one all-IC FirmwareConfig General Parameters structure and
  pilots it through the NT51927/NT51928 shared TP part. It also freezes their
  Initial-Code-shared and TP-shared author vocabulary, but does not create
  dedicated runtime relationship subclasses or migrate their DPCMI runtime
  binding.
- #176 binds the same global FirmwareConfig structure as the NT51950/NT51951
  topology prerequisite without creating another field table.
- #177 owns the remaining metadata bindings. Its slices include the
  family-owned NT51919/NT51929/NT51932 perfect-family DPCMI migration,
  NT51917/NT51927/NT51928 typed Initial Code/TP references, and the admitted
  NT51923/NT51926 exact-reference consumers. NT51950/51 retain their #176
  TP/FirmwareConfig relationship and may add only exact owner-approved shared
  facts.
- #177 replaces the transitional dedicated Initial-Code-shared/TP-shared
  DTO/schema/runtime branches with one `SharedFactRelationship`. Each entry
  carries a readable role, exact typed canonical fact references,
  applicability, reason, and evidence. A role cannot select runtime behavior or
  inherit support, publication, processor, topology, or another part.
- #221 removes NT51920, NT51925, NT51930, and NT51931 from production
  selectors, canonical admission, profiles/processors, relationships, package
  inventory, and Support Matrix. Their transitional #177 bindings are removal
  inputs, not target metadata.

No later slice may redefine FirmwareConfig fields, duplicate perfect-family
firmware semantics per member, introduce another partial-sharing runtime class,
or treat a readable shared-fact role as authority for an unreferenced fact.

## DiffDLM and Diff NF allocation

The 2026-07-27 owner correction supersedes any interpretation of a legacy
DiffDLM outer envelope as one contiguous writable range:

- Every profile whose canonical DiffDLM record composition includes Diff NF
  must bind explicit writable DLM and preservation-mask subranges whose
  non-overlapping union covers each complete active target record. Missing, `unknown`,
  overlapping, or incomplete mask authority blocks compilation; it is not a
  warning or compatibility fallback. A DiffDLM filename or outer envelope alone
  does not trigger this contract; DLM-only routes retain their separately
  declared write geometry.
- #219 owns the canonical full-stride-source-to-masked-target contract for the
  NT51919/NT51929/NT51932 perfect family. It pilots the owner-confirmed
  NT51932 4-IC geometry (`0x0B90` DLM bytes in a `0x1400` source/target stride,
  with the `0x0870` Diff NF tail preserved) and binds cascade IC Count `N` to
  exactly `N - 1` active DLM subranges.
- #219 must prove that preview, execution, and mutation audit preserve every
  NF byte, ignore invalid source NF filler, and reject any required DLM
  subrange that is entirely one repeated byte. Validation covers every required
  active record. For records after the active `IC Count - 1` prefix, every
  selected source byte present inside the profile-declared DiffDLM extent is an
  inactive passthrough to the same relative target byte; a missing suffix keeps
  the immutable reference and overflow is ignored with a warning without
  widening write authority.
- Every independent NF slot is unavailable for a resolved Cascade route using
  the preservation-mask policy. Presentation omits it, while the shared
  Application/CLI contract rejects stale or manually constructed bindings so
  this cannot be bypassed through another entry point. Single routes are not
  restricted, and full-artifact-replace Cascade routes retain their
  independently declared NF behavior. A future `NF0`/`NF1`/... per-record
  model requires a separate owner-approved contract; direct `DiffNFMerge.exe`
  authoring remains out of scope.
- NT51923, NT51926, and the NT51927 TP family use `FullArtifactReplace`;
  #187/#194 preserve that behavior and do not attach an NF mask because of a
  `DiffDLM.bin` filename.
- #188 owns the NT51950/NT51951 migration using the separately owner-confirmed
  950-like geometry: target record 0 starts at `0x33200`, stride is `0x1400`,
  writable Diff CtrlRAM is `[+0x0000,+0x0910)` (2320 bytes), and preserved Diff
  NF is `[+0x0910,+0x1400)` (2800 bytes). The current map's Cascade branch is
  2 IC / one slave record. No implementation may reuse NT51932's `0x0B90`
  split or infer a wider IC Count range by analogy. Direct expected-output
  evidence remains a promotion gate even though the record geometry is now
  owner-confirmed.
- #221 removes NT51920/25/30/31 rather than classifying or migrating their
  legacy `DiffDLM`/`NF_Diff_*` inventories.
- #194 migrates remaining consumers only after #219/#188 expose this behavior
  through the canonical compiled plan. #184/#194 project DiffDLM as one
  renderer-neutral segment with typed preservation details; #208 presents the
  compact hover/focus summary and lateral kept-range details. Presentation
  never owns the byte mask.

## Change control

Any dependency change must preserve all of the following:

1. the issue body and this repository anchor agree;
2. no ticket is moved ahead of its characterization, evidence, or ownership
   prerequisite;
3. a dependency depth change is not presented as an automatic release
   allocation;
4. `ready-for-agent` remains a specification-readiness label rather than a
   bypass for blockers; and
5. the final integration gate remains downstream of coverage, verifier,
   compatibility-owner deletion, and legacy-runtime retirement.
