# 0.10.x Ticket Dependency Plan

Status: owner-approved and published on 2026-07-25.

This document anchors the reviewed GitHub issue inventory for the `0.10.x`
maintainability program so the repository can be reviewed without reconstructing
planning state from GitHub. GitHub issue bodies remain the live execution
records. If an edge changes, update the issue and this table in the same
planning phase.

`ready-for-agent` means that a ticket is sufficiently specified for agent
execution. It does not override a listed blocker, evidence gate, branch rule,
review requirement, or owner approval. A ticket is on the executable frontier
only when every listed blocker is complete and its own intake gates are
satisfied.

Every ticket must also pass the mutable-surface and execution-slice admission
rules in [`ticket-execution-admission.md`](ticket-execution-admission.md). The
initial per-ticket disposition is recorded in
[`0.10.x-ticket-slice-audit.md`](0.10.x-ticket-slice-audit.md). A graph node is
not automatically one pull request.

Dependency depth is a topological planning aid, not a release number. Tickets
at the same depth may run independently only when they do not contend for the
same files, ownership seam, private evidence, or human reviewer. The owner
allocates dependency-ready tickets to an actual subordinate stage.

Owner allocation, 2026-07-25: the first subordinate stage is `0.10.1`, created
from the current `0.10.x` after this governance PR integrates. Its bounded
scope is headless #170 plus #171 and #172. Existing `0.10.1` work is candidate
evidence only until rebased or replayed, re-admitted, and reviewed against the
new `0.10.x` head. #173 and later data work remain unallocated until that stage
integrates; all Presentation tickets remain deferred.

## Owner execution priority: canonical data first

The first implementation wave reorganizes the repository's canonical IC-first
data structures and resolution flow according to `SPEC.md`. UI layout,
navigation, visual styling, selection-slot redesign, and ViewModel migration
are deferred. Presentation files do not enter a data-wave mutable surface
unless the owner explicitly opens the corresponding UI slice.

This remains vertical delivery: each data slice must carry one real workflow
from canonical facts through resolution/compilation to an Application-facing
query or command, with contract, CLI, integration, or golden evidence. Existing
UI behavior remains unchanged through a non-authoritative compatibility adapter
when required. A temporary adapter must have a named deletion criterion and
cannot duplicate offsets, ranges, metadata structures, formatter definitions,
or firmware policy.

If a headless child unblocks later data work while a sibling Presentation child
is deferred, the dependency follows the integrated headless child rather than
waiting for the parent ticket's UI completion. The issue tracker and execution
card must record that child-level edge before implementation begins.

## Change control

Any dependency change must preserve all of the following:

1. the issue body and this repository anchor agree;
2. no ticket is moved ahead of its characterization, evidence, or ownership
   prerequisite;
3. a dependency depth change is not presented as an automatic release
   allocation;
4. `ready-for-agent` remains a specification-readiness label rather than a
   bypass for blockers; and
5. the final integration gate remains downstream of coverage, verifier,
   compatibility-owner deletion, and legacy-runtime retirement.
