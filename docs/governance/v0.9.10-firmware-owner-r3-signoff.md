## Exact R3 decision scope

The firmware owner is asked to approve only the evidence-preserving execution
and I/O strategy below for v0.9.10. The release does not add an IC, workflow,
profile, range, command, CRC/header algorithm, postbuild route, support promise,
or product golden. `Golden verified`, `Evidence open`, and `Not available`
remain separate. NT51931 Replace remains Not available.

### Automatic Build

- One user Build performs one authoritative composition run and one output
  commit. It does not execute a hidden second composition for report creation.
- DP 256/512/1024 KiB changes from 2 runs / 4 successful artifact reads to
  1 run / 2 reads. CtrlRAM changes from 2 sessions / `2C` process launches to
  1 session / `C` launches: 2 commands stay 2 launches and 13 commands stay 13.
- Failed required input commits no output and starts no processor session.
- Output bytes/SHA, mutations, validations, issues, command argv, and report
  meaning are parity-locked by the 7/7 deterministic execution surface.

### Legacy Combiner pipeline

- Commands remain sequential and exact. No command is parallelized, combined,
  skipped, cached across runs, or reordered. Tool identity, argv, timeout,
  hidden-window behavior, cancellation, exit checks, immutable artifacts, and
  unexpected staging-entry rejection remain per-command gates.
- Every command consumes the same private staged firmware left by its
  predecessor. Intermediate full-image values are neither product output nor
  parity evidence, so the host does not read the complete file between normal
  commands merely to observe them.
- After the final successful command, the host reads the complete staged image
  once, diffs it against the pre-pipeline baseline, and rejects any change
  outside the union of all declared command write ranges. No intermediate
  failure can publish an output.
- Only an evidenced `MERGE_MODE` shortened-output path may read the smallest
  predecessor tail needed after minimum declared block coverage. It is not a
  complete-image read or parity checkpoint; other shortened command families
  fail closed.
- Complete staged-firmware reads therefore change from `2C+1` to 1 per
  successful session. Process launches remain exactly `C`.

## CtrlRAM TP-version ordering clarification

On 2026-07-20 the firmware owner explicitly confirmed that TP firmware-version
editing is required and that the exact order is **apply the confirmed version,
bar, and sub-version first, then invoke postbuild**. The release implementation
therefore uses this sequence:

1. clone the immutable reference into the output work buffer;
2. apply typed version/bar and sub-version plan patches;
3. apply the selected CtrlRAM mappings;
4. invoke the unchanged profile-owned postbuild processor;
5. verify the canonical Backup contains the confirmed version; and
6. atomically commit the output only after that validation passes.

This clarification is limited to exact admitted NT51926 V2 routes whose
canonical firmware-config source is already modeled. It changes no profile
JSON, region/range, processor id, command argv, CRC/header algorithm, short-file
prefix behavior, support status, or no-edit golden claim. A processor that does
not propagate the confirmed values to Backup fails before publication.

The focused processor test observes the patched bytes before invocation and the
negative test proves zero output commit when Backup is not propagated. The UI
end-to-end test builds through the registered processor and reads `2A / D5 / 0C`
from the output Backup. Existing NT51926 FW 2.0 no-edit golden coverage remains
9/9, and `python scripts/verify.py --all` passes at
`d28c166a51a0c14733ccbd658d4d80509154fc83` with Release build 0 warnings / 0
