## 判讀依據與 transition 定義

- [SPEC：Authoring state and shared application contracts](../../../SPEC.md#authoring-state-and-shared-application-contracts) 第 23–26 項：Application 擁有 `AuthoringSessionState` 與 transition policy；Presentation 持有固定的五個 mode session 及 UI 狀態，沒有 process-global accepted-state store。IC／IC Count 改變只保留相容輸入，失效 derived state；非同步發布必須通過當前身分檢查。
- [R09-01](../1.2.1/R09-01.md) C-02～C-05、D-03、E-01／E-03／E-04：inspection 是 Application publication，Presentation 持有未提交 request／selector token 與 viewed bank；typed draft 型別不是接受或執行的證明。[R09-02/03](../1.2.1/R09-02-03.md) §3 已記錄第一批 Memory Layout／pending facts 回到 Application，§4 的其餘 migration 與限制仍保留，不能用較早報告把已刪第二路徑寫成現況。
- `first-entry`：目的 mode 尚無當前、相容且成功接受的 context；Home shortcut 與直接導覽都須納入觀察。catalog default、顯示 label 或 picker draft 不等於使用者已確認，也不等於目的 mode 已接受。
- `context-switch`：改 IC、有效 Number／AB topology、mode，或 catalog `ResolutionToken`／route／compilation 改變；CtrlRAM write-bank／version request 變更也屬相依 authoring context 變更。Standard 的隱藏 Number token 不自行賦予 topology 語意；viewed bank 單純切換是 UI view，不是 write-bank 變更。
- `re-entry`：回到曾進入的 mode。先區分同 context 的 no-op、同頁 mode 往返、確認跨頁清除後返回，以及離頁期間 catalog／context 已變；最後一類套用 `context-switch`，context 已無效則回到 `first-entry`，不能因「曾進入」而略過重新解析。

表中 Keep／Invalidate 表達既有 owner 契約的條件，Source 記錄固定 head 的實際機制與落差 G1–G4。`無` 表示該類資料沒有可沿用的舊值。以下條件適用每條路徑：

1. **accepted context**：只有目的 mode 自己成功的 `Activate`／`Select`／inspection adoption 可建立當前 `ActiveSessionSnapshot`。失敗維持舊 snapshot 的行為，只代表原 context 仍在；不得把它重新標成新 IC／Number 的成功結果。
2. **相容輸入**：`AuthoringSessionState.ProjectSlots` 僅在 capability fingerprint 相同且 `DefinitionId` 相符時保留 `SelectedPath`／`FileStamp`；重建後 lifecycle 是 `Selected`／`Empty`，不是沿用 terminal health。`ProjectDraft` 對 CtrlRAM 優先使用新 exact execution plan 的 draft；其他 draft 依 `DraftCapabilityFingerprint` 相符才保留。Presentation 留下的 path 只是待檢查候選，不能代替這些條件。
3. **當前 publication**：`Activate` 的 no-op 必須同 route、compilation、slot definitions、resolution token 及同一 exact capability instance；`Select` 同 route 為 no-op。其他成功 transition 依既有 policy 修訂 revision 並重建 derived state；`InvalidateCanonicalPublication` 則直接清除 catalog／snapshot。舊 lease 不能因 UI generation 相同而取得發布權。
4. **derived 與歷史**：inspection／readiness／preview／validation／output 的「當前有效性」依 session、revision、route、compilation、slot 與 file identity／stamp 判定。歷史 Report 與已產生檔案各有生命週期；失效當前結果不表示刪除歷史或輸出檔，也不能把歷史結果套入新 context。

## 現行落差與保留的決策邊界

- **G1：首次選 IC 的 shared admission 尚未統一。** Home 經 `BeginWorkflowContext` 的 cancelable draft／Confirm；直接導覽走 `ShellNavigationViewModel`／`ActivateWorkflowPageContext`，`PublishCanonicalCatalogState` 與 page-context 初始化會投影 catalog default。`FirstWorkflowActivationTests` 明確分開兩種入口；這證明現行路徑，不證明直接導覽已符合 shared chooser 意圖。[first-entry handoff §1](../../ui/post-v1.1.0-navigation-and-ctrlram-first-open-handoff.md#1-shared-first-entry-ic-selection) 仍標示 pending design approval；chooser skip 的 session／process／persisted lifetime、跨 workflow reuse 與原子性未由本矩陣決定。
- **G2：re-entry 的輸入保留有不同前置事件。** 固定 mode sessions 與 page context 可以留在記憶體，但 `ConfirmNavigationAndClear` 在成功導覽後清除 source page inputs；`ClearSelectedInputs` 清除該頁各 mode 選檔、inspection 與 run display，並標記離頁 refresh。不能將 SPEC 的「只保留相容選擇」寫成「每次返回必定恢復檔案」。navigation Cancel 與已確認 clear 是不同事件；R15-02 Cancel／Back 的新流程與互動驗收仍在後續 scope。
