Evidence for the NVT marker rule (commander scan of the 198 Golden BINs in
`testdata`, 2026-09-26): complete `00 4E 56 54` markers occur only at the
end-flag position right after each bank's FWConfig Backup (TP section end
minus 4). Standard flash and TP inputs carry one: NT51923/926 `0x3BFFC`,
NT51927/928 `0x34FFC`, NT51929 `0x2EFFC`, NT51932 `0x30FFC`/`0x31FFC`/`0x33FFC`
by variant, NT51950/951 `0x36FFC`. AB flash carries exactly one per bank at the
same bank-local position: NT51929 `0x2EFFC` and `0x6EFFC`, NT51950 `0x36FFC`
and `0x76FFC`, including the 1 MiB Hiway Display OSD image, whose OSD bytes
contain no marker. No Golden file has a marker anywhere else. A rule that
checks the layout-declared end-flag position of each bank (and ignores
markers elsewhere) accepts every Golden case and excludes Display OSD bytes.

Header backup CRC investigation (wave 2, Codex `gpt-6-astra`, read-only, 2026-09-26;
private evidence stays outside Git): the 32 differing bytes are eight 4-byte CRC fields — per bank, the
DLM CRC and Header CRC of the main TP Header (`[0xA000,0xA200)`, B `[0x4A000,0x4A200)`) and of
`FLASHMAP_HEADER_COPY` (`[0x2D30C,0x2D50C)`, B `[0x6D30C,0x6D50C)`), file offsets in `ab-replace/output`.
The algorithm is CRC-32/MPEG-2 (poly `0x04C11DB7`, init `0xFFFFFFFF`, no reflection, no final XOR, stored
little-endian); DLM coverage per bank is `[0x22200,0x33200)`. The Header copy keeps the CRC values of an
earlier pass, and the copy lies inside the DLM coverage, so the initial Header state and processing history
carry into later CRCs. The existing two-pass sequence reproduces the candidate output exactly; one, two or
three passes from the known starting points do not reproduce the owner's TP, while composing the owner's
changed TP with the existing AB relocation rules reproduces the owner's output exactly, so the difference
exists in the TP before AB composition. Every main CRC and each copy's own Header CRC is valid in both
outputs; that does not prove boot or recovery safety. A separate defect: B normalization keeps a stale
Header CRC ([bug](bugs/BUG-20260926-b-normalization-stale-header-crc.md)). Owner facts needed: (1) how the
owner's changed TP was produced (fresh build or edited BIN; inputs, Combiner version, command order, Header
and copy state per pass); (2) at which stage the SVN changes and who initializes the copy and its CRC fields;
(3) what reads `FLASHMAP_HEADER_COPY` (runtime information, boot fallback or recovery) and what it validates;
(4) whether the copy's DLM CRC is meant to be an earlier-stage value and whether B-copy addresses are meant
to stay bank-local; (5) whether the Header CRC must be refreshed after B normalization before the copy, and
which CRCs should match when A and B use the same TP; (6) the firmware-owner basis for the historical
single-IC CtrlRAM 16-byte allowance. The fix is R3 through the existing profile and processor contracts,
never by adding passes or copying the owner's CRC values.

Release re-run analysis (wave 1 item E, read-only, 2026-09-26; evidence
reproduced on scratch clones against the history-audit helper only):
the validator audits finalized records with `diff-tree -m` and exempts a merge
only when its other parent is an ancestor of the tree-equal parent (ADR 0061).
The `1.1.x` trunk model (decision 22) therefore fails at every release, not only
after a stopped one: merging a release's `main` merge back into a diverged
trunk marks every finalized record and attestation as changed. Options:
A (interim, R2 governance text or R0 handoff rule): after a release pull
request merges, bring the release branch or trunk to `main` by fast-forward
before any further finalization, and rebase, not merge, the trunk onto `main`
for its first push; B (R3, validator exemption for a two-level containment
merge; conflicts with the planned supersession of ADR 0061); C (relax the
polytail base check; not recommended, also needs the ruleset change and B);
D (fresh candidate branch per attempt; recovery procedure only). Recommended:
A now; the root fix is WS-GOV retiring capability-reuse history replay. Also
note: main's ruleset requires up-to-date branches (`strict` required checks).

CI core-shard diagnosis (wave 1 item C, read-only, 2026-09-26; artifacts are
kept 3 days, so older names come from earlier local copies). Causes: H1, the
PowerShell helper of `FileSystemVersionManagerWriteLeaseTests` sometimes does
not print `STARTED` within its 10 s deadline (cold start; 3+ runs); H2, one
`NotSupportedException` from `RandomAccess.GetLength` in
`WindowsStableRelativeWriteTree.PrepareForPromotion` (suspected handle reuse;
the exception also escapes `InstallAsync`'s typed issues); H3, one legacy
launcher start returning false within 6 ms (cause hidden by a bool result); H4,
one empty Domain discovery inventory; H5, "Re-run failed jobs" let the
aggregate job pick the stale attempt-1 artifact in 2 of 5 reruns. Systemic:
`scripts/verify.py` drops a failing project's discovery, trx and coverage from
the upload, so the failing test names never reach the artifact. Proposals:
upload failing projects' evidence and print failing tests to the console and
step summary (R2); `overwrite: true` for evidence uploads, and until then start
a new run instead of re-running failed jobs (R2); split H1's child start from
its readiness deadline (R1, owner confirmation because the deadline was meant
not to be relaxed); diagnose H2 with the new evidence first; typed result for
H3; longer failure-artifact retention (R2).

## Working rules carried from 1.1.12

- R3: independent design review of the record and a proposal diff, then the
  admission commit, then the implementation commit.
- Before merging any pull request, read its review threads; the release
  workflow blocks on unresolved P1 threads.
- Documentation edits still run Architecture.Tests (2,500-line text ceiling).
- Finalize with the evidence commit as the reviewed head's direct child; R3
  owner attestations follow as its direct child; merge with merge commits.
- After a release pull request has merged, finalize later fixes only on a
  history that contains `main` (until the WS-GOV fix lands).
- Start `feature/1.1.13/<topic>` branches from `1.1.x`. A pull request head must
  contain its base, and the history audit flags a merge that brings the trunk
  into a branch after its records are final: merge the trunk into a feature or
  batch branch only before its evidence commit, then freeze, review and
  finalize that head.
- Release target date: not set; the owner decides.
