### 3.3 Retry 與 workflow rerun 不可混為一談

| 行為 | 現行規則 | 來源 |
|---|---|---|
| CI job-local retry | 完整首跑證據有效且 VSTest exit 1，才允許一次 failed-FQN retry；最多 20 FQNs，同 FQN 的全部 theory rows 一起重跑 | `docs/ci/pull-request-ci.md:79`、`:91` |
| retry coverage | 第二次不收 Coverlet；coverage 仍用完整首跑，不以小集合替代 denominator | `docs/ci/pull-request-ci.md:108` |
| 不可 retry | GoldenRegression、build/discovery failure、hang/crash、不完整或無效證據 | `scripts/verify.py:5833`；`docs/adr/0079-test-architecture.md:657` |
| 時間界線 | shard verifier 入口起算 25 分鐘 budget；剩不到 420 s 不開 retry；5 分鐘 blame-hang 是 inactivity timer，不是每 test 的 wall deadline | `docs/ci/pull-request-ci.md:118`；`docs/adr/0079-test-architecture.md:663` |
| flaky gate | 恢復者仍標 flaky；finalizer 要求 checkout 中 **open** bug record，且記載完整 FQN；release source-CI 不接受該 run 任何 attempt 的 flaky observation，即使已有 record | `scripts/verify.py:5808`；`docs/adr/0079-test-architecture.md:635`、`:645` |
| workflow rerun | finalizer 挑每個 producer 最新的 workflow-attempt artifact；未 rerun 者保留較早證據。但真實 workflow rerun 驗證尚未閉合，契約仍要求失敗後啟動新 run | `scripts/verify.py:6155`；`docs/ci/pull-request-ci.md:53` |
| 本機完整驗證 | exact partition 各 case 執行一次；沒有 CI failed-FQN retry，也沒有 partition 失敗後 unfiltered fallback | `docs/adr/0079-test-architecture.md:686`、`:1074` |

A′／B 的共同下界與限制：

- 在維持本次 case 速度、class 內序列及其成本的模型下，不拆 Rejection class 的 Bootstrap phase 下界約 **200.7 s**；其純 case duration 總和為 200.569 s，實際 class span 為 200.697 s。這不是跨機器、跨排程不變的常數。
- 含最慢 Equivalence case 的任何 part，固定該 case 速度時至少需要 **146.2 s**；若完整保留 Equivalence class，其本次 span 為 **190.9 s**。
- 審查的 `291→215 s` 把 case phase 與 TRX-start-relative 結束點混用。以上 A′ 已統一時間原點；約 88.4 s 是在列明前提下可消除的尾段模型，尚未實測。
- A′ 可能同時縮短 CI bootstrap job 與本機 pool 中 Bootstrap 的工作項；但目前 CI 模型仍由 UI 主導，縮短 Bootstrap 不等於縮短整體 CI wall。A 與 A′ 的收益也不能直接相加：A′ 改變 `t_bootstrap` 後，須重算 pool 排程。
- 本次沒有證明 A′ 能穩定先取 slot、其餘 collections 不會延後成為新尾端，或 B 的淨收益必然較差。優先 A′ 的理由是它避免新增 process、Release copy 與獨佔 batch 的成本。

方案 C 另有兩個現況判斷：

1. **若只縮 UI 且其他路徑保持目前模型**，.NET 分支最多由 `636+40=676 s` 降至 `477+40=517 s`，約省 **159 s**；整體 CI 先碰到 Python 的 **562 s**，所以整體約只省 **114 s**。這是僅改善 UI 的情境上限，不是 U4/U5 所有設計的總收益上限。
2. 單搬 core project 至 bootstrap，兩者原本皆短於 UI（445、477 < 636 s），沒有現成證據支持整體 wall 收益；又缺 core 各 project 時間，現在不能提出可信的搬移名單。來源：`evidence/1.2.1/R50-data.md:265`、`:267`、`:269`。

**建議順序：補資料 → A → A′ → 只有收益仍不足且 Bootstrap 確為本機瓶頸才試 B；C 維持獨立 G2/R3 交付。** U4 的 runner 工作量與 wall time 應分別量測。
