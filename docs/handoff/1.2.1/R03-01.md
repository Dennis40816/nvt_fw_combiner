- 沿用 inventory 的 R03-01／R03-02、R04–R06、C01、R09-03、R33-04、R37，不新增第二份 backlog。下表只是這些項目的現況與證據分解。
- 排程採 allocation decision 175：1.2.1 只交盤點、契約及決定，Launcher 更新實作在 1.2.6。舊 handoff 的「1.2.1 啟動開發」、inventory R03-02 的「缺陷納入 1.2.1」，以及 roadmap 舊 work package 的 1.2.0 說法，均不能授權本版改 production。〔E01〕
- decision 181 比 inventory 的 decision 164 摘要更新：R-4／R-6 已延至 1.2.6；R-3 已整合。R37 仍指 R-5，不能用 R37 完成來代稱 R-4／R-6 完成。這是待後續同步的文件差異，本次不改檔。〔E16、E22〕
- 「程式／契約存在」、「測試原始碼有覆蓋」、「歷史紀錄曾驗證」、「本候選實測通過」分別看待。本次只能建立前三者的抽樣證據，不能宣告第四者。
- 表內「待確認」表示指定範圍尚無足夠證據，不表示已證明全 repository 都沒有該能力。風險欄的 R2／R3 是後續改動涉及的 authority；本報告本身仍為 R0。

**1. O03：首 tranche 優先選哪一個有界候選？**

**2. O07：cold-health 的產品回應與後續版本如何選？**

- **A：保留 250 ms 契約，條件式納 1.2.6 C01-1／C01-2（建議先評估）。** 先量真實 packaged cold path，僅在既有 payload／entry owner 做有界減工；成功須同時達到核准 cold/warm 分類與 deadline，不得靠 test warm-up。若量測顯示無法合理滿足，就停止此修正方案，回 R03-02 選 B，不宣稱已解。
- **B：1.2.6 改成有明確上限的 cold-health observation／分段預算。** 必須先以量測決定數值、等待呈現、取消及 cleanup 邊界。現行 `DefaultHealthObservationDeadline = ProgressDelay`，兩者同為 250 ms；須先決定是否解耦 health cutoff 與 UI progress delay。若透過共用的 `ProgressDelay` 改預算，也會改變其所代表的進度顯示時機；須分別記明兩者預期值，同步 ADR 0062 `:123-124`、`:150-151` 與受影響 consumers。這個 health 階段與 Bootstrap START／ADMITTED 的 5.5 s admission 階段分開；超出新上限仍為 `HealthUnavailable`，不得在背景晚啟動或取得 recovery 刪除權。本報告不臆定 500 ms 等新數值。成功／失敗判斷要在 R03-02 填實後才能實作。〔E03、E31〕
- **C：產品修正延至 1.5.2，1.2.6 只保留明示缺口。** 維持現行 fail-closed 分類，記錄 cold 失敗及限制；此選項不等於問題關閉，也不能省掉 1.5.3 的 cold-start／recovery 驗收。

O07 還需在選定表內填入：目標機器／AV／儲存條件、何謂 cold、重複次數與 P95 計算、具體 hard budget（如有變更）。目前只有歷史局部耗時，沒有足以決定這些數值的 real-package 基準。decision 160 的「1.2.0 預期 single EXE」只是當時延期理由，不能當成修復或測試豁免。〔E02、E03〕
