## 1. 結論

目前 NFC 只有一個已 pin、已註冊、已隨包的 Combiner：`legacy-combiner-1.13.0`（`Combiner.exe` 41,472 bytes，SHA-256 `ed6b5828…0c76bf`，加 app-local `vcruntime140.dll` `d5e4d9a3…9066`），由兩個 Infrastructure adapter 呼叫：`LegacyCombinerPostbuildProcessor`（in-place、多命令 CtrlRAM postbuild）與 `ExternalCombinerProcessor`（input-output-file、單命令 AB merge）。目前使用的模式契約共 6 種 argv 形狀（§2.1），來自 11 個 postbuild invocation profile（161 條宣告命令，含各分支）與 2 個 AB merge invocation profile；帶 legacy binding 的 processorStage 共 31 個 profile（26 CtrlRAM Replace 全 `supported`；5 AB Merge 全 `executable-candidate`，其中 2 個是 decision 83 保留、未發布的特殊 Desay 宣告）。呼叫者為 10 個 IC 的 CtrlRAM Replace、NT51950/NT51951 AB Merge，以及 AB CtrlRAM Replace 的 bank 路徑（Perfect family NT51919/29/32 重用 M4；Partial family NT51950/51 重用 M5＋M6 finalizer，全部 candidate／contract-only）。Standard Merge、Perfect family AB Merge 與 General 候選都不呼叫 Combiner。Combiner 相關 Direct Golden 17 案：14 個 CtrlRAM 全為 `allowed-byte-difference`（核准 CRC 字差異契約），3 個 NT51950 AB 為 `direct-full-output`。

Python 候選在本 repo 內沒有任何檔案、hash、manifest、測試或 golden；只有 roadmap intake 文字。intake 的三個識別字各自代表不同東西：`d7b08b92…` 是 nvt_combiner 的來源 commit、`2.0.0.1` 是該 Python 產品的版本字串、`1.13.0.0` 是它模仿的 legacy console banner（legacy 1.13 原始碼 `main` 印出 `Combiner version:1.13.0.0`）——三者都不是可部署候選。可部署候選必須是（exact commit、可重現 build 方式、`Combiner.exe` SHA-256、唯一 `toolBindingId`）四件一組；registry 的唯一鍵是完整 `toolBindingId`，`toolVersion` 應忠實記錄選定產品版本，不以 legacy banner 作部署身分屬命名建議（待 owner 接受）。已驗證的 Python 證據只有 intake 自述的 AB Merge 與 range-safety 差分紀錄（已讀、未重跑、不覆蓋 CtrlRAM Replace 各 route）。因此 O08 的實質選擇是「是否以 owner pin 的 Python build 作為 1.2.5 R07-02/03 的候選，並以 legacy 1.13.0 為唯讀 parity 基準與回退」；建議是，且先取代 argv 最單純、既有樣本最多的 in-place 兩命令模式（§4 Q2）。host 的 write-range 檢查只是權限上界，不能替代完整 bytes parity（§3.2）；回退不是只回指 profile binding（§3.1、Q4）。

## 3. 取代時需要的契約

### 3.1 mode 對照與 binding 身分

1. argv drop-in 是最小充分的協定契約：候選對 M1–M6 每個 argv 形狀（含 block 四元組、`<fw> <fw>` 重複、`0x` 十六進位大寫格式）產生相同輸出 bytes 與相同副作用（`MERGE_MODE` 縮短輸出行為要嘛相同、要嘛不縮短——後者 host 仍通過，因 overlay 僅在需要時發生）。drop-in 讓兩個 adapter 與 `legacy-combiner-v1` stage kind 沿用（ADR 0006：同協定族一個 adapter），但**不代表只換 manifest／binding**：binding 身分在多層被比對——AB adapter 的 invocation index 以 `ProcessorId` 唯一且拒絕 invocation／request binding 不同（`external-tool.invocation.binding-mismatch`）；`RuntimeReferenceCompilationProof` 要求 compiled processor 與 postbuild plan 的 `ToolBindingId` 相同；Partial AB finalizer shape 寫死 `legacy-combiner-1.13.0`。同一 invocation id 目前不能同時登記兩種 binding。
2. 新 binding：依 `external-tools/README.md` 步驟建立 `external-tools/<toolId>/<version>/manifest.json`，`toolBindingId` 唯一（registry 唯一鍵）、`toolVersion` 為 exact 字串（忠實記錄選定產品版本）、`adapterId` 沿用 `legacy-combiner-postbuild-v1`（若 drop-in）；exe SHA-256 為部署身分。
3. R07-03 必須同步更新並驗證整條身分鏈，並定義回退單位：postbuild catalog 11 個 profile 的 `toolBindingId`、31 個 profile `processorStages`（含 trusted bundle content hash／trust index 重算）、`ExternalCombinerInvocationCatalog.ToolBindingId`、`V2CompositionPlanCompiler.RuntimeReferenceReplace.Banks.cs:380`、`scripts/external_tool_policy.py`（固定 tool 集合與 manifest 期望值）、`scripts/package.ps1`、`scripts/smoke-release.ps1`（hash 與 argv 寫死）、`ExternalProcessorEnvironmentLoader.cs:597`（只把 `toolId == legacy-combiner` 納入 runtime tool 清單）。回退方案可以是有界的雙 binding admission 設計（逐 route），或完整已驗證版本回退；本評估不替 owner 選定（Q4）。
4. B-bank 新模式（R08）不是 M1–M6 的取代，屬新 stage／invocation 契約；若只在 Python 候選實作，會使 Q1 的 A 選項失去該功能。

### 3.2 host staging、diff 與寫入範圍規則（不變，候選必須在此規則下通過）

- 外部 processor 只能改 host 建立的 staging copy：postbuild 在 `<stagingRoot>/<runId>/output/<fw>` + `BIN/` + 空 `map.txt`；AB 在 `work.bin`／`output.bin`；預設 stagingRoot `%TEMP%/nvt-fw-combiner/external-tools`，工具根 `AppContext.BaseDirectory/external-tools`。
- 共同前置：manifest SHA-256 比對；staging 目錄已存在拒絕；非 Bundled runtime 時另經 `ExternalRuntimeDeployment`（§4 Q4 限制）。
- postbuild adapter 專有前置：需 compiled protocol plan（否則 `legacy-combiner.compiled-plan.missing`）；argv 全路徑 > 259 字元拒絕（`external-tool.argument-path.too-long`）。AB adapter 專有前置：以 `ProcessorId` 解析 invocation profile，binding 不符拒絕；staged artifacts 寫成 host 檔並於執行後檢查未變。
- 每條 postbuild 命令後：檔長不變（`external-tool.output-length.changed`）、staged artifacts 未被改、`MERGE_MODE` 縮短輸出 overlay 規則、staging tree 無多餘檔案、timeout／exit code／process-tree cleanup（ADR 0081）。
- 最後：`ByteDiff.FindChangedRanges` + `ChangedRangePolicy(allowedWriteRanges)`，任何**超出**宣告寫入範圍的 byte → `external-tool.write-range.violation`；AB 路徑再由 profile 只 import 三個 header 字。
- 這項檢查的界限（F01）：`allowedWriteRanges` 是權限上界，不是必寫清單；空變更集合通過；postbuild 的 diff 在整個命令序列結束後做，無法證明中途寫入後又還原。候選若**漏寫**某個 CRC 字、或在範圍內寫錯值，host 不會拒絕。因此漏寫、範圍內錯值與 CRC／header 語意正確性必須由適用 output assertions、候選對固定 legacy 的完整 bytes parity、對 owner Golden 的差異契約與獨立寫入範圍證據驗證；write-range 檢查只證明「沒有越界」。
- 寫入範圍來源：profile `allowedWriteViewIds`（canonical map view）＋ `LegacyCombinerPostbuildPlanCompiler.WriteRanges` 依 family／mode／crcArgument 推得的 integrity 字。候選若寫到宣告以外的位置會 fail-closed，這是 parity 的第一道（但非充分）獨立證據。

### 3.3 Golden 證據要求

- 兩項分開的驗收：(a) 候選 vs 固定 legacy 1.13.0 的**完整輸出 exact parity**（相同起始 bytes、相同 argv、逐 route），差異 0 才算通過；(b) 結果 vs owner Golden 的**既有差異契約**——14 個 CtrlRAM Direct 依各案 `phaseBResult`／`allowedByteDifferenceContract`（例 nt51926 fw141 single 固定 16 bytes），3 個 NT51950 AB 依 `direct-full-output`。(b) 通過不能替代 (a)，(a) 通過也不擴張 (b) 的核准範圍。
- 17 個 Direct 案例經 `python scripts/verify.py --release-golden`（Windows；每案一次 fresh TRX passed）選入，含 nt51926 fw141 single（`profileId: not-materialized` 但有執行路徑與固定 actual SHA）；這是程式契約，本報告未執行。alias／self／input-only 案例只能證明輸入或差異契約，不能當輸出 parity。
- 沒有 Direct Golden 的 route（NT51917、NT51919、NT51928、NT51951 AB、NT51927 2/3-chip、AB CtrlRAM Replace R13/R14、保留 Desay）只能做 (a) 黑箱等價，不能宣稱 owner 認證；R07-02 報告需分開列。
- 保留 legacy 證據：legacy 的 golden、smoke 與 owner 1.13 源碼封存不因切換而刪除；Python repo 的差分紀錄不得當作全 route 認證（intake 原文）。
- 非幂等性：decision 161／BUG-20260926 已證明 postbuild 輸出依起始 CRC 欄位而異（12 bytes reset 可重現 owner 樣本）。(a) 必須在相同起始 bytes 下比對；若 R31-02 決定 reset 政策，(a)(b) 的基準要跟著改，順序已在 allocation（R31-02/03 → R07-02）。
- 變更 expected bytes 需與 firmware 語意同級的人工 gate（`testdata/AGENTS.md`），不得為讓候選通過而改 Golden。

## 4. Owner 決定題

**Q1（O08）選哪個候選？**
- A. 維持 legacy 1.13.0 為唯一 runtime；Python 只當 R07-02 的第二 oracle，1.2.5 不做 R07-03 切換。
- B. 以 owner 指定的 exact nvt_combiner commit（可為 `d7b08b92` 或更新）建置 `Combiner.exe`，以 exe SHA-256 pin、給唯一 `toolBindingId`（命名建議 `python-combiner-<ver>`），legacy 1.13.0 並存作回退。
- C. 待 owner 提供已建置 exe + hash + build 說明後再決定（延到 1.2.5 前）。
- 建議：B，附條件「commit + 可重現 build + exe hash 三者同時記錄；build 若不可重現則 pin exe hash 為準；候選大小與依賴先量測（Q4）」。理由：R07-02/03 與 R08 都需要一個可執行實體；A 讓 B-bank 新模式無處落地；C 只是把 B 的前置條件延後。

**Q2 哪些模式先取代？**
- A. 先 M4+M5（NtBased CRC8：NT51919/29/32/50/51 CtrlRAM Replace；Direct 7，皆 allowance；兩命令 in-place）。
- B. 先 M6（AB merge）——profiles 皆 executable-candidate、缺 firmware-owner review，切換不提升 support；但它是唯一有 direct-full-output Golden（3 案）的模式。
- C. 先 M1（`CRC_Enable`：NT51923/26；Direct 6，皆 allowance；兩命令 in-place）。
- D. 六種一次切換。
- 建議：第一波 A+C（13 個 Direct 樣本最多、argv 最單純、無縮短輸出；但 13 案全為 allowance，故 (a) exact parity 對 legacy 是主要驗收，且須先同步 R31 基準）；第二波 M6（與 R08 B-bank、R13 AB Replace finalizer 同批，需 firmware-owner review）；最後 M2+M3（105+24 條命令、縮短輸出 overlay、2/3-chip window copy、Direct 僅 1、release smoke 依賴 M3 不變輸出契約）。owner 亦可決定 M2+M3 永久留 legacy（雙套件常駐）。

**Q3 CLI 契約：drop-in 還是新協定？**
- A. drop-in：argv 與 M1–M6 完全相同，沿用 `legacy-combiner-postbuild-v1` adapter 與 `legacy-combiner-v1` stage kind；仍需 §3.1 第 3 點的整條身分鏈更新。
- B. 新協定：新 adapter、新 stage kind，需 ADR 0006 的 R2/R3 協定、封裝、安全與證據 gate。
- 建議：A；B-bank 新模式另立 stage kind（R08-02 決定），不混入 drop-in 範圍。

**Q4 回退單位與容量／runtime 限制？**
- A. 雙套件並存至少一個 release，逐 route 回退：需要有界的「雙 binding admission」設計（同一 invocation id 目前只能一個 binding；proof／finalizer 比對 binding），兩套 allowlist、smoke 與失敗驗收都保留。
- B. 完整版本回退：候選 release 整體切換，回退＝回到前一已驗證 release（含 legacy）；不需雙 binding，但無逐 route 粒度。
- 已知限制（不是待確認）：完整 release ZIP 上限 134,217,728 bytes（ADR 0060；`package.ps1`、`smoke-release.ps1` 實際檢查）；`NvtFwCombiner.exe` 另有 80,000,000-byte 上限，不適用於 Combiner；非 Bundled Toolchain runtime 路徑的 `ExternalRuntimeDeployment` 讀 exe／runtime 各受 16 MiB 限制且只複製 exe 與 `vcruntime140.dll`（one-folder 型 Python build 的旁置依賴不會被複製）；`ToolchainRuntimeCandidateInspector` 對 runtime tool 清單內的 exe 另有 8 MiB 檢查，而該清單只納入 `toolId == legacy-combiner`，新 toolId 是否受同一檢查須明定。
- 未知（待 owner／R07-03 量測）：候選 exe 大小、是否 one-file、依賴哪些 DLL、雙套件完整 ZIP 大小。
- 建議：A，前提是 R07-03 先提出雙 binding admission 設計並量測上述限制；若設計成本過高則 B。legacy 現有 payload 166,016 bytes 只是現況，不能推算候選 ZIP。
