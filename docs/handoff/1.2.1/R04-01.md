## 1. 結論

**建議 canonical ZIP R04-02 本輪 no-go，維持 `1.2.6` 不建置、權重為 0。** 以完整前版 ZIP 可供重用的條件量測，canonical ZIP CDC 加上修訂版模型 manifest 後，兩組節省分別為 **33.54%／14.84%**，以目標 ZIP bytes 加權的節省為 **24.19%**。尚未加入 Check、重試、fallback 或簽章成本，即未達本報告建議的「目標 ZIP bytes 加權平均至少 30%、每個 warm-cache 版本對至少 20%」門檻。這是候選門檻，**不是已批准的 owner 數值**。〔§4；`docs/handoff/1.1.14/1.2.x-allocation.md:182`〕

現行 Check 會完整驗證 package；Registry 選定候選的成功路徑驗證兩次。若保留這些來源讀取，再另做差異取得，canonical ZIP CDC 的比較收益約為 **6.71%／2.97%**。**這是未改契約、採 package 邏輯讀取下界的比較模型，不是 delta 設計的預期值或實測網路節省。** 提案要求先新增 metadata-only「可下載版本」狀態，該狀態變更屬另需准入的 R2；採納時應重新計算新流程的成本，不能把現行 `Q` 當成 delta 必然承擔的成本。〔§6；`docs/architecture/launcher-update-proposal-20260923.md:51-53`；`docs/handoff/1.2.1/R03-launcher-plan.md:37`〕

| 項目 | 可重現方法 |
|---|---|
| Entry identity | 移除各版 `NvtFwCombiner-v<version>-win-x64/` 外層目錄，以剩餘完整相對路徑配對，再比未壓縮內容 SHA-256。沒有忽略內部版本文字。45 個目錄另計，不當成檔案重用。 |
| 逐檔傳輸 | 加總目標版 changed／added entries 的 ZIP `compress_size`。依 local header 的 filename／extra 長度定位原始 compressed streams，另核對 identical entries：兩組均 **0 個不同**。 |
| CDC | 自製 deterministic Gear chunker；min 16 KiB、mask `0xffff`（名義 64 KiB）、max 256 KiB；每個 entry／整份 ZIP 起點及每次切塊後歸零，尾塊保留，空內容無 chunk。實際平均受 min/max、內容及尾塊影響。 |
| Gear table | `G[b] = LE64(SHA256(b"NFC-R04-01-GEAR-v1" + bytes([b]))[:8])`；逐 byte 更新 `h = ((h << 1) + G[b]) mod 2^64`；長度達 max，或達 min 且 `(h & 0xffff)==0` 時切塊。 |
| 重用範圍 | 目標 chunk 的 SHA-256 對照前一版**全部** chunks；缺少者按 hash 去重後傳一次。重用率分母是目標內容 bytes，不是檔案數。本次兩種 CDC、兩組比較的缺少 chunks 均無重複 hash。 |
| 未壓縮 CDC 傳輸 | 同時列未重用 raw bytes，以及每個缺少 chunk 獨立 raw DEFLATE、level 9 的 bytes。使用 `zlib.compressobj(9, zlib.DEFLATED, -15)`，計入 `compress()` 與 `flush()`；Python 3.13.5、zlib 1.2.13。這不是重新產生原 ZIP 的算法。 |
| canonical ZIP CDC | 對 ZIP 原始 bytes 直接分塊；缺少 chunks 原樣傳送。以舊 ZIP chunks 加新 chunks 依目標順序逐段比對並累計重組 hash；兩組均與目標 ZIP 完全相符。 |
| Metadata 估計 | 本修訂採下表明列的 JSON 模型重新計算。**數字是該模型的確切編碼大小，不是正式產品 metadata 成本；未包含正式 schema、簽章、憑證、Registry／Catalog 或 transport overhead。** |

**修訂版 metadata 編碼：** 使用 `json.dumps(obj, ensure_ascii=False, separators=(',', ':')).encode('utf-8')`，保留下表的 key 插入順序，不排序 object keys，無 BOM、縮排或尾端換行。整數採十進位，SHA-256 為小寫 64 字元。`version` 為不含 `v` 的目標版本字串；`zip.name` 為完整 ZIP basename。

| 物件／模型 | Keys 與順序 |
|---|---|
| 共用 `zip` | `name`、`size`、`sha256`；size／hash 對整份目標 ZIP |
| 共用 file record | `path`、`size`、`compressedSize`、`sha256`；path 已移除外層版本目錄，size／hash 對未壓縮 entry |
| 共用 `chunker` | `{"algorithm":"NFC-R04-01-GEAR-v1","min":16384,"mask":65535,"max":262144}`；algorithm 的 Gear table 與切塊規則如上 |
| a. Whole ZIP | `version`、`zip` |
| b. Per-entry reuse | `version`、`zip`、`files`、`removed`；files 包含全部目標檔案，依 path 的 Unicode code point 升冪排序；removed 為排序後的舊版獨有路徑，本次均為 `[]` |
| c. 未壓縮 CDC | `version`、`zip`、`chunker`、`files`、`removed`；每個 file record 最後追加 `chunks`，依該 entry 的切塊順序列出；chunk keys 為 `sha256`、`size`、`deflateSize` |
| d. Canonical ZIP CDC | `version`、`zip`、`chunker`、`chunks`；依整份 ZIP 的切塊順序列出，chunk keys 為 `sha256`、`size` |

Metadata 的有序 chunk arrays 保留每次出現；只有傳輸 payload 按缺少 hash 去重。目錄不進入 files。原稿未完整記錄 JSON keys，因此本修訂**不宣稱重現原稿 metadata 的原始編碼**；§4、§6 全部改用上述明定模型。Payload、chunk 數與重用 bytes 的重算結果則均與原稿相同。

## 6. Check、metadata 與 fallback 總成本

### Check 的實際程式路徑

| 階段 | 查核結果 | 當前 source 證據 |
|---|---|---|
| 取得 Catalog | direct root 優先 v2，僅不存在時退 v1；Registry 指定 exact Catalog path。Catalog 由 `FileStream` 完整讀入，最大 1 MiB | `src/NvtFwCombiner.VersionManagement.Infrastructure/VersionManagement/FileSystemUpdateCatalogSource.cs:19`、`:43-51`、`:69`、`:119-135` |
| Direct／manual-pin Check | Catalog 選 newer row；automatic 篩 newer `notify`；有 candidate 才呼叫一次 `VerifyPackageAsync` | `src/NvtFwCombiner.VersionManagement.Application/VersionManagement/VersionManagementExperience.cs:290-306` |
| Registry Check | 初選候選完整驗證；writer lease 下重讀 Registry／Catalog，並再次驗證選定 package。Explicit 路徑取 Catalog newest；automatic 才先篩 newer `notify` | `src/NvtFwCombiner.VersionManagement.Application/VersionManagement/VersionManagementExperience.Registry.cs:114`、`:165`、`:184`、`:276`、`:446`、`:464`、`:542` |
| 每次 package verification | 整個 ZIP SHA-256 → rewind → ZIP manifest、checksum 與全部 payload hash；回傳 typed candidate，離開時關閉 package stream | `src/NvtFwCombiner.VersionManagement.Infrastructure/VersionManagement/FileSystemManagedVersionRepository.cs:173-187`；`src/NvtFwCombiner.VersionManagement.Infrastructure/VersionManagement/ManagedPackageVerifier.cs:171`、`:212`、`:243`、`:548-578` |
| 零 package I/O 分支 | Automatic 沒有 eligible newer `notify` 時不開 ZIP；Registry 仍重做 metadata authority admission | `docs/adr/0066-update-catalog-v2-notification-policy.md:91-99`；`VersionManagementExperience.Registry.cs:216-227`、`:478-486`（完整路徑同上） |
| Install | 重新開來源 ZIP、完整 hash、驗證內容，再解壓安裝；不是直接沿用 Check 的 package stream | `src/NvtFwCombiner.VersionManagement.Infrastructure/VersionManagement/FileSystemManagedVersionRepository.Installation.cs:183`、`:187-200`、`:260`；`ManagedPackageVerifier.cs:283-325`（完整路徑同上） |

因此，Check 不是先下載完整包才解析版本列表；它是**先由 Catalog 選 row，再完整讀包，之後才可發布 Verified candidate**。只解析 metadata 不足以符合現行 `Verified` 契約。〔`docs/contracts/update-catalog-v1.md:178-180`〕

提案要新增的是「已驗證發布資訊的可下載版本」狀態，與「完整 bytes 已驗證的 candidate」分開，不能讓 metadata-only 冒充 `Verified`。這項 R2 狀態變更尚需獨立准入，不能在流量表中默認已完成。〔`docs/architecture/launcher-update-proposal-20260923.md:51-53`；`docs/handoff/1.2.1/R03-launcher-plan.md:37`〕

### 每次 Check 的 package 讀取量

令 `P=ZIP bytes`、`C=全部 compressed entry bytes`。一次 verification 至少消費 `P+C`：一次整包 hash，再讀壓縮內容完成全部檔案驗證。下表尚未計第二輪 ZIP headers／central directory、metadata、失敗候選或重試。

| 成功路徑的邏輯 package bytes 下界 | 目標 v1.1.15 | 目標 v1.2.0 |
|---|---:|---:|
| Direct Check：`P+C` | 235,996,506 | 235,997,708 |
| Registry Check：`Q=2(P+C)` | 471,993,012 | 471,995,416 |
| 隨後一次新安裝：`P+2C` | 353,932,250 | 353,934,516 |
| Registry Check＋新安裝：`3P+4C` | 825,925,262 | 825,929,932 |

這些是上述 code path 與樣本大小推得的**邏輯讀取下界，不是抓包結果**。Local file 可以完全沒有網路流量；UNC 的 OS／SMB 快取、read-ahead 與重複讀取會改變實際傳輸量，不能直接宣稱每次 Check 下載約 472 MB。表內僅計來源 package 讀取，未包含安裝後對本機 payload 的驗證讀取。

### 各方案的總流量模型

先保留現行 Registry Check。令 `G` 為另計的 Registry／Catalog／信任與 transport metadata，`R` 為重試 bytes，`d` 為失敗前已取得的差異 bytes：

- 成功：`G + Q + M + D + R`。
- Delta fallback：`G + Q + M + d + P + R`，其中 `0 ≤ d ≤ D`；§4 列的是 `d=D`。
- 此模型中的 `Q=2(P+C)` 是現行流程的邏輯 package 讀取下界。保留該流程時，a／b／c／d 都不能自行刪掉 `Q`。
- **採納 metadata-only 狀態後應重新建模。** 若遠端 Check 不再讀 package，成功取得項可改為 `G新 + M + D + R`，另計取得後的本機完整驗證；`G新`、信任處理、R2 狀態變更及時間成本仍須量測。這不是現有實作的結果。
- 若把 Check 已讀得的完整 target ZIP 留作本機 cache，後續就不必再取得該 target 的 delta；首次取得 target 的完整成本仍在。「省掉重複取得」與「跨版差異更新」應分開計功。

套用現行 Registry 的 `Q` 下界，假設 Check 後另做一次取得、其餘驗證使用本機內容：

| 保留現行 Check 的 canonical ZIP 比較；仍須另加 G、R 與未計結構讀取 | 1.1.14→1.1.15 | 1.1.15→1.2.0 |
|---|---:|---:|
| Check＋whole ZIP＋模型 metadata | 590,053,938 | 590,056,478 |
| Check＋ZIP CDC＋模型 metadata | 550,457,783 | 572,538,213 |
| 同上，晚期失敗再 full fallback | 668,518,545 | 690,599,113 |
| 成功時相對同表 whole ZIP 節省 | 6.71% | 2.97% |

這是**未改 Check 契約的比較模型，不是現行 Install 的實測總量，也不是完成 metadata-only 狀態變更後的 delta 預期收益**。「下界」指計入的邏輯 package 讀取量，不表示節省率是跨設計通用的下界。現行 Install 的額外來源讀取已另列於上一表。

樣本目錄沒有實際 Registry／Catalog，因此 `G` 或 `G新` 無法填成實測常數；§4 的 manifest estimate 不能冒充現場 metadata。Fallback 也只適用於允許的加速失敗：簽章錯誤、撤銷、來源衝突或回放不得改走較弱信任。〔`docs/architecture/launcher-update-proposal-20260923.md:46-49`〕

## 限制

- **只有兩組相鄰版本。** 其中一組是相同 product source 的版本發布，不能代表未來 runtime 更新、不同打包器、跳版或長期平均收益；未調參尋找最有利 CDC 結果。
- **量測的是 artifact bytes 與記憶體模型。** 未量現場傳輸時間、CPU／磁碟峰值、cache 命中率、併發、取消、斷線或失敗率；不宣稱 latency 改善，也不宣稱時間門檻已達成。
- **重用前提分開。** 未壓縮 entry 模型假設可取得前版內容；canonical ZIP 模型假設可取得前版 ZIP chunks。沒有驗證已部署 client 具備任何一種 persistent cache。§4 儲存數字是指定保留策略的容量計算，不是 cache subsystem 的磁碟峰值量測。
- **Metadata 是明定的評估模型。** 本版 keys 與編碼已完整列出並重算，仍不是正式 transfer schema。不能將模型大小當成已包含簽章、信任、Registry／Catalog 或 transport 的部署成本；修訂版 metadata 數字尚未經另一輪獨立交叉審查。
- **沒有因果重建。** 未拆 App／Launcher bundle、定位 build IDs 或做同輸入重建；只證明指定版本的內容及壓縮產物差異，不判定哪個建置步驟非決定性。
- **信任驗證有限。** SHA-256 相符證明樣本符合提供的 checksum，不等於 publisher 身分驗證、簽章驗證或安全發布認證。原 signed transfer proposal 的處置仍需 A1a／A1b 與對應 owner 決定。
- 本次完成的是 **R0 基準報告修訂**，沒有產品修改、建置、產品測試或發布結果。原稿已由 Claude Fable 5.1 完成交叉審查，本版回應全部 6 項 finding；仍待 owner 決定效益、儲存與必要時間門檻及 go/no-go，不構成規格批准、實作授權或 release gate。〔`docs/handoff/1.2.1/README.md:10-15`、`:26-27`〕
