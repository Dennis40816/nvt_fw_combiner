## 1. Conclusion

**Recommend no-go for canonical ZIP R04-02 this round, retaining no implementation in `1.2.6` and weight 0.** Measured with the complete previous ZIP available for reuse, canonical ZIP CDC plus the revised model manifest yields savings of **33.54%/14.84%** for the two pairs, and **24.19%** weighted by target ZIP bytes. Even before Check, retries, fallback, or signature costs, this falls short of this report's recommended threshold of “at least 30% average weighted by target ZIP bytes, at least 20% for every warm-cache version pair.” This is a candidate threshold, **not an approved owner value**. 〔§4; `docs/handoff/1.1.14/1.2.x-allocation.md:182`〕

The uncompressed-entry CDC model shows about **60.05%** weighted savings, but does not prove reconstruction of the same ZIP and cannot establish R04-02 success. The original proposal requires a byte-identical canonical ZIP and prohibits treating recompressed installed files as the same ZIP; it also reserves a route to **separately propose a per-file object format and re-review package identity/verification contracts** when ZIP chunk reuse is poor. This report lists that as a separate owner-selectable option, recommending against adoption this round; about 60% is only an optimistic model excluding full Check/trust and other costs, not an accepted benefit of the new format. 〔§4; `docs/architecture/launcher-update-proposal-20260923.md:35-44`〕

Current Check fully verifies the package; the successful Registry candidate-selection path verifies twice. Retaining those source reads and adding delta acquisition yields canonical ZIP CDC comparison benefits of about **6.71%/2.97%**. **This is a comparison model with unchanged contracts using a lower bound on logical package reads, not the delta design's expected value or measured network savings.** The proposal requires first adding a metadata-only “downloadable version” state, an R2 change requiring separate admission; adoption requires recalculating the new flow's costs, without treating current `Q` as an inevitable delta cost. 〔§6; `docs/architecture/launcher-update-proposal-20260923.md:51-53`; `docs/handoff/1.2.1/R03-launcher-plan.md:37`〕

| Item | Reproducible method |
|---|---|

| CDC | Custom deterministic Gear chunker; min 16 KiB, mask `0xffff` (nominal 64 KiB), max 256 KiB; reset to zero at the start of each entry/whole ZIP and after each chunk boundary, retain tail chunks, no chunk for empty content. Actual average depends on min/max, content, and tails. |
| Gear table | `G[b] = LE64(SHA256(b"NFC-R04-01-GEAR-v1" + bytes([b]))[:8])`; per-byte update `h = ((h << 1) + G[b]) mod 2^64`; cut when length reaches max, or reaches min and `(h & 0xffff)==0`. |
| Reuse scope | Compare target-chunk SHA-256 against **all** chunks from the previous version; deduplicate missing chunks by hash and transmit once. Reuse-rate denominator is target-content bytes, not file count. Missing chunks had no duplicate hashes for either CDC type in either comparison. |
| Uncompressed CDC transfer | List both unreused raw bytes and bytes from independently raw-DEFLATE-compressing each missing chunk at level 9. | Metadata estimate | This revision recalculates using the explicitly listed JSON models below. **Numbers are exact encoded sizes for these models, not formal product metadata costs; they exclude formal schema, signatures, certificates, Registry/Catalog, and transport overhead.** |

### Total-Traffic Models for Each Approach

Retain current Registry Check first. Let `G` be separately counted Registry/Catalog/trust and transport metadata, `R` retry bytes, and `d` delta bytes acquired before failure:

- Success: `G + Q + M + D + R`.
- Delta fallback: `G + Q + M + d + P + R`, where `0 ≤ d ≤ D`; §4 uses `d=D`.
- This model's `Q=2(P+C)` is the current flow's lower bound on logical package reads. Retaining that flow means a/b/c/d cannot independently drop `Q`.
- **Remodel after adopting the metadata-only state.** If remote Check no longer reads packages, successful acquisition can become “`G新 + M + D + R`,” with post-acquisition full local verification counted separately; “`G新`” (new G), trust processing, R2 state changes, and time costs still require measurement. This is not a result of the existing implementation.

<a id="限制"></a>

## Limitations

- **Only two adjacent-version pairs.** One is a release with the same product source; they cannot represent future runtime updates, different packagers, skipped-version upgrades, or long-term average benefits; parameters were not tuned to find the most favorable CDC result.
- **Measurements cover artifact bytes and in-memory models.** No field transfer time, CPU/peak disk usage, cache hit rate, concurrency, cancellation, disconnection, or failure rate was measured; no latency improvement or time-threshold achievement is claimed.
- **Reuse prerequisites are separate.** Uncompressed-entry model assumes previous-version content is available; canonical ZIP model assumes previous ZIP chunks are available. No deployed client was verified to have either persistent cache. §4 storage figures calculate capacity for a specified retention policy, not peak disk usage of a cache subsystem.
- **Metadata is an explicit assessment model.** This version fully lists and recalculates keys and encoding, but it is still not a formal transfer schema. Model size cannot be treated as deployment cost already including signatures, trust, Registry/Catalog, or transport; revised metadata figures have not undergone another independent cross-review.
- **No causal reconstruction.** App/Launcher bundles were not unpacked, build IDs not located, and same-input rebuilds not performed; only content/compressed-artifact differences between specified versions are proven, without identifying any nondeterministic build step.
- **Trust verification is limited.** Matching SHA-256 proves samples match supplied checksums, not publisher authentication, signature verification, or secure-publication certification. Disposition of the original signed-transfer proposal still needs A1a/A1b and corresponding owner decisions.
- This work completed an **R0 baseline report revision**, with no product modification, build, product-test, or release result. Claude Fable 5.1 cross-reviewed the original, and this version addresses all 6 findings; owner decisions on benefit, storage, necessary time thresholds, and go/no-go remain pending. This is not specification approval, implementation authorization, or a release gate. 〔`docs/handoff/1.2.1/README.md:10-15`, `:26-27`〕
