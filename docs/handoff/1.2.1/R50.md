# R50 開發與 release workflow 回顧（1.2.1）

- 日期：2026-10-01；撰寫：Claude Code commander（Claude Opus 5.5，decision 217）。
- 資料：`evidence/1.2.1/R50-data.md`（PR #484–#503、v1.1.15 與 v1.2.0 release；以 App 身分唯讀查詢 GitHub）。
- 用途：R41（核准觸點縮減，decision 210）與 R50 的 owner 訪談材料。本文只提出建議，不改任何 workflow、ruleset 或文件契約。

## 1. 結論

這 20 個 PR 從最後一次 push 到合併的中位數是 36 分鐘，其中 CI 約 12 分鐘、等 owner 核准約 17 分鐘、核准後到合併約 8 分鐘。真正拖慢的不是單次 CI，而是三種重複：

1. **審查紀錄迴圈**：`governance / authority` 跑了 108 次、失敗 64 次，其中 58 次的原因只是「這個 head 還沒有獨立審查紀錄」。流程本來就是先 push、再審查、再貼紀錄，但 authority 不會因為審查送出而重跑，只能再改一次 PR body 觸發，所以每個新 head 都至少紅一次、多一次手動步驟。
2. **被取代的 CI**：24 次 CI 跑到一半被新的 push 取消，共浪費 4 小時 01 分。多半是審查修正分好幾次推。
3. **flaky 測試**：15 次失敗的嘗試中，至少 9 次和 flaky 有關（UiSmoke 4、零 flaky 檢查 3、Golden 主機競爭 2）。merge 後的 push CI 有 4/14 次是紅的；v1.2.0 第一次 release 也因此被跳過，多了兩個 PR、約 2 小時。

owner 的觸點：19 個合併的 PR 共核准 23 次，另有 6 次核准因為之後又 push 而被撤銷、需要重新核准；兩次 release 各加一次 environment 核准（各等約 27–30 分鐘）。v1.1.15 共 5 次觸點，v1.2.0 共 8 次。

## 4. 改善提案（供 R41／R50 訪談）

| # | 提案 | 預期效果 | 代價／風險 | 需要誰 |
| --- | --- | --- | --- | --- |
| W1 | `governance / authority` 在審查送出（`pull_request_review: submitted`）時也重跑 | 不必再為了觸發而改 PR body；每個 head 少一次紅燈與一次手動步驟 | 要改 workflow（R3 governance）；改動那一批需要你暫時打開 App 的 Workflows 權限（decision 222） | 你授權一批 workflow 修改 |
| W2 | 只有「重大修改」需要你核准（R41）：用 CODEOWNERS 把 R3 路徑（韌體 profile、Golden、release、權限、governance）指定給你，ruleset 改成「需要 Code Owner 審查」、一般核准數 0；其餘 PR 憑獨立審查紀錄加綠燈 CI 合併 | 文件、測試、一般 R1/R2 的 PR 不再需要你；你的核准集中在真正重大的改動 | 要先和你定義「重大修改」；改 ruleset 與 ADR 0080；必須保留 Golden、簽章與發布邊界 | 你決定範圍，並在 GitHub 改 ruleset |
| W3 | 你核准後由 App 開 auto-merge（固定 head） | 省下「核准 → 合併」中位數約 8 分鐘，也不必通知我 | 已啟用；只需要定成固定做法 | 你同意即可 |
| W4 | 審查修正一次推完：先跑完相關的本地測試、等審查結果都出來，再一次 push | 少掉大部分被取代的 CI（目前浪費 4 小時）與被撤銷的核准（6 次） | 修正回到 PR 的時間會稍晚 | 我遵守 |
| W5 | 把 flaky 清零列為 1.2.1 第一優先，並在 flaky 第一次出現時就補 bug record | merge 後的紅燈和 release 重試減少 | 佔用 1.2.1 時間 | 我與 Codex |
| W6 | 把 UiSmoke 分片（原排 1.2.11 的 U5）或 R13-01 的 lane 重組提前評估 | CI 最長路徑 10–11 分鐘可再縮短 | 要先量測（R13-01） | R13-01 評估後由你決定 |
| W7 | 不再等待 Codex connector 的 PR 審查（額度已用完），以獨立審查紀錄為準 | 少一個無效的等待點 | 若之後恢復額度，它的留言串仍會擋合併，需再確認 | 你決定是否移除 connector |
| W8 | PR 一律由 App 開（#502 的教訓） | 避免無法核准而重開 | 無 | 我遵守（已記錄） |

## 5. 需要 owner 決定的問題

1. W2：哪些改動算「重大修改」、需要你核准？建議：R3 的韌體語意（profile、Golden、寫入範圍）、release／簽章／權限、governance 規則本身；其餘不需要。
2. W1：同意在 1.2.1 安排一批 workflow 修改（authority 在審查送出時重跑），並在那一批暫時開啟 App 的 Workflows 權限？
3. W3：你核准後，是否一律由 App 開 auto-merge？
4. W6：是否把 CI 縮短（UiSmoke 分片）提前到 1.2.1／1.2.3 評估？
5. W7：是否停用 Codex connector 的 PR 審查？

## 6. 限制

- PR body 編輯次數拿不到，只用 authority 在同一 head 的額外執行次數（48 次）當代理指標。
- environment 核准的時間是用 `release / promote` job 從建立到開始的間隔推估。
- 失敗的 .NET 測試名稱多半不在 log 裡（沒有下載 TRX），分類依 log 和 PR 說明。
- 你在 GitHub 以外的時間（對話、本機驗證）不在資料裡。
