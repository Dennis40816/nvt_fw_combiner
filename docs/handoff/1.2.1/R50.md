# R50 Development and release workflow retrospective (1.2.1)

- Date: 2026-10-01; written by: Claude Code commander (Claude Opus 5.5, decision 217).
- Data: `evidence/1.2.1/R50-data.md` (PR #484–#503, v1.1.15 and v1.2.0 releases; read-only GitHub queries as the App).
- Purpose: owner interview material for R41 (reducing approval touchpoints, decision 210) and R50. This document only proposes recommendations; it changes no workflow, ruleset, or document contract.

<a id="1-結論"></a>

## 1. Conclusions

For these 20 PRs, the median time from the last push to merge was 36 minutes: about 12 minutes for CI, about 17 minutes waiting for owner approval, and about 8 minutes from approval to merge. The real slowdown was not a single CI run but three kinds of repetition:

1. **Review-record loop**: `governance / authority` ran 108 times and failed 64 times; 58 failures were simply because “this head does not yet have an independent review record.” The workflow is inherently push first, review next, then post the record, but authority does not rerun when a review is submitted. Another PR body edit is needed to trigger it, so every new head gets at least one red check and one extra manual step.
2. **Superseded CI**: 24 CI runs were canceled midway by a new push, wasting 4 hours 01 minutes in total. Most resulted from pushing review fixes in several batches.
3. **Flaky tests**: at least 9 of the 15 failed attempts involved flakes (UiSmoke 4, zero-flaky checks 3, Golden host races 2). Post-merge push CI was red in 4/14 runs; the first v1.2.0 release was also skipped as a result, adding two PRs and about 2 hours.

Owner touchpoints: the 19 merged PRs received 23 approvals in total; another 6 approvals were dismissed by subsequent pushes and required approval again. Each of the two releases added one environment approval (each waiting about 27–30 minutes). v1.1.15 had 5 touchpoints in total, and v1.2.0 had 8.

2. W1: do you agree to schedule one batch of workflow changes in 1.2.1 (rerunning authority when a review is submitted), temporarily enabling the App's Workflows permission for that batch?

<a id="6-限制"></a>

## 6. Limitations

- PR body edit counts were unavailable; additional authority runs on the same head (48) were used as a proxy.
- Environment approval time was estimated from the interval between creation and start of the `release / promote` job.
- Most failed .NET test names were absent from the logs (TRX was not downloaded); classification used logs and PR descriptions.
- Your time outside GitHub (conversations, local verification) is not included in the data.
