## 四項需追蹤的差異與疑似缺陷記錄

repository 禁止寫入優先於 bug-ledger 的一般寫檔慣例；以下為外部報告內的待移交記錄，沒有在 docs/handoff/bugs 新增檔案。不是已核准 fix，也不是新的正式 board 編號。

### R39-F01 — [P2 / suspected] Build enablement 未統一消費 Build availability

- 來源：E06、E22、E33；B04。已確認程式路徑不同。假設同一 current session 具有 Preview 可用而 Build 不可用，Merge 的 gate 可以與 BuildAvailability 不同，Replace 有額外 Build 檢查。
- 影響：按鈕、blocker badge 與執行端拒絕可能不一致；未證明會產出未授權 bytes，不能以 UI gate 差異宣稱執行器繞過。
- 限制：AB 與 CtrlRAM 的 Application 都使用 RequireRuntimeDependenciesForPreview；因此「工具缺失一定只擋 Build」在這兩路不成立。General 隱藏，Standard 的現行 reachable 組合亦未重現。
- 後續：以 typed action matrix 的最小可達案例證明或反駁；若反駁使用者缺陷，仍可保留 owner 收斂處置，但不得當成已修 bug。驗收與版本見 B04。

### R39-F02 — [P2 / suspected] pre-run refusal 使用兩條 publication 路徑，涉及三個 caller

- 來源：E07、E32；B05。AB RunAbMergeAsync readiness refusal（MergePresentationViewModel.Execution.cs:222–229）及 RequestBuildOutputDeliveryAsync 的 CompositionPreRunRefusalException catch（:35–43）都直接 PublishRunResult，沒有 CompletedContext；Replace readiness caller 使用 ShowActionReadiness，帶 context 與 window-publication guard。
- **guard 不可混稱**：readiness 的 AB／Replace 兩 caller 在 await 後只以 current context 保護 readiness cache，拒絕發布未同等檢查 session lease；preparation catch 已以 IsAcceptedMergeSessionCurrent(context) 與 IsPreparationCurrent(preparation) 保護發布，包含 context.IsPublicationCurrent。後者的收斂理由是統一 context／typed provenance，不能宣稱它已證明相同 stale 競態。
- 可否證觸發：分別暫停 GetActionReadinessAsync 及 PrepareBundleProposalAsync，改 input／IC／mode／關窗；preparation 另加 Cancel／重開，才完成 unavailable／exception。比對新 run result、CompletedContext、PropertyChanged，以及既有 readiness refresh。真正可達競態尚未執行。
- Replace preparation 沒有相同 catch 不是漏處理證據：CompositionOutputNamingExperience.CaptureFormatAsync:119–127 只對 ExperienceIds.AbMerge 拋此 exception；保留 producer 的 workflow 差異。
- 後續：extend RunSession 的 refusal publication，三 caller 收斂到一致 guard／context 契約；不得刪 preparation freshness check 或把 exception.Message 固化成新語意 owner。O-R39-02 包含兩處 Merge 旁路；接 R18-01，並由 R09-02／R09-03 核對已收錄內容，不重做已關閉的 F01/F02/F25 歷史項目。

### R39-F03 — [P3 / policy-open] Settings staged draft 的 Close 政策不同

- 來源：E15、E16；B16。Config dirty-close 要先處置；Version source 關閉只撤 picker generation，仍保留 source editing/draft。source 的 explicit Cancel 會還原。
- 這是互動一致性缺口，不是 source 被偷提交，也沒有現有規格證明「Close 必須丟棄」；owner 可以選擇把保留草稿記為合法 workflow 差異。
- 建議：保留草稿、不自動提交，但讓 RequestSettingsClose 統一表示各 section 的 close disposition，並驗證重開仍能找回未提交來源；避免新增另一個 dirty cache。與新 F04 一起交 O-R39-04 定案，但 F03 只記 Settings 內部 Close／Cancel 差異，不重複計 exit 缺口。

### R39-F04 — [P3 / policy-open] Settings 關閉與 application 退出對未提交狀態的確認範圍不同

- 來源：B20；E15/E16、E28–E31。MainWindowViewModel.HasSelectedFiles:14–18 只聚合 workflow、Hex 與 Report 選檔；MainWindow.OnClosing:173–189 在一般使用者退出時依此提示，然後進 drain，未經 RequestSettingsClose。Settings 自身 Close 則會攔 EB／Toolchain dirty。

- 建議：O-R39-04 定義 navigation、modal Close 與 application exit 的 disposition；各 state owner 提供當前狀態，ShellNavigation 統一呈現確認，Settings 保留 section 內 commit／discard owner。採 A 時補 Settings dirty 的退出處置；採 B 時把 selected-file-only exit 明列為例外。均不自動提交、不共用一份全域 dirty flag、不變更 launcher restart／durable transaction 的 lifetime。
