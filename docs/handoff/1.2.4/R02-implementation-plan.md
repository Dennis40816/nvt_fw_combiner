# R02 / R27-01 large-file implementation slicing plan for NFC 1.2.4

## 1. Status and purpose

Status: Proposed slices, statically checked against the accepted decisions; 2026-10-03.
This is a planning document, not an implementation approval, independent review record, or runtime pass.
Source: `8479dee8ee95dbcee9f38ecf4793e70858c9ff41` (the plan was written against this commit; the code of P1 is rebased on the current trunk), branch `feature/1.2.4/r02-plan-p1`.
Purpose: make R02-03 through R02-08 and R27-01 separately implementable and reviewable, with explicit
prerequisites, write ownership, byte evidence, commander checks, and merge authority.
The form follows [the Desktop plan](../1.2.3/R14-03-04-plan.md), especially its sections 2 through 4.

### Accepted decisions

- **Decision 229:** General authoring retains identity, not the complete source payload; every run validates
  complete content and uses immutable content through its last consumer. R02 and R43 share Application identity
  admission and Infrastructure capture/read owners; no watcher. The snapshot mechanism and resource numbers
  still require measurements and an owner decision. Customized Merge reopens and is accepted in 1.2.4
  (`docs/handoff/1.2.x.md:312`, `docs/handoff/1.2.x.md:320`, `docs/handoff/1.2.x.md:322`).
- **Decision 230:** Customized Replace is retired through R54. Do not implement the old R02-01 General Replace
  Base proposal as a new large-file feature. Preserve surviving CtrlRAM Replace and historical reports
  (`docs/handoff/1.2.x.md:325`, `docs/handoff/1.2.x.md:330`, `docs/handoff/1.2.x.md:333`).
- **Decision 256 / current allocation:** reuse the early R02-02 seam and preparation-freshness work, integrating
  them in 1.2.4. Include the two remaining nullable-byte corrections in R02-03
  (`docs/handoff/1.1.14/1.2.x-allocation.md:205`). Freshness is required before the public entry reopens
  (`docs/handoff/1.1.14/1.2.x-allocation.md:210`).
- **Accepted allocation:** R02-06 is loose delivery, R02-07 is bundle delivery, and **R02-08** is capacity and
  mapping UI feedback (`docs/handoff/1.1.14/1.2.x-inventory.md:173`,
  `docs/handoff/1.1.14/1.2.x-inventory.md:174`, `docs/handoff/1.1.14/1.2.x-inventory.md:175`).
  The request's capacity-feedback label R02-07 is interpreted using these canonical IDs.
- **Accepted sequencing:** first large-source/small-output execution, then large-output storage and delivery;
  R27-01 must identify its difference from R02. R27-02 assesses aggregate budgets separately; no new numeric
  budget is approved (`docs/handoff/1.1.14/1.2.x-inventory.md:478`,
  `docs/handoff/1.1.14/1.2.x-inventory.md:324`, `docs/architecture/nfc_roadmap.md:522`,
  `docs/architecture/nfc_roadmap.md:528`). The allocation owns the current 1.2.4 version assignment, including
  R27; older inventory section headings are not a competing schedule
  (`docs/handoff/1.1.14/1.2.x-allocation.md:201`, `docs/handoff/1.1.14/1.2.x-allocation.md:204`).

### This plan's proposals

Everything marked **Proposal**, including slice boundaries, new filenames, storage interfaces, migration
bridges, bounded evidence access, and parallel work, is this plan's proposal. Sizes are complexity estimates,
not elapsed-time promises or a replacement for the allocation's version totals.
Q1 in section 6 was answered on 2026-10-04 (board decision 305: option A, the host-owned staging copy per run, plus a reminder to reload when the external file changes, designed with R02-03 and R43 and without a file watcher unless decision 229 is reopened); the slices that depend on it are implementation-ready once their listed dependencies are met.
Future implementers record semantic owner search and `reuse` / `extend-owner` / `reject-duplicate` at admission.
This prose does not itself modify an ADR, schema, profile, resource ceiling, or runtime.

## 3. Contract to implement

The accepted behavior comes from R02-01 section 5 as qualified by decisions 229 and 230, and the inventory rows.

### Invariants applying to every item

For identical admitted inputs, preserve complete output bytes, half-open checked ranges and address spaces,
operation sequence, overlap rules, blank fill, padding/truncation policy, CRC/header/postbuild behavior,
output naming, route/support/evidence declarations and the single planner/executor.
General's only intended difference for changed sources is refusal, never silently accepting new content.
General Merge still has no physical-map or CRC/header authority; surviving fixed workflows retain their own
accepted-byte, metadata and processor contracts. Domain receives storage capabilities, never paths or file I/O.
These constraints are retained by R02-01 (`docs/handoff/1.2.1/R02-01.md:85`,
`docs/handoff/1.2.1/R02-01.md:87`, `docs/handoff/1.2.1/R02-01.md:123`) and ADR 0019
(`docs/adr/0019-general-merge-logical-output-v2.md:44`).
