## Table A: CLI

Commands follow nvt_fw_combiner. Build destinations mean --output <path> OR
--bundle-parent <existing-directory> [--bundle-name <plain-folder-name>]. Omitted loose output uses the
name chosen by the product's naming rules in the current directory. --report <path> requests JSON, not a screenshot.
Preview returns a console result and optional JSON without committing a BIN. Successful Build returns a BIN
or bundle, its identity/hash receipt, and optional JSON; bundles also return directory/artifact receipts.
Completed runs return 0 for success or 1 for a failed result. Argument errors generally use 64.
The outer handler returns 70 for caught I/O, permission/path exceptions and cancellation
(src/NvtFwCombiner.Cli/CliApplication.cs:115; src/NvtFwCombiner.Cli/CliApplication.cs:120).
Some commands handle input/preparation failures earlier, with different exits and no JSON; see A33.

## Decisions for the owner (O13)

Ask these one at a time. Options are proposals, not accepted contracts or final option spellings.

1. **CLI additions:** Which missing choices should the CLI gain in R14-02?
   - A: AB Dummy selection with an explicit acknowledgement option confirming that 0xFF replaces all non-TP
     output; CtrlRAM bank/version choices; and a list of available workflows, counts and slots.
   - B: A plus inspecting a BIN or saved report without running a workflow.
   - C: List available workflows, counts and slots only; defer the missing authoring choices.
   Recommendation: A. It adds the missing choices using the same checks the screen already uses.
   For all options, leave early-refusal behavior unchanged (A33): an error message and the current failure
   exit code, without promising JSON. No option reopens General or adds firmware behavior.

2. **Report tabs:** Which existing tabs should launch-and-capture expose?
   - A: Inputs, Changes, Operations, Postbuild, Issues and Raw.
   - B: Changes, Inputs and Issues initially; explicitly defer the other three.
   Recommendation: A. All six exist; selecting a named tab lets a script open it without mouse clicks.
   Reject unknown names; Summary remains a panel, not a new tab.

3. **Screens:** Which screens can a scripted launch open?
   - A: A saved report only, with a set theme, language, motion setting and window size.
   - B: A plus Standard/AB/CtrlRAM screens with files loaded, applicable LDC, approved Dummy/bank choices,
     the workflow setup screen and input Details open or closed.
   - C: B plus History, diagnostics, Hex Editor with a BIN loaded, Build Settings and named Settings sections.
   Recommendation: A first. Real saved reports and the shipped screen meet the minimum screenshot goal.
   Defer B/C explicitly. Launch choices do not change saved preferences or invent ready/error states.

4. **Paths:** Which screenshot destinations should a script be allowed to use?
   - A: A full path and filename; the containing folder must already exist.
   - B: A full path or one relative to the current directory, with a filename and an existing folder.
   - C: B, with missing folders created automatically.
   Recommendation: B. It follows current path handling and limits writes to the requested destination.
   For every option, refuse a screenshot path that points at an input or report file.

5. **Overwrite:** What happens when the screenshot destination exists?
   - A: Replace only when asked; if saving fails, the old file stays unchanged.
   - B: Always replace; if saving fails, the old file stays unchanged, as with CLI report export.
   - C: Save under a numbered filename and tell the script the actual path, as with bundle folders.
   Recommendation: A. Scripts get the requested filename and existing screenshots are protected by default.
   This choice applies only to screenshots; current CLI BIN/report/bundle behavior stays unchanged.

6. **Exit and errors:** How should a scripted Desktop screenshot finish and describe a failure?
   - A: Close after success or failure: 0 success, 1 report-loading/drawing/saving failure, 64 invalid capture
     arguments, 70 unexpected system failure/cancellation. An error message says what failed and where.
   - B: Close with 0 success or 1 for every capture failure; an error message says what failed and where.
   - C: Keep the window open and show errors only on screen.
   Recommendation: A. The script can distinguish an invalid request from a failed screenshot.
   A/B write errors to standard error; every option preserves existing managed-startup exits 64/22.
   With A, help exits 0 without opening a window; invalid capture arguments create no screenshot.
   Ordinary interactive launches remain interactive.

## Limits

- Static inspection at the stated commit only. No network, builds, tests, firmware runs or Desktop launches.
- Runtime success, complete per-IC/count/profile availability, output bytes, Golden parity and support
  certification were not checked. Default Both-bank support is inferred from preparation/classification code.
- Desktop managed-option errors use 64 and invalid inherited context uses 22 in code; UI argument issues
  remain startup state (B43/B44). No public capture exit contract exists; packaged behavior was not run.
  Screenshot fidelity/timing, native DPI/scale and capture readiness were not measured.
- Filesystem alias edge cases, permissions, races and overwrite durability were not exercised. Existing
  path/overwrite behavior comes from code/SPEC, not a fresh runtime pass.
- Remote/state effects, report-schema compatibility and fixture/capture helpers were not audited.
  Managed paths, the catalog probe and NFC_STARTUP_TRACE_PATH are excluded plumbing (named above),
  as are internal trust probes and test hooks.
- The 31 gaps include Settings section selection and optional O13 targets; owner scope approval is still required.
