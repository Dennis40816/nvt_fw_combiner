## Boundary

The comparison uses a generated 1 MiB raw document and one generated 8 KiB
manual-UI document. No firmware BIN, private golden, filesystem path, output,
or screenshot is committed. Both generated inputs were deleted after capture
and can be reproduced from the descriptions below.

The extraction remains Presentation-owned and read-only. The Raw Hex Editor
host retains Application editing/session, search, history, save, filesystem,
and context-menu authority. The viewport accepts only a bounded immutable
numeric snapshot and emits typed interaction intent. It has no Application,
firmware, profile, file, path, save, or command authority.

## Machine and method

- Windows 11 Enterprise `10.0.26200`
- Intel Core i9-10900F, 20 logical processors
- .NET SDK `10.0.302`, Release configuration
- one test process per capture; elapsed values are observations, not CI limits
- allocations use `GC.GetAllocatedBytesForCurrentThread`; the asynchronous
  search observation uses `GC.GetTotalAllocatedBytes(precise: true)`

The executable routine gate is:

```text
dotnet test tests/NvtFwCombiner.UiSmoke.Tests/NvtFwCombiner.UiSmoke.Tests.csproj -c Release --filter "FullyQualifiedName~HexViewportRefactorBeatsReleasedAllocationBaseline" --logger "console;verbosity=detailed"
```

It loads the same generated 1 MiB byte pattern, locks the visible window to 12
rows x 16 bytes, alternates the first/last window 128 times, alternates two
selected bytes 10,000 times, and alternates two hover cells 10,000 times.

| Routine hot path | Released observation | Candidate observation | Result |
| --- | ---: | ---: | --- |
| Scroll/snapshot, 128 | 33.274 ms / 10,175,656 B | 12.975 ms / 10,040,320 B | lower elapsed and allocation |
| Selection, 10,000 | 22.015 ms / 3,360,000 B | 34.715 ms / 1,120,928 B | 66.6% lower allocation; +1.27 microseconds per selection |
| Hover, 10,000 | 17.694 ms / 400,000 B | 3.616 ms / 320,000 B | lower elapsed and allocation |

The allocation assertions are intentionally stable and executable:
scroll <= 10,150,000 B, selection <= 1,500,000 B, and hover <= 350,000 B.
Elapsed observations are not hard thresholds because scheduler, antivirus,
JIT, and renderer initialization noise are material at these durations.

## Rendered workflow characterization

A temporary UI-smoke characterization used the same generated 1 MiB document
for both commits. Its last three bytes were `NVT`; every other byte was `0x41`.
After asynchronous load/search completed, the normal Windows Avalonia platform
was initialized and the actual released/refactored control rendered into a
fresh `DrawingGroup` per sample. The identical sequence measured:

1. 16 alternating first/last snapshot refreshes;
2. four alternating scroll-and-render operations;
3. eight alternating selection-and-render operations;
4. one full-document ASCII search for `NVT`;
5. eight alternating `00`/`FF` edits and renders at address zero; and
6. eight renders with original comparison rows visible.

| Workflow | Released elapsed / allocated | Candidate elapsed / allocated |
| --- | ---: | ---: |
| Snapshot x16 | 6.397 ms / 1,197,240 B | 5.610 ms / 1,177,200 B |
| Scroll + render x4 | 170.418 ms / 8,470,864 B | 175.602 ms / 9,127,368 B |
| Selection + render x8 | 166.024 ms / 14,555,176 B | 176.162 ms / 15,876,640 B |
| Search x1 | 10.608 ms / 1,267,776 B | 10.524 ms / 1,266,272 B |
| Edit + render x8 | 183.516 ms / 15,750,376 B | 182.875 ms / 16,950,088 B |
| Comparison render x8 | 166.105 ms / 14,744,176 B | 161.279 ms / 16,034,112 B |

The rendered elapsed observations range from 2.9% lower to 6.1% higher and are
treated as same-machine noise, not a universal latency claim. `DrawingGroup`
retains drawing commands and reports 7-9% higher allocation in four compound
render loops; it is not an application working-set measurement. The routine
operation gate above is the allocation regression authority and is lower for
scroll, selection, and hover. This distinction is explicit for owner review;
the data is not presented as an across-the-board allocation improvement.

The temporary characterization tests and generated BINs were removed after
capture. They were measurement instrumentation, not production behavior or
golden fixtures. The method and exact loop counts above are sufficient to
repeat the observation without adding a permanent platform initialization to
the parallel UI-smoke suite.

## Visual, interaction, and accessibility parity

Manual Windows inspection used an 8 KiB file filled with `0x5A` and confirmed:

- 16-byte HEX and ASCII alignment, row address labels, selection fill, column
  header selection, and vertical scrolling;
- pointer selection, arrow navigation, F2 inline edit overlay, Escape cancel,
  and no byte mutation after cancellation;
- comparison/decorated row layout and bounded viewport sizing; and
- focus exposed through Windows UI Automation as
  `custom Hex Editor`, automation id `HexViewport`, with selected-byte help
  text such as `0x000000: 5A`.

The renderer is in the UI Automation content view, creates a
`ControlAutomationPeer`, and remains keyboard focusable. The host supplies the
localized accessible name and selected-byte help text.

Independent UI review found one parity defect after the first extraction:
when inserted current data extends beyond the original document tail, the
missing comparison ASCII cell rendered `.` instead of the released blank.
Commit `c705cdf1` restores the blank only for a missing reference value. A
missing current value and a non-printable present byte still render `.`. The
executable contract is:

```text
dotnet test tests/NvtFwCombiner.UiSmoke.Tests/NvtFwCombiner.UiSmoke.Tests.csproj -c Release --filter "FullyQualifiedName~HexViewportKeepsMissingComparisonAsciiBlank"
```
