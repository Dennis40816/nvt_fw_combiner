# v0.9.11.10 first-frame and background warm-up evidence

## Scope and decision

`0.9.11.10` is the owner-selected integration branch name, not a four-part
release version. The package and in-app version remain `0.9.11`. The owner
approved composite ReadyToRun and exact 80,000,000-byte ceilings for both the
main EXE and complete release ZIP.

The startup lifecycle is now:

1. create and open the Home window;
2. warm immutable catalog/profile projections on a worker thread;
3. populate deferred Settings/workflow/Hex Editor ViewModel state;
4. materialize Device Context, Replace, Merge, Settings, and Hex Editor visual
   trees one `DispatcherPriority.Background` step at a time; and
5. retain the materialized controls for subsequent navigation.

Warm-up cannot navigate, open a modal, read a user firmware path, launch an
external processor, select support, change a profile, or acquire Build
authority. A user navigation that happens first retains the original lazy
first-use path, and warm-up never replaces already materialized content.

The retained median background deltas were 1,659.950 ms for immutable catalog
warm-up, 5.530 ms for deferred ViewModel state, 25.460 ms for Device Context,

for Hex Editor visual-tree materialization. Dispatcher waits are included in

bytes. This is the measured memory trade-off for removing common-page cold
materialization on this machine. No universal startup, navigation, or memory
claim is made from five local samples.
