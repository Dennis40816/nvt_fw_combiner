# v0.9.11 reconstructed startup and package evidence

## Scope and decision

This record measures the reconstructed `v0.9.11` candidate whose only accepted
predecessor is the final `v0.9.10` release. The exact application and package
source is commit `b73f8876ad3af41ec792141a929b866c59df4462` on
`feature/0.9.11.10/reconstruct-from-v0.9.10`.

The owner-approved release targets are:

- process start to a visible Home window near one second, with 0.8 seconds kept
  as the aspirational target rather than a release-blocking universal promise;
- a main self-contained executable near 70,000,000 bytes, with 80,000,000 bytes
  as the release ceiling; and
- background warm-up after the Home window so commonly used pages do not pay
  their full first-use visual-tree construction cost.

On this machine, the one-second target and both size limits pass. The 0.8-second
target does not: the measured median is 908.146 ms, 108.146 ms above it. This is
local evidence and must not be represented as a universal wall-clock claim.

## Environment and measurement protocol

- Windows `10.0.26200`, .NET SDK `10.0.302`, and PowerShell `7.5.8`;
- packaged self-contained `win-x64` single-file application with compression,
  composite ReadyToRun, native libraries included, and trimming disabled;
- one warm-up excluded from summary statistics followed by five measured Home
  launches; all six raw traces remain in the JSON;
- process time starts immediately before `Start-Process`; the visible-window
  endpoint requires a nonzero native main-window handle;
- every process is closed before the next launch;
- opt-in startup traces record monotonic application stages, process working
  set, and cumulative managed allocation traffic; and
- allocation counters are cumulative allocation traffic, not retained live
  heap size.

The exact command was:

```text
./scripts/measure-startup.ps1 \
  -ApplicationPath ./artifacts/package-work/NvtFwCombiner-v0.9.11-win-x64/NvtFwCombiner.exe \
  -OutputPath ./artifacts/startup-measurements/packaged-home-0.9.11-reconstructed-b73f8876-v2.json \
  -WarmupRuns 1 -Runs 5 -Page home
```

## First-screen attribution

The largest measured synchronous Home construction interval is
`shell-data-context.assigned`: median 276.016 ms and 33,824,392 allocated bytes.
Assigning the root DataContext causes Avalonia to instantiate and bind the
visible Home data template. Preferences, shell ViewModel construction, initial
launch-option application, theme application, and notification setup are each
small by comparison.

The Home screen is visually restrained but its live template still binds three
action panels, seven commands, nested layout containers, styles, and dynamic
resources. No firmware, profile, catalog, user-file, or processor I/O occurs in
this critical interval. Moving Home materialization until after the
`main-window.opened` marker would improve the number while delaying meaningful
first-screen content, so it is not accepted as an optimization.

After the window opens, immutable catalog warm-up and low-priority Device
Context, Replace, Merge, Settings, and Hex Editor materialization retain their
existing authority boundaries. Warm-up cannot navigate, select support, open a
modal, read user firmware, mutate a profile, launch an external processor, or
acquire Build authority.
