# v0.9.11 startup measurement tool

`scripts/measure-startup.ps1` measures the packaged desktop application from
process creation to a nonzero main-window handle and correlates that external
observation with opt-in in-process startup milestones. It requires only
PowerShell and the application being measured; it does not install or download
`dotnet-trace`, PerfView, or another runtime dependency.

## Usage

```powershell
./scripts/measure-startup.ps1 `
  -ApplicationPath ./artifacts/package-work/NvtFwCombiner-v0.9.11-win-x64/NvtFwCombiner.exe `
  -OutputPath ./artifacts/startup-measurements/v0.9.11-home.json `
  -WarmupRuns 1 `
  -Runs 5 `
  -Page home
```

`-Page` accepts `home`, `settings`, `merge`, `replace`, or `hex-editor` so page
projection costs remain separate. The runner starts every sample with a unique
trace path, waits for both the main-window handle and the trace, closes the
process, verifies an identical ordered stage sequence, and writes raw samples
plus minimum/median/maximum summaries. Existing output files are rejected.

The application activates tracing only when the runner supplies the
`NFC_STARTUP_TRACE_PATH` environment variable to that child process. Normal
launches do not create a trace. The app writes once after `main-window.opened`,
uses create-new semantics, never creates the requested directory, and treats a
diagnostic write failure as non-fatal. The trace contains runtime/process
metadata and timings only; it contains no firmware bytes, input paths, profile
selection, report data, or external-tool arguments.

## Stages

| Stage | Boundary |
| --- | --- |
| `managed-entry` | First managed startup-trace statement in `Program.Main`. Native host and single-file work before this point are visible only in the external process-to-window result. |
| `launch-options.parsed` | UI launch options parsed. |
| `avalonia-builder.started` / `ready` | Avalonia builder configuration. |
| `application-xaml.started` / `ready` | Application XAML and global resources. |
| `framework-initialization.started` / `completed` | Classic desktop lifetime main-window assignment. |
| `main-window-constructor.started` / `completed` | Complete synchronous window construction. |
| `main-window-xaml.ready` | MainWindow compiled XAML and controls loaded. |
| `shell-preferences.loaded` | Bounded local shell preferences loaded. |
| `shell-view-model.created` | Initial shell ViewModel created. |
| `main-window.assigned` | Window assigned to the desktop lifetime. |
| `main-window.opened` | Avalonia reports the window opened; the trace is then written. |

Each stage reports elapsed milliseconds from `managed-entry` and delta from the
previous stage. The difference between external process-to-window time and the
internal final elapsed time approximates native host, single-file/runtime entry,
window-handle observation, and instrumentation coordination cost; it is not an
exact attribution of those components.

## Interpretation limits

Results are same-machine observations, not CI timing thresholds or universal
claims. Record package commit/hash, Windows build, publish flags, warm-up count,
run count, page, power state, and whether virus scanning or other foreground
load changed. This lightweight phase trace identifies the next boundary to
profile. CPU stacks, JIT method attribution, file I/O stacks, or native/Avalonia
render internals still require a separately controlled EventPipe/WPR/PerfView
capture after this tool identifies a dominant phase.
