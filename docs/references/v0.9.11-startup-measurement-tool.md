# v0.9.11 startup measurement tool

`scripts/measure-startup.ps1` measures the packaged desktop application from
process creation to a nonzero main-window handle and correlates that external
observation with opt-in in-process startup milestones. It requires only
PowerShell and the application being measured; it does not install or download
`dotnet-trace`, PerfView, or another runtime dependency.

The v2 trace and measurement result also record managed allocation growth at
every stage and bounded UI-thread work intervals. Those additions distinguish
first-frame synchronous construction from the short background-priority
materialization steps that run after Home is visible.

## Usage

```powershell
./scripts/measure-startup.ps1 `
  -ApplicationPath ./artifacts/package-work/NvtFwCombiner-v0.9.11-win-x64/NvtFwCombiner.exe `
  -OutputPath ./artifacts/startup-measurements/v0.9.11-home.json `
  -WarmupRuns 1 `
  -Runs 5 `
  -Page home
```

`-Page` accepts `home`, `settings`, `merge`, `replace`, or `hex-editor` so page
projection costs remain separate. The runner starts every sample with a unique
trace path, waits for both the main-window handle and the trace, closes the
process, verifies an identical ordered stage sequence, and writes raw samples
plus minimum/median/maximum summaries. Existing output files are rejected.

The application activates tracing only when the runner supplies the
`NFC_STARTUP_TRACE_PATH` environment variable to that child process. Normal
launches do not create a trace. The app writes once after `main-window.opened`,
uses create-new semantics, never creates the requested directory, and treats a
diagnostic write failure as non-fatal. The trace contains runtime/process
metadata and timings only; it contains no firmware bytes, input paths, profile
selection, report data, or external-tool arguments.

`allocatedBytesSinceManagedEntry` is the process-wide value reported by
`GC.GetTotalAllocatedBytes(false)` relative to the first managed trace statement.
It is cumulative allocation traffic, not live heap size. `allocationDeltaBytes`
is the non-negative change since the previous stage. Working set remains an
external process observation at first window, completed trace, and peak.

## Stages

| Stage | Boundary |
| --- | --- |
| `managed-entry` | First managed startup-trace statement in `Program.Main`. Native host and single-file work before this point are visible only in the external process-to-window result. |
| `launch-options.parsed` | UI launch options parsed. |
| `avalonia-builder.started` / `ready` | Avalonia builder configuration. |
| `application-xaml.started` / `ready` | Application XAML and global resources. |
| `framework-initialization.started` / `completed` | Classic desktop lifetime main-window assignment. |
| `main-window-constructor.started` / `completed` | Complete synchronous window construction. |
| `main-window-xaml.ready` | MainWindow compiled XAML and controls loaded. |
| `shell-preferences.loaded` | Bounded local shell preferences loaded. |
| `shell-view-model.created` | Initial shell ViewModel created. |
| `shell-preferences.applied` | Saved theme, language, and reduced-motion choices applied to the ViewModel. |
| `shell-data-context.assigned` | Root compiled bindings receive the shell ViewModel. |
| `shell-initial-content.ready` | The selected first page has materialized. |
| `shell-theme.applied` / `shell-notifications.ready` | Window theme and persistence/report subscriptions are ready. |
| `initial-launch-options.applied` | Synchronous launch-option state is applied without loading a firmware path. |
| `main-window.assigned` | Window assigned to the desktop lifetime. |
| `main-window.opened` | Avalonia reports the first Home window opened. |
| `startup-launch-options.ready` | Any explicit diagnostic launch option has been applied. |
| `startup-warmup.catalogs.ready` | Immutable catalog/profile projections have warmed on a worker thread. |
| `startup-warmup.*.started` / `ready` | One common page starts and completes materialization inside one background-priority UI callback. |
| `startup-warmup.completed` | Common-page warm-up is complete and the v2 trace is written. |

Each stage reports elapsed milliseconds from `managed-entry` and delta from the
previous stage. The difference between external process-to-window time and the
internal final elapsed time approximates native host, single-file/runtime entry,
window-handle observation, and instrumentation coordination cost; it is not an
exact attribution of those components.

The runner reports two UI-thread observations:

- first-frame synchronous work is the sum of application XAML loading and
  framework-initialization-to-window-assignment;
- background UI materialization is the sum and longest value of the five
  explicit `startup-warmup.*.started`/`ready` callback intervals.

The background intervals intentionally exclude time waiting in the Dispatcher
queue. These values locate app-controlled synchronous work; they are not a
complete event-loop latency trace and do not prove that the OS, compositor, or
another process never delayed a frame.

## Packaged integration observation

Commit `31e08f06` was published as compressed single-file, self-contained
`win-x64`, with trimming disabled and native libraries included in the bundle.
One warm-up plus five Home measurements produced process-to-window samples of
2,064.768, 2,032.706, 2,036.853, 2,030.859, and 2,014.124 ms; the median is
2,032.706 ms. Managed-entry-to-opened samples are 1,998.480, 1,977.497,
1,971.555, 1,974.897, and 1,956.753 ms; the median is 1,974.897 ms.

The median stage deltas identify the initial shell ViewModel construction as
the largest measured managed block at 771.030 ms. MainWindow XAML is 291.050
ms, the opened transition is 258.770 ms, application XAML is 104.300 ms, and
shell preferences are 35.920 ms. Independently calculated per-stage medians do
not sum to the median total. The complete 24,027-byte result has SHA-256
`c6ea860de392107e71013cbcb589158bf51ae2a651e69374f5552fe3877fde90`.

This observation changes the next diagnostic priority: split or simplify
initial shell ViewModel construction before pursuing NativeAOT. It does not
replace the tagged before/after package evidence and is not a universal startup
claim.

## Interpretation limits

Results are same-machine observations, not CI timing thresholds or universal
claims. Record package commit/hash, Windows build, publish flags, warm-up count,
run count, page, power state, and whether virus scanning or other foreground
load changed. This lightweight phase trace identifies the next boundary to
profile. CPU stacks, JIT method attribution, file I/O stacks, or native/Avalonia
render internals still require a separately controlled EventPipe/WPR/PerfView
capture after this tool identifies a dominant phase.
