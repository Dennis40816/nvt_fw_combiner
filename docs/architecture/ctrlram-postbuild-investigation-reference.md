Date: 2026-07-04.

Search keywords: CtrlRAM postbuild, first run base, self-pasteback, NT51926, NT51927, NT51928, NT51930, NT51931, SINGLE golden, LDC DP.

## Purpose

This note records the current CtrlRAM Replace/postbuild investigation conclusions so future questions can be answered by searching this file first.

It covers:

- which additional owner golden BIN files are still needed;
- whether current normalized postbuild commands match the original postbuild BAT evidence;
- the current per-IC explanation for non-identical self-pasteback output;
- the NT51931 exception and why it is not a catalog transcription fix.

This note does not approve new byte behavior, support exposure, or relaxed write ranges. Production changes to command order, ranges, checksums, copy-header behavior, or allowed write ranges still require firmware-owner evidence and golden regression.

## Postbuild BAT Consistency

The current normalized catalog was checked against original postbuild BAT command shapes.

Confirmed consistent:

- NT51920: `CRC_Enable`; single/cascade match BAT.
- NT51923: `CRC_Enable`; cascade includes split `DiffDLM.bin`; single does not.
- NT51926: `CRC_Enable`; single and cascade header-copy are both `0x0 -> 0x32A70`, length `0x100`.
- NT51927: `MERGE_MODE` plus `NT51927BASED_GEN_CRC_MODE CRC32`; single, 2-chip, and 3-chip branches match BAT.
- NT51928: owner-approved alias of NT51927 non-NB postbuild flow.
- NT51930: `NT51930BASED_NORMAL_MODE CRC8`; single and cascade match BAT.
- NT51931: BAT explicitly uses `NT51930BASED_NORMAL_MODE CRC8`; catalog matches BAT.
- NT51932: `NT51932BASED_NORMAL_MODE CRC8`; single/cascade match BAT.
- NT51950: `NT51950BASED_NORMAL_MODE CRC8`; single/cascade match BAT.
- NT51919/NT51929/NT51951 aliases match the current owner-confirmed alias model.

Important correction:

- NT51931 should not be changed to `NT51931BASED_NORMAL_MODE` based only on diagnostics. The official inspected BAT uses `NT51930BASED_NORMAL_MODE CRC8`. The current issue is that committed Combiner 1.13.0 crashes on the NT51931 golden when run with the official BAT-shaped command.

## Current Per-IC Conclusions

### NT51926

Observed self-pasteback diff with committed Combiner 1.13.0:

- final diff: `251` bytes;
- main header CRC words: `0x1C..0x1F` and `0xFC..0xFF`, total `8` bytes;
- copy-header target diff: mostly inside `[0x32A70, 0x32B70)`, total `243` bytes.

The copy length is still exactly `0x100` bytes. The `243` bytes are only the bytes that differ after copying.

The original bytes in the changed copy-header target were mostly `0xFE` and `0x00`, not `0xFF`. The issue is therefore not erased flash padding. It is a copy-header target state mismatch:

```text
source: [0x00000, 0x00100)
target: [0x32A70, 0x32B70)
length: 0x100
```

After command 1, the target equals the original main header except for later recalculated CRC words. Additional NT51926 golden outputs are needed to determine whether the target should already be initialized in true postbuild output.

### NT51927

NT51927 2-chip and 3-chip branches explicitly contain whole-window copies in the BAT. These are not inferred from flash-map UI names.

2-chip right-window copy:

```text
source: 0x16000
target: 0x1F000
length: 0x9000
```

3-chip includes the same right-window copy and an additional left-window copy:

```text
source: 0x16000
target: 0x28000
length: 0x9000
```

After those copies, the BAT overlays CtrlRAM subregions, but it does not overwrite every byte in the copied windows. Therefore non-CtrlRAM bytes can remain changed if the base golden was not produced by the same chip-count branch.

Current interpretation:

- NT51927 single self-pasteback mostly reduces to header-word drift.
- The current NT51927 golden is SINGLE and matches the current investigation scope.
- NT51927 2-chip/3-chip testing would require matching owner golden outputs for those branches if those branches become in-scope.
- Running a single-branch golden through a multi-chip branch is not a valid first-run-identity test.

### NT51928

NT51928 non-NB follows the NT51927 postbuild flow for CtrlRAM.

LDC/LD is Display/DP-side data, not CtrlRAM:

- `test_ic_config.json` declares `extra_bins` item `LD`;
- range is `[0x40000, 0x62000)`;
- Standard Merge profile declares `ld-input`;
- `TpFlashMapCatalog` classifies `dp-ldc-51928` as `TpFlashMapRegionKind.Dp`;
- UI exposes NT51928 LDC under DP Replace, not CtrlRAM Replace.

Conclusion: NT51928 LDC belongs to Display/DP merge/replace handling.

### NT51930

The original BAT confirms:

- single branch does not pass `DiffDLM.bin`;
- cascade branch passes `DiffDLM.bin`.

However, committed Combiner 1.13.0 still mutates DiffDLM-like data in single branch:

```text
after[0x32000, 0x33000) == base[0x31A00, 0x32A00)
```

This is a hidden internal move/copy by `NT51930BASED_NORMAL_MODE CRC8`, not a BAT-listed `DiffDLM.bin` argument.

Current interpretation:

- NT51930 postbuild catalog matches BAT.
- The single-branch large diff is real combiner behavior, not a catalog transcription error.
- Any production acceptance of this write requires explicit processor-owned/protected range evidence and firmware-owner review.

### NT51931

The original BAT confirms NT51931 official postbuild uses:

```text
NT51930BASED_NORMAL_MODE CRC8
```

The current catalog matches that BAT.

Observed behavior with committed Combiner 1.13.0:

- no-block diagnostic exits nonzero without useful output;
- any official block-bearing NT51931 command crashes with access violation `0xC0000005`;
- `NT51931BASED_NORMAL_MODE` exists in the executable and can run diagnostic commands, but it is not the inspected official BAT flow.

Current interpretation:

- NT51931 is the main "catalog matches postbuild but tool behavior may be wrong version" case.
- Most likely investigation direction: combiner executable version drift or source/header-state compatibility mismatch.
- Do not change the production catalog to `NT51931BASED_NORMAL_MODE` without owner postbuild evidence.
