# 0.9.x Completion Roadmap

Status: active owner roadmap.

This document is the execution goal through the reviewed `v0.9.9` convergence
and `v0.9.10` full performance remediation program. It separates a completed
migration milestone from a firmware-support claim and leaves later version
assignment to the post-remediation owner decision gate.

The evidence-backed issue inventory and dependency order are maintained in the
[0.9.x Codebase Readiness Audit](0.9.x-codebase-readiness-audit.md). The audit
remains an issue inventory, but its earlier `v0.9.10` through `v0.9.16`
assignment is superseded by the owner's 2026-07-18 decision: `v0.9.9` owns
legacy/contract/support convergence, `v0.9.10` owns end-to-end process, I/O,
memory, report, and UI performance,
and later routing is selected only after both merge.

## Program goal

Complete the owner-selected AB, CtrlRAM, typed family/evidence, support-matrix,
and legacy-retirement scope in `v0.9.9` through the existing V2 boundary and
one composition engine. Reconcile that result into `v0.9.10`, then measure and
remediate process/UI bottlenecks without changing firmware behavior or support
truth. The program includes composition orchestration, legacy Combiner
launches/readbacks, Build responsiveness, report scalability, UI file
inspection, progress feedback, and proven same-owner buffer copies. Runtime
FWConfig facts always come from the unique NVT Backup copy at
terminal `T - 0xFFF`; a primary flash-map address is evidence only and is never
a runtime fallback.

### Scope

1. Implement AB Merge for NT51919, NT51929, NT51932, NT51950, and NT51951
   through V2 bundle data, the existing compiler, and the existing composition
   engine. There is no AB-only executor or UI-owned byte logic.
2. Every AB profile initializes its output from the complete submitted DP_AB
   container, then applies only profile-declared TPA/TPB overlays. Customer
   information follows the submitted DP_AB container unless owner evidence
   declares a narrower exception.
3. NT51919 may reuse NT51929/NT51932 AB facts only through an approved
   fact-scoped map binding with direct parity evidence. It is not a whole-map
   alias.
4. NT51950 topology-dependent AB behavior derives its chip count from the
   canonical FWConfig Backup layout. Profile applicability selects the needed
   CMD/CMD-BK facts; it must not expose eight synthetic modes when aliases
   produce the same executable behavior.
5. Implement the generic `transform-scalar` operation only where a profile
   declares the approved TPB relocation field. It remains checked for width,
   byte order, expected-before value, and overflow.
6. Verify whether the external Python CRC transform and legacy Combiner are
   equivalent separately for each approved 950/951 AB branch. No equivalence
   is assumed from their names or from Normal/CtrlRAM postbuild behavior.
7. On CtrlRAM Replace Build only, present a pre-Build review choice to retain
   the TP FW major/sub-version or edit both values. Preview never edits the
   version. The version reader and any approved writer use
   `FirmwareConfigLayout` and the NVT Backup copy only; fields, write ranges,
   ordering relative to Combiner postbuild, and output differences require
   owner evidence and tests.

### Required evidence and tests

- Archive each owner-supplied AB golden outside Git unless it is an approved
  fixture. Commit only manifests, hashes, provenance, and explicit evidence
  decisions.
- Add direct V2/reference output parity and negative tests for every approved
  IC/topology/capacity branch. Test initializer order, overlays, customer-info
  ownership, scalar relocation, CRC/header declared writes, and rejection of
  malformed/ambiguous metadata.
- Test both CtrlRAM version choices against the same base image: retain is
  byte-identical to the existing approved branch; edit changes only the
  declared version and postbuild ranges. Confirm an invalid or missing NVT
  Backup fails closed.
- Run the affected contract, engine, worker, Bootstrap, UI, and golden tests;
  finish with `python scripts/verify.py --all`, Polytail, independent review,
  and firmware-owner review. A failed or unavailable remote CI is recorded,
  never represented as a passing firmware gate.

## v0.9.4: automated IC intake

Provide a manifest-driven intake command or UI that reads declared evidence
into a caller-selected empty staging directory and emits candidate bundle rows
plus validation reports. It must be deterministic, read Office files without
macros, reject path escapes/overwrite/lock files, and have no runtime profile
registration, support promotion, range inference, or automatic schema allowlist
change. A human still reviews and promotes a candidate through the normal
bundle materialization path.

## v0.9.5: V2 workflow convergence

Migrate one workflow family at a time until its V2 runtime/profile/map path
has direct byte, naming, processor, report, CLI, and UI parity. Only then
retire the corresponding legacy definition named in the retirement matrix.
This includes the remaining Replace/General compiler authority, flash-map and
metadata compatibility projections, and legacy Combiner postbuild catalog when
their R3 evidence permits replacement. Do not delete a legacy catalog merely
because it is old or because one adjacent workflow has migrated.

## v0.9.6: release and support consolidation

Remove compatibility projections whose `v0.9.5` retirement rows are closed;
reconcile the IC/workflow support matrix; close clean-machine Windows package,
SBOM/provenance, hash, signing-policy, report/history, and release-manifest
evidence. This milestone does not introduce new firmware behavior or use
packaging as a substitute for firmware-owner support approval.

## v0.9.7: UI token consolidation and code-size discipline

Risk class: R1/R2 according to the affected UI boundary. Candidate work may
start before the reviewed `v0.9.6` tag under the pre-tag policy, but integration
and release follow that tag. It consolidates exactly equivalent Avalonia visual,
text, and spacing tokens so one semantic UI concept has one owner. It also
records a production/UI/test line-count inventory and removes only definitions,
adapters, or compatibility paths that have an exact retained replacement and
direct regression coverage.

It must not:

- place firmware ranges, profile behavior, integrity policy, or firmware
  terminology decisions in UI tokens;
- replace accessibility labels, localization resources, or meaningful state
  distinctions with visually similar shared values;
- remove required tests, manifests, golden evidence, or review records to
  improve a line-count metric; or
- introduce a second theme, localization, or token hierarchy.

Exit evidence records the baseline and resulting line counts, every retired
definition and its retained owner, UI smoke/accessibility coverage for affected
surfaces, and an independent review that confirms no semantic token collapse or
firmware-boundary drift. A smaller codebase is an outcome of exact replacement,
not a standalone acceptance target.

## v0.9.9: legacy convergence and verified patch closure

The original planned target was at most 54,000 nonblank production C#/AXAML
lines, with the portable package within the same 1% growth ceiling. Every
refactored legacy compiler, profile, catalog, facade, and runtime path may be
retired only after its exact V2 replacement is reviewed. The explicit
exception is Legacy Combiner: the approved executable and constrained runner
remain.

`LegacyCombinerPostbuildCatalog` declarations may move into V2 processor data
only with exact command, tool binding, staging, read/write range, full-output
golden, and firmware-owner evidence. Until then the catalog remains an R3
authority, not removable debt. This milestone also closes confirmed patch
gaps, including bundle/package reparse or TOCTOU findings, without speculative
checks or support promotion. NT51919, NT51932, NT51951, and every other
candidate retain their recorded direct/fact-scoped evidence and owner gates.

The 2026-07-17 audit found that this numerical goal was not met:
`origin/0.9.9` records 56,731 nonblank lines, while the audited `0.9.10`
lineage records 56,742. Before `0.9.10` can integrate, the owner must accept the
exact measured ratchet or the branch must complete only evidence-backed
retirement. Safety checks, tests, firmware evidence, and required compatibility
paths must not be deleted merely to force 54,000.

On 2026-07-18 the owner clarified that source-line reduction is not a
`v0.9.10` priority. The exact ratchet remains a non-gameable measurement, but
reviewed performance contracts, instrumentation, tests, and maintainable
boundaries may update it to the measured value. Safety or evidence must never
be removed to offset an authorized performance change. The selective Combiner
I/O slice records `56,821` production nonblank lines, and the isolated Build
scheduling slice records `56,838`. The first background/bounded report slice
records `57,115`; the first immutable UI inspection slice records `57,636`.
The first typed Application progress slice records `57,916`; source size
remains a measured maintainability ratchet rather than a `0.9.10` performance
target. The lazy report-detail slice records `58,112`; its success criterion is
bounded materialization and preserved report evidence, not source reduction.
The sequential JSON-slice phase records `58,179`; its acceptance is measured
summary latency/allocation plus complete JSON and lazy-detail parity. Source
size remains only an exact maintainability ratchet, not a performance KPI.

### Performance CHANGE rationale

The current branch provides the following concrete reasons to investigate a
change:

| Area | Current evidence | Why change |
| --- | --- | --- |
| Automatic Build orchestration | Historical node A at `74fb1028` ran a complete Preview and then a complete Build after a successful Preview; provisional C now owns one run in Application. | Node A repeated the same artifact reads, reference clone, engine operations, external processors, validation, hashes, diff, and report work for one Build click; final B/C must confirm the single-run result after rebase. |
| CtrlRAM postbuild I/O | For each command, `LegacyCombinerPostbuildProcessor` reads the full staged firmware before the command and again during shortened-output normalization, then reads the final firmware once more. A session with `C` commands therefore performs `2C + 1` host full-image reads. | A 13-command branch costs 27 host reads per processor session. Node A used two sessions (26 launches and 54 derived reads); provisional C uses one, while any further adapter reduction remains R3. |
| Workbench file inspection | Slot selection asks independent firmware-fact, IC-mismatch, context-suggestion, metadata, and postbuild projections to inspect the same selected BIN. | Repeated synchronous full-file reads increase selection latency and UI-thread pressure, especially for category-dependent CtrlRAM paths such as NT51926 and NT51930. |
| Run progress feedback | The current shell exposes only a generic indeterminate Preview/Build bar. | Long input, composition, and CtrlRAM postbuild runs do not reveal the current truthful lifecycle step; users cannot distinguish active work from a stalled-looking surface. |
| Build click responsiveness | The ViewModel publishes run ownership and then directly invokes the async workbench delegate; synchronous work before its first incomplete await can delay the first progress repaint, and result/report projection resumes on the UI dispatcher. | The Build surface can appear briefly frozen even when composition is healthy. Active state must render first, and heavy planning, I/O, hashing, composition, processing, and report projection must stay off the dispatcher. |
| Large change reports | Report JSON is parsed synchronously and every difference, mutation, fact, group, summary row, legacy hex field, and raw JSON binding is eagerly materialized into non-virtualized item controls. | Reports with many changed bytes/ranges can block completion and modal interaction. The UI needs summary-first background projection, bounded previews, lazy detail, and virtualization or paging while preserving the complete report. |
| Buffer ownership | Artifact, Application, Domain, normalization, external-processing, result, and report boundaries include multiple defensive byte-array copies. | Domain must keep its defensive snapshot, but copies repeated inside one owning layer add allocation and memory-bandwidth cost without adding trust. |
| Output-difference explanation | `DeclaredReplacement` is the stable classification for accepted differences inside declared Replace write ranges. Generic non-processor operations, including a TP FW version `patch-scalar`, may therefore receive this classification. | The term does **not** mean "firmware version changed". A generic "Declared replacement" label can hide whether bytes came from a CtrlRAM payload, an explicit TP FW version edit, FWConfig propagation, or CRC/header refresh. |
| Measurement | Run reports have overall timestamps, but automatic Build returns only the final Build report and external process records do not expose duration or deterministic invocation/read counters. | Optimization cannot be reviewed reliably without separating engine, processor, I/O, and UI-inspection costs. |

Baseline evidence has three named nodes:

| Node | Meaning | Use |

Every B/C comparison records the commit, clean/dirty state, Windows/.NET
version, CPU, run count, warm-up policy, input and expected-output SHA-256,

thresholds.

heartbeat gap, report summary-ready and detail-ready latency, initially
materialized row/control counts, cancellation latency, and full-report export
parity. Combiner evidence records length checks, final full reads, selective
tail reads/bytes, normalization writes, and staged artifact reads separately so
an apparent I/O reduction cannot hide work or weaken validation.

4. Publish Build active/progress state before heavy work can occupy the UI

8. Document byte-buffer ownership and remove only redundant same-owner copies.

9. Keep stable report classifications unless a versioned contract migration is
   approved. Application should provide typed semantic subjects such as

evidence covers omitted phases, localization, run isolation, and static motion.
Authoritative click-to-step and dispatcher measurements remain node B/C work.

Reusing an earlier Preview output as the later Build artifact is rejected: it
creates stale-input and stale-policy authority. Skipping hashes or independent
diff validation, parallelizing ordered Combiner commands, or removing Domain's
defensive snapshot is also rejected. Optimizing only Presentation is
insufficient because the dominant CtrlRAM costs cross Application and
Infrastructure boundaries.

#### Acceptance, risk, and gates

- Automatic Build executes the engine once and opens one processor session;
  the 13-command case reduces process launches from 26 to 13.
- The separately reviewed Combiner adapter retains exactly `C` sequential
  launches. A non-merge two-command or 13-command session performs `C` metadata
  checks and one final full firmware read instead of five or 27 full reads.
  Merge-mode plans additionally record one selective tail read per merge
  command; tail bytes, artifact reads, and normalization writes remain visible.
- A Build click renders active/phase state before a deterministic blocking fake
  can occupy background work, and dispatcher heartbeat evidence shows the UI
  remains responsive through planning, execution, processing, and result
  projection.
- Large reports expose correct global summary/review-required counts with a
  bounded initial row/control count. Lazy pages and byte previews do not alter
  saved/exported JSON, hashes, ranges, classifications, or processor evidence.
- One UI selection performs at most one full-file read for its inspection
  snapshot. Changing file identity or content invalidates the snapshot.
- Preview and Build show the current applicable typed lifecycle phase. Phase
  order, run-id isolation, failure/cancellation behavior, localization,
  accessibility, high contrast, and reduced motion are tested. No determinate
  byte percentage or remaining-time estimate is shown without a real contract.
- After the separately reviewed adapter phase, a 13-command automatic Build
  reduces host staging-firmware reads from the current worst case of 54 to at
  most 13. Staged-source artifact immutability reads are tracked separately and
  are not hidden from evidence.
- Golden output bytes and SHA-256, operation/mutation traces, exact processor
  argv and order, difference classifications, warnings, output naming, and
  failed-run atomicity remain identical unless a separately approved contract
  change explicitly names a report-only semantic difference.
- Self-replacement that produces identical final bytes still emits no output-
  difference row. A `DeclaredReplacement` row proves an accepted changed range,
  not that a version edit occurred.
- Counters and byte assertions are deterministic CI gates. Timing results are
  recorded as benchmark evidence rather than flaky pass/fail thresholds.
- Instrumentation and isolated UI inspection work are R1 unless they alter a
  public report or use-case contract. Automatic-Build orchestration, report
  semantics, and buffer-ownership changes are R2 and require architecture/
  contract review. External postbuild I/O convergence is R3 and requires exact
  CtrlRAM golden parity plus firmware-owner review.
- Any changed range, operation order, checksum/header behavior, processor
  authority, public classification token, or output byte is outside this
  optimization authorization and must stop for its normal R3 evidence and
  human gate.

Implementation proceeds as separate reviewable `v0.9.10` phases:

1. preserve node A and define the B/C comparison record;
2. after the final `0.9.9` rebase, capture node B with deterministic counters,
   golden output/report parity, process-window behavior, timing, and allocation;
3. replay the provisional Application-owned single-execution automatic Build
   slice on final `0.9.9` and compare it with B;
4. reduce Legacy Combiner staging I/O in a separate ADR 0025 R3 phase, starting
   from the NT51926 two-command full-output golden; use final-only full read for
   non-merge families and selective tail preservation for `MERGE_MODE`, and
   admit wider command plans only when their required owner evidence exists;
5. publish Build progress before background work and move heavy execution and
   result projection off the UI dispatcher, with heartbeat/cancellation tests;
6. make report review summary-first, background-projected, lazy, bounded, and
   virtualized or paged while preserving complete export evidence;
7. after the `0.9.9` UI contracts freeze, implement one immutable asynchronous
   inspection snapshot per selected file identity/hash and compare UI file
   reads, projection work, UI-thread blocking, timing, and allocation with B;
8. add the ADR 0024 Application phase contract and accessible UI step-progress
   animation, then measure bounded progress events and UI-thread impact; and
9. remove only proved same-owner buffer copies.

`v0.9.10` cannot integrate or release until its branch is reconciled with the
reviewed `v0.9.9` baseline and each included phase passes its own narrow tests,
Polytail, the canonical final verifier, required golden parity, and independent
review.

## Post-remediation decision gate

No `v0.9.11` or later milestone is committed by this roadmap. After reviewed
`v0.9.9` and the `v0.9.10` remediation both merge, the owner will select and
version the remaining route using measured B/C results and the final support
matrix.
The decision inventory remains visible without assigning premature versions:

- any residual performance work that did not satisfy its `v0.9.10` evidence or
  review gate;
- whether typed report subjects/Application inspection ports are still needed;
- whether any R3 postbuild I/O convergence has enough direct full-output golden
  coverage beyond the NT51926 scoped case;
- remaining operability, cancellation, accessibility, soak, release, security,
  clean-machine, legal, SBOM, provenance, and review gates; and
- later support requests such as NT51931, which is not available in stable
  `0.9.9` but is not permanently banned.

Legacy/V2 retirement, support matrix, family/evidence status, and workflow
exposure are not part of this future inventory: they are explicit `v0.9.9`
responsibilities. The first signed-off stable sample remains `v1.0.0`, but its
intermediate version sequence is selected only at this decision gate.

## Scope fence

No milestone may add a per-IC executor, a second compiler, a second runtime
schema/loader hierarchy, UI firmware semantics, primary-FWConfig fallback, or
unchecked binary patch. Any proposed exception requires an ADR, precise R3
evidence, and owner approval before implementation.
