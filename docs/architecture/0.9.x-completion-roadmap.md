# 0.9.x Completion Roadmap

Status: active owner roadmap.

This document is the execution goal for the remaining `0.9.x` milestones. It
separates a completed migration milestone from a firmware-support claim and
keeps each later release small enough to verify independently.

## Program goal

Deliver the owner-approved AB Code and CtrlRAM version-edit work through the
existing V2 family/profile/compiler boundary and the one composition engine,
then standardize IC intake, retire only fully replaced legacy routes, and close
release/support evidence. Runtime FWConfig facts always come from the unique
NVT Backup copy at terminal `T - 0xFFF`; a primary flash-map address is
evidence only and is never a runtime fallback.

The following are deliberately not omissions from `0.9.1` or `0.9.2`:

- Remaining legacy Replace/General runtime routes and compatibility projections
  are governed by the [Legacy Retirement Matrix](../governance/legacy-retirement-matrix.md)
  and belong to `v0.9.5` only after exact V2 replacement evidence exists.
- Unsigned or private CtrlRAM/General Replace golden evidence for unrelated ICs
  is not silently promoted by either migration milestone. `v0.9.3` closes the
  evidence required by its own AB and version-edit work only.
- Product support remains a firmware-owner decision. A V2 runtime route or a
  tagged migration milestone never changes a profile to `Supported`.

## Release order

```text
v0.9.1 (tagged)
  -> v0.9.2 (tagged release baseline)
  -> v0.9.3 AB Code + CtrlRAM version edit
  -> v0.9.4 candidate IC intake
  -> v0.9.5 V2 workflow convergence and legacy retirement
  -> v0.9.6 release/support consolidation
  -> v0.9.7 UI token consolidation and code-size discipline
```

`0.9.3` integration and release must start from the reviewed `v0.9.2` tag.
Candidate AB work may start earlier under the policy below, but it must rebase
or merge onto that tag before integration. Do not backfill the tag after AB
integration has started: that would make the AB evidence baseline ambiguous.

### Pre-tag candidate-development policy

Owner policy, 2026-07-14: development of a later `0.9.x` feature branch is
allowed before its preceding release tag and without owner firmware evidence.
This permission is limited to deterministic candidate, architecture, intake,
or test work. It does not grant runtime support, change a promotion stage,
replace direct golden/legacy parity, permit a release tag, or allow a merge to
`main`. Each early branch names its target milestone and must rebase or merge
onto the required reviewed predecessor tag before that target can integrate or
release.

## v0.9.3: AB Code and CtrlRAM version edit

Risk class: R3. A separate `feature/0.9.3/<topic>` branch is required for each
independently reviewable firmware slice, with firmware-owner review before the
release tag.

### Scope

1. Implement AB Merge for NT51919, NT51929, NT51932, NT51950, and NT51951
   through V2 bundle data, the existing compiler, and the existing composition
   engine. There is no AB-only executor or UI-owned byte logic.
2. Every AB profile initializes its output from the complete submitted DP_AB
   container, then applies only profile-declared TPA/TPB overlays. Customer
   information follows the submitted DP_AB container unless owner evidence
   declares a narrower exception.
3. NT51919 may reuse NT51929/NT51932 AB facts only through an approved
   fact-scoped map binding with direct parity evidence. It is not a whole-map
   alias.
4. NT51950 topology-dependent AB behavior derives its chip count from the
   canonical FWConfig Backup layout. Profile applicability selects the needed
   CMD/CMD-BK facts; it must not expose eight synthetic modes when aliases
   produce the same executable behavior.
5. Implement the generic `transform-scalar` operation only where a profile
   declares the approved TPB relocation field. It remains checked for width,
   byte order, expected-before value, and overflow.
6. Verify whether the external Python CRC transform and legacy Combiner are
   equivalent separately for each approved 950/951 AB branch. No equivalence
   is assumed from their names or from Normal/CtrlRAM postbuild behavior.
7. On CtrlRAM Replace Build only, present a pre-Build review choice to retain
   the TP FW major/sub-version or edit both values. Preview never edits the
   version. The version reader and any approved writer use
   `FirmwareConfigLayout` and the NVT Backup copy only; fields, write ranges,
   ordering relative to Combiner postbuild, and output differences require
   owner evidence and tests.

### Required evidence and tests

- Archive each owner-supplied AB golden outside Git unless it is an approved
  fixture. Commit only manifests, hashes, provenance, and explicit evidence
  decisions.
- Add direct V2/reference output parity and negative tests for every approved
  IC/topology/capacity branch. Test initializer order, overlays, customer-info
  ownership, scalar relocation, CRC/header declared writes, and rejection of
  malformed/ambiguous metadata.
- Test both CtrlRAM version choices against the same base image: retain is
  byte-identical to the existing approved branch; edit changes only the
  declared version and postbuild ranges. Confirm an invalid or missing NVT
  Backup fails closed.
- Run the affected contract, engine, worker, Bootstrap, UI, and golden tests;
  finish with `python scripts/verify.py --all`, Polytail, independent review,
  and firmware-owner review. A failed or unavailable remote CI is recorded,
  never represented as a passing firmware gate.

### Exit criteria

`v0.9.3` may be tagged only when all five approved AB targets and the selected
CtrlRAM version-edit branches have their required R3 evidence, owner review,
and immutable golden/legacy parity records. Unapproved ICs, modes, capacities,
or CtrlRAM postbuild variants remain candidate data with explicit blockers.

## v0.9.4: automated IC intake

Provide a manifest-driven intake command or UI that reads declared evidence
into a caller-selected empty staging directory and emits candidate bundle rows
plus validation reports. It must be deterministic, read Office files without
macros, reject path escapes/overwrite/lock files, and have no runtime profile
registration, support promotion, range inference, or automatic schema allowlist
change. A human still reviews and promotes a candidate through the normal
bundle materialization path.

## v0.9.5: V2 workflow convergence

Migrate one workflow family at a time until its V2 runtime/profile/map path
has direct byte, naming, processor, report, CLI, and UI parity. Only then
retire the corresponding legacy definition named in the retirement matrix.
This includes the remaining Replace/General compiler authority, flash-map and
metadata compatibility projections, and legacy Combiner postbuild catalog when
their R3 evidence permits replacement. Do not delete a legacy catalog merely
because it is old or because one adjacent workflow has migrated.

## v0.9.6: release and support consolidation

Remove compatibility projections whose `v0.9.5` retirement rows are closed;
reconcile the IC/workflow support matrix; close clean-machine Windows package,
SBOM/provenance, hash, signing-policy, report/history, and release-manifest
evidence. This milestone does not introduce new firmware behavior or use
packaging as a substitute for firmware-owner support approval.

## v0.9.7: UI token consolidation and code-size discipline

Risk class: R1/R2 according to the affected UI boundary. Candidate work may
start before the reviewed `v0.9.6` tag under the pre-tag policy, but integration
and release follow that tag. It consolidates exactly equivalent Avalonia visual,
text, and spacing tokens so one semantic UI concept has one owner. It also
records a production/UI/test line-count inventory and removes only definitions,
adapters, or compatibility paths that have an exact retained replacement and
direct regression coverage.

It must not:

- place firmware ranges, profile behavior, integrity policy, or firmware
  terminology decisions in UI tokens;
- replace accessibility labels, localization resources, or meaningful state
  distinctions with visually similar shared values;
- remove required tests, manifests, golden evidence, or review records to
  improve a line-count metric; or
- introduce a second theme, localization, or token hierarchy.

Exit evidence records the baseline and resulting line counts, every retired
definition and its retained owner, UI smoke/accessibility coverage for affected
surfaces, and an independent review that confirms no semantic token collapse or
firmware-boundary drift. A smaller codebase is an outcome of exact replacement,
not a standalone acceptance target.

## Scope fence

No milestone may add a per-IC executor, a second compiler, a second runtime
schema/loader hierarchy, UI firmware semantics, primary-FWConfig fallback, or
unchecked binary patch. Any proposed exception requires an ADR, precise R3
evidence, and owner approval before implementation.
