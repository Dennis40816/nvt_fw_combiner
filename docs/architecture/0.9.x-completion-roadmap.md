# 0.9.x Completion Roadmap

Status: active owner roadmap.

This document is the execution goal through the reviewed `v0.9.9` convergence
and `v0.9.10` full performance remediation program. It separates a completed
migration milestone from a firmware-support claim and leaves later version
assignment to the post-remediation owner decision gate.

The evidence-backed issue inventory and dependency order are maintained in the
[0.9.x Codebase Readiness Audit](0.9.x-codebase-readiness-audit.md). The audit
remains an issue inventory, but its earlier `v0.9.10` through `v0.9.16`
assignment is superseded by the owner's 2026-07-18 decision: `v0.9.9` owns
legacy/contract/support convergence, `v0.9.10` owns end-to-end process, I/O,
memory, report, and UI performance,
and later routing is selected only after both merge.

## Program goal

Complete the owner-selected AB, CtrlRAM, typed family/evidence, support-matrix,
and legacy-retirement scope in `v0.9.9` through the existing V2 boundary and
one composition engine. Reconcile that result into `v0.9.10`, then measure and
remediate process/UI bottlenecks without changing firmware behavior or support
truth. The program includes composition orchestration, legacy Combiner
launches/readbacks, Build responsiveness, report scalability, UI file
inspection, progress feedback, proven same-owner buffer copies, report-history
persistence, and a read-only Hex Diff review workspace. Runtime
FWConfig facts always come from the unique NVT Backup copy at
terminal `T - 0xFFF`; a primary flash-map address is evidence only and is never
a runtime fallback.

### Scope

1. Implement AB Merge for NT51919, NT51929, NT51932, NT51950, and NT51951
   through V2 bundle data, the existing compiler, and the existing composition
   engine. There is no AB-only executor or UI-owned byte logic.
2. Every AB profile initializes its output from the complete submitted DP_AB
   container, then applies only profile-declared TPA/TPB overlays. Customer
   information follows the submitted DP_AB container unless owner evidence
   declares a narrower exception.
3. NT51919 may reuse NT51929/NT51932 AB facts only through an approved
   fact-scoped map binding with direct parity evidence. It is not a whole-map
   alias.
4. NT51950 topology-dependent AB behavior derives its chip count from the
   canonical FWConfig Backup layout. Profile applicability selects the needed
   CMD/CMD-BK facts; it must not expose eight synthetic modes when aliases
   produce the same executable behavior.
5. Implement the generic `transform-scalar` operation only where a profile
   declares the approved TPB relocation field. It remains checked for width,
   byte order, expected-before value, and overflow.
6. Verify whether the external Python CRC transform and legacy Combiner are
   equivalent separately for each approved 950/951 AB branch. No equivalence
   is assumed from their names or from Normal/CtrlRAM postbuild behavior.
7. On CtrlRAM Replace Build only, present a pre-Build review choice to retain
   the TP FW major/sub-version or edit both values. Preview never edits the
   version. The version reader and any approved writer use
   `FirmwareConfigLayout` and the NVT Backup copy only; fields, write ranges,
   ordering relative to Combiner postbuild, and output differences require
   owner evidence and tests.

### Required evidence and tests

- Archive each owner-supplied AB golden outside Git unless it is an approved

- Add direct V2/reference output parity and negative tests for every approved

## v0.9.4: automated IC intake

Provide a manifest-driven intake command or UI that reads declared evidence
into a caller-selected empty staging directory and emits candidate bundle rows
plus validation reports. It must be deterministic, read Office files without
macros, reject path escapes/overwrite/lock files, and have no runtime profile
registration, support promotion, range inference, or automatic schema allowlist
change. A human still reviews and promotes a candidate through the normal
bundle materialization path.

## v0.9.5: V2 workflow convergence

Migrate one workflow family at a time until its V2 runtime/profile/map path
has direct byte, naming, processor, report, CLI, and UI parity. Only then
retire the corresponding legacy definition named in the retirement matrix.
This includes the remaining Replace/General compiler authority, flash-map and
metadata compatibility projections, and legacy Combiner postbuild catalog when
their R3 evidence permits replacement. Do not delete a legacy catalog merely
because it is old or because one adjacent workflow has migrated.

## v0.9.6: release and support consolidation

Remove compatibility projections whose `v0.9.5` retirement rows are closed;
reconcile the IC/workflow support matrix; close clean-machine Windows package,
SBOM/provenance, hash, signing-policy, report/history, and release-manifest
evidence. This milestone does not introduce new firmware behavior or use
packaging as a substitute for firmware-owner support approval.

## v0.9.7: UI token consolidation and code-size discipline

Risk class: R1/R2 according to the affected UI boundary. Candidate work may
start before the reviewed `v0.9.6` tag under the pre-tag policy, but integration
and release follow that tag. It consolidates exactly equivalent Avalonia visual,
text, and spacing tokens so one semantic UI concept has one owner. It also
records a production/UI/test line-count inventory and removes only definitions,
adapters, or compatibility paths that have an exact retained replacement and
direct regression coverage.

It must not:

- place firmware ranges, profile behavior, integrity policy, or firmware
  terminology decisions in UI tokens;
- replace accessibility labels, localization resources, or meaningful state
  distinctions with visually similar shared values;
- remove required tests, manifests, golden evidence, or review records to
  improve a line-count metric; or
- introduce a second theme, localization, or token hierarchy.

Exit evidence records the baseline and resulting line counts, every retired
definition and its retained owner, UI smoke/accessibility coverage for affected
surfaces, and an independent review that confirms no semantic token collapse or
firmware-boundary drift. A smaller codebase is an outcome of exact replacement,
not a standalone acceptance target.

## v0.9.9: legacy convergence and verified patch closure

The original planned target was at most 54,000 nonblank production C#/AXAML
lines, with the portable package within the same 1% growth ceiling. Every
refactored legacy compiler, profile, catalog, facade, and runtime path may be
retired only after its exact V2 replacement is reviewed. The explicit
exception is Legacy Combiner: the approved executable and constrained runner
remain.

`LegacyCombinerPostbuildCatalog` declarations may move into V2 processor data
only with exact command, tool binding, staging, read/write range, full-output
golden, and firmware-owner evidence. Until then the catalog remains an R3
authority, not removable debt. This milestone also closes confirmed patch
gaps, including bundle/package reparse or TOCTOU findings, without speculative
checks or support promotion. NT51919, NT51932, NT51951, and every other
candidate retain their recorded direct/fact-scoped evidence and owner gates.

The 2026-07-17 audit found that this numerical goal was not met:
`origin/0.9.9` records 56,731 nonblank lines, while the audited `0.9.10`
lineage records 56,742. Before `0.9.10` can integrate, the owner must accept the
exact measured ratchet or the branch must complete only evidence-backed
retirement. Safety checks, tests, firmware evidence, and required compatibility
paths must not be deleted merely to force 54,000.

On 2026-07-18 the owner clarified that source-line reduction is not a
`v0.9.10` priority. The exact ratchet remains a non-gameable measurement, but
reviewed performance contracts, instrumentation, tests, and maintainable
boundaries may update it to the measured value. Safety or evidence must never
be removed to offset an authorized performance change. The selective Combiner
I/O slice records `56,821` production nonblank lines, and the isolated Build
scheduling slice records `56,838`. The first background/bounded report slice
records `57,115`; the first immutable UI inspection slice records `57,636`.
The first typed Application progress slice records `57,916`; source size
remains a measured maintainability ratchet rather than a `0.9.10` performance
target. The lazy report-detail slice records `58,112`; its success criterion is
bounded materialization and preserved report evidence, not source reduction.
The sequential JSON-slice phase records `58,179`; its acceptance is measured
summary latency/allocation plus complete JSON and lazy-detail parity. Source
size remains only an exact maintainability ratchet, not a performance KPI.

#### Baseline comparison protocol

Baseline evidence has three named nodes:

| Node | Meaning | Use |
| --- | --- | --- |
| A: pre-rebase baseline | `feature/0.9.10/replace-performance-baseline` at `74fb1028`, based on `0.9.9` `7e18cfa0` | Historical diagnosis only; never the final performance claim. |
| B: reconciled before | Final reviewed `0.9.9` rebased into `0.9.10`, before optimization | Authoritative before value and parity source. |
| C: optimized `0.9.10` | Same reconciled code, inputs, tool hashes, machine/runtime settings, with the accepted performance changes | Compared with B for the optimization decision. |

Every B/C comparison records the commit, clean/dirty state, Windows/.NET
version, CPU, run count, warm-up policy, input and expected-output SHA-256,
Legacy Combiner manifest hash, and cold/warm distinction. Deterministic counts
and byte/report equality are CI assertions. Elapsed p50/p95, allocation, peak
working set, and UI-thread blocked time are local evidence, not hard timing
thresholds.

UI B/C evidence also records click-to-first-progress, maximum dispatcher
heartbeat gap, report summary-ready and detail-ready latency, initially
materialized row/control counts, cancellation latency, and full-report export
parity. Combiner evidence records length checks, final full reads, selective
tail reads/bytes, normalization writes, and staged artifact reads separately so
an apparent I/O reduction cannot hide work or weaken validation.

The reconciled probe must additionally separate report diff discovery,
semantic classification, hashing, report-object creation, JSON serialization,
Presentation projection, history capture, history persistence, history reopen,
and relocalization. It records retained history payload/projection bytes, GC
counts, peak working set, startup first-paint delay, range-index creation,
Hex Diff first-page readiness, address-jump latency, and visible control count.
The current synthetic JSON projection result is retained but is not accepted as
evidence for these upstream and persistence stages.

The first reconciled matrix uses only evidence with the stated scope:

- DP Replace: public deterministic NT51950/NT51951 cases at `0x40000`,
  `0x80000`, and `0x100000`, plus owner-golden-backed 51950 256 KiB and 51951
  512 KiB base smoke cases;
- CtrlRAM full-output parity: NT51926 Common FW 1.4.1 cascade TP-base case
  `nt51926-cascade-tp-base-self-regression-20260717`, with its two-command
  Legacy Combiner plan;
- CtrlRAM count-only coverage: cases without an independent expected output may
  measure sessions, commands, reads, and launches but cannot claim firmware
  parity; and
- UI: cold selection, repeated same-file selection, IC/mode/IC-num changes,
  coverage projection, and report projection over the same typed `0.9.9`
  workflow state. Exact file-read and projection counts are captured before an
  asynchronous snapshot/cache is introduced.

General Replace has no owner full-output golden and is excluded from firmware
performance parity. Standard Merge and AB goldens remain useful regression
anchors but are not used to imply Replace support.

#### Proposed direction and ownership

1. Add deterministic counters and a local benchmark harness before changing
   execution. Cover DP container lengths `0x40000`, `0x80000`, and `0x100000`;
   CtrlRAM two-command and 13-command plans; NT51926/NT51930 base-file
   selection; and small plus very large synthetic change reports. Record
   p50/p95 locally, allocations, working set, full-image read counts, engine
   executions, processor sessions, process launches, UI heartbeat, and
   initially materialized report rows. Do not add a runtime dependency or hard
   timing assertion to CI.

2. Add one Application-owned automatic-Build use case that snapshots and
   validates current inputs, executes the compiled composition once, performs
   final validation, and atomically promotes exactly those validated bytes.
   Standalone Preview remains non-committing. An explicit Preview-token Build
   remains bound to compiled fingerprint, hashes, and output options and must
   fail closed when they change.
3. In a separate R3 adapter phase, preserve one exact sequential Legacy
   Combiner session with `C` declared command launches. Normal, NT-based, and
   CRC-only commands use length metadata and continue without intermediate full
   reads. A `MERGE_MODE` command preserves only the tail after maximum declared
   write coverage and appends the missing suffix if the output is short. Read
   the complete firmware once after all commands without changing argv/order,
   tool identity, failure attribution, final host diff, or allowed-write-range
   validation.
4. Publish Build active/progress state before heavy work can occupy the UI
   dispatcher. Run planning, file I/O, hashing, composition, processors, and
   report projection off the dispatcher with existing cancellation and run-id
   ownership; marshal back only bounded state.
5. Keep canonical report JSON complete while projecting a small summary first.
   Parse/project in the background, load detail per selected tab, use bounded
   byte previews and virtualized or paged collections, and disclose full legacy
   hex/raw JSON only on request. Export, global counts, review-required ordering,
   and all machine-readable evidence remain complete.
6. Give the UI one immutable asynchronous inspection snapshot per selected
   file identity/hash and project firmware facts, mismatch guidance, context,
   metadata, and postbuild readiness from it. Build must still perform its own
   authoritative read and hash; a UI cache is never Build authority.
7. Add the ADR 0024 typed Application progress phases and render one localized,
   accessible step indicator. The UI may animate only the active phase and must
   honor reduced motion; it never derives phases from operation ids, filenames,
   reason strings, or elapsed time and never presents a fake byte percentage.
8. Document byte-buffer ownership and remove only redundant same-owner copies.
   Retain the ADR 0015 Domain snapshot, immutable input identity, processor
   before/after evidence, and immutable report/result projections.
9. Keep stable report classifications unless a versioned contract migration is
   approved. Application should provide typed semantic subjects such as
   `CtrlRAM replacement`, `TP FW version edit`, `FW configuration / postbuild
   update`, and `Postbuild CRC/header refresh`; Presentation only localizes and
   renders them. It must not branch on operation ids or reason strings to infer
   firmware meaning.

#### Change Report read-only Hex Diff workspace

The `v0.9.10` Changes experience becomes a spatial byte-review workspace rather
than a list of prose rows. It reuses the existing Hex Editor's visual grammar
and bounded viewport behavior, but it does **not** reuse its editable session,
undo history, mutable work buffer, structural source-offset map, Save As path,
or firmware-neutral change-reason generator.

The default desktop layout is a resizable two-column workspace:

- The left, visually dominant area uses roughly two thirds of the available
  width for a read-only virtualized Hex Diff viewport. It shows address,
  16-byte hex columns, and ASCII for the final output. Only bounded visible
  rows have byte-cell view models or controls. Changed bytes are styled by
  typed report verdict: expected replacement, expected firmware/version fact,
  expected postbuild CRC/header, or review required. Color is never the only
  signal; high-contrast borders/patterns and accessible text carry the same
  state.
- A `Show original rows` toggle inserts the verified reference/base row directly
  below each visible changed output row, matching the existing Hex Editor
  interaction. It is off by default to keep the output readable. Enabling it
  does not duplicate the complete document or create controls for off-screen
  bytes. Unchanged context rows remain single-row unless the reviewer explicitly
  requests a broader comparison mode.
- The upper-right information area explains the currently selected field or
  range. It shows the typed semantic subject, address space, half-open range
  `[start, end)`, length, expected/review verdict, modification reason,
  operation and evidence ids, before/after hashes, and relevant processor
  section. Presentation localizes these facts; it never infers them from
  filenames, operation-id substrings, colors, or free-form reason text.
- The lower-right navigator groups changes by typed semantic section, with
  review-required groups and rows first and address order stable inside each
  group. Every row shows a concise subject, verdict, address range, and byte
  count. Selecting a row scrolls and focuses the left viewport at its first
  changed byte; start/end actions jump to either boundary. Selecting a changed
  byte in the viewport selects the owning navigator row and updates the
  information area. Next/previous change, keyboard navigation, focus return,
  copy-address, and copy-bounded-bytes actions are available without enabling
  editing.

The comparison source is a typed, UI-session-local, immutable contract outside
the canonical report JSON:

1. A current Preview/Build may expose the already-authoritative reference and
   final output through a bounded read-only comparison provider. Ownership must
   reuse accepted Application buffers or a host-owned immutable snapshot; it
   must not add another unconditional pair of full-image copies merely for the
   modal.
2. The provider is bound to run id, address space, length, reference SHA-256,
   output SHA-256, and report identity. It is cancelled and disposed when the
   run/report is replaced. It cannot be supplied to Preview/Build and is never
   an input cache or support authority.
3. A persisted or manually loaded report does not contain enough bytes to
   reconstruct a full diff. The UI may ask the reviewer to attach the reference
   and output artifacts, read/hash them off the dispatcher, and enable the
   viewport only when size and SHA-256 match the report. When verified bytes
   are unavailable, the complete semantic range list and report evidence stay
   usable and the viewport states `Binary comparison unavailable`; preview
   snippets are never presented as a fabricated full document.
4. Output-difference ranges remain Application/report facts. The read-only
   viewport performs bounded byte lookup and navigation only. Any future
   compact report representation must retain exact ranges and provide a
   backward-readable migration; it cannot replace golden parity or host diff
   validation.

The workspace is lazy: opening Summary or another report tab retains no binary
viewport state. Opening Changes builds a range index and first viewport page
on a cancellable background worker, then publishes only bounded immutable
state. Range lookup uses an ordered index rather than scanning every change on
each pointer or scroll event. Report history stores neither comparison buffers
nor byte-cell models.

Acceptance covers small, 10,000-range, and adversarial fragmented reports;
0x40000/0x80000/0x100000 DP containers; the NT51926 two-command full-output
golden; preview and committed Build; missing/deleted/mismatched attached
artifacts; review-first navigation; original-row toggle; keyboard and screen
reader use; high contrast; reduced motion; stale-run cancellation; bounded
control count; jump/scroll latency; allocation and peak working set; and
unchanged complete report save/export bytes. This is R2 Presentation/
Application contract work. It becomes R3 only if a proposed report migration
changes firmware facts, exact ranges, processor evidence, or golden output.

The first deterministic orchestration baseline was captured on 2026-07-18 in
[Replace Performance Baseline](../references/replace-performance-baseline.md).
It locks the three DP capacities plus two-command and 13-command CtrlRAM run,
input-read, processor-session, process-invocation, and commit counts. Timing,
allocations, UI inspection, and measured Infrastructure staging reads remain
explicit follow-up evidence rather than inferred CI results. This is node A;
all counters and source-audited assumptions must be rebuilt as node B after the
final `0.9.9` rebase because base acceptance, short-input normalization,
postbuild catalog commands, and process/session ownership may change.

The provisional node C process slice is recorded at `315272b3` on the same
pre-final-rebase predecessor. Automatic DP Build now records one composition
and two input reads instead of two/four; CtrlRAM records one processor session
and `C` launches instead of two sessions and `2C`. Tests compare full bytes,
output SHA-256, mutation summaries, and argv against the retained two-run
sequence, and the NT51926 cascade TP-base full-output golden remains exact.
This is implementation evidence for the prototype shape, not the authoritative
B/C timing claim; it must be replayed after final `0.9.9` is rebased.

The first provisional UI scheduling slice captures all mutable Merge/Replace
inputs before yielding, publishes active state, explicitly yields the
dispatcher, and runs the unchanged Workbench/Application delegate on a
background worker with the same cancellation token. Blocking-fake coverage
locks progress-before-worker ordering and off-caller-thread execution; a
context-change smoke locks the captured IC/file bindings. This resolves the
pre-await execution stall only. Synchronous report parsing/projection remains
the independently measured next slice and no final B/C timing claim is made
before the final `0.9.9` rebase.

The report path projects run/manual-load JSON on a background worker with
cancellation and publishes bounded UI pages for every high-cardinality report
surface. Review-required change groups/rows sort first; legacy full-hex fields
render only a 64-byte preview; complete JSON remains the history/save/export
authority. A second slice scans output-difference JSON for summary/group facts
without creating detail row models, then memoizes detail by source index.
Collapsed groups materialize 0 rows, first expansion at most 24, and paging
only the requested next rows; global and group views share instances. The
1,000-difference/40-section synthetic case records 0 -> 24 -> 25 detail models
while loading more group headers stays at 25. Authoritative B/C
summary-ready/detail-ready timing, allocation, working set, and a virtualizing-
control comparison remain open after final rebase.

The first provisional ADR 0024 core slice keeps the lifecycle contract in
Application: seven typed phases are published through a per-run bounded
asynchronous feed, duplicate phase entries coalesce, and failed, cancelled, or
skipped work is not represented as completed. The feed isolates composition
and atomic output commit from host/UI callbacks. A standalone Presentation
projection now preserves the snapshot's applicable/completed sequence, ignores
stale run ids, localizes all phase and assistive labels, and disables only the
active animation when reduced motion is requested. Bootstrap feed consumption,
the live-region/XAML stepper, high-contrast styling, and platform reduced-motion
detection remain deliberately unwired until the final `0.9.9` UI rebase. Core
evidence covers success, multiple processor operations, input failure,
cancellation, final-validation rejection, and output-commit failure; UI model
evidence covers omitted phases, localization, run isolation, and static motion.
Authoritative click-to-step and dispatcher measurements remain node B/C work.

Reusing an earlier Preview output as the later Build artifact is rejected: it
creates stale-input and stale-policy authority. Skipping hashes or independent
diff validation, parallelizing ordered Combiner commands, or removing Domain's
defensive snapshot is also rejected. Optimizing only Presentation is
insufficient because the dominant CtrlRAM costs cross Application and
Infrastructure boundaries.

#### Acceptance, risk, and gates

- Automatic Build executes the engine once and opens one processor session;
  the 13-command case reduces process launches from 26 to 13.
- The separately reviewed Combiner adapter retains exactly `C` sequential
  launches. A non-merge two-command or 13-command session performs `C` metadata
  checks and one final full firmware read instead of five or 27 full reads.
  Merge-mode plans additionally record one selective tail read per merge
  command; tail bytes, artifact reads, and normalization writes remain visible.
- A Build click renders active/phase state before a deterministic blocking fake
  can occupy background work, and dispatcher heartbeat evidence shows the UI
  remains responsive through planning, execution, processing, and result
  projection.
- Large reports expose correct global summary/review-required counts with a
  bounded initial row/control count. Lazy pages and byte previews do not alter
  saved/exported JSON, hashes, ranges, classifications, or processor evidence.
- Report completion, history capture/save, startup restore, reopen, and
  relocalization do not perform full-report parsing, encoding, serialization,
  or filesystem writes on the UI dispatcher. Inactive history entries retain
  no live difference-row projection or UTF-8 range index.
- The Changes tab renders a bounded read-only Hex Diff viewport whose selected
  range, typed reason, expected/review verdict, evidence, navigator selection,
  and optional original row agree. Imported history enables full bytes only
  after attached artifacts match report size and SHA-256; missing bytes degrade
  explicitly without hiding the range list.
- One UI selection performs at most one full-file read for its inspection
  snapshot. Changing file identity or content invalidates the snapshot.
- Preview and Build show the current applicable typed lifecycle phase. Phase
  order, run-id isolation, failure/cancellation behavior, localization,
  accessibility, high contrast, and reduced motion are tested. No determinate
  byte percentage or remaining-time estimate is shown without a real contract.
- After the separately reviewed adapter phase, a 13-command automatic Build
  performs one processor session, 13 exact sequential launches, 13 length
  metadata checks, one final full firmware read, and one selective tail read
  for each actual `MERGE_MODE` command. The reconciled B count is recorded
  rather than assumed. Staged-artifact immutability reads, tail bytes, and
  normalization writes are tracked separately and are not hidden from
  evidence.
- Golden output bytes and SHA-256, operation/mutation traces, exact processor
  argv and order, difference classifications, warnings, output naming, and
  failed-run atomicity remain identical unless a separately approved contract
  change explicitly names a report-only semantic difference.
- Self-replacement that produces identical final bytes still emits no output-
  difference row. A `DeclaredReplacement` row proves an accepted changed range,
  not that a version edit occurred.
- Counters and byte assertions are deterministic CI gates. Timing results are
  recorded as benchmark evidence rather than flaky pass/fail thresholds.
- Node B/C includes end-to-end report generation and persistence, not only
  projection of pre-generated JSON. It also records byte-buffer allocations,
  retained history memory, GC counts, Hex Diff first-page readiness, and
  address-jump latency.
- Instrumentation and isolated UI inspection work are R1 unless they alter a
  public report or use-case contract. Automatic-Build orchestration, report
  semantics, and buffer-ownership changes are R2 and require architecture/
  contract review. External postbuild I/O convergence is R3 and requires exact
  CtrlRAM golden parity plus firmware-owner review.
- Any changed range, operation order, checksum/header behavior, processor
  authority, public classification token, or output byte is outside this
  optimization authorization and must stop for its normal R3 evidence and
  human gate.

Implementation proceeds as separate reviewable `v0.9.10` phases:

1. preserve node A and define the B/C comparison record;
2. after the final `0.9.9` rebase, capture node B with deterministic counters,
   golden output/report parity, process-window behavior, timing, and allocation;
3. replay the provisional Application-owned single-execution automatic Build
   slice on final `0.9.9` and compare it with B;
4. reduce Legacy Combiner staging I/O in a separate ADR 0025 R3 phase, starting
   from the NT51926 two-command full-output golden; use final-only full read for
   non-merge families and selective tail preservation for `MERGE_MODE`, and
   admit wider command plans only when their required owner evidence exists;
5. publish Build progress before background work and move heavy execution and
   result projection off the UI dispatcher, with heartbeat/cancellation tests;
6. after the `0.9.9` UI contracts freeze, implement one immutable asynchronous
   inspection snapshot per selected file identity/hash and compare UI file
   reads, projection work, UI-thread blocking, timing, and allocation with B;
7. remove dispatcher-bound report-history counting, save, restore,
   relocalization, and inactive-entry projection while preserving atomic local
   persistence and complete JSON;
8. measure and remediate report diff discovery, classification, hashing,
   report creation, serialization, parsing, and lazy bounded detail as separate
   stages; retain exact machine-readable evidence and backward compatibility;
9. implement the read-only Hex Diff comparison provider, dominant viewport,
   typed information panel, review-first range navigator, verified artifact
   fallback, and original-row toggle without reusing editable editor state;
10. add the ADR 0024 Application phase contract and accessible UI step-progress
   animation, then measure bounded progress events and UI-thread impact; and
11. remove only proved same-owner buffer copies, then separately consider
    bounded process-output capture and identical-state staging-tree scan
    removal if their measurements justify the change;
12. rerun node C, Polytail, focused architecture/UI/golden review, and
    `python scripts/verify.py --all`, recording every residual human or private
    golden gate before integration.

`v0.9.10` cannot integrate or release until its branch is reconciled with the
reviewed `v0.9.9` baseline and each included phase passes its own narrow tests,
Polytail, the canonical final verifier, required golden parity, and independent
review.

## Post-remediation decision gate

No `v0.9.11` or later milestone is committed by this roadmap. After reviewed
`v0.9.9` and the `v0.9.10` remediation both merge, the owner will select and
version the remaining route using measured B/C results and the final support
matrix.
The decision inventory remains visible without assigning premature versions:

- any residual process, buffer, I/O, report, history, Hex Diff, progress,
  inspection, startup, cancellation, accessibility, or working-set item that
  did not satisfy its `v0.9.10` B/C target and review gate;
- any compact/versioned report representation found necessary by fragmented
  change evidence but not accepted in `v0.9.10`; it must retain exact ranges,
  typed semantics, hashes, processor trace, complete export, and backward
  reading of `composition-report-v1`;
- any R3 postbuild I/O convergence beyond the NT51926 scoped case. The current
  13-command cases remain count/timing evidence until independent pre-base plus
  full expected-output golden evidence and firmware-owner approval exist;
- General Replace full-output parity. Current contract/synthetic coverage is
  not an owner golden and cannot promote a product or broaden performance
  parity claims;
- DP Reference FlashCode evolution for future AB FlashCode. An AB container
  requires an AB-specific profile and extractor; normal offsets, DP Replace
  reference acceptance, or filename patterns cannot be guessed into AB
  support;
- candidate-IC intake from proposed ADR 0023. It remains deterministic staging
  and human-reviewed evidence authoring only, with no automatic firmware fact
  inference or support promotion;
- later support requests such as NT51931. Stable `0.9.9` keeps it Not available
  because the official command crashes and the alternative drifts by 108
  bytes; future work requires reproducible tool behavior, direct golden, and
  owner review rather than a UI exception;
- broader direct golden coverage for aliases/families and CtrlRAM cases that
  currently provide inventory or expected-derived audit only. A new direct
  product golden may justify a later support decision but never retroactively
  changes the `0.9.9` support truth;
- remaining operability and product hardening: repeated-run/large-file soak,
  crash recovery, cancellation latency, stale temporary cleanup, accessibility
  audit, high contrast/reduced motion, localization review, clean-machine
  Windows portable smoke, package ceiling, dependency/license review, SBOM,
  provenance, hashes, signing policy, CI reliability, independent Codex/human
  review, and release notes; and
- the owner-selected path to the first signed-off `v1.0.0` sample, including
  which of the above items are mandatory for that sample and which remain
  explicitly unsupported rather than silently deferred.

Legacy/V2 retirement, support matrix, family/evidence status, and workflow
exposure are not part of this future inventory: they are explicit `v0.9.9`
responsibilities. The first signed-off stable sample remains `v1.0.0`, but its
intermediate version sequence is selected only at this decision gate.

## Scope fence

No milestone may add a per-IC executor, a second compiler, a second runtime
schema/loader hierarchy, UI firmware semantics, primary-FWConfig fallback, or
unchecked binary patch. Any proposed exception requires an ADR, precise R3
evidence, and owner approval before implementation.
