# v0.9.14 Roadmap and Release Gates

Status: release-candidate implementation; Release EXE visual approval and final release gates remain open.

## Release identity

- Version integration branch: `0.9.14`
- Stable predecessor tag: `v0.9.13`
- Peeled predecessor and `origin/main` SHA:
  `f9f8dbcd979ecdef43f432016787e57763819492`
- Predecessor tree: `09ce7cc0c6f80126d0bc36e644105b7b614aa4a9`
- Merge target after all gates: protected `main`

The version branch starts from the stable tag/main identity above, not from the
older `0.9.13` branch tip. Independently reviewable work uses
`feature/0.9.14/<topic>` branches and merges only into `0.9.14` until the final
version PR.

## Product outcomes and scope fence

`v0.9.14` has three primary outcomes:

1. re-admit the owner-approved NT51919/NT51929/NT51932 AB perfect-family pilot
   through typed production authority, exact byte evidence, and the shared
   composition engine;
2. add typed load diagnostics, the minimum AB authoring surface, IC detail
   disclosure, and narrowly scoped UI correctness fixes without attempting a
   cross-workflow redesign; and
3. make stable release promotion CI-owned while reducing duplicate GitHub
   Actions work and retaining a protected human promotion gate.

Cross-workflow Merge/Replace header, Evidence, and Memory coverage unification,
the shared Raw Editor/Changes Hex viewport, full Report redesign, global Button
pressed rollout, global icon/spacing migration, NT51950/NT51951 AB admission,
Saved Rules, and arbitrary scripts remain outside this release. They stay in
`v0.9.15` or a later owner-selected milestone.

The `v0.9.15` Report redesign includes a high-priority issue-triage surface.
Each issue must expose severity, one concise primary reason, affected
scope/output, and one explicit next action at first glance. Long raw messages,
ranges, command traces, and diagnostic payloads move behind an expandable
detail. Issues are grouped and sorted `blocking > warning > info` so the user
can identify the problem without first reading a paragraph or opening Raw.

## Milestone 1 — toolchain and CI foundation

Suggested branch: `feature/0.9.14/toolchain-ci-foundation`

Risk: R2 tooling and CI architecture; no firmware behavior.

Deliverables:

- provide one canonical repository entry point that locates or bootstraps the
  pinned .NET SDK and an approved PowerShell 7 runtime without requiring the
  caller to remember a shell-specific sequence;
- classify invocation, dependency, assertion, evidence, and environment errors
  once and provide actionable failure output;
- keep `scripts/verify.py` as the sole canonical verifier rather than adding a
  competing verifier;
- keep PR check names stable, cancel superseded runs, and run expensive jobs
  only when the PR is review-ready or explicitly requests the full gate; and
- stop packaging every ordinary push to `main`.

The Windows entry point is `./scripts/nfc.ps1`. When invoked from Windows
PowerShell it re-enters itself under an installed PowerShell 7 host, installs
the exact repository-pinned .NET SDK when needed, and delegates verification to
`scripts/verify.py`; it does not introduce a second verifier. Its `bootstrap`,
`structure`, `verify`, and `package-policy` tasks classify dependency,
invocation, environment, assertion, and evidence failures with one stable
prefix. The explicit `host-diagnostic` task reports only the re-entered
PowerShell host/version and is never a verification result. The verify task
installs Python verification dependencies only when its module probe shows they
are missing.

Exit gate: a clean checkout can invoke narrow tests, full verification, and a
release-candidate dry run through documented deterministic commands on Windows.

## Milestone 2 — typed input inspection and AB normalization

Suggested branch: `feature/0.9.14/ab-input-authority`

Risk: R2 diagnostics plus R3 firmware input authority.

The Application-owned inspection result exposes, per slot:

```text
requirement
lifecycle
severity
stable issue code
actual length
required endExclusive
expected outer length
accepted execution-snapshot span
compiled overlay source/target ranges
ignored trailing length
decoded metadata or Unknown
Build impact
next action
```

Presentation and CLI only project this typed state. They do not infer a family,
length, range, version offset, or processor rule from an IC label or filename.
Selecting a path means `selected`, not `valid`; Build repeats authoritative
validation and remains available after files are selected so a blocked report
can be produced.

For the pilot AB plan:

- DP_AB below `0x80000` is blocking because `[0,0x80000)` is required;
- TPA/TPB below `0x40000` are blocking because their declared source views read
  through `0x40000`;
- a longer DP_AB/TPA/TPB input is accepted with a warning, the execution
  snapshot exposes only the declared prefix/view, and the report records the
  actual hash/length plus ignored trailing byte count;
- no input padding is authorized and original files remain immutable.

Exit gate: one generic compiled input policy drives profile/compiler,
Application, CLI, Report, and UI diagnostics. Runtime admission occurs only
through Milestone 3; user-facing authoring remains hidden until Milestone 4.

The deterministic severity order is `blocking > warning > inspecting/stale >
valid > empty`. Equal-severity issues use stable issue-code/order rather than
async collection timing. The canonical collapsed state must show both selection
and health, for example `Common · 1 error · 2 selected / 4`.

The IC detail popover identifies the selected IC before reading facts. It does
not overlap or intercept the selector. Focus exposes the same content as hover,
`Esc` dismisses it, focus remains on the selector, and the popover stays inside
the viewport at 100%, 150%, and 200% Windows scale.

## Milestone 5 — targeted UI correctness and AB coverage

Suggested branch: `feature/0.9.14/ui-correctness`

Risk: R1 style/template work, or R2 if a public Bootstrap DTO changes.

Deliverables:

- filename hover details never intercept the filename reveal-and-focus click;
- while any modal is open, the modal and scrim stay above the composition
  action rail and the background actions receive no hover, focus, or click;
- remove the action rail's large shared border/background/shadow; each action
  remains an independently floating button;
- shorten `Show latest output BIN` to `View file` and keep its localized label,
  accessible name, and exact reveal behavior;
- View file and Build share collapsed size, expansion direction, timing,
  corner radius, shadow, focus ring, pressed feedback, disabled behavior,
  reduced motion, and high-contrast treatment while retaining secondary versus
  primary color hierarchy;
- Replace coverage distinguishes `available/planned`, `selected`, and actual
  report `changed`; zero selected CtrlRAM slots remain neutral, uncolored, and
  never say Changed;
- each Output layout normalizes the largest used `endExclusive` to 100% of the
  available bar width; the rendered segment proportions fill that width, and
  visible trailing whitespace is allowed only for a typed unallocated range;
- retained base keeps the approved grey fill with black diagonal hatch; and
- a blocked run may show a planned target range but must not imply that a
  partial or oversized mutation was committed.

For the pilot, input acceptance and output coverage remain distinct:

```text
Expected TPA/TPB outer length     0x40000 / 256 KiB
Accepted execution snapshot      [0x00000,0x40000)
TPA overlay source/target         [0x07000,0x40000) / 228 KiB
TPB overlay source/target         [0x07000,0x40000) ->
                                  [0x47000,0x80000) / 228 KiB
Ignored oversized input tail      [0x40000,actualEnd)
```

The ignored input tail never appears in the output-image address space. A
blocked TPA may render a dashed planned target with an explicit blocked marker;
it must not render as an existing `After` image.

Exit gate: empty, partially selected, and built Replace states have truthful
coverage semantics; action-rail collapsed/expanded/modal states match the
owner-approved Release EXE references; AB coverage matches the compiled plan.

## Milestone 6 — CI-only stable release promotion

Suggested branch: `feature/0.9.14/release-promotion`

Risk: R3 security/release architecture with independent release/security owner
review and a protected human authority gate.

Deliverables:

- feature PRs target `0.9.14`; the final `0.9.14 -> main` PR opens only after the
  version branch is frozen and complete release-note fragments are assembled;
- Draft/early PR updates run lightweight policy checks, while review-ready and
  final PRs run the required matrix;
- an exact-main-SHA promotion run verifies version/review/tree identity, runs
  `verify.py --all`, packages, smokes, and stages immutable candidate artifacts;
- the workflow pauses at the protected `release` environment for the owner's
  final tag confirmation;
- only the post-approval job receives `contents: write`, creates the immutable
  annotated tag, and publishes complete notes, the Windows ZIP, SBOM,
  provenance, and hashes;
- GitHub-generated source ZIP/tar.gz downloads are verified; and
- published assets are downloaded into a fresh directory, their digests are
  compared, and the package smoke runs again.

The candidate additionally binds the final merged PR, exact reviewed head tree,
current-head approval, required checks, workflow definition SHA/ref, run id,
closed asset manifest, and artifact-service digest. Post-tag recovery is limited
to rerunning the failed promotion job in that same workflow run; it may upload
only missing byte-identical assets and can never move a tag or clobber an asset.
Fresh tag creation requires the candidate to remain current protected `main`;
an exact-tag recovery may continue after `main` advances only while the source
remains its ancestor. Zero- and one-asset partial Releases retain JSON-array
semantics and pass through the same closed-set recovery policy.

No PR code receives release secrets or a write token. The workflow never uses
`pull_request_target`, never moves an existing stable tag, and never clobbers an
existing stable asset.

Exit gate: zero manual tags, zero automatic package runs on ordinary `main`
pushes, one final full PR gate, one exact-SHA candidate package, one protected
promotion, complete notes, and published-asset verification.

## Fixed acceptance denominator

Progress is reported only from these eight completed milestones. A milestone is
complete only when its exit gate passes on a reviewed clean SHA; elapsed time,
commit count, and partially implemented controls do not count.

AB input boundary evidence includes, for each DP_AB, TPA, and TPB slot, one byte
short, exact, and one byte oversized cases. It also includes a large ignored
tail, missing/unreadable input, `Unknown` version, mixed TPA/TPB versions, stale
async inspection, source immutability, and no-output-on-failure.

The oversized TPA/TPB evidence appends decoy terminal-relative version bytes
near the actual file end. The decoded version and output must remain identical
to the exact-prefix case, while the full-file hash/length and ignored byte count
remain distinct report evidence.

Canonical Release EXE screenshots include:

- Home with AB Code available;
- Merge AB empty, exact/ready, oversize-warning detail, and short/blocking detail;
- IC selector hover and keyboard-focus details;
- Replace CtrlRAM coverage with zero selected, one selected, and completed run;
- action rail collapsed, `View file` expanded, Build expanded, and modal-open;
- filename hover beside an operable reveal-and-focus target;
- a collapsed slot group with deterministic aggregate severity.

Every screenshot records version, Windows scale, window size, theme, language,
and state. Visual comparison supplements, but never replaces, behavior,
accessibility, range, and golden tests.
