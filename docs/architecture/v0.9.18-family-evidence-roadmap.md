# v0.9.18 Family and Evidence Model Unification Roadmap

Status: owner-selected future milestone, recorded 2026-07-23.

`0.9.18` starts only from the official reviewed `v0.9.17` release. Its purpose
is to turn the currently scattered Perfect-family and LDC-family evidence rules
into one reviewable model before any IC family/rule authoring UI is attempted.
It is not an authorization to change a profile, map, processor, support stage,
or golden fixture.

## Outcome

Every support-matrix row, report, review handoff, and later UI proposal must be
able to answer all of these without an IC-specific exception hidden in prose:

1. What is the named family relationship?
2. Which workflow class and topology does it cover?
3. Is the evidence direct, Perfect-family scoped, or LDC-TP-only scoped?
4. Which DP/TP/header/processor facts remain deliberately uncovered?

Family membership remains evidence metadata. Requested IC, compiled profile,
declared map, and topology continue to select execution; a golden, PID, version,
filename, observed chip count, or family label never selects a runtime route.

## Normalized relationship vocabulary

| Relation | Initial members | May share only when the complete declared contract matches | Explicitly cannot share |
| --- | --- | --- | --- |
| `perfect-family` | NT51919/NT51929/NT51932 where the owner-approved relationship applies | Like-for-like workflow, address map, ordered operations, input/output shape, and topology. | Any workflow/topology whose declared facts differ. |
| `ldc-tp-only` | NT51927/NT51928 | TP-owned CtrlRAM evidence only: TP regions, topology, input/output contract, and postbuild authority must each match. | DP Replace, Standard Merge, AB Code, any DP layout/range/header/command fact, and any DP-writing workflow. |
| `ldc-tp-only` | NT51950/NT51951 | The same TP-owned CtrlRAM conditions as above, reviewed independently for this pair. | DP Replace, Standard Merge, AB Code, any DP layout/range/header/command fact, and any DP-writing workflow. |

`ldc-tp-only` is not a transitive four-IC group: NT51927/NT51928 evidence does
not automatically cover NT51950/NT51951, nor the reverse. The presence or
absence of local dimming is a DP behavior boundary even when TP layout is
shared.

## Milestone plan

| Work slice | Required result | Explicit boundary |
| --- | --- | --- |
| Family/evidence ADR and typed contract | Define the relationship vocabulary, covered workflow/topology scope, source provenance, approval state, and deny scope. | It may model evidence authority only; it cannot become a new runtime IC selector or profile mutation path. |
| Existing-catalog inventory | Reconcile every existing Perfect/LDC statement in the support matrix, profile evidence, golden manifests, and review handoff so one vocabulary is used. | No new golden claim and no reinterpretation of a fact-scoped alias as a direct golden. |
| Report/review projection | Present `direct`, `perfect-family`, or `ldc-tp-only` evidence basis together with excluded DP facts and residual gates. | A presentation cannot hide missing golden, firmware-owner review, unsupported topology, or an R3 safety failure. |
| Rule-authoring design gate | Produce the owner/firmware/architecture workshop record for a later authoring UI: permissions, proposal/version lifecycle, diff/approval/rollback, audit trail, and reviewer visibility. | No editable family/rule UI ships in `0.9.18`; a later owner-selected milestone may implement only the approved proposal model. |

## Exit evidence and gates

- An architecture and firmware-owner-reviewed ADR records the vocabulary and
  every initial relationship above.
- Contract tests prove a `perfect-family` relation cannot cover a mismatched
  map/topology, and an `ldc-tp-only` relation cannot cover a DP workflow.
- The support matrix, report contract, and review-handoff schema use the same
  evidence-basis terms and declare their excluded facts.
- No profile promotion, AB route exposure, golden fixture change, or external
  Combiner authority is claimed by this milestone. Those are separate R3 work
  with direct evidence and firmware-owner approval.

The IC family/rule authoring UI remains a large follow-on design track. It is
blocked on this model rather than being allowed to invent it while editing a
screen.
