# 0.7.0 Refactor and Evidence Plan

Status: active planning note for 0.7.0 development.
Last updated: 2026-07-05.

This document tracks the remaining 0.7.0 cleanup and evidence work after Standard Merge, DP Replace workbench paths, and CtrlRAM postbuild execution became traceable. It is not a release support claim.

## Owner-provided evidence checklist

For each IC/mode selected for release, provide these artifacts or hashes:

| Evidence | Required details |
| --- | --- |
| Flash-map workbook or export | IC, revision/date, sheet/section name, sanitized source label, SHA-256 hash, and owner approval. Do not record confidential source paths. |
| Flash header / mmap reference | Header-copy source/target/length, FWConfig start, CtrlRAM ranges, customer-info/protected ranges, overlay/map requirements, SHA-256 hash. |
| Postbuild BAT/CMD/log | Exact command order, mode arguments, IC-number branches, map.txt requirement, and expected tool version. |
| Combiner identity | Tool binding id, executable version, SHA-256, source-code category if reviewed, and whether it is 1.x or 2.0-era behavior. |
| Base firmware | IC, IC-number branch, Common FW version, FW version/bar, PID, size, SHA-256, and confidentiality/commit approval. |
| Replacement BINs | Slot id/region, intended source offset, size, SHA-256, and whether the file is exact, oversized-to-truncate, or padded by policy. |
| Expected output | Final postbuild-clean output size/hash and allowed changed ranges. This is required before promotion from "executes" to "OK". |
| Review decision | Firmware-owner sign-off, unsupported branches, and whether alias behavior is accepted for release. |

For NT51926/NT51930 specifically, include FWConfig Common FW version in every CtrlRAM Replace case:

- NT51926 Common FW `1.4.1` selects `PostbuildSetup_51926_1.4.1.bat`; Common FW `2.0.0` selects `PostbuildSetup_51926_2.0.0.bat`.
- NT51930 Common FW `1.x.x` selects archived `PostbuildSetup_51930_1.4.0.bat`; Common FW `2.0.0` selects `PostbuildSetup_51930_2.0.0.bat`.

## Universal special-value BIN validation

A universal validation BIN can reduce owner effort before real golden outputs exist. It does not replace golden parity, but it catches mapping mistakes quickly.

Recommended pattern:

1. Use a base firmware whose target regions are not already the same repeated byte.
2. Generate one replacement BIN per slot with a deterministic sentinel pattern:
   - `normal`: seed `0xA1`
   - `mp`: seed `0xB2`
   - `diff/dlm`: seed `0xC3`
   - `vn`: seed `0xD4`
   - `nf`: seed `0xE5`
3. Within each BIN, encode offset as `byte = (seed + offset) & 0xFF`; this proves both start address and length.
4. Run Replace + required postbuild.
5. Verify that every selected declared region contains the matching sentinel/address pattern, except bytes explicitly owned by postbuild CRC/header/header-copy writes.
6. Verify that unselected regions match base, except declared postbuild writes.
7. For truncation policy, add one oversized file per CtrlRAM slot and assert the report contains the truncation warning and the output uses only the declared region length.

This universal case is useful for:

- confirming slot-to-address wiring;
- finding swapped `Normal/MP/VN/NF/DiffDLM` inputs;
- confirming `single/cascade/2/3` visibility;
- validating General Replace explicit mapping bounds.

It cannot prove:

- exact legacy combiner parity;
- customer real-output CRC correctness;
- overlay/map.txt behavior;
- NT51931 production mode selection.

## XML/core hard-coding audit

Current assessment for 0.7.0:

| Area | Finding | Refactor need |
| --- | --- | --- |
| `MainWindow.axaml` | Large file with repeated slot/report/coverage visual structures and hard-coded colors/sizing. | Extract reusable styles/templates and keep typography/buttons/dropdowns consistent. This is UI quality debt, not firmware behavior risk. |
| ViewModels | Mode labels and UI strings are still constants in ViewModel partials. | Acceptable short term, but should move toward a localization/resource model and catalog-driven mode descriptors. |
| Workbench service | Still mixes workbench planning, report conversion, DP length policy, and Replace execution in large partials. | Split by command handlers/use-case adapters so Bootstrap remains an adapter, not a second firmware semantics layer. |
| `LegacyCombinerPostbuildCatalog` | Static firmware facts are intentionally hard-coded evidence, but versioned categories now make IC-only lookup unsafe. | Keep facts in catalog, add category metadata and tests; do not move ranges into UI. |
| `TpFlashMapCatalog` | Current rows are IC-level, not postbuild-category-level. | Needs versioned rows for NT51926/NT51930 before those paths can be promoted. |
| CLI | Thin enough for current commands, but CtrlRAM CLI still does not expose the same multi-slot workbench flow. | Add a UI-controllable CLI/workbench process surface in 0.7 if automation/report screenshots remain a priority. |

Bad-sense items to avoid in 0.7.0:

- more IC-specific `if NTxxxxx` logic in UI/XAML;
- command strings assembled outside `LegacyCombinerPostbuildCommandLineBuilder`;
- using max DP length labels when actual DP/base length is variable;
- treating FWConfig read failure as "use latest postbuild";
- adding expected golden hashes that only match an unexplained implementation change.
