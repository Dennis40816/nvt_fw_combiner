## Outcome and release boundary

The near-term objective is a maintainable repository:

- deep modules with small, stable interfaces;
- explicit ownership and planned migration seams;
- higher behavioral, contract, and integration coverage;
- one authoritative definition for each control, class, function, formatter,
  firmware fact, and state transition;
- no parallel compatibility owner after migration completes; and
- an architecture that can support a future IC-authoring UI without making
  that late-stage feature the current priority.

`0.10.0` performs architecture inventory and design only. It does not perform
the production restructuring described here. The planned sequence remains:

| Version | Maintainability phase | Required outcome |
| --- | --- | --- |
| `0.10.0` | M0/M1 baseline and design | Record ownership, evidence, intended seams, and migration order without changing production behavior. |
| First subsequent `0.10.x` release | First bounded implementation slices | Begin with only the characterized, dependency-ready foundations selected after the ticket dependency graph is approved; it is not the container for the complete refactor. |
| Later `0.10.x` releases | Ordered migration and cleanup | Distribute M2/M3/M4 across reviewable releases, move one vertical slice at a time, prove parity, and remove a superseded owner only in the release where all of its callers have moved. Exact version allocation is intentionally decided from the approved ticket graph. |

No production Support Matrix, release-recovery, or maintainability slice is
allocated to `0.10.0` by this record. Those implementation outcomes remain
separate, dependency-gated tickets for later `0.10.x` allocation.

## Confirmed workshop decision ledger

This ledger is the quick completeness check; the detailed sections below own
the reasoning, consequences, migration, and evidence requirements.

| Area | Confirmed direction |
| --- | --- |
| Near-term objective | Make the repository maintainable through deep modules, one owner per concept, higher behavioral coverage, shared controls, and deletion of superseded paths. A future IC-authoring UI is enabled by the model but is not the near-term deliverable. |
| IC resolution | IC is the query root, topology is a first-class selection axis, and explicit capability resolution produces one resolved capability and then one `CompiledComposition`. Product consumers receive metadata structures and TP Header instances only through that IC-rooted result; no public `TpHeaderResolver` or catalog may bypass it. Inspected metadata never selects IC/family/topology implicitly. |
| Resolution snapshot | Application owns `ResolvedCapability` as one immutable, coherently published read-only query/session snapshot composed from strongly typed child models rather than one flat god DTO. It may reference the existing Domain `ResolvedFirmwareImageMap` and `CompiledComposition`, but neither replaces nor duplicates them: the former remains physical resolution authority and the latter remains sole execution authority. Each consumer receives only its required child model; all children share one `ResolutionToken` and cannot be mixed across resolutions. `CapabilitySelection` is limited to selected definition references and typed topology/count/variant values; trusted provenance and `CapabilityFingerprint` remain explicit root facts. Trusted-bundle JSON and generic dictionaries never cross the resolution seam. A child may reference the one resolved canonical fact graph but must not restate another child's firmware ranges, artifact parts, metadata fields, behavior bindings, processor declarations, or integrity routes. Metadata and composition plans contain references plus resolved state; only per-run user/inspection values absent from canonical definitions may be materialized. |
| Capability authority | Application owns `CanonicalCapabilityCatalog` as the one runtime join/query authority for every exact IC/workflow/IC Count/map-variant route. Profiles normalizes trusted definitions and resolves/compiles; Infrastructure loads hash-pinned bundle, authoring, evidence, and publication sources through ports; Bootstrap wires only. `ResolvedCapability` is the selection-scoped projection and `SupportMatrix` the enumerated reporting/CI projection. Neither stores duplicate firmware facts or support lists. |
| Route identity and approval revisions | Stable `RouteId` contains IC, workflow, IC Count variant, and map variant only. Firmware-semantic facts—including integrity/processor behavior—produce `CapabilityFingerprint`. Authoring, evidence, and publication decisions pin both values; a changed fingerprint makes each old decision stale until reviewed supersession, rather than creating another logical row or inheriting approval. |
| Authoring policy | One versioned exact-route policy supplies the same `Available`/`Unavailable` result to UI and CLI. Missing or stale policy is fail-closed, never implicit `Unavailable`. Ordinary authoring selectors show only `Available`; Support Matrix shows both with provenance. Authoring policy is independent from evidence and publication. |
| Publication policy | A versioned, owner-approved policy is the sole source of `Supported`, `Candidate`, `Internal`, or `TestOnly`. Missing policy is a materialization error. #195 completed the migration by assigning an explicit conservative `Internal` baseline where no support promotion existed and deleting the legacy `Unclassified` value. Publication never infers authoring or byte execution. |
| Evidence classification | `EvidenceStatus` is separate from publication policy and resolves only from exact canonical declarations, in fixed precedence: `DirectGolden` > `ApprovedAlias` > `SyntheticOracle` > `ContractOnly` > `Missing`. Direct-golden, synthetic-oracle, and contract declarations must name the requested route identity/fingerprint exactly. An alias must name source/target identities, expected fingerprints, and a fact scope. A valid `Missing` result does not block Build; `Supported + Missing` is a critical certification inconsistency that blocks support promotion and release. |
| Capability readiness | There is no mutable global `IsReady`. Shared authoring availability, compiler-proved execution admission, input readiness, and refreshable runtime dependency readiness derive Build. Evidence and publication remain certification/release dimensions. ADR 0048 keeps per-slot prerequisite readiness (`NotApplicable`/`PendingInput`/`Blocked`/`Ready`) independent from selected-artifact health (transient `Checking`, then `Verified`/`Warning`/`Error`). `PendingInput` names the prerequisite, supplies the typed next action, and disables an independent dependent-slot transition through `CanSelect = false`; an atomic headless request containing both inputs remains order-independent. UI and CLI consume the same Application result. Before a run, disabled Build shows an exclamation with the highest-priority typed blocker; this hint is not a report. |
| Artifact composition | DP is a logical artifact containing required Initial Code plus an LDC part only when the resolved IC/map declares it. TP is a separate logical artifact. One DP card may render Initial Code/LDC child inputs. NT51927 and NT51928 share exact Initial Code/TP facts through typed `SharedFactRelationship` references rather than a perfect family. NT51928 Standard Merge and DP Replace each remain one capability with declared `0x40000` no-LDC and `0x80000` LDC map variants. For Standard Merge, absence selects the `0x40000` candidate; supplied LDC selects the `0x80000` candidate and must pass structural validation without fallback. DP Replace resolves from accepted Reference length: before Reference inspection both replacement members are `PendingInput` and not independently selectable; afterward Initial Code/LDC are individually optional and one group requires `1..2` applicable selections. |
| Source projection and FlashCode admission | One checked source view maps to one checked target view. Initial Code, DP, TP, LDC, and TPA are normally address-aligned; TPB uses the same TP-native window plus a resolved bank delta; only compact CtrlRAM currently uses payload byte `0` as the normal origin for a nonzero built-in target. Section slots use source-view coverage and may read a compatible same-IC FlashCode. Replace Reference and complete DP AB remain exact declared containers. FlashCode means a resolved complete DP/Initial-Code + TP container, with LDC only in declared variants; NVT marker, ASCII IC hint, CMI, PID, version, length, and plausibility checks are composable signals rather than one signature, and inconclusive classification is `Unknown`. |
| Metadata | An artifact or part declares zero or more metadata structures exactly once. One common BIN inspector and one formatter execute only the structures declared by the resolved IC/map/topology/slot. `ResolvedMetadataPlan` contains references plus resolved applicability/readiness only; it never restates structure offsets, fields, ranges, or formatter definitions. |
| TP Flash Header | TP Flash Header is `structureKind = tp-flash-header` inside the common trusted artifact-metadata model, not a parallel TPHeader schema or catalog. It is resolved by IC/map/topology/artifact instance. Named spans, fields, repeated field series, and semantic roles are defined once. A repeated CRC series retains every physically defined field, while the resolved topology marks each field `Active`, `Unused`, or `Unknown`; existence never implies write authority. `TP BIN offset`, `Flash image offset`, `Header stored address`, and `TPB placement delta` are distinct typed values. Inspection, formatting, relocation, header copy, integrity/processor authority, memory projection, and report diff all consume the same resolved definition rather than repeating raw offsets. |
| Firmware coordinate vocabulary | The accepted coordinate/address terms receive one canonical explanatory architecture document during `to-spec`, including definitions, equations, NT51950/NT51951 examples, code/schema names, and links from normative contracts. UI help may reuse those definitions; parallel glossaries are forbidden. |
| DPCMI | There is one DPCMI at DP CMD1/Page 0/registers `[0x16, 0x19)`. It belongs to Initial Code and is the target-model source of DP Version and Jira. Absolute Flash offsets are results of Initial Code address mapping, not separate DPCMI definitions. |
| Legacy DP version | The legacy contiguous DP-version reader leaves runtime/UI authority, remains only for migration parity, and is deleted when that migration closes. |
| Family relationships | `PerfectFamilyRelationship` remains the strong complete-equivalence invariant. Every partial relationship compiles through one typed `SharedFactRelationship` containing a readable role plus exact canonical fact references; adding TP Flash Header or DiffDLM sharing does not add another runtime relationship class. NT51919/NT51929/NT51932 consume one complete modeled firmware definition while keeping member evidence/publication separate. NT51917/NT51927 form another perfect family; NT51928 remains outside it and explicitly references only approved Initial Code/TP facts while retaining LDC and its complete DP/container map. NT51950/NT51951 reference only their approved shared TP/DiffDLM facts and do not inherit each other's Initial Code/LDC layout. |
| Retired capability boundary | ADR 0042 removes NT51920, NT51925, NT51930, and NT51931 from the `0.10.x` production set. Their historical locators/evidence may remain non-production, but no selector, canonical route, profile/processor, partial relationship, or Support Matrix row survives. The target runtime never falls back to legacy DP-version bytes to re-admit them. |
| Metadata prerequisites | A missing prerequisite remains typed. NT51950 may retain its selected DP while its topology-dependent Initial Code address map waits for TP FWConfig `ChipNumber`; UI displays `TP input pending`. |
| AB Code | AB is a separately resolved layout capability. NT51929 family uses one symmetric `0x40000` bank definition instantiated as A/B with instance-relative coordinates. NT51950/NT51951 use topology-resolved opaque whole-image/bank seed plus only the required CMD1 Page 0 and TP paste mappings. A paste mapping references a named TP artifact section and declares only its topology-specific destination; internal Initial Code/LDC ordering is not modeled when execution does not need it. |
| AB input semantics | `DP AB` is one owner-supplied Display input that already combines DP A and DP B. `TPA` is TP Normal Code; `TPB` is TP Backup Code. Their currently known content-section shape is shared, while each role/topology may have a different TP bank start. Composition seeds from the combined DP AB input, then pastes TPA/TPB into their corresponding A/B destinations. |
| AB TP relocation | Each evidenced TP Header layout declares a named `tp-bank-relative-start-addresses` field group containing only stored BIN-start addresses that move with the TP bank, such as the applicable ILM/DLM/DLM DIFF fields. AB capability bindings reference this group and assign every selected field to exactly one execution owner/stage rather than repeating offsets. One resolved `TPB placement delta` (`B TP placement start - A TP placement start`) drives both TPB placement and those stored-address adjustments. Owner-confirmed fixed delta is `+0x40000` for NT51929-family and every currently function-open NT51950 AB topology, and `+0x80000` for NT51951. |
| AB TPA handling | The accepted TPA artifact remains immutable and its declared TP section is pasted byte-for-byte. TPA receives neither relocation nor POSTBUILD. Any future exception is a new evidence-backed profile capability, never an implicit extension of TPB behavior. |
| AB POSTBUILD applicability and authority | Among current AB profiles, only NT51950/NT51951 declare POSTBUILD; NT51919/NT51929/NT51932 perform TPB relocation without CRC/POSTBUILD. POSTBUILD is semantically TP-only: for NT51950-series AB it may receive engine-owned staged A/B bank containers because the approved legacy command requires that transport shape, but DP regions remain outside processor mutation authority and must be preserved byte-for-byte. Host-accepted effects are limited to the declared TPB header ILM, DLM, and CRC fields; the original DP AB input remains immutable. Container/read scope never grants DP semantic or write authority. |
| UI state | Application owns the host-independent `AuthoringSessionState` model and transition policy without a process-global mutable store. Desktop Presentation owns exactly one metadata-only in-memory instance for each of Standard Merge, AB Merge, General Merge, DP Replace, CtrlRAM Replace, and General Replace plus UI-only navigation/disclosure state; CLI creates an ephemeral instance over the same contract. IC/IC Count changes revise the same mode instance rather than creating an unbounded cache. Navigation restores compatible user inputs, while derived state is invalidated and stale asynchronous results cannot publish across revisions, slots, files, or resolutions. Authoring sessions and inspection caches never retain full BIN payloads. |
| Shared authoring capabilities | Repeated slots use one session-owned typed `AuthoringSlotState`, BIN inspector, formatter, validation model, and visual control. The immutable resolved artifact plan is separate from the mutable selected-file lifecycle. Binary padding/truncation policy and UI use one shared typed normalization capability rather than workflow-specific implementations. |
| General mapping authoring | General Merge and General Replace share one session-owned `AuthoringMappingState`, invariant range codec, `AddressRangeEditor`, typed draft, output occupancy ledger, and Application readiness path. File rows expose Source Slice or From File Start over the same Start + Length operation; Use full file length only materializes an inspected value. Each accepted BIN is pinned by byte length plus SHA-256 `FileStamp`; changed content preserves editable rows but blocks until explicit Reload/Rebind and never silently changes a materialized range. Every user-writer overlap is an order-independent blocker; profile-owned POSTBUILD remains separate processor authority. Effective mapping/file limits intersect Application ceilings, Trusted Parent contracts, and Saved Rule narrowing. General Merge owns exact capacity and arbitrary blank byte (default `00`); Replace clones Reference. UI, CLI, and Saved Rule converge before validation/compilation, while Domain receives only half-open `ByteRange`. Legacy inclusive-end syntax survives only in a one-way importer until caller/parity/deletion gates close. |
| Saved Rule ownership and lifecycle | A Saved Rule references one exact separately installed Trusted Parent and may only narrow its authority; it never embeds or imports trust. General Merge rules close over exact output capacity, blank fill, and mappings. General Replace rules clone Reference and inherit protected ranges, conditional POSTBUILD, tool bindings, stage order, and allowed writes from the Parent. A local user-owned/imported JSON may be saved in place, but any semantic edit changes its canonical hash, returns it to Draft, invalidates approval/evidence/promotion, and requires a new version before republication. An installed Trusted Catalog snapshot is immutable and read-only; Edit creates a separate working copy. Path and display name are not identity, and reports retain the exact rule id/version/hash and Parent identity. |
| General Replace diagnostic Preview | After one exact canonical General Replace route compiles, a missing required Parent POSTBUILD stage or runtime tool blocks Build. An explicit Preview action may then emit a labelled plan-only diagnostic report showing accepted/compiled mappings, projected Kept/Changed coverage, the compiled required stage, and the exact blocker. It executes no mapping or processor, emits no BIN, and claims no final Header/CRC/hash validity. A target with no exact canonical route fails route admission before the runtime probe and produces no diagnostic report. A disabled-action readiness hint is not itself a report, and missing Parent authority remains distinct from a missing runtime dependency. |
| Output naming | Output names are a compiled capability, not Bootstrap/Presentation string helpers. A canonical `OutputNamingRule` compiles to the sole `CompiledOutputNamingRequirement`; one resolution over the accepted inspection snapshot supplies metadata tokens and report provenance without rereading input files. Normal output follows `{IC}_{OutputType}_{VersionInfo}_{Date}.bin` (`Date`, not `Data`), with output-type-specific version formatting and explicit missing-token policy. Output folder, explicit override, protected-path checking, and atomic commit remain separate host/infrastructure concerns. |
| Slot presentation | An empty dependency-ready slot presents its requirement and keeps selection enabled; a dependency-pending slot shows a yellow `Waiting for <artifact>` badge, such as `Waiting for DP BIN` or `Waiting for Reference FlashCode`, and disables Browse/drop only from Application `CanSelect = false`. After selection, the requirement indicator yields to transient `Checking`, then explicit `Verified`, `Warning`, or `Error`. `Verified` uses a green check plus green text badge; health color remains on the badge while the selected card uses a separate low-intensity blue surface and strong blue border. Hover and keyboard focus expose the localized reason/next action, while screen readers receive the same accessible description and live state. File identity and DP/TP/LDC/AB metadata use one aligned shared anatomy and typed fact states. The default card remains compact; selected-file metadata is progressively disclosed inline by activating the summary surface, using a quiet details/info affordance rather than a large accordion arrow. Later workflow pages adopt this shared slot-selection design rather than reproducing it. The accepted unloaded-file design is the prototype's quiet single-row variant, augmented during active drag-over by its restrained inset drop-surface treatment without changing the card's dimensions. |
| Report issue presentation | Every issue retains stable code and technical evidence but leads with one localized operator-facing summary, impact, and next action derived from typed arguments. CtrlRAM truncation is a warning summarized as a too-long file whose trailing bytes were ignored, not an undifferentiated technical-code error. |
| Message Center | One compact shell entry presents separate Run Reports and System Information sections. Run Reports remain immutable persisted run evidence; system status is refreshable, re-probed at startup, and retains only bounded in-memory session transitions. Active system issues drive badges/global blockers. Explicit privacy-filtered diagnostic export never becomes Report History. |
| Shared visual controls | Equivalent actions use shared semantic button roles, density/shape tokens, and complete Normal/Hover/Pressed/FocusVisible/Disabled states. Information surfaces share one responsive card/fact-grid anatomy without forcing unrelated firmware semantics into a god card model: stacked left-aligned label/value cells auto-flow from one to at most three columns, compact views expose at most four primary facts, and additional facts use quiet inline disclosure. Typed Unknown, PendingInput, NotApplicable, Warning, and Error presentation replaces ambiguous gray placeholders. NT51928 dependent Initial Code/LDC slots remain visible but not independently selectable before Reference inspection; `0x40000` then enables required Initial Code and displays `Reference length does not include LDC`, while `0x80000` enables the declared optional group members. |

Normal, NF, MP, VN, Vector, and derived DIFF/DLM use one shared Presentation palette; master/slave/side use markers, while `Kept`/`WillReplace` use the common disposition effects. The labeled region list below the bar is the CtrlRAM legend; no separate repeated legend consumes the narrow right panel. Multi-IC layouts group rows by IC/endpoint, expanding affected or problematic groups while permitting all-Kept groups to remain summarized. DiffDLM remains one primary segment rather than splitting Diff CtrlRAM and Diff NF into competing layout bars. CRC, Header, and Header Copy remain technical trace/safety facts and receive no Memory Layout color, marker, rail, or legend entry unless a failure becomes a report issue. |

Known input size remains visible, but an unresolved placement is represented by a non-proportional pending/blocked item with its prerequisite and next action, never a guessed gray range. One typed `MemoryContentRole` selects the primary fill from the accepted DP/TP/TPB/LDC/General/Reserved or CtrlRAM-subtype palette; workflow disposition, A/B or endpoint identity, diagnostics, observed change, selection, and focus use separate patterns, boundaries, markers, icons, and text. A `PreserveActiveDiffNf` DiffDLM segment exposes a compact hover/focus summary and quiet side-detail affordance for the kept active NF ranges; `FullArtifactReplace` says `Entire DiffDLM` and has no kept-range panel. Semantic color tokens are global and Presentation-owned; profiles and Application results never carry HEX colors or pixel widths. The current workflow-page composition is preserved: authoring/input remains in the left column and Memory Layout remains in the fixed right-hand panel; shared card/fact-grid work changes only internal anatomy and responsive wrapping. |

Both read-only hosts project the same snapshot without inheriting an editor ViewModel or duplicating viewport mechanics. The current Hex Editor appearance, custom-drawn rendering approach, interaction model, and complete editing feature set are an accepted baseline, not a redesign target; extraction may ship only with measured equal-or-better performance and visual/behavioral parity. |
| Verification orchestration | `scripts/verify.py` remains the only canonical verifier. Full verification schedules bounded structure/policy, repository-scripts-plus-Python, and .NET lanes concurrently with isolated deterministic logs and one aggregated verdict; `--jobs 1` preserves a deterministic low-memory/diagnostic fallback. Each top-level lane has a 600-second default wall-clock deadline (explicitly configurable only from 60 to 900 seconds), and each command receives the remaining lane budget; a timed-out command terminates its platform process tree/session before the lane reports failure. Dependencies inside the .NET lane remain sequential until measurement proves a safe deeper seam. CI selects each component explicitly so repository-script tests have one owner rather than running in both Python and .NET jobs. |
| Behavior disposition | Characterization does not automatically create a compatibility contract. Every observed behavior is classified as `RequiredInvariant`, `KnownDefect`, `EvidenceRequired`, or `ApprovedChange`. Only the first is a pure parity blocker. Known defects receive tests for the corrected behavior; uncertain firmware semantics remain fail-closed pending owner evidence; approved changes record and test the deliberate delta. |
| Refactor release train | The maintainability work is distributed across ordered `0.10.x` releases. The first subsequent release contains only an owner-approved dependency-ready frontier; exact vertical-slice and version allocation is a downstream `to-tickets` planning output, not a remaining architecture question. |
| Trusted definitions | IC, artifact, topology, metadata, relationship, workflow, and integrity facts converge into versioned, hash-closed trusted bundles admitted by a separate package trust index. Existing-vocabulary IC onboarding becomes data-only; bundles cannot contain code/scripts/plugins. Compiler and host code branch only on closed semantic kinds, never IC/family/workflow identity. A genuinely new behavior requires one reusable reviewed schema/Domain/compiler/fingerprint primitive, not an IC workaround. A future authoring UI emits only untrusted candidates pending independent review and atomic trust-index promotion. Runtime loads at startup and refreshes only through explicit Application `Reload Catalog`, never file watching. |
| Fingerprint ownership | Current definitions and compiled artifacts repeat portions of identity serialization. | Trust admission first verifies the pinned exact raw-document hash. From the canonical definition upward, one versioned language-neutral chain flows through capability fingerprint, compiled-plan fingerprint, and run/Preview identity. Every layer adds only new state and references the prior hash. One writer/encoding owner excludes reflection, dictionary order, C# names, and storage paths; semantic format changes explicitly stale and repin policy. |
| Validation ownership | Schema, normalizer, Domain, compiler, Application, and host adapters can repeat related checks and diagnostics. | Each invariant has one runtime owner: Contracts shape, Domain firmware semantics, compiler selection/lowering, Application session/readiness, or processor-host actual mutation/tool checks. Local engine/host safety checks remain mandatory without becoming alternate firmware-fact or diagnostic owners. |

Trusted processor-plan data owns IC/topology/command differences; Infrastructure owns manifest/tool lifecycle and actual mutation audit without firmware-identity branches. Existing-protocol IC onboarding changes no C#. |

Admit only catalog snapshot, artifact inspection, Hex viewport/page, and runtime-dependency caches with full identity keys and explicit lifetime/invalidation. Authoring stores identities/revisions, not BIN/cache ownership; UI/workflows have no parallel cache. |
| Single evaluation | UI, naming, layout, report, and execution paths can independently repeat reads, inspection, resolution, compilation, or processor work. | Within one accepted operation/revision, parse/inspect/resolve/compile/execute each applicable step once and share immutable results. Projections never rerun semantic work. Gate deterministic invocation counts and bounded allocation; timing ratchets require stable evidence. |
| Canonical tracer | The first migration is exactly NT51929 Standard Merge through IC-neutral Application query/command contracts. Its output is `0x40000`: DP `[0x0000,0x6000)`, explicit gap `[0x6000,0x7000)`, TP `[0x7000,0x40000)`, operations `copy-tp` and `copy-dp`, and no processor. `0x80000` and CtrlRAM POSTBUILD remain separate AB/Replace route facts. |

## Architecture audit method and opportunity register

The maintainability review does not stop when an owner identifies one
duplication. Each core concept is traced proactively through:

```text
canonical authority
    -> resolution/compilation
    -> session and cache lifecycle
    -> UI/CLI/report projection
    -> behavioral, contract, and architecture tests
```

For each trace, the review records duplicated decisions, string/filename
inference, implicit prerequisites, manual invalidation, parallel DTOs, and
tests coupled to implementation location. A recommended seam must pass the
deletion test: removing the module would force meaningful complexity back into
multiple callers. Existing tests are replaced only after equivalent behavior
and failure coverage exists at the new interface.

That migration's issue/PR records the exact old symbols, callers, line debt,

unclosed debt blocks the relevant #194/#195/#196 milestone. Core Convergence
creates no new deletion debt.

The accepted migration entry gate is one `SupportMatrix` projected from
`CanonicalCapabilityCatalog`. During convergence its denominator is the union
of executable registries, UI-selectable catalogs, and publication/support
catalogs, and every divergence must be explicit. Each exact route reports
authoring availability, execution admission, publication/support status, and
one of `DirectGolden`, `ApprovedAlias`, `SyntheticOracle`, `ContractOnly`, or
`Missing`; every migration slice keeps the route denominator stable and may not
downgrade an evidence classification. UI-selectable but non-executable routes
fail the gate. Exact routes whose authoring policy is explicitly `Unavailable`
stay visible in Support Matrix with policy provenance/reason while remaining
absent from ordinary UI/CLI authoring selectors. Missing policy is a fail-closed
materialization error, not an availability value. Publication classifications
such as internal, candidate, or test-only remain independent and must also be
explicit; omitted publication policy is a materialization failure, while
`EvidenceStatus.Missing` remains a valid evidence classification. #195 closed
the publication denominator with explicit decisions and policy intake rejects
the retired `Unclassified` value.
The target stable `RouteId` contains IC, workflow, IC Count variant, and map
variant only. Integrity/processor and every other firmware-semantic revision
belongs to `CapabilityFingerprint`; authoring/publication/evidence decisions
pin the expected fingerprint and become stale rather than silently carrying
availability, support, or evidence approval to changed semantics.
For a valid current fingerprint, `Supported` plus
`EvidenceStatus.Missing` remains Build-capable when the independent authoring,
execution, input, and runtime-dependency gates are ready, but is a critical
certification inconsistency that blocks support promotion and release. Corrupt
or hash-invalid evidence/policy bytes are catalog integrity failures rather
than an `EvidenceStatus.Missing` classification.
The same gate first records real .NET/Python coverage baselines and then applies
a non-decreasing changed-module ratchet instead of inventing a passing
percentage. An R3 slice may use characterization and differential evidence to
move through a compatibility seam, but it may not delete the previous byte or
processor owner for an affected route whose required direct/independent
evidence remains missing.

### Domain ubiquitous-language consolidation

The target model also requires one canonical domain term and one owner per
firmware concept. This is different from the technical suffix vocabulary:
`DPCMI`, DP Version, FlashCode, topology, FWConfig, and AB roles carry firmware
meaning and must be reconciled across SPEC, contracts, profiles, code, UI,
reports, and tests.

Terms are classified before renaming:

1. true synonyms share one canonical model and retain at most an explicit
   boundary/display alias;
2. a structure and its derived fields share one authority but keep distinct
   names for distinct levels, such as DPCMI versus its displayed DP Version;
3. related but different concepts remain separate, with definitions that make
   substitution impossible.

The current register is:

| Current terms | Classification and accepted/pending direction |
| --- | --- |
| `DPCMI`, `DP CMI`, `CMI DP`, `CmiDpCode`, legacy DP-version locator/catalog, and AB regions named `a-cmi-dp-version`/`b-cmi-dp-version` | **Accepted authority consolidation.** DPCMI is the one Initial Code metadata structure at CMD1/Page 0/registers `[0x16,0x19)`. DP Version and Jira are derived typed fields/presentations from that structure, not separate locator definitions. `GenFlashVersionCatalog` currently proves the drift by maintaining separate `DpVersionRulesByIc` and `CmiDpCodeRulesByIc`; the former becomes parity evidence and is deleted after generic metadata parity. AB bank placement resolves DPCMI instances and must not preserve `*-dp-version` as a second physical-fact owner. |
| `DP`, `Initial Code`, and `LDC` | **Accepted distinction.** DP is the logical artifact; Initial Code is its required part; LDC is an optional declared part. They are not interchangeable names and their physical placement comes from the resolved map. |
| `TPA`/`TP Normal`/`TP Normal Code` and `TPB`/`TP Backup`/`TP Backup Code` | **Accepted role consolidation.** The domain roles are TP Normal and TP Backup; TPA/TPB may remain compact owner/UI labels. “A Code” and “B Code” are rejected because they confuse TP roles with display A/B banks. |

The working register records evidence and owner decisions, but it will not
become a parallel glossary authority. During `to-spec`, product-facing workflow
and artifact terms move into `SPEC.md`; physical/map and metadata terminology
moves into the owning contracts/architecture documents; surprising durable
distinctions amend the applicable ADR. Compatibility aliases receive an
explicit removal or boundary-retention disposition and may not remain as
second runtime authorities.

Owner-supplied
`docs/references/ic-flashmap/common-fw/ap_fwconfig.c` is the current source
evidence for the `ST_PUB_FW_CONFIG.gstFwSettings` layout. It declares General
Parameters `[0x000,0x029)`, Hardware Information `[0x029,0x080)`, and later
Switch/Threshold/algorithm sections. FirmwareConfig structure and field layout
are common to every current IC; values remain artifact-specific. The current
`FirmwareConfigLayout` compatibility reader materializes fields only through
`[0x000,0x07C)` and therefore stops before the source-declared
`ILM_End_Addr [0x07C,0x080)`. The target artifact metadata model declares one
`FirmwareConfig` definition with named sections and fields, instantiates it at
Primary/Backup locators, and adds later sections only when a consumer and
owner-reviewed evidence require them. A format/IC-specific layout difference
becomes an explicit variant; it never causes callers to copy another offset
catalog.

The owner identifies General Parameters `[0x000,0x029)` as the first and most
valuable modeled section. It contains TP firmware version/complement and
sub-version; X/Y total sensor counts in `u8AlgNumberX/Y`; Display X/Y resolution
in `u16LCMResolutionX/Y`; TP resolution; maximum operable fingers in
`u8ReportFingerNum`; report interrupt type in `u8IRQ_Type`; Common FW format and
version components; event-buffer format; exact observed IC count;
`u8BC_EN`, whose owner-confirmed meaning is whether the outermost IC is selected
as Master; project ID; cascade/AFE/count facts; and event-buffer address bytes.
Hardware Information
`[0x029,0x080)` and every subsequent switch/threshold/algorithm section are
explicitly outside the initial target model; no speculative fields, unknown
tail, or placeholder section is created beyond `0x029`. They may enter a later
model only with a concrete inspector, validation, authoring, report, or
resolution consumer plus owner-reviewed evidence. Any existing compatibility
reader consumer of later offsets remains behind its migration adapter until
that consumer is deliberately retired or the later section is separately
approved; it is not silently claimed as migrated. This scope boundary does not
permit callers to recreate General Parameters offsets outside the one
canonical definition.

The complete 41-byte General Parameters section is declared once rather than
creating a second four-field UI catalog. Every source field has one
structure-relative offset, width, encoding, and retained `ap_fwconfig.c`
provenance name; reserved bytes are explicit reserved spans. Signedness and
byte order are never inferred. The firmware-version complement is a typed
relation validation, the three Common FW components format one
`CommonFirmwareVersion`, source `ChipNumber` projects to `ObservedIcCount`, and
`u16NovaTekProjectID` projects to `Pid`. Incomplete event-buffer address bytes
remain raw fields, and Boolean-looking source values remain typed unsigned
values until evidence authorizes a closed Boolean encoding.

The common Inspector decodes the complete section, while the compact default
slot/info projection shows only TP FW, Common FW, PID, and IC Count. Resolution,
X/Y sensor totals, Display/TP resolution, maximum fingers, and report IRQ type
are preferred TP Info details. `UseOutermostIcAsMaster` is a typed
TP/controller-topology detail; it does not choose IC Count or a route. Format,
buffer, AFE, and other facts remain available in progressive details and are
promoted to a visible warning/error only when a declared validation or
prerequisite requires it.
Formatter/projection choices never create another field or offset authority.

The Backup locator requires exactly one complete `00 4E 56 54` marker. A count
failure uses one stable summary:
`Expected exactly one NVT marker (00 4E 56 54), but found {count}.`
The diagnostic retains the observed marker count. A unique marker whose
`T - 0xFFF` prefix is out of range reports that distinct locator/range failure
rather than reusing the marker-count message.
