# 0.10.x Maintainability Working Design — AB and Trusted Bundles

Status: continuation of the promoted workshop record.

This document preserves detailed reasoning and evidence behind the canonical
[0.10.x maintainability specification](../../SPEC.md#15-010x-maintainability-program-specification).
It is not an ADR, executable contract, profile, support claim, or independent
firmware-fact authority.

### AB Code reuses definitions without forcing one layout shape

AB Code is a separately resolved workflow capability. It may reuse the same
Initial Code metadata, TP definitions, inspector, formatter, and composition
operation algebra, but Normal/Replace artifact decomposition does not
automatically define an AB layout.

The three authoring inputs have distinct domain meanings:

- **DP AB** is one owner-supplied Display artifact that already contains the
  combined DP A and DP B code.
- **TPA** is TP Normal Code associated with the A side.
- **TPB** is TP Backup Code associated with the B side.

TPB is therefore a complete TP Backup artifact, not a physical “TP Backup
anchor” inside DP AB. The combined DP AB input may expose separate A/B views for
inspection and placement without becoming two user input slots. Whether either
DP side contains LDC is an IC/map fact requiring evidence; the combined file
name alone does not establish it.

Two declarative lowering shapes are currently required:

1. **Symmetric bank instances.** The NT51929 perfect AB family has a symmetric
   `0x40000` bank shape. One bank definition is instantiated as A at base
   `0x00000` and B at base `0x40000`; the profile must not duplicate equivalent
   A/B bank or metadata declarations. This removes duplicated layout
   definitions, not the distinct TPA and TPB input roles: the user may still
   supply different TP artifacts for the two instances.
2. **Opaque seed plus TP paste mappings.** NT51950/NT51951 AB layouts are not
   forced into the symmetric template. The resolved IC/topology map declares
   only the fixed anchors that inspection or execution needs, including CMD1
   Page 0 placement, TPA/TPB paste mappings, and processor-authorized integrity
   fields. A TP paste mapping references a named section, such as `tp-code`,
   from the resolved TP Normal or TP Backup artifact definition and declares
   its destination through the applicable TP bank placement. The TP artifact
   owns the section's source half-open range, accepted layout, and inspection
   rules; an AB profile must not repeat those source offsets or lengths.
   Composition copies the complete owner-supplied DP AB image or bank into a
   work/output image first. The accepted TPA input remains immutable: its
   declared TP section is copied byte-for-byte to the TPA destination, with no
   relocation or POSTBUILD. TPB is separately cloned into an engine-owned work
   artifact and its declared relocation completes there. NT51919/NT51929/
   NT51932 then paste the relocated TPB section without any POSTBUILD.
   NT51950/NT51951 currently follow the golden-backed legacy command contract:
   the engine materializes staged A/B bank artifacts after their TPA/TPB
   overlays, the processor reads those staged banks, and the host accepts only
   the declared B-header ILM, DLM, and CRC writes before importing the verified
   B result. The original DP AB input is immutable and is never the processor's
   mutable target. The legacy A/B container shape is an adapter concern and
   does not make POSTBUILD a DP operation: every DP-owned byte remains outside
   allowed write ranges and must be preserved byte-for-byte. Internal Initial
   Code/LDC ordering remains opaque when no operation or inspection fact
   depends on it.

Both shapes compile to the same `CompiledComposition` initialization, ordered
copy/transform/processor operations, range validation, and report projection.
They are profile/layout differences, not separate execution engines. A/B
DPCMI facts instantiate the one logical DPCMI structure against each bank's
resolved Initial Code address-map view; there is no A-specific, B-specific, or
AB-specific DPCMI decoder.

The authoring surface remains the three meaningful inputs **DP AB**, **TPA**,
and **TPB**. Header/CRC recalculation is a declared processor effect shown in
preview/report evidence when relevant; it is not a fourth input slot or a
top-level memory-coverage category.

Topology may select fixed CMD1 Page 0, TPA/TPB paste destinations, and bank
anchors for NT51950/NT51951. Those physical mappings remain firmware facts
requiring the normal trusted-profile evidence and human gate. `Overlay`
describes only the compiled copy operation's replace-existing behavior; it is
not the domain name of the TP placement fact. The opaque strategy does not
authorize inspecting, editing, or exposing undeclared internal DP ranges.

TPA and TPB are separate slot instances because their files and displayed facts
and Normal/Backup roles differ. They may reference the same compatible named TP
section definition when their structure is shared. A genuinely different TP
layout must resolve a different artifact/section definition; a workflow cannot
override a shared section with ad hoc source offsets.

For all currently known AB cases, a different TP bank start is placement data,
not evidence of a different TP content definition. The resolved IC/topology
owns a bank start for each Normal/Backup role, and the paste destination is
derived from that placement plus the named section's relative range:

```text
TP destination
    = resolved TP bank start(role, topology)
    + named TP section relative range
```

This keeps TP content inspection stable while allowing TPA and TPB to land at
different addresses. A future IC requires another TP artifact definition only
when evidence shows a real section/layout difference, not merely another bank
base.

Some TP fields contain addresses whose values must move with the destination
bank. They are modeled as named relocation fields with explicit width, byte
order, value interpretation, and relocation basis. The compiler derives:

```text
TPB relocation addend
    = resolved TPB bank start
    - resolved TPA bank start
```

Only declared relocation fields may be transformed, and transformation occurs
on an engine-owned TPB work buffer before paste. The user's TPB input remains
immutable. The current executable profiles establish these concrete cases:

| AB profile evidence | Owner-confirmed fixed delta | Currently declared relocated fields |
| --- | ---: | --- |
| NT51929 family | `+0x40000` | ILM, DLM, and DIFF address fields |
| NT51950 Single | `+0x40000` | DIFF address field |
| NT51950 Cascade | `+0x40000` | DIFF address field |
| NT51951 | `+0x80000` | DIFF address field |

These deltas are owner-confirmed placement facts for the listed function-open
AB cases, not merely incidental current-profile values. They do not permit the
same delta or field set to be inferred for another IC or a newly introduced
topology. Firmware evidence still declares which named fields use that
relocation basis.

The current evidence establishes two AB integrity routes:

1. NT51919/NT51929/NT51932 clone TPB, relocate only their declared named
   address fields, and paste the resulting named TPB section. They have no
   POSTBUILD stage.
2. NT51950/NT51951 clone and relocate TPB, overlay immutable TPA and the
   relocated TPB into engine-owned staged A/B bank artifacts, run the approved
   legacy Combiner command over those staged bank inputs, independently reject
   every mutation outside the declared B-header ILM/DLM/CRC ranges, and import
   the verified result into the output work image.

DP AB remains an immutable owner input and is never directly mutated by
POSTBUILD. TPA is likewise outside processor write authority: its accepted
named TP section is copied byte-for-byte. Although the approved legacy adapter
materializes A/B bank containers, that transport/read scope does not give the
processor DP domain authority. Supporting TPA transformation in the future
still requires a separately named profile capability, authoritative firmware
evidence, processor ranges, tests, and the normal human gate.

This rejects three tempting sources of duplication:

- per-IC or per-topology DPCMI definitions containing absolute Flash offsets;
- repeated A/B declarations when one symmetric bank definition can be
  instantiated with different bases; and
- repeated TP source offsets/lengths in every AB profile instead of one named
  TP artifact section;
- duplicated TP Normal/Backup content definitions created only because their
  destination bank starts differ;
- per-profile magic relocation addends when the same value is derivable from
  the resolved bank placements;
- automatic adjustment of undeclared address-looking bytes;
- a requirement that every irregular topology provide a complete
  instance-relative Initial Code/LDC map; and
- a universal symmetric-bank abstraction that forces NT51950/NT51951 to expose
  internal Initial Code/LDC arrangements their whole-image-seed flow does not
  need.

M2 characterization must lock the existing byte behavior before this ownership
moves. At minimum it covers NT51927/NT51928 shared Initial Code DPCMI resolution,
NT51928's independent LDC part, NT51950 single/cascade TP-dependent address-map
resolution, NT51951's applicable map, NT51929 `0x40000` bank-template expansion,
and NT51950/NT51951 whole-image seed followed by declared TPA/TPB paste mappings,
compiled overlay operations, the current staged A/B read contract, proof that
POSTBUILD cannot mutate the original DP AB or TPA inputs, byte preservation of
every DP-owned range, and rejection of every write outside the approved TPB
header fields. Production
physical mappings, processor authority, and golden output remain R3 firmware
facts. This document-only phase changes no executable behavior, but it does not
lower their human-review or evidence classification.

The future contract tests must prove that the paste source half-open range
resolves from the named TP artifact section, the destination resolves from the
role/topology-specific TP bank start, and lowering produces the same ordered
copy operation without an AB-owned duplicate of the source geometry. Tests must
also prove that changing only the bank start changes the target range without
changing the TP content/section definition. Relocation tests must cover each
declared field, byte order, checked arithmetic, immutable caller input, both
`0x40000` and `0x80000` deltas, and proof that undeclared bytes remain
unchanged.

### Trusted definitions use versioned bundles

The intended representation is a hybrid set of small JSON documents, not one
giant JSON file:

- a small IC index/definition;
- references to shared perfect-family or TP-family facts;
- artifact and metadata definitions;
- workflow profiles and integrity routes; and
- a root manifest that closes and verifies the bundle.

Every definition has a stable typed identity independent of its storage path,
for example an IC, artifact, metadata structure, workflow, integrity route, or
fact-scoped relationship ID. Cross-document references use only those typed
IDs; they never embed a second definition or treat a relative JSON path as
firmware identity. Only the root manifest maps each ID to its document path,
document kind, and SHA-256. Moving or splitting a document therefore does not
change the referenced firmware fact.

The loader validates the closed manifest paths and hashes before resolving the
typed reference graph. Missing references, duplicate IDs, kind mismatches,
reference cycles, unlisted documents, and unknown closed discriminators fail
closed. Domain and Application receive normalized typed references and
definitions, never bundle paths or open-ended JSON property bags. Extensible
metadata kinds use a closed, versioned discriminator with a typed payload.

Versioning is intentionally bundle-scoped: the root manifest has one
`schemaVersion` for the complete JSON contract and one human-readable
`bundleVersion` for the release unit. One bundle content hash plus each entry's
SHA-256 provide exact identities. Individual family, profile, artifact, and
metadata documents do not maintain parallel schema versions or definition
revisions. Firmware metadata such as DP/TP version or DPCMI remains artifact
data and is unrelated to bundle schema versioning. A future independently
evolving contract is added only with demonstrated compatibility need, not as
speculative version machinery.

Trusted means strict schemas, closed manifest paths, per-entry SHA-256 values,
a bundle content hash, and a release trust anchor. Loading arbitrary user JSON
must never grant firmware authority.

A separate versioned package trust index admits exact reviewed bundle roots by
typed bundle identity, schema/bundle version, and expected content hash. It
trusts bytes only. Authoring availability, evidence classification, and
publication status remain separate versioned sources and are joined by
Application; none is inferred from trust-index membership or embedded into a
composition profile.

Stable logical `RouteId` contains IC, workflow, IC Count variant, and map
variant. The resolved bundle facts that can affect firmware resolution,
inspection, or compilation—including integrity and processor behavior—produce
`CapabilityFingerprint`. Authoring, evidence, and publication decisions pin
both. A fingerprint change therefore makes old decisions stale until explicit
reviewed supersession; it neither duplicates the logical route nor inherits
availability/support/evidence.

For an IC that uses the existing closed vocabulary, onboarding is data-only:
the bundle may declare identity, fact-scoped relationships, maps/count
applicability, artifacts, metadata, workflows, and integrity references, while
the independent policy/evidence sources record their decisions. The bundle
cannot carry executable code, scripts, dynamic assemblies, arbitrary processor
implementations, Avalonia/Workbench types, or host reflection contracts. A new
semantic kind requires a reviewed schema/domain extension rather than a plugin.

Current profile-bundle JSON and its generic loader are the migration starting
point. Manually maintained parallel C# IC catalogs become compatibility
adapters only. They are removed after all consumers use the trusted model and
parity is proven. C# continues to own generic loading, normalization,
resolution, compilation, inspection, and formatting behavior.

Production runtime reads only the current trusted-bundle schema. During the
`0.10.x` transition, one explicit temporary legacy adapter may read the current
profile bundle solely to prove parity and move consumers; it is removed with
the legacy authority. Future schema changes use a separate, deterministic,
tested `vN -> vN+1` converter that writes a new candidate bundle rather than
silently rewriting its source or adding permanent compatibility branches to
the production loader. Unknown older or newer schemas fail closed with an
actionable version diagnostic.

Historical reports persist the resolved identities, bundle fingerprint,
semantic results, and required display evidence; they do not require the
current runtime to reload an obsolete bundle schema. A future IC-authoring UI
emits only the current schema as an untrusted candidate.

A future IC-authoring UI may create only an untrusted candidate bundle in a
staging area, with validation and a reviewable diff. Promotion still requires
repository review, firmware-owner approval, golden evidence, CI, and a release
trust anchor. This UI is intentionally later than the maintainability work.
It never edits the live catalog. Promotion atomically updates the reviewed
trust index; a running host loads the result only through the explicit
Application `Reload Catalog` command. Runtime filesystem watching and implicit
hot reload are forbidden. Reload publishes one completely validated immutable
snapshot or retains the last-known-good snapshot with a typed system
diagnostic; a cold start without a valid snapshot blocks Build.
