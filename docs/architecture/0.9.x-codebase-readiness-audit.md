## Purpose and method

This audit converts important current codebase gaps into explicit `0.9.x`
release work. It inspected repository instructions, SPEC, accepted/proposed
ADRs, production projects, tests, profiles and evidence manifests, living
support/retirement reports, local/remote branch lineage, CI workflows, package
scripts, and the canonical verifier.

The scan distinguished:

- **confirmed** issues that have direct source, test, branch, or workflow
  evidence;
- **evidence gates** where code can remain candidate-only until the owner
  supplies firmware or release proof; and
- **research** that must be measured before an implementation decision.

The original audit assigned each issue to a milestone. Those assignments are
now historical; the active routing is the owner update above and the
[completion roadmap](0.9.x-completion-roadmap.md). A version branch may exclude
an optional workflow only through an explicit owner scope decision. It may not
hide an unresolved release-scope blocker by moving it to an unspecified later
major/minor line.

## Verified baseline

- The repository contains eight production C# projects and nine test/support
  projects. Production builds with nullable analysis and warnings-as-errors.
- No production `TODO`, `FIXME`, `NotImplementedException`, unpinned per-run
  executable path, or production dependency on `refcode/` was found.
- `python scripts/verify.py --all` on 2026-07-17 passed repository structure,
  Polytail, 19 repository Python tests, Ruff, Pyright, Pylint, 28 CRC-worker
  tests at 98.88% coverage, restore, format, and Release build with zero
  warnings/errors.
- The same full gate passed 1,605 .NET tests but failed one Infrastructure test:
  `RunAsyncTimeoutKillsChildProcessBeforeReturning` did not observe the child
  PID before the three-second runner timeout. The isolated test then passed in
  three seconds. The current `origin/0.9.9` branch already extends that timeout
  and adds headless process-start coverage; current `origin/0.9.10` does not
  contain those commits. The full gate is therefore still red for the audited
  `0.9.10` lineage and may not be represented as passing.
- Two Unix-special-file bundle tests are expected to skip on Windows. CI runs
  .NET tests only on `windows-latest`, so the FIFO and Unix-domain-socket cases
  are not currently exercised by protected CI.
- At the 2026-07-17 audit, `origin/0.9.9...origin/0.9.10` had five commits
  unique to `0.9.9` and two unique to `0.9.10`; the branches were siblings
  after `v0.9.8`. The 2026-07-18 local rebase now provides a temporary ancestor
  chain, but multiple active `feature/0.9.9/*` branches and the eventual final
  `0.9.9` tip still require a final rebase and explicit merge, supersede, or
  close decisions.
- The documented `v0.9.9` production-source goal is 54,000 nonblank lines, but
  `origin/0.9.9` ratchets 56,731 and audited `0.9.10` ratchets 56,742. Firmware
  safety must not be weakened to force the old number; the milestone must
  either complete exact proven retirement or record an owner-accepted measured
  ratchet.

## Architecture disposition

The primary use cases remain normal Merge and normal Replace from the same UI
workbench and CLI. Both create typed Application requests, compile through one
profile/compiler boundary, execute through one Domain composition engine, and
use Infrastructure only through ports for filesystem, staging, process, and
report persistence. Candidate intake produces reviewable candidate records; it
does not become another runtime loader or executor.

The affected durable contracts are V2 family/map/profile bundles, compiled
composition plans, external-processor declarations, immutable run/report
projections, and the candidate-intake records proposed by ADR 0023. The
required dependency direction is Presentation/CLI -> Application -> Domain,
with Infrastructure implementing Application ports. Domain remains free of
filesystem, process, JSON, and UI dependencies.

The selected strategy now has two active owners: `v0.9.9` closes the selected
retirement/contract/support scope, and `v0.9.10` measures and prototypes
process/UI performance after reconciliation. Later staging is selected at the
post-prototype decision gate. The following alternatives are rejected:

- discard confirmed issues merely because their later version is unassigned;
- reuse Preview output as Build authority or let a UI cache authorize bytes;
- infer report semantics in Presentation from operation ids or reason strings;
- add a second compiler/executor or a UI-only firmware restriction;
- delete safety, test, evidence, or compatibility paths to reach a line count;
- move UI-local preference/history persistence merely to satisfy a blanket
  layer rule.

Stable report classifications and schema tokens remain compatible until a
separately reviewed versioned migration exists. Firmware output, operation
order, processor authority, ranges, hashes, and support state remain unchanged
by R0-R2 convergence. Each R3 workflow phase requires its direct golden and
owner gate. Release metadata changes only at the final reviewed milestone, so
candidate branches cannot imply package or support promotion.

No feature branch targets `main`. Each feature branch is created from and
reviewed back into its exact version branch. A later version branch starts only
from the reviewed predecessor. The owner selects the post-`0.9.10` sequence at
the explicit decision gate; unassigned issues remain visible in this inventory
and are not silently treated as complete.

## Dependency order and stop conditions

1. Reconcile branch lineage before accepting any `0.9.10` implementation or
   benchmark result.
2. Restore a green canonical gate before using the branch as a performance or
   migration baseline.
3. Let `v0.9.9` freeze workflow/support/evidence contracts before wiring the UI
   performance prototype.
4. Capture reconciled node B before optimizing; keep Build authority
   independent of any UI inspection snapshot.
5. Complete exact product golden parity before any R3 postbuild optimization.
6. Compare node C with B under identical input/tool/machine/runtime settings.
7. Select later versions only after reviewed `v0.9.9` and `v0.9.10` merge.
8. Close legal, redistribution, clean-machine, protected-CI, and
   independent-review gates before a stable tag or release.

Any changed firmware range, operation order, CRC/header behavior, processor
read/write authority, golden hash, or support promotion stops for R3 evidence
and firmware-owner review. Any workflow excluded from `v1.0.0` remains visibly
candidate/deferred and cannot be used to block closure of the selected support
subset.

## Items inspected but not promoted to important issues

- Central package versions, lock files, NuGet audit, the exact repository SDK
  installer, and warnings-as-errors are already enforced.
- External processes use `ProcessStartInfo.ArgumentList` with shell execution
  disabled; `origin/0.9.9` additionally records headless process start.
- The two Windows skips are platform conditions, not fake tests. The issue is
  protected Linux .NET coverage, not removal of the skip reason.
- Localization `CS1591` suppressions and large partial aggregates require
  narrow justification/ownership review in a later selected phase, but no correctness
  failure was found from their presence alone.
- Code-size reduction is not an independent product goal. Only exact semantic
  retirement with retained evidence may lower a ratchet.

## Audit completion rule

This inventory is complete when every P0/P1 row is either closed with
tests/review evidence or explicitly excluded by an owner decision that does not
contradict the selected `v1.0.0` support scope. New confirmed issues receive a
stable id. Version assignment occurs at the post-prototype decision gate rather
than being inferred from the historical id or milestone column.
