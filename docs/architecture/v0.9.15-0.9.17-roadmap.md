## Common release and safety rules

- `0.9.15` starts only from official `v0.9.14` tag
  `58f5bbf4cdbfb4e02036c8c1b40c48aa88fa21f7`, peeled commit
  `9b15d8757ccb44167c471ca4e602036066bcdea9`.
- `0.9.16` may start only from the official reviewed `v0.9.15` release tag;
  `0.9.17` may start only from the official reviewed `v0.9.16` release tag;
  `0.9.18` may start only from the official reviewed `v0.9.17` release tag.
  A feature branch from an earlier candidate, local commit, or stale worktree is
  not a substitute baseline.
- A release must retain one composition engine, typed profile authority, named
  address spaces, half-open ranges, immutable inputs, staged external tools, and
  independently verified write ranges. UI text, filenames, PID, TP version,
  Common FW version, a golden hash, and observed IC count do not select a route.
- Code-size measurement is a visible review metric only. Readability, clear
  ownership, executable tests, firmware safety, and evidence are release gates.
- Cross-workflow header/Evidence/Memory coverage unification, the shared Hex
  viewport, Changes redesign, and global Button feedback remain unassigned
  Presentation backlog. They do not enter `0.9.15`, `0.9.16`, `0.9.17`, or `0.9.18`
  without a separate owner milestone assignment.

## Delivery-to-review automation contract for `0.9.15`

The automation produces review evidence; it does not make release decisions. A
review handoff must identify:

1. the exact release tag and peeled commit used as baseline, current branch, and
   clean/dirty worktree state;
2. the complete changed-file inventory, commits, and whether a version branch
   or feature branch unambiguously descends from that baseline;
3. executed checks, CI state, code-size review warnings, and the precise
   distinction between a warning and a failed gate;
4. profile/IC/mode impact and all unchanged candidate boundaries; and
5. outstanding human firmware-owner, golden, packaging, release-owner, and
   Codex-review gates.

The automation must fail closed for ambiguous lineage or a dirty worktree before
it performs development actions. It never starts a build merely because a
release tag exists, and it never creates a release, alters a tag, merges a PR,
or promotes candidate support.

The repository command `python scripts/collect_review_handoff.py` implements
this collection boundary. It is local-Git and evidence-only: it requires an
annotated baseline tag and exact expected peeled SHA, a clean non-`main` branch,
baseline ancestry, a clean committed range diff, at least one verification
record, impact and unchanged-candidate declarations, and explicit states for
firmware-owner, golden, packaging, release-owner, and Codex-review gates. CI is
reported as supplied or `not-collected`; the command never invents a CI result.
It prints ASCII JSON to stdout by default. An explicitly requested file output
is written atomically outside the repository so the collector cannot dirty the
reviewed worktree.

### Perfect-family optional A FlashCode delivery

`0.9.15` includes the owner-requested optional A-only FlashCode delivery for
NT51919/NT51929/NT51932 AB Build.  The user chooses Yes/No before any output is
written; Yes collects the AB and A names in two Save dialogs, then delivers both
artifacts from one AB execution.  It is a direct slice of that completed AB
output, not a second Standard Merge.  The primary report name remains the exact
selected AB filename; the exact selected A filename and commit status are
recorded as a delivery artifact.  Eligibility, range derivation, typed naming
tokens, path safety, partial-delivery reporting, and the explicit
NT51950/NT51951 exclusion are defined in
[ADR 0037](../adr/0037-perfect-family-ab-a-flashcode-delivery.md).
This is a delivery convenience only; it does not change candidate certification,
golden debt, AB map authority, or postbuild authority.

For the current release line, a handoff invocation has this shape (the
verification/gate values are evidence inputs, not commands the collector runs):

```text
python scripts/collect_review_handoff.py --baseline-tag v0.9.14 --expected-baseline-sha 9b15d8757ccb44167c471ca4e602036066bcdea9 --verification architecture=pass --ci-state not-collected --impact "NT51919/NT51929/NT51932/NT51950/NT51951 AB Merge" --unchanged-boundary "No family-wide workflow refactor or support-certification promotion" --gate firmware-owner=open --gate golden=open --gate packaging=not-collected --gate release-owner=open --gate codex-review=open
```

## Family evidence-reuse policy

This policy governs future evidence planning and support certification. It never
selects a runtime route, weakens an R3 gate, or turns a golden into an inferred
memory map.

- **Perfect family:** treat members as the same for a *like-for-like workflow*
  once their perfect-family relationship and the applicable plan facts are
  approved. A direct golden may cover the other members only when the workflow,
  address map, operation sequence, input/output shape, and topology are the
  same. Individual source identity and observed metadata remain report facts.
- **LDC family:** for LDC-related families such as NT51927/NT51928 and
  NT51950/NT51951, the presence or absence of local dimming divides DP behavior
  even where TP hardware remains shared. A golden for a TP-owned workflow such
  as CtrlRAM may be shared only after the TP regions, postbuild authority,
  topology, and declared input/output contract are shown identical.
- **DP boundary:** no LDC-family golden may be shared for DP Replace, AB Code,
  Standard Merge, or any other DP-writing/DP-layout workflow. Each IC requires
  its own direct DP evidence for that workflow, including its declared topology
  and size boundary. TP/CtrlRAM sharing is not evidence for a DP range, header,
  command placement, output length, or processor sequence.

The future IC family/rule authoring UI must model this distinction explicitly:
it may propose evidence relationships, but a reviewer must be able to see
whether a relation is `perfect-family` or `LDC-TP-only`, the workflow it covers,
and the evidence it deliberately does not cover.

## v0.9.18: family and evidence model unification

`0.9.18` turns the scattered Perfect-family and LDC-family evidence rules into
one reviewable model before any IC family/rule authoring UI is attempted. Every
support-matrix row, report, review handoff, and later UI proposal must state the
named relationship, covered workflow/topology, evidence basis (`direct`,
`perfect-family`, or `ldc-tp-only`), and deliberately uncovered facts. Family
membership remains evidence metadata: requested IC, compiled profile, declared
map, and topology continue to select execution.

| Relation | Initial members | May share only when the complete declared contract matches | Explicitly cannot share |
| --- | --- | --- | --- |
| `perfect-family` | NT51919/NT51929/NT51932 where the owner-approved relationship applies | Like-for-like workflow, address map, ordered operations, input/output shape, and topology. | Any workflow/topology whose declared facts differ. |
| `ldc-tp-only` | NT51927/NT51928 | TP-owned CtrlRAM evidence only: TP regions, topology, input/output contract, and postbuild authority must each match. | DP Replace, Standard Merge, AB Code, any DP layout/range/header/command fact, and any DP-writing workflow. |
| `ldc-tp-only` | NT51950/NT51951 | The same TP-owned CtrlRAM conditions as above, reviewed independently for this pair. | DP Replace, Standard Merge, AB Code, any DP layout/range/header/command fact, and any DP-writing workflow. |

`ldc-tp-only` is not a transitive four-IC group: NT51927/NT51928 evidence does
not automatically cover NT51950/NT51951, nor the reverse. The presence or
absence of local dimming is a DP behavior boundary even when TP layout is
shared.

| Work slice | Required result | Explicit boundary |
| --- | --- | --- |
| Family/evidence ADR and typed contract | Define relationship vocabulary, covered workflow/topology scope, provenance, approval state, and deny scope. | It may model evidence authority only; it cannot become a runtime IC selector or profile mutation path. |
| Existing-catalog inventory | Reconcile every Perfect/LDC statement in the support matrix, profile evidence, golden manifests, and review handoff. | No new golden claim and no reinterpretation of a fact-scoped alias as a direct golden. |
| Report/review projection | Present evidence basis together with excluded DP facts and residual gates. | It cannot hide missing golden, firmware-owner review, unsupported topology, or an R3 safety failure. |
| Rule-authoring design gate | Produce owner/firmware/architecture workshop record for a later UI: permissions, lifecycle, diff/approval/rollback, audit trail, and reviewer visibility. | No editable family/rule UI ships in `0.9.18`; a later owner-selected milestone may implement only the approved proposal model. |

Exit evidence requires an architecture and firmware-owner-reviewed ADR, contract
tests proving `perfect-family` cannot cover a mismatched map/topology and
`ldc-tp-only` cannot cover a DP workflow, plus synchronized matrix/report/
handoff vocabulary. No profile promotion, AB route exposure, golden fixture
change, or external Combiner authority is claimed by this milestone.
