# v0.9.15–v0.9.17 AB Delivery Roadmap

Status: active owner roadmap, amended 2026-07-23.

This document assigns the next three milestones without turning a candidate,
golden input, observed version, or topology into a firmware support claim.
It supersedes only the future-scope assignments in earlier planning documents;
the released `v0.9.14` changelog remains historical release evidence.

## Common release and safety rules

- `0.9.15` starts only from official `v0.9.14` tag
  `58f5bbf4cdbfb4e02036c8c1b40c48aa88fa21f7`, peeled commit
  `9b15d8757ccb44167c471ca4e602036066bcdea9`.
- `0.9.16` may start only from the official reviewed `v0.9.15` release tag;
  `0.9.17` may start only from the official reviewed `v0.9.16` release tag.
  A feature branch from an earlier candidate, local commit, or stale worktree is
  not a substitute baseline.
- A release must retain one composition engine, typed profile authority, named
  address spaces, half-open ranges, immutable inputs, staged external tools, and
  independently verified write ranges. UI text, filenames, PID, TP version,
  Common FW version, a golden hash, and observed IC count do not select a route.
- Code-size measurement is a visible review metric only. Readability, clear
  ownership, executable tests, firmware safety, and evidence are release gates.
- Cross-workflow header/Evidence/Memory coverage unification, the shared Hex
  viewport, Changes redesign, and global Button feedback remain unassigned
  Presentation backlog. They do not enter `0.9.15`, `0.9.16`, or `0.9.17`
  without a separate owner milestone assignment.

## Delivery-to-review automation contract for `0.9.15`

The automation produces review evidence; it does not make release decisions. A
review handoff must identify:

1. the exact release tag and peeled commit used as baseline, current branch, and
   clean/dirty worktree state;
2. the complete changed-file inventory, commits, and whether a version branch
   or feature branch unambiguously descends from that baseline;
3. executed checks, CI state, code-size review warnings, and the precise
   distinction between a warning and a failed gate;
4. profile/IC/mode impact and all unchanged candidate boundaries; and
5. outstanding human firmware-owner, golden, packaging, release-owner, and
   Codex-review gates.

The automation must fail closed for ambiguous lineage or a dirty worktree before
it performs development actions. It never starts a build merely because a
release tag exists, and it never creates a release, alters a tag, merges a PR,
or promotes candidate support.
