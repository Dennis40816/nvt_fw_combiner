# 0.8.0 Goal and Acceptance Criteria

Status: active milestone goal.

## Version decision

This work is a `0.8.0` milestone, not another `0.7.x` polish patch.

Reason: the scope crosses profile catalogs, Application flash-map/header categories, Bootstrap workbench routing, report presentation, contract tests, UI smoke expectations, and onboarding documentation. A `0.7.x` patch is still appropriate for isolated wording, spacing, color, or one-screen UI fixes. The changes below alter how future IC support is added and reviewed.

## Goal

Make Merge and Replace support easier to extend and easier to audit:

1. A new IC or IC mode should be introduced through a small set of explicit C# catalogs/categories instead of scattered UI, CLI, and profile special cases.
2. Report screens should read like human review reports, not debug logs: the first view explains pass/fail and byte differences, while detailed trace data remains available for audit.
3. Existing byte behavior must not change unless a profile/catalog row and test explain the change.

## Acceptance Criteria

### IC onboarding architecture

- `IcSupportCatalog` is the first C# entry point for IC workflow exposure, alias facts, and high-level onboarding notes.
- `TpFlashMapCatalog` remains the canonical flash-map region source for TP/DP/CtrlRAM/customer/protected rows.
- `TpHeaderCatalog` remains the canonical TP header/write-section source for report labels, postbuild write classification, overlap priority, header copy, backup, CRC, and TP window sections.
- `LegacyCombinerPostbuildCatalog` remains the only source for legacy Combiner postbuild command categories, Common FW version rules, IC-number branch rules, staged-file names, and command order.
- Family policies that affect more than one workflow have a dedicated catalog. Current example: `DpPerspectiveCatalog` owns NT51950/NT51951 DP Perspective supported lengths and TP/customer-info ranges used by both Standard Merge and DP Replace.
- FlashCode output naming is created by a catalog-backed Bootstrap policy from selected slot roles and metadata. DP version metadata is decoded as contiguous main/sub bytes (`Dxxxx`). UI code must not decide DP version offsets, FWConfig token priority, or the final file-name format.
- Workbench/UI/CLI code may adapt catalog/profile data into requests, but must not introduce new firmware ranges, operation order, postbuild rules, or output naming semantics.
- Adding one supported IC/mode updates only the relevant catalog/profile rows plus tests and docs. Any extra code path requires an explicit justification in the PR.

### Report readability

- The default report view states the outcome, generated artifact name, and whether differences are accepted, unexpected, or blocking.
- SHA-256 and raw hashes are kept in saved/raw report details, not exposed as primary screen text unless the user opens audit details.
- Diff rows are grouped by the best-known TP flash/header section, for example `Header`, `Header copy`, `DLM CRC`, `NF CtrlRAM`, `VN CtrlRAM`, or `Unclassified`.
- `Header` and `Header copy` are shown as distinct sections when `TpHeaderCatalog` can classify them.
- Byte differences use a readable bytes view: offset, before bytes, after bytes, changed length, and section label. Long byte runs are chunked instead of rendered as one continuous line.
- Operations render as a vertical ordered timeline using sequence numbers such as `100`, `200`, `300`, with one clear action per step.
- Postbuild details are separate from normal copy/replace operations. A postbuild command may reference the operation it refreshes, but it is not duplicated as an operation step.
- Inputs are presented as aligned human-readable rows with role, file name, size, detected metadata, and status. Detailed path/hash data is audit-only.
- Empty/debug-only sections are hidden by default and available only in raw/audit detail mode.

### Verification

- Profile contract tests cover every centralized policy that replaces duplicated constants or workflow exposure rules.
- IC onboarding contract tests reject duplicate IC rows, unknown workflow ids, orphan alias sources, and Standard Merge aliases without executable source profiles.
- Application catalog tests prove that supported ICs have matching flash-map/header/postbuild coverage when the workflow requires it.
- Current cross-catalog guards verify every postbuild planner write-section id resolves to a declared `TpHeaderCatalog` section, so report labels and write-range classification stay in the same catalog.
- UI/report smoke tests cover at least one successful CtrlRAM Replace self-replacement report and one blocking report.
- Golden/self-replacement tests remain byte-for-byte stable for existing approved fixtures.
- `python scripts/verify.py --all` passes locally before the milestone is considered complete.

### Release gate

- No new firmware BIN, private source, or generated release package is committed unless it is an owner-approved golden fixture.
- Existing 0.7.x behavior remains available while 0.8.0 refactoring is in progress.
- The milestone is not promoted as a support claim until owner-selected IC/mode rows have matching evidence, tests, and sign-off.
