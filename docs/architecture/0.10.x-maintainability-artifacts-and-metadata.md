# 0.10.x Maintainability Working Design — Artifacts and Metadata

Status: continuation of the promoted workshop record.

This document preserves detailed reasoning and evidence behind the canonical
[0.10.x maintainability specification](../../SPEC.md#15-010x-maintainability-program-specification).
It is not an ADR, executable contract, profile, support claim, or independent
firmware-fact authority.

### DP is a logical artifact composed from declared parts

DP and TP are logical artifact roles. Initial Code and LDC are DP part roles,
not independent metadata:

```text
DP
|-- Initial Code (required)
|   `-- DPCMI and other declared Initial Code metadata
`-- LDC (present only when the resolved IC/map declares it)
```

A DP without LDC consists only of Initial Code. A DP with LDC consists of
Initial Code plus the declared LDC part. The plus sign describes logical
composition, not implicit byte concatenation; the resolved physical map owns
each part's placement. One DP authoring surface may therefore render an Initial
Code slot and, when applicable, an LDC child slot without treating them as
unrelated top-level firmware concepts.

Each logical artifact or part may declare zero or more metadata structures,
for example DPCMI, FWConfig, version fields, or PID fields. DPCMI belongs to
Initial Code and is the sole target-model source of the displayed DP version
and Jira facts. The legacy contiguous DP-version reader is a migration
cross-check only; it must leave runtime/UI authority and be deleted after
parity is established.

Presentation renders semantic facts such as **DP Version** and **Jira**.
`DPCMI` is structure/provenance terminology for diagnostics, not a second
user-facing version value. If DPCMI is undeclared for an IC, the UI must expose
that typed absence or evidence gap rather than manufacture a version from the
legacy reader.

There is one logical DPCMI definition:

```text
DP CMD1 / Page 0 / registers [0x16, 0x19)
```

It is not duplicated for each IC, topology, physical offset, or AB bank. A
conceptual `InitialCodeAddressMap` translates logical
`command + page + register` coordinates into an artifact or Flash address.
For example, CMD1 Page 0 placed at physical base `0x3B000` resolves DPCMI to
`[0x3B016, 0x3B019)`, while the same page placed at `0x05000` resolves it to
`[0x05016, 0x05019)`. These are two results from one mapping interface, not
two DPCMI locator definitions.

The mapping interface does not force every AB layout into one representation.
A genuinely symmetric layout such as the NT51929 family may define one
instance-relative bank map and instantiate it at A/B bank bases. An irregular
NT51950/NT51951 topology instead declares only the named logical anchors needed
by inspection or execution. Both forms resolve the same logical metadata
coordinates; topology variation does not create another DPCMI structure.

The common BIN inspector executes only structures declared for the resolved:

```text
IC + map/topology + slot
```

One formatter then renders the resulting typed facts. Metadata results must
distinguish at least:

- `NotDeclared`: this artifact has no such structure;
- `Loading`: the requested immutable artifact read/evaluation is in flight;
- `WaitingForArtifact`: a named required artifact binding is absent;
- `BlockedByArtifact`: the required artifact exists but its prerequisite
  structure is invalid, ambiguous, or unreadable;
- `Unknown`: the structure is declared but the value cannot be established;
- `Invalid`: bytes were available but violate the declared structure; and
- `Value`: a validated typed value is available.

This prevents an absent declaration, unavailable data, and invalid firmware
from collapsing into the same UI state.

Structure admission is slot-specific. A CtrlRAM Replace slot resolved as a TP
artifact does not execute DPCMI or any other DP-only inspection path merely
because the selected IC also supports DP metadata. The resolved declaration,
not a workflow-wide IC switch, determines which structures run.

### Artifact prerequisites form a typed dependency graph

One artifact's layout or metadata evaluation may require a field decoded from
another artifact. That prerequisite is part of the IC/map/metadata declaration,
not an implicit UI file-selection order and not a nullable parameter whose
reason is lost.

The current NT51950 inspection path demonstrates the required model: the
physical placement of DP CMD1 Page 0 differs by single/cascade context, and the
current reader uses `ChipNumber` decoded from TP NVT Backup FWConfig to select
the applicable Initial Code address map. DPCMI itself does not vary. Existing
trusted declarations and tests remain authoritative for the physical mapping;
this working design records only how the dependency must flow through the
system.

The metadata evaluation states above retain the reason and provenance.
`WaitingForArtifact` carries the required artifact binding and structure/field
identity. Presentation resolves that binding through the active slot
definition, so NT51950 `WaitingForArtifact(tp-input)` displays **TP input
pending**. The phrase is localized view policy; the dependency is declared by
the trusted profile/Domain model and its current state is projected by
Application. No ViewModel hard-codes an IC id, TP rule, or physical DPCMI
offset.

Artifact dependency edges must be acyclic after capability resolution. The
inspector reads each immutable file once, caches facts by session/context/file
identity, and invalidates only downstream evaluations when an artifact changes.
Users may select DP before TP; the DP selection remains intact, and adding TP
re-evaluates only DP facts that depend on TP metadata.

The current path loses this distinction: `InspectFirmware` passes an optional
TP-derived chip number directly into physical-offset-based DP CMI decoding, a
failed decode becomes nullable `CmiDpCode`, and Presentation turns the missing
result into the generic string `Pending`. M2 must characterize that behavior,
then replace the nullable collapse with the typed prerequisite and logical
address-map result.

### Topology is a first-class selection axis

Topology belongs under an IC capability. A map, workflow, slot, metadata
structure, and integrity route must either be invariant for the parent
capability or explicitly narrow its applicability.

Applicability is declared at the highest cohesive capability/profile/map level.
Children inherit it; only exceptions override or narrow it. The model must not
require repeated `single`/`cascade` tags on every leaf.

Known examples that the model must be able to express include NT51929 cascade
`2–8 IC`, NT51930 cascade `2–13 IC`, and NT51927/NT51928 exact `2 IC`/`3 IC`
variants. These examples describe representational needs only; existing trusted
profiles remain the execution authority.

### Perfect-like and shared-part families are distinct

An owner-declared `perfect-like-family` owns one complete modeled firmware
definition. Members resolve the same artifact parts, maps, metadata structures,
workflow geometry, integrity/processor behavior, and topology/IC Count rules.
They retain separate requested IC identity, evidence provenance, and publication
status. A member cannot override one firmware fact while remaining in the
perfect-like family.

NT51919/NT51929/NT51932 are the first confirmed perfect-like family. Their DPCMI,
Initial Code/TP geometry, Header model, and applicable workflow definitions are
family-owned rather than copied or represented by three firmware offset
catalogs. Direct versus approved-alias evidence remains accurate per member.

Partial relationships remain named and part-scoped. An IC may participate in
several at once:

- `initial-code-shared-family` shares Initial Code and metadata owned by it;
- `tp-shared-family` shares TP and metadata owned by it; and
- another relationship must name its exact shared part/fact.

NT51927/NT51928 share both Initial Code and TP. Their common Initial Code makes
the single DPCMI structure resolve identically; their common TP owns one
FirmwareConfig and later TP metadata definition. NT51928's additional LDC and
complete DP/container map remain IC-specific. NT51950/NT51951 share approved TP
facts while retaining topology-sensitive Initial Code/LDC arrangements. They
still use the same logical DPCMI structure through their separately resolved
Initial Code address maps.

NT51920 and NT51931 now have owner-backed canonical DPCMI bindings admitted by
#177: `dp-code + 0x14 = 0x3E014` for NT51920 and
`dp-code + 0x18 = 0x3E018` for NT51931. Both resolve the one three-byte DPCMI
definition, and that canonical structure is the target inspection authority for
DP Version and Jira.

`GenFlashVersionCatalog` remains only as a #194 compatibility adapter for
existing `WorkbenchCompositionService` inspection, slot-fact, and output-name
consumers. It reads the same major/minor bytes but owns no profile, locator,
admission, or support fact. A declared canonical DPCMI read—including its typed
failure—must never fall back to this adapter. #194 may remove the adapter only
after every caller consumes canonical DPCMI with parity coverage; #195 retains
the final zero-caller/deletion gate for the Workbench facade.

A semantic difference removes a member from a perfect-like family or converts
the relationship to explicit shared parts. Shared-part family answers “which
parts may be reused?” Topology answers “which variant applies within this IC or
shared part?” They are independent axes.

### TP Flash Header is one detailed, executable metadata model

TP Flash Header belongs to the TP artifact. It is not merely a report category,
a CRC allowlist, or a collection of workflow-specific views. The target model
defines its structure once and resolves that definition for the selected
IC/map/topology/artifact instance:

```text
TP Header definition
    + resolved IC/map/topology
    + TP artifact binding and instance placement
    -> Resolved TP Header
```

This is a typed specialization of the common artifact-metadata structure, using
`structureKind = tp-flash-header` as its discriminator. It is not a second
TPHeader schema, catalog, loader, inspector, or formatter. The common structure
contract continues to own stable identity/version, artifact binding,
applicability, locator, documented length/ranges, evidence, and validation
assertions. The typed TP Flash Header payload adds the spans, fields, repeated
field series, semantic groups, and address-value facts required by this
structure kind. Other future metadata kinds reuse the same common resolution
and inspection pipeline while declaring only their own typed payload.

The structure definition contains physical geometry and value semantics, but
not workflow execution policy. A composition-profile behavior binding
references the already resolved `structureId` and instance plus an exact
`spanId`, `fieldId`, or `fieldGroupId`. That binding owns the operation,
execution stage/owner, applicability, and processor/integrity disposition.
Consequently the header definition remains reusable across inspection, AB
Code, Replace, memory projection, and reporting, while each workflow receives
only the authority it explicitly declares.

The intended boundary can be summarized as:

```text
common metadataStructure
    + structureKind = tp-flash-header
    + TP Header typed payload (spans, fields, series, groups)
    -> resolved metadata structure instance

composition behavior binding
    + resolved structure/instance/field-or-span references
    + workflow operation and execution ownership
    -> compiled composition behavior
```

The exact versioned JSON representation and compatibility rules remain a
`to-spec` task; the architectural decision does not. No public
`TpHeaderCatalog` or independent TPHeader authority survives the migration.

The resolved header is the common input to inspection, formatting, relocation,
header copy, integrity/processor authorization, memory projection, and report
diff classification. Those consumers may add behavior, but none may restate a
header offset or infer semantics from a field name.

The current repository already contains valuable characterization in
`TpHeaderCatalog`: evidenced layouts for 920/923, 925/926, 927-family,
930, 931, 932-family, and 950/951, including named CRC fields. However, that
catalog is Application-owned, uses absolute offsets, and explicitly serves
inspection/report semantics only. Execution separately declares profile views,
scalar transforms, postbuild copy blocks, string-derived section categories,
and processor allowed-write ranges. The target deep module absorbs those
repeated facts behind one resolved interface; the existing catalog remains only
a migration/parity adapter until its last caller moves.

The trusted definition contains these distinct concepts:

| Concept | Required facts | Purpose |
| --- | --- | --- |
| Header definition | stable id/version, artifact-relative locator, total/documented ranges, applicability, evidence | Owns one reusable physical header layout. |
| Named span | stable id and half-open relative range | Includes complete copy/read coverage, including reserved or padding bytes that are not modeled fields. |
| Field | stable id, containing span, relative offset, width, encoding, byte order, semantic subject/role, optional logical index | Decodes and names one value without deriving meaning from its display label. |
| Field series | field template, explicit index set/count, first offset, stride, and applicability | Represents DLMx CRC and repeated header records without hand-writing every identical field. |
| Header instance/placement | definition id, TP artifact binding, instance id/role, source and target address-space identities, resolved base/locator, provenance | Binds one definition to a source artifact or target bank/output placement without changing the definition's relative geometry. |
| Behavior binding | named span/field/group references plus operation-specific evidence | Authorizes relocation, copy, integrity reads/writes, or another compiled behavior without duplicating geometry. |

Four values that were previously all easy to call “offset” use these direct
domain names and must remain different typed facts:

| Coordinate/value | NT51950 example | Meaning |
| --- | ---: | --- |
| `TP BIN offset` | TPA header `0xA100`; TPB header `0xA100` | Byte position inside each immutable TP input BIN. TPA and TPB have the same unshifted layout. |
| `Flash image offset` | A `0xA100`; B `0x4A100` | Byte position inside the final composed Flash BIN. NT51951 resolves the B header to `0x8A100`. |
| `Header stored address` | evidenced value plus the resolved `TPB placement delta` when that field is selected | Address integer encoded inside a TP Header field. Changing it does not move the field's byte position in the TPB work buffer. |
| `TPB placement delta` | `0x40000` | Signed movement from the TPA TP placement start to the TPB TP placement start; a distance, not a byte position. |

The intended code vocabulary follows the same plain names:
`TpBinOffset`, `FlashImageOffset`, `HeaderStoredAddress`, and
`TpbPlacementDelta`. Presentation may render the spaced labels above;
profile/schema fields retain the same concepts rather than introducing another
synonym set. The legacy Combiner adapter may internally describe an offset
inside its zero-based A/B staging bank, but that adapter-only value is normally
identical to `TP BIN offset` for the current whole-block mappings and is not
part of the public Domain interface.

During `to-spec`, these terms are promoted into one canonical
`docs/architecture/firmware-coordinate-vocabulary.md`. That document owns each
term's definition, origin/basis, valid arithmetic, NT51950/NT51951 examples,
and mapping to code/schema names. `SPEC.md`, contracts, profile schema
descriptions, reports, and future UI help link to that document instead of
copying another glossary.

Therefore an accepted TPA BIN and TPB BIN are not pre-offset artifacts. For
NT51950, both expose the same TP Header definition at source-artifact offset
`0xA100`. The application clones TPB, changes only the selected encoded address
values, and leaves their byte locations unchanged. A later paste mapping places
the TPB section into the B-bank destination; only at that projection does the
same header byte at source/bank-local `0xA100` appear at final Flash
`0x4A100`. NT51951 follows the same rule with final Flash `0x8A100`.

For the currently evidenced AB layouts, TP is placed as one shifted block.
Consequently one resolved `TPB placement delta` is reused, not copied:

```text
TPB placement delta:
    B TP placement start - A TP placement start

placement:
    Flash image offset := TP BIN offset + TPB placement delta

relocation:
    selected Header stored address := value + TPB placement delta
```

The placement rule applies to the TPB bytes as a block. The relocation rule
applies only to explicitly selected TP Header fields whose semantic role is a
BIN start address, such as evidenced ILM, DLM, or DLM DIFF fields. SRAM
destination addresses, sizes, options, and CRC values do not become relocation
targets merely because they are in the same header. Neither rule permits code
to add the shift twice.

Each TP Header layout packages the applicable stored BIN-start addresses into
a named `tp-bank-relative-start-addresses` field group. Membership is an
evidenced layout fact, not a query such as “all fields whose name contains
start.” FWConfig, CtrlRAM, MP CtrlRAM, SRAM destination, and other
address-looking fields therefore remain outside the group unless separate
firmware evidence explicitly adds them for that layout.

Group membership declares which stored values follow TP bank placement; it
does not declare who mutates them. One AB capability behavior binding
references the resolved group and assigns each selected field to exactly one
execution owner/stage:

| Current AB scope | Host before POSTBUILD | External POSTBUILD | Separate integrity output |
| --- | --- | --- | --- |
| NT51919/NT51929/NT51932 | ILM, DLM, and DLM DIFF stored BIN-start addresses | none | none |
| NT51950/NT51951 | DLM DIFF stored BIN-start address | ILM and DLM stored BIN-start addresses | Header CRC |

This table records current evidence, not a generic split inferred from field
names. NT51950/NT51951 POSTBUILD still has no DP authority; its ILM/DLM and
Header CRC writes resolve to TPB Header fields. A future processor or IC must
declare a new evidence-backed ownership binding rather than inheriting this
table.

Capability compilation fails closed unless every applicable group member has
exactly one declared execution owner, that owner runs at a valid stage, and its
write authority resolves to that exact field. Duplicate host/processor
ownership, an unassigned required member, a field outside the group, or a
POSTBUILD range wider than its resolved fields is invalid.

Fields carry structured semantics rather than category strings. At minimum the
model distinguishes:

- **subject**: ILM, DLM, DLM DIFF, FWConfig, CtrlRAM, MP CtrlRAM, header,
  common header, or another evidenced subject;
- **role**: BIN start address, SRAM destination address, size, integrity
  result, topology/count, link/next-header address, option, version, or raw
  documented value;
- **encoding**: byte width, signedness/value kind, and byte order;
- **index**: a separate numeric identity for repeated values such as
  `DLM CRC 0..N`, never parsed from a label; and
- **value address space/basis** when the stored value represents an address.

The field definition says what a value means. A behavior binding says what a
workflow may do to it. A CRC field is not writable merely because its semantic
role is `integrity-result`; a processor obtains write authority only by
referencing that exact resolved field or an explicitly approved resolved field
group. Likewise, an address field is not relocated automatically. The AB
capability explicitly references the resolved evidenced field group and assigns
its execution ownership; the compiler validates that each member has an address
semantic and a compatible relocation basis.

Named spans are necessary in addition to fields. Header copy and integrity
calculation may cover reserved bytes between known fields. A copy therefore
references a source span and destination instance/span; it must not synthesize
a range by taking the first and last known fields. The compiler resolves both
half-open ranges, verifies equal length and compatible address spaces, applies
the declared overlap policy, and emits a normal copy operation. This makes
header copy use the header definition while preserving bytes whose meaning is
not yet known.

Repeated structures preserve physical capacity separately from runtime
applicability:

```text
field series definition
    -> every physically defined concrete field

physical field + resolved topology/count evidence
    -> Active | Unused | Unknown
```

The physical repeat count or explicit index set is a trusted layout fact.
Topology/count applicability is a second trusted fact. It may map some physical
fields to `Active` and the remainder to `Unused`; when that mapping is not
evidenced, the result is `Unknown`, not an IC-count formula guessed by the
resolver. The inspector may display every physical field with its applicability
state, preserving the workbook/table shape.

Workflow write authority is narrower. A normal field/group binding may mutate
only `Active` fields. `Unused` fields remain documented and inspectable but
read-only. `Unknown` applicability blocks any supported mutation that depends
on that series. An approved processor may cover the complete physical series
only through an explicit evidence-backed `full-series` binding whose exact
fields/range and topology scope are declared; physical existence alone never
grants that authority.

For example, the 932-family Type A/B layout, the 930 layout, the 931 DLM CRC
series, and the 950/951 DIFF/DLM CRC series may each declare different physical
series and activity rules even when their rendered labels look similar.
Single/cascade and chip-count applicability resolve the declared rule; they
never cause the inspector to scan until bytes “look like CRC.”

The model must preserve these current evidence shapes during migration:

| Header fact scope | Structural pressure the model must express |
| --- | --- |
| 920/923 and 925/926 | Related normal headers with a shared core and small descriptor-field differences. |
| 927 with 917/928 fact-scoped reuse | Multiple named header records/copies and continuation coverage; copy spans may include bytes beyond individually decoded fields. |
| 932 with 919/929 fact-scoped reuse | Type A/B layout and owner-confirmed cascade applicability through 2–8 IC, with explicit DLM CRC series. |
| 930 | Distinct 2–13 IC applicability and its own evidenced DLM CRC series; no count formula is borrowed from 932. |
| 931 | Normal header plus DLM DIFF and a separate repeated DLM CRC sequence. |
| 950/951 TP-shared scope | TPA and TPB share the unshifted TP Header definition at source offset `0xA100`. AB placement independently projects the B instance to final Flash `0x4A100` for 950 and `0x8A100` for 951; selected encoded address values use the same bank delta through a separate relocation operation. |

The TP Header implementation remains behind the IC-rooted resolution
interface, not beside it as another public resolver. That resolution returns
zero or more fully resolved metadata/header instances or typed pending/blocked
outcomes as part of one capability snapshot. Inspection consumes those
resolved instances and immutable bytes to return typed values and issues.
Compiler, memory projector, and live report-generation code query resolved
field/span identities from the same snapshot; they do not know catalog
construction, repeat expansion, alias resolution, locator mechanics, or how to
select an IC/topology. A historical report viewer consumes the recorded
snapshot projection instead of current resolution.

Ownership stays layered:

- Domain owns immutable definition/resolved types and validates ids, ranges,
  field/span containment, overlap, checked arithmetic, series expansion, and
  address-space compatibility.
- Profiles/trusted bundles own evidenced definitions, applicability, aliases,
  behavior bindings, and promotion state.
- Application resolves one IC context, inspects immutable artifacts, and
  lowers field/span references into normal composition operations and
  processor authority.
- Infrastructure loads validated bundles and adapts external Combiner
  transport; it cannot invent header semantics.
- Presentation formats/localizes typed field results and uses the shared Hex
  Viewer to highlight resolved spans/fields; it never parses ids or offsets.

Fail-closed validation includes:

- unique definition, instance, span, field, series, and concrete expanded ids;
- every field fully contained by exactly one declared span and the artifact;
- no unintended field overlap and no series overflow or duplicate index;
- applicable topology/count/map variant resolves to exactly one definition;
- every relocation/copy/integrity reference resolves and is applicable;
- every encoded address names its value address space and basis;
- processor writes are a subset of resolved TP-owned fields/spans and never a
  DP-owned range;
- header-copy source and destination spans have equal lengths; and
- unknown integrity behavior remains unsupported rather than becoming `none`.

Migration is replace-not-layer:

1. characterize the current `TpHeaderCatalog` layouts, semantic diff labels,
   postbuild ranges, AB relocations, and golden outputs;
2. extend the common artifact-metadata schema with the typed
   `tp-flash-header` kind, add trusted definitions and common resolution, and
   retain the old catalog as a read-only parity adapter;
3. move inspector/formatter and report diff classification to resolved fields;
4. move AB relocation and processor allowed writes to field references;
5. move postbuild header-copy/read coverage to named span references;
6. move memory projection and Hex Viewer decorations to the same resolved
   instances; and
7. delete the hard-coded layout catalog, raw header profile views that merely
   repeat fields, and block-name/string classification only after behavioral,
   contract, and golden parity.

Tests target the deep interface and retain independent firmware evidence. They
must cover every evidenced layout/alias/variant, repeat expansion at minimum
and maximum physical counts, `Active`/`Unused`/`Unknown` resolution, rejection
of unused/unknown writes, explicit full-series authority, unshifted TPA/TPB
source offsets, bank-local versus final Flash placement, 950/951 AB deltas,
prevention of double-add relocation, exact field decoding, field-group
membership, exact-once execution ownership, host-versus-POSTBUILD ordering,
reserved-byte span copies, rejected unknown field references, out-of-range
processor mutation, DP byte preservation, and golden byte parity. UI tests
assert typed formatting/highlighting results, never the construction details
of the resolver.
