# 0.10.x Maintainability Working Design — Shared Authoring and UI

Status: continuation of the promoted workshop record.

This document preserves detailed reasoning and evidence behind the canonical
[0.10.x maintainability specification](../../SPEC.md#15-010x-maintainability-program-specification).
It is not an ADR, executable contract, profile, support claim, or independent
firmware-fact authority.

## Shared UI capabilities

### Slots are one capability, not merely shared XAML

Repeated firmware slots should derive from one shared authoring module
containing:

- a binding from an immutable resolved artifact-instance/input-role reference
  to one session-owned `AuthoringSlotState`;
- the common BIN inspector;
- semantic formatting;
- validation and action-availability projection over that state; and
- one shared visual control.

Each workflow declares only its actual differences, such as required/optional,
artifact role, accepted capability, or access policy. This does not create a
god control or move selected-file state into the resolved artifact plan:
workflow orchestration and firmware semantics remain outside the visual
component.

Repeated spacing, padding, sizing, and visual roles use shared design tokens.
The same semantic value must not acquire a separate formatter or fallback
policy merely because it appears on another page.

Binary padding/truncation is a separate typed normalization capability, not
visual padding and not workflow-specific byte logic. A trusted slot/profile
declares the permitted policy, fill byte, length bounds, warning/error outcome,
and evidence. One shared slot control presents that policy; one Application
normalizer applies it for every admitted workflow. UI code never chooses a fill
byte or silently enables normalization.

The slot header must expose one primary current-state signal rather than
accumulating unrelated badges. Requirement and inspection state have different
lifecycles:

- an empty required slot shows one requirement icon on an action/info surface;
  an empty optional slot may use a quieter optional icon;
- after selection, `Required` no longer competes with the selected file's
  health. The requirement remains available to accessibility/help and the
  primary state becomes `Checking`, `Verified`, `Warning`, or `Error`;
- accepted oversized input is a warning and states how many trailing bytes are
  ignored; input shorter than the minimum readable/required end is blocking;
  and
- requirement, file identity, inspection health, and metadata facts remain
  separate typed fields even when one control renders them.

The current slot already has typed pending/valid/warning/blocking inspection
state, but it always renders the static `RequirementLabel` and separately adds
a health icon/text. Its metadata facts are shallow label/value chips in a
horizontal wrap panel. The target slot instead uses one stable visual anatomy:

1. artifact icon and title;
2. one right-side compact status icon on a semantic state surface;
3. selected filename and path/reveal action;
4. one shared hover/focus/accessibility reason and next-action presentation;
   and
5. a shared, aligned metadata fact layout for DP, TP, LDC, AB, and future
   declared structures.

The slot remains compact by default. Selecting a file does not automatically
expand its metadata. Its summary layer retains the artifact identity, selected
filename and concise size, current health indicator, and primary file action.
Warning/error state and any action needed to proceed must therefore remain
discoverable without opening details.

Activating the non-action portion of the summary surface reveals the aligned
metadata facts inline beneath it. Browse, reveal-file, status-help, and other
nested actions handle their own activation and must not also toggle details.
The disclosure uses no large chevron or visually dominant accordion header. A
quiet 24-pixel details/info affordance supplies discoverability; hover/focus
may strengthen its surface and show “Show details”/“Hide details,” while the
expanded state is otherwise communicated by a subtle divider, supporting
surface tint, and the affordance's selected state. An ellipsis is not used
because it conventionally announces a menu rather than disclosure.

The reveal combines height and opacity over approximately 160 milliseconds
with a restrained ease-out curve. Reduced-motion settings remove the
transition. The summary surface and quiet affordance expose one toggle action
to accessibility, support `Enter`/`Space`, publish the expanded/collapsed
state, retain a visible focus indicator, and do not create duplicate tab
stops. Expansion is Presentation/session state only: a new slot starts
collapsed, while an already-open slot may remain open during its compatible
authoring session. It carries no firmware meaning and is invalidated with the
owning session rather than leaking across modes.

This shared compact-selection pattern is the reference for later workflow
pages. A new page composes the same `AuthoringSlotState` behavior and control rather than
copying its file picker, drag/drop, status, disclosure, fact formatting, or
accessibility behavior.

The unloaded-file treatment preserves these separate typed states without
conflating them:

- **available and empty**: an active compact drop/select surface with artifact
  identity, concise instruction, Browse action, and required/optional
  affordance; it is not a warning and has no empty metadata grid;
- **dependency pending**: a prerequisite/next-action message such as **Load TP
  first**, while retaining any file identity and known size already supplied;
- **blocked**: the actual validation/evidence issue and recovery action, using
  diagnostic semantics rather than an empty-slot appearance; and
- **not applicable**: omitted from the active selection set rather than shown
  as a disabled gray slot.

The owner accepted the prototype's **A + C** combination. The persistent
available-and-empty state is A's quiet single-row summary: it keeps the
selected-card geometry, artifact icon/title, concise drop-or-browse
instruction, local requirement affordance, and explicit Browse action. It
avoids a large upload illustration, dominant dashed box, or separate heavy
action rail.

C contributes only the transient active drag-over feedback. The same slot
footprint gains a restrained inset drop surface, action/info tint, stronger
border, and concise **Drop to use this file** instruction. It must not add a
second permanent row, change card height/width, or move neighboring slots while
the pointer is carrying a file; layout movement under a drag target would make
the drop interaction unreliable. Pointer hover and keyboard focus use quieter
versions of the same local surface/border vocabulary without pretending that
a drag is active.

The accepted status presentation is:

| Slot state | Icon | Local background role |
| --- | --- | --- |
| Required / select input | upload/add or required-input glyph | action/info surface |
| Optional / no input | hollow add or optional-input glyph | neutral surface |
| Checking | clock/progress glyph | info surface |
| Verified | check-circle glyph | success surface |
| Warning | warning-triangle glyph | warning surface |
| Error / blocking | error-circle glyph | danger surface |

The semantic background belongs to the compact status surface, not the complete
slot card, so file identity and metadata remain readable and multiple cards do
not become large colored panels. The title row normally shows no status word.
Pointer hover and keyboard focus display the localized state, reason, and next
action; the same content is the indicator's accessible name/description and a
polite live announcement when state changes. Hover is therefore a low-reading-
cost disclosure mechanism, never the only way to discover the reason. A
warning/error remains available in the report issue hierarchy and must not be
hidden from keyboard or screen-reader users.

Metadata values must not float at inconsistent upper-right positions. The
shared fact layout aligns labels and values, uses the technical-value
typography where appropriate, and carries typed warning/unknown state rather
than a screen-specific Boolean styling shortcut. The exact shared fact-grid
layout remains part of the Information Card question to prototype before
`to-spec`; it no longer keeps the slot state lifecycle open.

### General mappings have one authoring seam

General Merge and General Replace retain different composition semantics but
do not own different address syntaxes, parsers, validation lifecycles, or
round-trip models. One mapping-authoring module accepts source role, operation
kind, source/target ranges, alignment, overlap policy, reason, and provenance,
then produces one typed mapping draft or typed issues. A valid draft is the
only input used by live Memory Layout projection and compilation; neither path
reparses ViewModel strings.

The session-owned `AuthoringMappingState` retains the user's editable text,
selected source, operation/source role, and current typed validation result. It
does not become another firmware mapping authority and does not duplicate a
compiled `ExplicitMapping`. One invariant address/range codec converts accepted
decimal/hexadecimal text at the authoring boundary. Domain and compiler
contracts receive only checked half-open `ByteRange [start, endExclusive)`.

The shared `AddressRangeEditor` uses **Start + Length** as the editable form for
both Merge and Replace. If the UI displays an end address for firmware-table
convenience, it is a derived, read-only **End (inclusive)** value; the label is
explicit and the value is never parsed back into the model. Range overflow,
zero length, reversed/invalid derived values, alignment, source bounds, target
bounds, and overlap are reported through stable typed issues rather than
workflow-specific strings.

Workflow differences are expressed through the typed draft:

- General Merge uses `CopyRange`, a file/artifact source binding, an optional
  non-zero source start, and a target range of the same length.
- General Replace uses `ReplaceRange`; a file source normally maps its declared
  source range to the target, while overwrite/fill patches are virtual source
  kinds materialized only by the execution adapter.
- Patch/file source kind, source role, and operation kind are closed typed
  values. They do not select separate range parsers or controls.

UI, CLI, and Saved Rule are adapters into this same draft contract. Saved Rule
numeric ranges do not pass through text merely to reuse the UI; they construct
the same typed values directly. A round trip must preserve range, alignment,
overlap policy, reason, operation kind, source identity, and provenance. If a
consumer cannot preserve one of those facts, it fails with an explicit
compatibility issue rather than silently projecting a weaker command.

Characterization and replacement tests cover boundary/overflow cases and prove
that equivalent UI, CLI, and Saved Rule inputs produce the same typed draft,
compiled operation, Memory Layout projection, report provenance, and output
bytes. The legacy General Merge/Replace parsers and workflow-specific mapping
DTO conversions are deleted only after all callers cross the common seam.

### Report issues lead with the operator outcome

Reports retain technical detail and evidence, but every issue first presents a
localized one-line summary that tells the operator what happened. A report
issue has:

- a stable machine-readable code and typed severity;
- a typed subject plus structured arguments/facts;
- a concise localized summary;
- impact and next action/remediation; and
- expandable technical evidence such as operation id, address space, ranges,
  actual/used/ignored lengths, and hashes.

The summary is formatted from the stable code and typed arguments; consumers
must not parse an English detail string. Older reports that lack structured
arguments may fall back to their stored message/code.

### Message Center shares an entry, not a data model

The shell exposes one compact right-side Message Center icon rather than adding
another top-level product tab. Its panel/modal has two distinct sections:

- **Run Reports** contains immutable Preview/Build reports and their bounded
  persisted history. Each entry describes exactly one requested composition
  run and retains the report JSON as its audit authority.
- **System Information** contains one refreshable Application-owned status
  snapshot: application version, current catalog/trust identity, runtime
  dependency readiness, refresh time, and typed system diagnostics. It is not a
  run, is not appended to Report History, and never manufactures a
  `CompositionRunReport`.

The two sections may share cards, issue anatomy, localization, filtering, and
detail disclosure because those are Presentation concerns. They do not share a
catch-all message DTO, persistence format, sequence, retention policy, or
source-of-truth model.

Ordinary healthy system facts do not increment a badge. An active warning or
error may badge the Message Center with severity and count. A cold start with
no valid catalog additionally shows a concise global blocker and disables
Build; activating that blocker or the disabled-Build explanation opens the
exact System Information diagnostic. The item leads with localized outcome,
impact, and recovery action, then discloses bundle/index identity, hash,
collision/materialization facts, and timestamps. Keyboard, focus,
screen-reader, contrast, and reduced-motion behavior expose the same content.
CLI renders the same typed issue code and facts with a non-zero exit result;
neither UI nor CLI parses loader exception prose.

System Information is current-state first. Process startup re-probes it, and
the Message Center retains only a contract-bounded in-memory list of recent
state transitions for that process. A resolved warning/error no longer
contributes to the active badge, although its recent transition may remain
visible until the session bound evicts it. System events are not automatically
written to Report History or another permanent notification log.

An explicit **Export Diagnostics** action may create a versioned,
privacy-filtered diagnostic JSON containing current system facts and the bounded
transition evidence needed for support. Paths, user identifiers, environment
values, and other potentially sensitive host data are omitted or reduced to the
contract-approved representation. The export is never accepted as a Build
Report and does not share the report-history schema.

The System Information section may expose an explicit **Reload Catalog**
action backed by the Application command. It does not watch directories or
reload automatically. While a complete replacement snapshot is being
materialized, the current snapshot remains active and the action reports
progress. Success atomically replaces the displayed catalog identity; failure
retains the last-known-good identity and shows the new diagnostic without
invalidating an otherwise usable authoring session.

CtrlRAM truncation is a warning rather than an error. Its leading message is
equivalent to **CtrlRAM file is too long — trailing bytes were ignored.** The
detail states the retained prefix, ignored trailing length, affected slot, and
that the immutable source file was not modified. The current report parser
uses the raw issue code as the title and the message as detail, which preserves
evidence but misses this operator-first hierarchy.

Preview and Build availability use one typed action-readiness projection across
all workflow pages. With sufficient IC/mode/count context, Preview may execute
a blocked diagnostic run without processor invocation or byte mutation. Build
requires current capability, input, and runtime-dependency readiness; evidence
status remains a review/release fact.

Before execution, disabled Build shows an exclamation on a hoverable/focusable
outer affordance. The existing restrained animation reveals the
highest-priority current check-time blocker and `+N` for additional blockers.
The disabled button itself remains disabled; the wrapper/icon owns pointer and
focus behavior. Keyboard and screen-reader users receive the same reason, and
reduced-motion keeps the icon/text static. The readiness hint does not create a
report. Only an actual Preview or Build run creates a report containing that
run's validation, processor, mutation, or other runtime issues.

### Interactive controls use a shared state-complete style system

Equivalent actions use shared Presentation-owned button roles and density/
shape tokens. Padding, minimum target size, content alignment, icon/text
placement, typography, color intent, and corner shape are declared once.
Container-owned spacing remains outside the button because external margin is
layout context rather than button semantics.

Every interactive role defines and visibly tests `Normal`, `Hover`, `Pressed`,
`FocusVisible`, and `Disabled` for light, dark, and high-contrast themes. A
semantic role cannot suppress the base template's feedback by overriding its
content-presenter background without supplying the corresponding interaction
states. Current `secondary`, `danger`, `iconButton`, and several generic action
styles lack an explicit hover contract even though more specialized buttons
define one; this is a shared-style defect, not a page-by-page repair.

Pure visual reuse remains XAML styles/templates rather than a C# wrapper.
A reusable control is introduced only when it owns stable behavior or a typed
data contract. Architecture/UI tests should reject repeated inline style
bundles and semantic button roles missing required interaction states.

### Information cards share anatomy, not firmware semantics

Memory Layout, IC Details, slot metadata, and report summaries may use the same
Presentation card anatomy without forcing their domain facts into one generic
firmware model:

1. a header with icon/title and optional status or action;
2. an optional concise summary;
3. an aligned fact grid grouped into small coherent sections; and
4. optional expandable detail/evidence.

Each fact cell stacks a quiet label above a left-aligned value. Ordinary values
never float at the card's upper-right edge; the header's right edge is reserved
for status or actions. The grid uses a shared minimum fact-cell width and
row-major auto-flow rather than page-selected column counts: a narrow surface
becomes one column, the current approximately 430-pixel Memory Layout panel
normally produces two columns, and wider report/card surfaces stop at three
columns. Responsive wrapping changes presentation only; it never changes fact
identity, ordering, grouping, or formatter selection.

The compact body exposes at most four projection-declared primary facts.
Additional facts remain in the same card behind the accepted quiet inline
details disclosure rather than a large accordion arrow. Section headings
appear only when they separate coherent fact groups, not merely to decorate a
short list. Fact order is explicitly declared by the owning projection and is
never alphabetical or reconstructed independently by a page.

Typed fact state is rendered consistently:

- `Unknown` shows an explicit localized value and question/help icon rather
  than a blank or ambiguous dash;
- `PendingInput` appears as a prerequisite and next-action surface rather than
  as an invented fact value;
- `NotApplicable` is omitted from the active fact set;
- `Warning` and `Error` place their compact icon next to the affected value,
  with the reason available through pointer hover, keyboard focus, accessible
  description, and report evidence; and
- ordinary metadata is never converted into a badge merely to achieve visual
  consistency. Badges remain state/status affordances.

Addresses, sizes, IDs/PID, versions, hashes, and ranges use the shared
technical-value typography; prose values use the normal UI typography. The
formatter remains the one selected by the resolved metadata definition and
common inspector, so a screen cannot create another display rule for the same
fact.

One source-neutral Presentation card/fact contract is justified only where
behavior and data shape are stable; otherwise shared XAML anatomy, templates,
and tokens are sufficient. Memory Layout retains its bar/projection body, IC
Details its domain-specific groups, slot cards their file actions and status
lifecycle, and reports their issue/evidence hierarchy. The current exterior
card treatment is acceptable, so this work reorganizes internal hierarchy
rather than introducing a new visual language.

This is a component-internal refactor, not a workflow-page redesign. The
existing desktop composition remains the baseline: Replace and Merge authoring
and input cards stay in the flexible left column, while the Output/Memory
Layout card stays in the current fixed 430-pixel right column. A fact grid may
organize supporting facts inside either card, but must not move Memory Layout
into the left flow, put input slots above it, or reorder other major page
regions. Any such move is a separate owner-approved UI redesign. At narrower
widths, a later responsive rule may stack the same regions without changing
their desktop ownership or semantic order.

### Modes own isolated authoring sessions

Application owns the host-independent `AuthoringSessionState` model and
transition policy: IC/IC Count selection, slot-definition references, mapping
drafts, `AuthoringRevision`, compatibility preservation, and derived-state
invalidation. It does not keep a process-global mutable session store. Desktop
Presentation owns the six in-memory instances described below together with
page, disclosure, hover, file-picker, localized text, and other UI-only state.
CLI creates an ephemeral instance over the same Application contract.

`MainWindowViewModel` remains only as the shallow shell that composes these
instances and focused page/feature ViewModels. It owns top-level navigation,
current-page selection, global language/theme, and child lifetime. Merge,
Replace, Report, History, Settings, Build Result, and workflow-session
presentation move behind focused children. IC/IC Count rules, slot
compatibility, firmware metadata, mappings, processor readiness, report
parsing, and Build policy may not remain in the shell. Adding more partial
files or moving the same cross-cutting fields into one generic workflow
ViewModel does not satisfy this boundary.

The in-memory authoring-session set is fixed by workflow mode, not multiplied
by IC, IC Count, map, or visited selection. There is exactly one session for
each of Standard Merge, AB Merge, General Merge, DP Replace, CtrlRAM Replace,
and General Replace. Settings, Home, report modals, and Hex Editor are not
authoring sessions. Navigation restores the corresponding mode's compatible
user-entered selection and file paths, but modes never share derived
inspection, validation, readiness, memory projection, or Preview/Build state.

Changing IC or IC Count updates the same mode session and increments its
`AuthoringRevision`; it does not retain another session keyed by the former
selection. Still-compatible selected file paths may survive the change, but
the session atomically invalidates and regenerates every derived fact. A
removed or incompatible artifact role is cleared rather than silently rebound
to another slot. Explicit Clear/reset removes that mode's authoring state.

An authoring session retains only current slot state, selected paths,
content-authoritative `FileStamp` values (accepted byte length plus SHA-256),
decoded metadata facts, and the minimum resolved/derived
state needed to present the current mode. A slot has no history of previously
selected files. Neither an authoring session nor its inspection cache retains
a complete BIN payload. Consequently, the fixed six-session set needs neither
a generic LRU nor an arbitrary megabyte budget; its structural bound is the
workflow count and each workflow's declared slot/mapping limits.

Complete reference/output bytes required for current Hex Diff belong only to
one current inspection snapshot. Input mutation, a replacement Preview/Build,
or closure of that current inspection releases or replaces those bytes.
Historical report storage retains only its separately bounded report evidence
and previews; it must not turn into an authoring-session payload cache. Hex
Editor remains a separate, explicitly bounded document session. Authoring
sessions are not persisted across application restart.

The former single `profile fingerprint` responsibility is split into four
accepted concepts:

1. `CapabilityFingerprint`, derived deterministically from `BundleHash` and
   the selected map, artifact, metadata, workflow, integrity, IC Count, and
   variant definitions that affect firmware resolution, inspection, or
   compilation;
2. `ResolutionToken`, generated for one atomically published
   resolved-capability snapshot and shared by every child;
3. `AuthoringRevision`, incremented whenever session inputs change; and
4. `FileStamp`, the accepted complete-file byte length plus SHA-256 used by
   inspection/cache and immutable run-verification decisions. Path, display
   name, and last-write time are non-authoritative hints.

Authoring policy, evidence, and publication sources each retain their own
version/hash provenance, while runtime dependency readiness is an environment
snapshot. None participates in `CapabilityFingerprint`. A policy-only catalog
publication still receives a new `ResolutionToken`, so UI/CLI action state is
re-evaluated without needlessly invalidating an otherwise compatible
firmware-inspection cache.

The UI binds to one immutable or coherently published `ActiveSessionSnapshot`.
An inspection cache key includes `CapabilityFingerprint`, slot `DefinitionId`,
and `FileStamp`. An asynchronous result may publish only when its
`ResolutionToken`, `AuthoringRevision`, slot `DefinitionId`, and `FileStamp`
still match the active session. On restore, matching `CapabilityFingerprint`
and `FileStamp` may reuse an eligible metadata-only inspection-cache entry. A
fingerprint change follows the same preserve-compatible-paths and
invalidate-derived-state rule, and Preview/Build state is never restored as
currently valid.

General selected-file Reload/Rebind is explicit: it advances
`AuthoringRevision`, retains the editable mapping row, clears derived state,
and accepts a new content stamp only after inspection. `Use full file length`
copies the currently inspected length into the editable Start + Length row and
never becomes a dynamic execution mode. Execution rejects unbound General file
rows instead of inspecting them implicitly. The desktop passes the same
content-bound draft from Preview to Build until an explicit edit or
file-selection Reload clears it; ephemeral CLI and Saved Rule adapters inspect
once before calling that strict boundary. Preview/Build reopen the immutable
run binding and verify accepted length plus SHA-256 before the bytes enter a
composition address space. ADR 0044 records the compatibility and deletion gate
for the former timestamp-shaped stamp boundary.

The historical AB Code to Replace selector defect demonstrates the current
risk. `SelectedIc`/`SelectedNumber` were shared across Merge and Replace while
the selected Merge mode remained live. The fix in commit `35e1d581` introduced
an active-page-aware AB context. The regression
`ReplaceDoesNotInheritAbMergeSelectorProjection` protects the symptom, but the
long-term correction is explicit session ownership rather than more manual
property refresh calls.

The implementation order is:

1. characterize page × mode × IC × topology transitions;
2. extract a deep authoring-session module;
3. leave navigation, modal state, and active-session routing in
   `MainWindowViewModel`;
4. move shared slot inspection/formatting/control behavior behind the session;
5. remove old refresh/invalidation compatibility paths only after parity.
