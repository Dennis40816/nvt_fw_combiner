# 0.9.2 Profile Bundle Consolidation Plan

## Purpose

0.9.1 keeps each deployed trusted bundle self-contained. That is correct for
the current loader: a bundle root is a closed inventory, includes the exact
schema snapshots it declares, and never discovers a schema from a sibling
directory or process-global mutable state.

The cost is repeated checked-in copies of unchanged schema snapshots as more
IC bundles are added. 0.9.2 may reduce that source and package duplication,
but it must not weaken the closed-root or hash-anchor guarantees.

## Scope

The intended 0.9.2 change is one shared, content-addressed source inventory
for immutable contract schemas and a deterministic materialization step for
each built-in bundle's runtime root.

At runtime the existing loader still receives a complete directory containing:

- its manifest;
- only the manifest-listed profile and family entries;
- exact local schema snapshot files whose hashes match the manifest; and
- no links, parent traversal, network fetch, sibling-bundle lookup, or
  mutable global schema registry.

This is a storage and packaging refactor. It must not change profile IDs,
family/map selection, range semantics, operation order, input policy,
compiled-composition fingerprints, or promotion state.

## Future Automated-Intake Boundary

0.9.2 establishes the only input/output contract that a later 0.9.4 automated
IC-intake interface may consume. The later interface may accept a declared
intake manifest and evidence files, then emit a candidate source bundle,
materialized closed root, validation report, and missing-evidence list.

It must not scan arbitrary directories, fetch schemas, inspect an arbitrary
BIN to infer firmware facts, or edit an approved bundle in place. It cannot
infer ranges, CRC/header behavior, aliases, FW Config layouts, support status,
or promotion. A human-reviewed, committed bundle remains the only route to
runtime authority.

## Required Design Rules

1. One schema source may be reused only by content hash. A schema id/version is
   not enough to imply identical bytes.
2. Materialization must copy or generate the local snapshot before the loader
   sees the bundle. The loader must not resolve `../`, another bundle root, or
   a shared mutable directory.
3. A manifest remains the complete allowlist for its materialized root.
   Unlisted files, duplicate paths, reparse points, and hash mismatches remain
   failures.
4. The publish layout and test layout must be byte-identical for every
   materialized bundle. Source-tree convenience must not become a different
   trust mode.
5. Built-in hash anchors continue to bind each final manifest. Any changed
   entry path or content requires the normal manifest-hash and Bootstrap-anchor
   update.
6. There is one materializer and one existing loader. Do not add a second V2
   loader, schema resolver hierarchy, or per-IC package path.

## Migration Steps

1. Inventory all built-in bundle schemas by `(schemaId, contentHash)` and
   prove the intended shared entries have identical canonical bytes.
2. Define one content-addressed source inventory owned by the profile package,
   not by UI or Bootstrap.
3. Implement deterministic materialization into a staging root for tests and
   publish output. Keep the current closed-inventory verifier and schema
   validation unchanged against that root.
4. Migrate one existing bundle first, compare source/materialized/deployed file
   hashes, and run its trusted V2 plan and golden regression unchanged.
5. Migrate all built-in bundles only after the first bundle proves manifest,
   loader, Bootstrap deployment, preview/build report, and golden parity.
6. Remove duplicated source snapshots only after every runtime/test path uses
   the materializer and repository checks reject direct loading from an
   incomplete source bundle.

## Acceptance

- Every materialized bundle passes the existing closed inventory, manifest
  hash, local schema, and semantic validation checks.
- Every Bootstrap deployed bundle is byte-identical to its materialized test
  root.
- Existing Normal/Standard Merge golden outputs and compilation fingerprints
  are unchanged.
- No loader accepts a parent path, sibling bundle, network schema, reparse
  point, or unlisted schema entry.
- `python scripts/verify.py --all` passes, with architecture and Infrastructure
  tests covering the source-to-materialized boundary.

## Non-Goals

- No AB Code implementation or promotion.
- No firmware-map, profile, CRC/header, range, or overlap-policy changes.
- No trust-anchor relaxation or runtime schema caching service.
