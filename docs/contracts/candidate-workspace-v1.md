# Candidate Workspace Contract 1.0

Status: Proposed — architecture and security acceptance required.

The executable manifest schema is
[`candidate-workspace-v1.schema.json`](candidate-workspace-v1.schema.json).
This contract wraps the existing four-record candidate intake export together
with schema-validated generated declarations and PR-ready diagnostics. It has no
runtime, support-promotion, Git, process, or firmware-mutation authority.

## Directory contract

A caller explicitly chooses either the existing compatibility export or this
workspace export. The compatibility command remains unchanged: its selected
empty directory receives exactly the four current JSON files at its root. A
workspace is a different selected empty directory with this closed shape:

```text
candidate-workspace.json
compatibility-export/
  candidate-bundle-rows.json
  candidate-evidence-manifest.json
  missing-evidence.json
  validation-report.json
generated/
  families/*.json
  profiles/*.json
  bundles/*.json
  evidence/*.json
```

`compatibility-export/` is itself the exact four-file compatibility export: the
names and bytes are unchanged and no fifth entry is allowed there. Generated
directories and files exist only when explicit confirmed facts are sufficient
to produce a document that validates against an already approved schema.
Missing facts omit the document; they never receive inferred defaults.

The complete workspace inventory is exactly:

1. `candidate-workspace.json`;
2. the four fixed `compatibilityExport.records`; and
3. every `generatedArtifacts[].path`.

No other file, directory, link, reparse point, device, socket, or alternate data
stream is admitted. Paths are `/`-separated relative paths. Absolute paths,
backslashes, empty segments, `.`/`..`, case-colliding paths, duplicate paths,
and names outside the closed prefixes fail validation.

## Manifest integrity

`inventoryHash` is lowercase SHA-256 over the RFC 8785 canonical JSON byte array
of all compatibility and generated file records, sorted by ordinal `path`. Each
hash record contains exactly `path`, `sizeBytes`, and `contentHash`; the manifest
does not hash itself and cannot establish trust in itself. A future signed pack
or release authority must authenticate the expected workspace/pack digest from
outside the downloaded content.

The writer snapshots every generated byte sequence before publication, computes
its size and SHA-256 from that snapshot, and publishes the closed workspace
atomically into a caller-selected empty destination. Input workbooks, mmap/BAT
evidence, sample firmware, and expected outputs remain immutable. Private BIN
bytes are never copied into the workspace; evidence manifests retain only their
declared logical names, sizes, hashes, provenance, and citations.

## Generated artifacts

The only artifact kinds are:

- `firmware-family` validated by `firmware-family-v1`;
- `composition-profile` validated by an already approved composition-profile-v2
  schema supported by the installed engine;
- `profile-bundle` validated by `profile-bundle-v1`; and
- `evidence-manifest` validated by `firmware-evidence-manifest-v1`.

Every artifact identifies the canonical schema id and exact schema content hash
used for validation and cites at least one explicit source fact id. A workspace
cannot
add or edit a schema, processor allowlist, tool manifest, executable, command,
runtime registration, or support claim. A profile-bundle document in this
workspace is candidate output, not a trusted installed bundle.

## Diagnostics and gates

Diagnostics are embedded in `candidate-workspace.json`; there is no second
diagnostic sidecar to drift from the manifest. They record compiler and optional
parity outcomes, required reviewer roles, and at least one residual gate.

- `compiler.status: passed` requires the exact profile id and compilation
  fingerprint produced by the existing V2 compiler.
- `parity.status: passed|failed` requires a named reference kind and both exact
  output SHA-256 values. A mismatch is evidence and never rewrites declarations.
- `requiredReviews` names the remaining architecture, security, dependency,
  firmware-owner, golden, or release roles.
- `residualGates` uses stable codes and fact/evidence references. A workspace is
  invalid when it pretends no gate remains.

`capabilities` is a closed set of five literal `false` values: runtime
registration, support promotion, private-payload copy, command execution, and
Git mutation. The exporter reports what a reviewer must do; it never invokes
Git, opens a PR, runs submitted BAT/macros, executes Legacy Combiner, or installs
a profile.

## Determinism and semantic validation

JSON Schema validates document shape. The workspace validator additionally
enforces:

- ordinal ordering and uniqueness for file paths, artifact ids, fact ids,
  issue codes, reviewer roles, evidence references, and gate codes;
- exact four-record compatibility membership and byte parity with the standalone
  compatibility export;
- `inventoryHash`, every file size/hash, closed-directory membership, and
  regular non-reparse files throughout the final locked snapshot;
- artifact kind/path/schema agreement and full validation against the named
  repository-approved schema;
- equal expected/actual hashes for `parity.status: passed`;
- no `supported` promotion stage or trusted-bundle registration side effect;
  and
- atomic output, cancellation cleanup, competing-output preservation, and
  private-payload exclusion.

The first executable implementation must provide positive and negative vectors
for these semantic rules. Schema acceptance alone does not authorize persistence
or UI exposure.

## Firmware and release invariants

This contract declares no range, offset, operation order, integrity behavior,
processor write authority, alias, or supported IC. In particular it cannot
alter the NT51950/NT51951 full-DP AB base, add an AB `map.txt`, authorize C# AB
header CRC writes, replace exact Legacy Combiner 1.13.0 parity through
`legacy-combiner-1.13.0`, or weaken direct or approved fact-scoped evidence gates
for NT51919/NT51932.

The schema adds no runtime dependency and is not copied into the portable
package. While it remains under `docs/contracts`, its repository bytes do
contribute to the release manifest's `embeddedSchemaBundleSha256` provenance
digest; that digest contribution does not embed, activate, or authorize the
candidate workspace contract at runtime. Any future runtime/package use needs a
separately reviewed implementation and package decision. Before merge it
requires architecture and security review; any generated firmware facts,
profile behavior, golden output, processor authority, or support promotion
retains its normal R2/R3 owner gates.
