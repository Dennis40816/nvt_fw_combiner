# Release Manifest Contract 1.x

`RELEASE-MANIFEST.json` is the machine-readable inventory for the minimal Windows package. It is generated by the protected release packager and validated before upload.

Rules:

- JSON Schema Draft 2020-12.
- UTF-8, deterministic property order, no unknown properties.
- SHA-256 is lowercase 64-character hex.
- Package paths are relative package paths. Root self-contained application/runtime files use role `application`; approved external tool payloads live under `external-tools/`; built-in materialized profiles live under `profiles/built-in/`; the canonical capability policy has its one exact `docs/contracts/canonical-capability-policy-v1.json` path; human-review evidence and owner-approved golden fixtures live under `reference/`.
- The manifest lists every shipped package file except itself and `SHA256SUMS.txt`. It requires `NvtFwCombiner.exe`, the three root legal/readme files, the CRC Worker at `external-tools/crc-worker/0.1.0/Nfc.CrcWorker.exe`, the canonical capability policy, and at least one built-in profile. No runtime adapter may maintain a smaller handwritten role/path allowlist.
- `SHA256SUMS.txt` is the one canonical auxiliary inventory. It is strict UTF-8 without BOM and contains exactly one lowercase SHA-256 line for every manifest-listed file plus `RELEASE-MANIFEST.json`; it does not list itself. Missing, duplicate, malformed, mismatched, or extra lines fail package admission.
- Owner-approved golden firmware fixtures use role `goldenFixture`; non-BIN reference evidence uses role `reference`.
- An exact empty evidence file may be represented only by role `reference`, with `size: 0` and the SHA-256 of its empty bytes. Application, launcher, legal/readme, capability, profile, external-tool, and `goldenFixture` entries remain non-empty.
- Built-in profile/schema/processor digests also pin the aggregated embedded authority, while every separately shipped profile/capability/tool file remains independently listed and hashed.
- The release packager validates the actual generated `RELEASE-MANIFEST.json` against this schema immediately after writing it and again after the final closed-package allowlist comparison, before ZIP creation. Release smoke, managed installer, and installed-version verifier consume this same schema and closed inventory. Validation counts actual decompressed bytes, not only ZIP metadata.
- `licenseSpdx` is `MIT`.
- Signing fields may be omitted only when the release owner explicitly approves the exact package for unsigned distribution. This unsigned disposition does not waive the closed manifest, SHA-256 inventories, SBOM, provenance, package smoke, legal/redistribution review, or immutable release identity. When present, `signingIdentity` must describe the real verified signing identity and must not contain a placeholder.
- Schema `1.1` remains readable for already-installed pre-1.0 packages and must not contain launcher fields. It is historical-inventory compatibility only and cannot be admitted as a fresh Setup candidate.
- Schema `1.2` is mandatory for managed 1.0 releases. It requires `versionManagementProtocolVersion: 1`, one strict `launcher` identity, and exactly one matching `launcher/NvtFwCombiner.Launcher.exe` file with role `launcher`. The launcher version is a stable three-component version; prerelease/build suffixes are rejected. The launcher's path, size, and SHA-256 must match both declarations.
- Schema `1.3` is the bounded stable `manual-only` contract introduced for v1.1.0. It requires `distributionMode: manual-only`, the exact v1.1.0 version and tag identities, exactly one `application`-role file named `NvtFwCombiner.exe`, and forbids Launcher, Bootstrap, deployment, Catalog/Registry handoff, and every `reference` or `goldenFixture` payload. It remains a closed Windows x64 Application package with the same hashes, SBOM, provenance, worker, profile, and capability-policy checks. Managed Version verification rejects schema 1.3 fail closed; it is never a Setup or update candidate.
- `NvtFwCombiner.Bootstrap.exe` is the immutable installation trust anchor. It is outside every version payload and therefore must not appear in a version release manifest, ZIP update payload, or version-scoped SBOM component list. Replacing Bootstrap requires an installer-level release, not managed self-update.
- The distribution Launcher and its embedded Root Bootstrap use the separate closed installer evidence contract in `installer-release-manifest-v1.md`. That external manifest never changes this version manifest's schema or inventory and is not Launcher/Setup runtime authority. The `launcher` field here continues to mean only the version-scoped Launcher inside the version ZIP.
- There is no launcher-only package. Each managed app release couples its launcher identity to the exact app release-manifest SHA and installed admission identity. The schema 1.3 direct-package exception carries no launcher identity.
