# v1.0.8 Catalog v2 notification-policy specification

- Status: Product-owner approved on 2026-09-01; corrected minimal design is
  pending fresh independent R2 admission
- Target: v1.0.8
- Authority: ADR 0051, ADR 0053, ADR 0058, and ADR 0066
- Risk: R2 implementation; R3 live Registry/Catalog publication

## Goal and exclusions

Add strict Catalog v2 entries whose background-notification policy is exact
`manual-only` or `notify`. Preserve the v1 update path so a real v1.0.7 client
can install v1.0.8.

This version does not add automatic install, a second updater, new package or
Catalog identity types, a full-admission wrapper, an install token, a new
no-eligible result, Presentation policy logic, Environment Self-test behavior,
or persisted direct-root schema-floor state/UI.

## Capability-reuse contract

Implementation extends these existing owners:

| Required fact | Existing owner |
| --- | --- |
| Package admission identity | `UpdateCatalogVersionSnapshot.Identity` |
| Exact Catalog schema and byte identity | `UpdateCatalogContentIdentity` |
| Automatic versus explicit request mode | `CheckAsync(bool isAutomatic, ...)` |
| Parsed publication equality on readmission | `CatalogPublicationEquals` |
| Registry serialization and anti-rollback | Existing writer lease, second read, revision/digest checks, and state store |
| Durable-generation equality | `VersionManagerState.CreateDurableSnapshotToken` and `DurableSnapshotToken.Matches` |
| Published changelog | Existing Catalog `releaseNotes` |
| Catalog generation | Existing `scripts/create_update_catalog.py` |
| Registry schema-version editing | Existing positive `catalogSchemaVersion` editor input |

`UpdateCatalogVersionSnapshot.Identity` must remain limited to package fields.
`UpdateCatalogContentIdentity` must remain schema version plus exact stable-file
SHA-256. `CatalogPublicationEquals` gains only the policy comparison. No second
identity, writer, selection engine, or state store is permitted.

ADR 0066 narrows ADR 0053's package-admission rule, not its durable-state
invariant. An automatic all-manual check may admit the exact Registry/Catalog
authority publication without admitting a package/source candidate. It may
persist only a revision/digest change to an already coupled, v1.0.7-readable
source/Registry state. A null `UpdateSource` never gains a non-null
`VersionSourceRegistryState`; no field, schema, migration, store, or writer is
added.

The existing durable snapshot token remains the one generation owner. Its
field comparison must include `SourceRegistryState` so revision-only and
digest-only changes invalidate an older Launcher self-test or managed setup
recovery generation. Registry readmission must reuse the same token and remove
its private duplicate durable-state equality helper.

## Wire contract

Catalog v1 remains the existing distinct strict schema and wire DTO. Runtime
admission maps every valid v1 entry explicitly to effective `notify` without
rewriting its document.

Catalog v2:

- uses fixed direct-root filename `update-catalog.v2.json`;
- has exact integer root `schemaVersion: 2`;
- retains every required v1 root and entry field;
- requires each entry to contain `notificationPolicy` exactly once; and
- accepts only exact lowercase `manual-only` or `notify`.

Missing, null, duplicate, case-variant, numeric, or unknown policy values,
unknown root/entry fields, and every existing Catalog validation failure reject
the complete v2 document. Distinct v1/v2 schemas and document DTOs prevent an
optional v2 property from making malformed v2 look like v1. Infrastructure
performs bounded schema dispatch through distinct source-generated v1/v2 DTO
metadata and publishes the existing typed snapshot and
`UpdateCatalogContentIdentity` only after strict admission. The normative v2
schema and companion contract prose are updated together.

## Application behavior

### Automatic check

The existing `CheckAsync(isAutomatic: true, ...)` owner filters policy before
opening a package path.

- Select the newest version newer than the active version whose effective
  policy is `notify`.
- Verify at most that selected package before allowing the existing prompt.
- Publish no `manual-only` row, version, release note, policy fact, badge,
  accessibility state, or package candidate.
- Never download, install, activate, or switch automatically.

If a Registry Catalog has no eligible newer `notify` entry:

1. perform zero package-port calls;
2. acquire the existing writer lease;
3. reload state and the existing launcher fence;
4. re-read the same Registry and Catalog through the existing path;
5. repeat existing revision/digest anti-rollback and Registry assertion checks;
6. confirm the same exact `UpdateCatalogContentIdentity`, admitted entries,
   and no eligible `notify` entry;
7. only when the reloaded state already has a normalized non-null
   `UpdateSource`, an existing non-manual-pin `SourceRegistryState`, and the
   selected Registry `SourceRoot` path-equals that source, atomically advance
   only the existing accepted Registry revision/digest; otherwise perform no
   durable save; and
8. return the existing connected, no-candidate, no-prompt snapshot.

This is Registry/Catalog authority-publication admission, not package/source
candidate admission. The optional save must preserve source, Registry entry,
manual-pin state, package, prompt, projection, inventory, installation,
activation, rollback, and all other state. It must not create a
`NoEligibleNotification` result or fall through to a second route after the
publication has been validly admitted.

When `UpdateSource` is null, Registry state is missing, the state is manually
pinned, or the selected Registry route does not match the effective source,
the operation returns the same snapshot without saving. This preserves
released v1.0.7 backward-read compatibility. Until an explicit package/source
admission couples and persists the source with Registry state, the two reads
protect the current check but no Registry high-watermark advancement is
remembered across restart. This is an accepted bounded v1.0.8 limitation.

The exact all-manual automatic projection is `Catalog = null`,
`VerifiedCandidate = null`, `SourceStatus = Connected`,
`CatalogIssue = None`, and `ShouldPromptForUpdate = false`, with the existing
status of the selected Registry entry and no policy-specific issue. A mixed
automatic projection contains only the selected verified `notify` row; it
cannot reuse a prior explicit/full Catalog snapshot.

This no-package branch is implemented outside `InspectCandidateAsync`.
`RunEnvironmentSelfTestAsync`, `InspectFreshInstallationAsync`, and
`ReverifyFreshInstallationAsync` continue invoking the shared newest-package
inspection and therefore verify the Registry-asserted newest package even when
its policy is `manual-only`.

### Explicit check and install

The existing `CheckAsync(isAutomatic: false, ...)` path exposes all admitted
newer rows, including `manual-only`. Installation remains an explicit user
selection plus the existing confirmation, package verification, lease-held
durable-state reload, and mutation path.

`CatalogPublicationEquals` compares effective policy with its existing entry
fields only between the existing first Registry read and lease-held second
Registry/Catalog read. A correction in either direction during that interval
fails closed without a new token or mutation matrix. `InstallAsync` does not
reread the Catalog: a policy-only change after explicit Check does not revoke
the already explicit selection because both policies permit explicit install;
the existing install path still re-verifies package identity and bytes.
Policy-only correction does not change `UpdateCatalogVersionSnapshot.Identity`
when package identity is unchanged.

### Policy meaning

- `manual-only`: explicit Check and explicit install remain available;
  automatic notification and package I/O are suppressed.
- `notify`: preserve current notification behavior; installation remains
  explicit.

Presentation renders the existing Application snapshot. It does not parse,
filter, or re-derive policy and receives no new policy engine.

## Source behavior

### Registry route

The current Registry `catalogPublication` assertion, candidate order, exact
Catalog digest, writer lease, second read, revision/digest anti-rollback, and
atomic state save remain authoritative. Catalog schema version `1` or `2` must
match the exact admitted Catalog. The automatic all-manual exception admits
only Registry/Catalog publication authority without forming a package/source
candidate. It may advance durable revision/digest only for an already coupled
source/Registry state satisfying the four guards above; it never creates a
null-source Registry state.

### Direct/manual-pinned root

Look up fixed names without directory search:

1. When `update-catalog.v2.json` is present, load it. Unsafe, unreadable,
   unstable, oversized, or invalid v2 fails closed without trying v1.
2. When v2 is absent, load `update-catalog.v1.json` through the existing path.

No per-root schema floor is persisted in v1.0.8. If a direct root previously
served v2 and later removes it, a subsequent check may admit v1. This accepted
bounded limitation must be covered by a characterization test and documented;
it must not trigger state migration, downgrade-warning UI, or source
reconfirmation work in this release. Registry-routed anti-rollback is
unchanged and is revision/digest monotonicity, not a Catalog-schema floor. A
release owner may deliberately publish a higher Registry revision asserting
v1; that is an R3 live-publication decision rather than automatic fallback.

## Publisher

Extend `scripts/create_update_catalog.py` only.

- Default invocation produces the existing byte-compatible v1 publication.
- Explicit v2 generation writes `update-catalog.v2.json` and requires one
  complete `VERSION=manual-only|notify` assignment for every aggregate entry.
- Missing, extra, duplicate, case-variant, or unknown assignments fail before
  write.
- Both policy correction directions are valid only as new complete
  publications.
- Existing package byte/hash/manifest verification, stable-entry rules,
  atomic replacement, publication lock, and release-note preservation remain
  unchanged.
- When v2 is absent, the first explicit v2 publication imports stable
  `publishedAt`, `releaseNotes`, and package metadata from valid v1. Every
  subsequent v2 publication/correction uses the existing strict v2 aggregate
  as its stable-metadata authority even when v1 is stale.
- Complete policy assignment plus every metadata/package validation succeeds
  before the first controlled atomic Catalog, Registry, or manifest-copy
  write. Default/no-v2-option invocation does not inspect or alter v2 and
  remains byte-for-byte v1 behavior.
- Existing Catalog `releaseNotes` remain the only published changelog source.
- Registry rendering binds the schema version read from the exact admitted
  Catalog. The existing Registry editor is reused; no replacement editor is
  added.

## Required focused evidence

### Contracts and source adapter

- Existing v1 fixtures remain byte/behavior compatible and map to effective
  `notify`.
- v2 schema and runtime parser agree for valid mixed/all-manual Catalogs.
- Missing, null, duplicate, case-variant, numeric, unknown policy, unknown
  fields, and existing invalid values reject the entire v2 Catalog.
- Direct root prefers v2, rejects present-invalid v2 without fallback, uses v1
  only when v2 is absent, and demonstrates the documented non-sticky behavior
  after prior v2 removal.

### Application and Registry

- Mixed policy chooses only an eligible newer `notify` entry during Automatic
  and exposes no manual-only fact.
- All-manual Automatic performs zero package-port calls and returns the
  existing connected/no-candidate/no-prompt snapshot.
- Registry all-manual handling repeats authority-publication admission under
  the existing lease. It changes only revision/digest when the four coupled
  source/Registry guards hold; null-source, missing-state, manual-pin, and
  source-mismatch cases perform no durable save. A field-by-field comparison
  proves every other durable field unchanged, and the released v1.0.7 reader
  accepts every state v1.0.8 persists.
- Revision-only and digest-only Registry-state changes invalidate the existing
  durable snapshot token; Launcher self-test and managed setup recovery reject
  the stale generation rather than accepting a state-changed plan.
- Exact mixed/all-manual snapshot fields match the projections above and never
  leak or reuse a manual-only/full prior Catalog.
- Explicit Check exposes all rows; explicit installation and cancellation
  retain current behavior.
- `CatalogPublicationEquals` rejects either policy correction between the two
  Registry reads while package identity remains stable when package bytes do;
  a policy-only change after Check preserves explicit-install behavior.
- Direct and Registry checks use the same Application policy selection.
- Environment Self-test and fresh-install inspection continue verifying the
  Registry-asserted newest package for v2/manual-only publications.

### Publisher and release

- Default publisher output remains v1-compatible.
- v2 requires complete assignments and admits both correction directions while
  preserving existing `releaseNotes` and package identity rules.
- First-v2 migration imports valid v1 stable metadata; later-v2 correction uses
  strict v2 even with stale v1, and every policy/metadata rejection occurs
  before any controlled atomic Python write.
- Real v1.0.7-to-v1.0.8 discovery/install/READY/offline/rollback uses v1.
- A staged v2 canary from that installed v1.0.8 proves mixed/all-manual
  selection, explicit installation, exact hashes, and both policy corrections.
- Only a release-owner R3 approval may advance the live Registry to the exact
  canary-proven v2 Catalog.

Tests use only the declared fixed test area. The frozen candidate requires the
normal R2 review, scoped Polytail, narrow tests, and canonical final gate.

## Acceptance

- One strict source adapter supports distinct v1/v2 contracts.
- One existing Application request-mode owner handles both routes.
- Automatic manual-only filtering happens before package I/O and leaks no
  policy fact.
- No new identity, token, terminal result, state field, Presentation engine,
  self-test branch, publisher, or Registry editor exists.
- The direct-root downgrade limitation is explicit and Registry anti-rollback
  remains intact.
- Both required canaries pass before R3 live cutover.

## Open decisions

None. Fresh independent R2 review is an admission gate, not a product decision.
