# Draft specification: v0.10.6 managed version experience

- Status: Owner-approved on 2026-08-21; implementation evidence pending
- Date: 2026-08-21
- Target: `v0.10.6` internal proving release; first user-distributed managed
  baseline is `v1.0.0`
- Owners: Product owner, architecture owner, release owner
- Risk: R2 architecture, filesystem/process, package, and UI contract; R3
  release approval remains required for a distributed stable package
- Builds on: `SPEC.md`, ADR 0049, accepted ADR 0051, the `v1.0.0` extension in
  ADR 0056, and
  `docs/ci/release-package.md`
- Visual reference:
  `artifacts/settings-version-management-approved-2026-08-21.png`

## Problem and intended outcome

The current Windows portable package starts `NvtFwCombiner.exe` directly and
has no stable owner for discovering, verifying, installing, activating, or
rolling back application versions. Replacing a running executable in place is
unsafe, and binding package identity to one configured drive or share would
make an otherwise identical update set unusable after relocation.

`v0.10.6` must prove one managed installation model before `v1.0.0`: a small
stable launcher owns side-by-side version directories and atomic activation;
the Settings Version page discovers packages from a user-configured folder,
verifies content rather than path identity, and requires explicit consent for
every install or deletion. The app remains usable while discovery runs or the
source is offline. Firmware composition semantics and support claims do not
change.

## User stories

1. As an operator, I can open the app immediately while a background check
   determines whether a verified newer version is available.
2. As an operator, I can edit or browse the update-source folder, confirm the
   draft path once, and avoid repeated reloads while typing.
3. As an operator, I can review release notes and explicitly accept or defer a
   verified update; the app never installs automatically.
4. As an operator, I can see installed, available, active, verified, and damaged
   versions, then switch among verified installed versions even while offline.
5. As an operator, I can individually delete any non-active installed version
   after confirmation and receive a reminder, not automatic deletion, when
   more than three healthy versions are installed. `v1.0.0` first retires an
   explicitly confirmed launcher rollback target and blocks active/pending
   launcher owners.
6. As an operator, I recover to the last-known-good version when a newly
   activated version cannot reach its bounded startup-ready handshake.

## Scope

- A stable Windows launcher/updater outside version directories.
- Side-by-side managed application payloads and an atomic active-version
  reference.
- A versioned, bounded update catalog selected by a strict Registry loaded from
  the fixed primary/backup filesystem replicas or an explicit diagnostic override.
- Content-based package and installed-version verification.
- Background discovery, explicit install consent, staged installation,
  activation readiness, rollback, switching, damaged-version reporting, and
  explicit deletion.
- A unified Settings modal with General, Appearance, Version, and Support
  Matrix sections using the approved visual system in Light and Dark modes.
- An isolated local update-source lab under
  `artifacts/version-update-source-lab/` with synthetic, release-safe
  ReadyProbe packages using `0.10.x` test identities, plus a root-bound
  managed-root lab generated outside committed artifacts. These protocol
  fixtures are not production application packages or release candidates.
- Folder-content, root-binding, source-relocation, launcher, smoke, accessibility, architecture, and
  release evidence needed to advance the internal candidate to `0.10.6`.
  `v0.10.6` does not replace the existing end-user portable-package pipeline;
  the managed end-user package transition is reserved for `v1.0.0`.

## Explicit non-goals

- No change to firmware bytes, ranges, operation ordering, CRC/header behavior,
  output naming, profiles, support, or Golden authority.
- No in-place overwrite of a running executable.
- No conversion tool for an already published unmanaged `0.10.5` portable
  directory. The first end-user managed baseline is `1.0.0`.
- No general internet service, unbounded share/filesystem discovery, arbitrary executable path,
  package signing, certificate, or key-management system in `v0.10.6`.
- No silent update, silent installed-version deletion, or automatic rollback
  after a version has already reported ready.
- The internal `v0.10.6` proving slice has no launcher self-update. The first
  end-user `v1.0.0` package implements only the reviewed ADR 0056 Bootstrap,
  version-scoped launcher, protocol-1 fence, and exact rollback contract.
- No firmware or release-policy logic in Presentation.

Both the running desktop and the launcher consume the same Application policy
and Infrastructure adapters. The launcher entry point may select only the
activation/recovery use cases it needs; it does not acquire firmware execution
authority. The existing Bootstrap library remains composition-only. The
immutable `v1.0.0` Bootstrap executable owns only ADR 0056 launcher selection
and supervision; it has no firmware or Settings authority.

## Managed installation and local state

The managed root is resolved from the stable launcher and is not package
content identity:

```text
NvtFwCombiner/
├─ NvtFwCombiner.Bootstrap.exe       # immutable v1.0.0 trust anchor
├─ version-manager.seed.v1.json
├─ versions/
│  └─ 1.0.0/
│     ├─ <closed application payload>
│     └─ launcher/NvtFwCombiner.Launcher.exe
└─ .staging/<host-created transaction>/
```

Launcher state is stored separately under the existing per-user local
application-data root as `version-manager.v1.json`. It records schema version,
configured update source, active version, last-known-good version, installed
admission identities, pending activation/recovery journal, and whether a
post-update retention review is due. It also records exactly one normalized
managed-root identity. It records semantic version and content admissions,
never a source-folder name as trust identity.

For the first distributed `v1.0.0` managed baseline, accepted ADR 0053 adds
fixed-registry revision/digest and durable manual-pin state to this same file.
Legacy state with null registry state remains schema version 1 during ordinary
non-registry saves. The first successful manual pin, registry selection, or
Resume writes schema version 2 atomically; all later writes remain version 2.
Readers accept both. No sidecar or second writer exists, and internal `0.10.x`
reverse-read of version-2 state is not a distribution promise.

Update state must not be added to `preferences.v1.json` or
`report-history.v1.json`. Existing shell preferences and report history remain
cross-version compatible and unchanged by this feature. State writes are
atomic. Install and delete use one persisted prepared-mutation journal: intent
is durable before filesystem mutation, and admitted state is committed
afterward. On restart, an install journal commits only an exact healthy
self-admission or clears an absent target; a delete journal retries the exact
admitted delete and clears only after absence is observed. A save failure is a
typed `StateUnavailable` outcome and never permits an unjournaled process launch
or a second ambiguous mutation. Malformed state never guesses an active
version; the launcher performs a guarded inventory and exposes a recovery
diagnostic.

All state/filesystem/process writers share one cross-process lease scoped to the
normalized exact `version-manager.v1.json` path only. Managed root remains the
repository inventory authority but is not part of writer identity: different
managed roots sharing one state file contend, while different state files stay
independent. After lease acquisition, a missing durable root binding or a
binding different from the current normalized root fails closed before any
inventory, install, delete, activation, or launch action. Seed import, install,
delete, activation prepare/cancel, launcher
ready, rollback, and restart recovery acquire the lease before reading
authority, reload durable state while holding it, and retain it until the
complete transaction's terminal save. Desktop mutations fail immediately with
a typed unavailable outcome when contended; the stable launcher waits at most
five seconds and returns typed `Busy`. Normal process termination or forced
termination closes the OS handle, allowing a restart to acquire the same
identity without stale-lock cleanup.

All production starts share one process-local Platform gate; original READY, START, ADMITTED, and lifetime handles stay non-inheritable, while only short-lived duplicates cross an explicit `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`.
Launcher/Setup to Bootstrap gets START, ADMITTED, and Bootstrap lifetime; Bootstrap to Launcher gets READY and Launcher lifetime; Launcher to Desktop gets READY and Application lifetime; direct Bootstrap gets none.
Job, Setup marker, root/tree custody, writer lease, and ambient handles never cross. Child entry captures and clears the typed pipe before descendant start.
Any duplicate, environment, attribute-list, validation, or create failure closes temporary authority and fails closed without state or protocol change.

After the usable-main-window boundary, one Application startup coordinator
consumes the inherited one-use READY context and initializes the Version
experience exactly once. The adapter returns a typed outcome: no inheritance,
exact READY reported, invalid inherited context, or write failure. Only exact
expected-version inheritance whose READY write succeeds may wait up to five
seconds for the launcher to finish its ready commit and release the exact
state-path lease; after acquisition it reloads durable state. Missing, partial,
mismatched, malformed, unwritable, or unmanaged contexts initialize with zero
wait. Settings refresh and install/delete/source/activation mutations also keep
their existing zero-wait behavior. Presentation renders the returned snapshot
and cannot repeat READY classification or initial state loading.

The required filesystem recovery matrix is:

| Durable boundary | Required behavior after failure or restart |
| --- | --- |
| Prepared save fails | Do not call install/delete; report `StateUnavailable`. |
| Prepared install exists, target absent | Clear the journal; no admission is created. |
| Prepared install has exact healthy self-admission | Commit that exact admission. |
| Prepared install differs or is damaged | Keep the journal and expose recovery; never self-admit it. |
| Prepared delete still exists | Retry only the exact guarded admitted target. |
| Prepared delete is already absent, including an initial `NotInstalled` result after prepare | Commit deletion idempotently and remove the exact admission. |
| Repository failure and journal-clear save fails | Keep the prepared journal so the next start retries or clears from inventory facts. |
| Filesystem success and commit save fails | Keep the prepared journal and converge idempotently on the next start. |
| Complete inventory cannot be observed | Return typed `Unavailable`, publish no partial rows, start no process, and retain every prepared install/delete journal. |

The packaged seed is bootstrap input, not mutable runtime state. The launcher
may import `version-manager.seed.v1.json` only when the destination per-user
state is genuinely missing. Before import it requires the exact seed shape: one
installed admission, the same semantic version as both active and
last-known-good, no update source, no pending activation, failed activation, or
retention reminder, and a fully verified installed payload. Existing malformed,
unsupported, unreadable, or permission-denied state is never overwritten by the
seed. The seed template itself is unbound; after its one installed payload is
verified under the current root, the first destination write creates the exact
root binding. Missing legacy bindings and later root changes fail closed.
Relocation/adoption requires a future explicit verified transaction and is not
inferred by `v0.10.6`.

### Single-entry Launcher and first-install Setup

ADR 0062 adds one user-facing distribution Launcher without adding another
updater. Setup is a branch of that Launcher, while the immutable Root Bootstrap
and version-scoped Launcher retain their existing internal roles. One
Application coordinator owns the entry result:

- an exact healthy bound installation is handed to Root Bootstrap;
- genuinely missing state plus a genuinely absent root shows Setup; and
- damaged, moved, partial, foreign, busy, timed-out, or ambiguous facts return
  a typed non-Setup terminal result.

The owner-selected first-install rule treats the distribution Launcher as
delivery media rather than managed-installation provenance. Therefore a
remaining Launcher does not prevent `SetupRequired` when exact state, root,
transaction marker, and staging container are all absent. No provenance
sidecar, registry registration, parent-directory scan, or additional startup
I/O is permitted. The existing writer-lease recheck immediately before
materialization remains the concurrency and no-overwrite authority.

Normal entry classification is bounded local admission. Before state/root
observation, the same Application coordinator asks the sole embedded-payload
source to read at most 64 KiB plus one rejection byte from the strict descriptor
and compare only the embedded Bootstrap resource's existence and exact declared
length. The descriptor may declare 1 through 200,000,000 Bootstrap bytes. This
projection, strict state, and exact-root observation share one absolute 250 ms
health budget. Healthy entry and merely returning Setup read and hash zero
embedded Bootstrap content bytes; explicit Setup inspection/capture performs
the exact streaming hash and bounded custody. It then reads the exact root
binding, Active release manifest, and only the Root Bootstrap and version
Launcher that will execute. Each executable is hashed once through
a stable handle held through process start. It does not contact Registry,
SharePoint, `G:`, UNC, Catalog, packages, or release notes; scan all versions;
or run deep inventory/self-test. The 200,000,000-byte executable safety ceiling
is not a package-size optimization gate. Local state/exact-root classification targets
100 ms P95 and has a 250 ms hard cutoff; progress appears only after 250 ms.
Root Bootstrap handoff targets 300 ms P95, verified version Launcher start
targets 750 ms P95, writer contention waits at most 250 ms, and
the complete local admission deadline is two seconds: at most 1.5 seconds for
operation and at least 0.5 seconds reserved for whole-process-tree cleanup.
Cleanup shares the same absolute monotonic deadline. Timeout never becomes
`SetupRequired`; if termination cannot be proved, it becomes the typed
`TerminationUnconfirmed` outcome.

Local admission uses a fresh per-invocation outer Bootstrap Job under the
deterministic state-path prefix; the exact state-path writer lease remains the
serialization authority. A one-use parent-to-child `START` gate is required before Root
Bootstrap gains process/state-mutation authority, plus a separate one-use
`ADMITTED` receipt emitted only after the version Launcher starts. The complete
tree stays in one outer Bootstrap Job. After ADMITTED, READY and one possible
LKG rollback remain separate from health inspection: each attempt keeps the
existing 20-second limit, while the enclosing Bootstrap completion is capped
at 45 seconds, split into 44.5 seconds operation and 0.5 seconds cleanup, to
allow both attempts and bounded commit overhead. Successful READY returns
immediately rather than waiting for that cap.

Only `SetupRequired` may contact the existing Registry/Catalog/package owner.
Fresh admission selects the latest compatible completely verified candidate,
including one equal to the distribution Launcher version. Its immutable token
binds Registry replica/revision/digest, Catalog publication/digest, source root,
version, package path/size/SHA-256, release-manifest SHA-256, and entry identity.
The existing state-path writer lease fences one exact recheck before mutation;
changed source authority fails closed.

One sibling transaction marker binds measured distribution Launcher identity,
embedded descriptor and Bootstrap, exact state path/root, candidate, closed
owned paths, and phase. The root adapter copies the captured Launcher, writes
the descriptor-bound Bootstrap, delegates package installation to the existing
repository, and writes one canonical unbound Active=LKG seed through the shared
seed policy. It verifies the closed tree and atomically promotes into an absent
root. Setup never writes per-user version state, update source, or
`PendingActivation`.

After recording launch phase, Setup releases the writer and starts the exact
Root Bootstrap through stable custody. Bootstrap remains the only owner that
binds the seed, selects the version Launcher, and completes READY/LKG. A zero
exit plus exact bound-state reinspection permits deletion of the marker. A
later process never resumes or cleans surviving residue; it routes to
`RECOVERY-105-01`.

The final distribution Launcher and its embedded descriptor/Bootstrap are
bound afterward by a separate installer manifest, SBOM, provenance, and
checksum. Those files are release evidence only. The existing version ZIP and
five version assets remain unchanged and Bootstrap-free. Full local inventory
and network update checks begin only after Desktop READY. Setup is not delivered
until the v1.0.6 integrated Setup/recovery gate passes.

## Update catalog v1

The configured source contains exactly one root document named
`update-catalog.v1.json`. Discovery does not recursively scan the source. The
catalog has:

- `schemaVersion`: exact `1`;
- `product`: exact `NVT FW Combiner`;
- `runtimeIdentifier`: exact `win-x64`;
- `versions`: at most 128 entries, ordered for display only.

Each entry has a unique stable SemVer `version`, ISO-8601 UTC `publishedAt`,
bounded release-note text, and one safe relative `packagePath` plus exact
`packageSize`, lowercase SHA-256 `packageSha256`, and lowercase
`releaseManifestSha256`. Absolute paths, drive-qualified paths, traversal,
alternate data streams, empty segments, device names, and any resolved path
outside the selected source root are rejected. Reparse/link traversal is not
followed.

The raw catalog is limited to 1 MiB and each release-note value to 64 KiB UTF-8.
Catalog version/product/RID mismatch, duplicate SemVer, unsafe path, invalid
hash/length/date, unknown required field shape, or bound excess fails the whole
candidate catalog with `InvalidManifest`; no partial catalog is published.

The configured source folder is the administrative trust boundary. Moving the
complete catalog/package set to another local path, drive, or UNC share does
not change any package identity. After the user edits and confirms the new
source path, identical content verifies identically. `Verified` means catalog,
SHA-256, inner release manifest, and closed-package checks passed; it does not
mean publisher signature verification.

## Discovery and source editing

Accepted ADR 0053 is required for `v1.0.0`. Bootstrap injects the ordered fixed
production Registry locator set. An explicit option or environment override
continues to replace that set with one diagnostic local/UNC or HTTPS locator.
The production set is the versionless primary/backup pair
`G:\AUTO\projects\模組專案開發\NVT_FW_Combiner\update-source-registry.json`
and `G:\AUTO\Tool\NVT_FW_Combiner\update-source-registry.json`. These are
replicas of one logical Registry publication; they are not Catalog sources and
their contents are never merged. Runtime chooses the newest admissible replica
by its positive monotonic in-document publication revision, never by file time
or workstation clock. A same-revision content conflict fails closed. Resolution tries
its unique latest `catalogPath` followed by available `catalogPath` entries in
array order and never
automatically selects deprecated. Every candidate's complete catalog and
newest package are verified before selection and re-admitted under the existing
state-path writer lease before one atomic source/revision/digest commit.
Lower revisions, same-revision digest conflicts, changed authority, and every
failed candidate preserve prior durable state and installed inventory.
The candidate commit compares the complete ordered catalog publication,
including every non-newest entry and release note, and remains fenced by any
ADR 0056 pending launcher transaction even when the state-path OS lease is
temporarily free.

The Version environment self-test is a separate read-only use case. It reads
the same fixed registry and runs the same complete catalog/newest-package
admission for latest followed by every available entry, reports those bounded
attempts in order, and omits deprecated entries. Before and after candidate
inspection it reads the durable Registry authority without acquiring its writer
and applies the same revision/digest anti-rollback check as normal Check. A
concurrent Check that advances authority therefore makes the older in-flight
Self-test fail as `RevisionRollback` rather than report a stale success. It
never calls source Check, advances prompt generation, acquires the state writer,
changes the current snapshot, persists selection, installs, or deletes; caller
cancellation is propagated without partial publication.
For HTTPS, bounded redirect, timeout, and body limits apply. An HTTP 200 login
page is `AuthenticationRequired`; Self-test succeeds only after strict JSON,
schema, candidate catalog, and newest-package verification.
For the production filesystem pair, both replica reads start concurrently and
each has a 45-second user-visible deadline. Self-test reports the ordered
Primary/Backup issue and revision even when one valid replica permits Catalog
admission, so a stale or unavailable backup remains visible for repair. Each
replica is single-flight: repeated or concurrent checks cannot accumulate more
than one blocked physical read for that replica, and a late result after the
deadline is discarded.
The fixed production locator set is compiled into Bootstrap and therefore belongs
to package identity; changing it requires a rebuilt package. The deployed
Registry filename is permanently `update-source-registry.json`; wire schema,
Registry publication revision, and latest application release version remain
distinct in-document values. The Registry's `catalogPublication` contains only
the selected Catalog's asserted `latestVersion`, `catalogSchemaVersion`, and
exact-byte `catalogSha256`. All three must match the admitted Catalog or the
Registry publication fails without state mutation. The complete version list,
package paths/hashes, release notes, and minimum-supported-version policy remain
outside the Registry and under their existing Catalog/Application owners.
`publishedAtUtc` is informational audit metadata and cannot order replicas.
Runtime overrides
and the live Registry JSON remain external and do not change package identity.

- The main window becomes usable before discovery starts.
- One background discovery begins after the usable main window. It cannot fail
  or delay normal startup.
- Discovery is single-flight and generation-keyed. Confirming a new path or
  pressing Check now cancels/supersedes the prior request; stale callbacks
  cannot replace current state.
- The source field is read-only by default. Its leading fixed segment owns the
  current status icon and its trailing action owns Edit.
- Edit creates a draft. Browse changes only the draft. Confirm atomically saves
  the path as a durable manual pin and starts one new discovery; Cancel restores
  the committed path and performs no load. Explicit Resume clears the pin only
  as part of a successful registry candidate commit; failure preserves pin and
  source.
- Checking shows a rotating progress ring in the leading segment. Reduced
  motion uses a non-rotating determinate/indeterminate status treatment without
  changing work.
- Offline, missing, permission-denied, malformed, and unverified states remain
  visible on Version through localized tooltip/accessibility text but never
  open an interrupting startup dialog.
- Background discovery fully verifies only the newest newer candidate needed
  for an automatic prompt. Other catalog rows remain Available until an install
  action performs their complete verification.

## Package admission and installation

The existing stable release-package identity remains the application payload.
Until reviewed package-size reduction replaces it, a catalog package ZIP is
limited by the temporary inclusive 134,217,728-byte compressed ceiling from
ADR 0060. Version 1.0.2 is a one-time fresh/manual installation and does not
claim managed auto-upgrade from immutable 1.0.0 or 1.0.1. Before visible
mutation, Infrastructure:

1. obtains one stable file handle and verifies admitted length and SHA-256;
2. extracts into a host-created sibling staging directory without following or
   creating escaping paths, links, reparse points, or alternate streams;
3. limits verification and extraction to 4,096 entries and 512 MiB total actual
   decompressed bytes through one shared per-pass counter; ZIP length metadata
   is an early rejection hint, not the byte-limit authority; each nonnegative
   declared entry length is compared to the remaining budget before addition,
   so ZIP64 metadata cannot overflow or escape the typed `UnsafeArchive` result;
4. requires one expected package root, the exact inner
   `RELEASE-MANIFEST.json` hash, the canonical release-manifest schema,
   matching product/version/RID, every declared file length/hash/role, the
   production package paths, and no undeclared files; the unique auxiliary
   `SHA256SUMS.txt` must exactly hash every declared file plus the manifest;
5. rechecks the staged closed payload before promotion; and
6. atomically renames the complete staging directory to `versions/<version>`
   on the same volume.

The production release packager must evaluate the manifest it actually writes
against `docs/contracts/release-manifest-v1.schema.json` immediately after
generation and again after the final closed-allowlist comparison, before ZIP
creation. A synthetic DTO or separate test manifest is not a substitute for
this production-path validation.

An already installed identical version is idempotent success. The same SemVer
with different admitted identity fails closed and requires explicit removal of
the non-active installed version before reinstall. Cancellation, disk-full,
permission, unstable-read, malformed ZIP, path escape, manifest/hash mismatch,
collision, or promotion failure removes only the host-created staging directory
and leaves active/installed state unchanged.

## Activation, switching, readiness, and rollback

Install does not overwrite the running process. After package admission and
Update/Switch consent:

1. Application records one `Requested` pending activation containing candidate
   identity and previous active/last-known-good identities.
2. The desktop completes existing persistence/shutdown gates and hands control
   to the stable launcher.
3. The launcher re-verifies the selected installed payload, persists
   `CandidateLaunchRecorded`, and only then starts the candidate.
4. The launcher starts its executable with an inherited, one-use ready channel
   and a bounded deadline; credentials are not exposed in ordinary command-line
   arguments or logs.
5. The app reports ready only after the usable main window and required local
   startup state are available.
6. Ready commits active and last-known-good state, clears the recovery journal,
   and lets the launcher exit.

If the process cannot start, exits before ready, fails integrity, or misses the
deadline, the launcher persists `RollbackLaunchRecorded` before starting the
preceding last-known-good version. Restart from `CandidateLaunchRecorded` never
starts the uncertain candidate again and advances to that exact fallback.
Restart from `RollbackLaunchRecorded` may retry only the same fallback until its
ready or terminal outcome is durably committed; a power cut between process
start and state commit cannot provide exactly-once process-start semantics. The
failed candidate becomes Damaged/FailedActivation
and is not switchable until repaired or reinstalled. If no valid
last-known-good version remains, the launcher exposes a bounded recovery error
and performs no arbitrary directory launch.

Once a version reports ready, later runtime crashes do not cause automatic
rollback. The user may switch explicitly from Version. Every launch and switch
re-verifies the target payload.

## Installed inventory, retention reminder, and deletion

Opening/refreshing Version and every switch attempt inventory managed version
directories. File missing/change, unsafe/unexpected path, unreadable content,
manifest mismatch, or SHA mismatch marks that version `Damaged`. Damaged
versions are never launchable or switchable.

`Damaged` requires a complete root inventory and evidence about one version.
When I/O, permission, or directory-enumeration races prevent a complete root
observation, the repository instead returns a whole-inventory `Unavailable`
result with no partial rows. The Version snapshot exposes that issue separately
from durable-state load and source connectivity. Launcher, seed bootstrap,
install, delete, activation, and recovery fail closed; no process starts and no
prepared mutation journal is cleared until a later complete inventory read.

Inventory separately reports directories that are not present in committed
admission state. An exact healthy self-admission may reconcile only a matching
prepared install; every other unknown directory remains `Unadmitted`, is shown
as recovery-required, and is neither counted as installed nor offered ordinary
Switch/Delete actions.

The Version page reports healthy and damaged admitted counts plus any recovery
count. Every non-active admitted installed row exposes the destructive trash
icon. The active row has no enabled delete
action. Delete requires a confirmation naming the exact version; deleting an
application or launcher last-known-good owner adds a rollback-loss warning.
The exact launcher fallback is retired durably before its owner directory is
prepared for deletion. An active or pending launcher owner remains blocked.
Invalid or unavailable launcher state fails closed. Infrastructure
resolves the exact child beneath the managed versions root and rejects root,
outside-root, traversal, link/reparse, and active targets before mutation.

Three healthy installed versions is the default soft reminder threshold. After
a successful update makes the healthy count exceed three, the new app prompts
the user to review individually selected non-active versions. Keep all is
valid. No installed version is automatically deleted. Damaged versions do not
count toward the healthy reminder. Failed/cancelled staging is always cleaned
automatically because it was never an installed version.

## Update prompt and Version-page UI

Only a newer, fully verified catalog package may trigger one automatic update
confirmation per app session. The confirmation names the version, presents
release notes, and offers Update or Later. Later suppresses automatic prompts
for that session but does not disable Check now. Install never starts without
Update consent. Older catalog versions remain manually installable/switchable
when their package verifies; they never trigger the newer-version prompt.

Settings follows the approved visual reference:

- shared left rail: General, Appearance, Version, Support Matrix;

- shared typography, spacing, 2 px borders, modern non-growing scrollbars,

  Edit/Confirm/Cancel behavior;
- current-version state, verified update banner, available/installed table,

- no status meaning through color alone. Every icon/action has localized

- modal focus trap, Escape/upper-right close, focus restoration, reduced motion,
  and background status announcements remain deterministic.

## Functional failure requirements

- Source failure keeps the app usable and the last installed inventory visible;
  it never converts stale data into a new verified success.
- A newer check supersedes an older one. Cancellation consumes its generation
  and publishes no partial catalog/package state.
- No package is shown Verified before its complete required verification.
- No partial installed directory or active-pointer change survives failed
  admission.
- No delete path is derived from UI text or catalog path. It comes from the
  launcher-owned admitted inventory and is revalidated at mutation time.
- No active, outside-root, root, link/reparse-escaped, or unknown directory is
  deletable.
- Process/ready failure performs at most one automatic last-known-good rollback
  attempt; it cannot oscillate indefinitely.
- Background dialogs are session-bounded. Update, retention, and destructive
  confirmations never stack or appear over an existing blocking modal.
- Every user-visible failure uses a stable typed issue and localized actionable
  projection. Logs omit firmware paths/content, credentials, and handshake
  material.

  `G:\AUTO\projects\模組專案開發\NVT_FW_Combiner`, with its catalog at the root

## Testing and evidence plan

### Contract and Application

- Catalog schema: exact/min/max, duplicate version, invalid SemVer/date/hash,
  wrong product/RID/schema, unknown/unsafe/escaping path, entry/note/catalog
  bounds, and deterministic ordering.
- State machine: generation supersession, background/manual checks, no prompt
  before verification, once-per-session prompt, Later, install consent,
  idempotence, identity conflict, pending activation, ready commit, rollback,
  and stable issue codes.
- Inventory/retention/delete policy: active guard, LKG warning, healthy/damaged
  counts, soft threshold three, Keep all, and no automatic installed deletion.

### Infrastructure and launcher

- Stable reads and content identity after moving an identical source tree.
- ZIP-slip, absolute/device/ADS paths, reparse/link escape, file/count/expanded
  bounds, duplicate entries, growth/truncation, malformed archive, inner
  manifest/hash/role/extra-file mismatch, disk/permission failure, cancellation,
  collision, staging cleanup, and atomic promotion.
- Forged underreported ZIP entries must fail through both the real Verify and
  Install adapter paths without a target or residual staging tree. Installed
  inventory must fail closed when the aggregate of actual manifest, checksum,
  and payload bytes crosses the same 512 MiB production ceiling.
- A real two-entry ZIP64 fixture whose second declared expanded length is
  `long.MaxValue` must make both Verify and Install return `UnsafeArchive`
  without an arithmetic exception, target, or residual staging transaction.
- Installed tamper/missing/extra/unreadable detection and guarded delete,
  including idempotent convergence when a prepared delete target is already
  absent.
- Whole-inventory enumeration I/O, permission, and disappearing-directory
  races return `Unavailable` without partial rows; launcher starts zero
  processes, seed import returns `StateUnavailable`, startup remains typed, and
  prepared install/delete journals survive until a complete retry.
