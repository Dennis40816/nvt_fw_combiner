# 0.10.x Legacy Architecture Retirement

Status: LAR-01..12 implemented; LAR-00 terminal verification and release gates pending
Decision date: 2026-08-09
Stable predecessor: PR #352 / `6ba7217299c3e2ddb1c38467e6f288d5710ffef1`

## Problem and intended outcome

The headless canonical foundation is complete, but production still routes
through migration-era Workbench models and large Bootstrap authoring,
inspection, planning, memory, naming, execution, report, and catalog owners.
UI and CLI can therefore reach duplicated projections or recompute accepted
facts after the canonical Application boundary. The intermediate architecture
also keeps Bootstrap as a semantic layer and inflates production size even
though Domain, Profiles, and Application already own most canonical behavior.

The intended outcome is one authoritative production route for every module.
Application owns use cases and immutable lifecycle results; Profiles owns
profile semantics and compilation; Infrastructure owns trust and platform/tool
adapters; Presentation and CLI consume the same typed use cases; Bootstrap is
only the composition root. All production `Workbench*` symbols and equivalent
renamed facades are removed while UI behavior, durable external contracts, and
every existing BIN golden remain unchanged.

## User stories

1. As a desktop operator, I can switch among all six workflows and retain one
   isolated session per workflow without stale selections or derived results
   crossing modes.
2. As either a UI or CLI user, I receive the same route, slot readiness,
   automatic filename, Preview/Build decision, output bytes, issues, and typed
   report for the same accepted inputs.
3. As an operator, I see memory regions, required slots, warnings, and blockers
   derived from the exact compiled composition rather than UI or Bootstrap
   heuristics.
4. As a Build user, Preview and Build reuse the same accepted session,
   inspection, naming admission, capability fingerprint, compilation
   fingerprint, and Preview token, and stale state fails closed.
5. As an AB user, an optional additional delivery is extracted from the
   completed immutable primary output under the compiled range/naming policy
   without a second composition run.
6. As a maintainer, I can reload one trusted catalog publication and know that
   UI, CLI, inspection, readiness, execution, and reporting consume the same
   `ResolutionToken` and exact capability instance.
7. As a firmware owner, I can compare every pre- and post-retirement golden and
   observe identical complete BIN bytes, hashes, naming tokens, mutation trace,
   and external-processor outcome.

## Scope

- Retire the migration-era Application, Bootstrap, CLI, and Presentation
  Workbench contract graph.
- Converge catalog publication, authoring mutation, inspection, readiness,
  memory projection, output naming, Preview/Build, reporting, delivery, and
  external processor dispatch onto their named canonical owners.
- Migrate desktop and CLI live callers in vertical, dependency-ordered,
  net-negative slices.
- Move CLI-owned parsing and rendering from Bootstrap to the CLI assembly and
  remove Presentation's Bootstrap dependency.
- Remove accidental-public CLR migration APIs without compatibility shims.
- Add architecture/call-graph guards for zero legacy symbols and zero renamed
  parallel semantic owners.
- Lower runtime, slice, and full-production measurements with exact accounting.

## Non-goals

- No UI redesign, workflow change, new option, new IC support, support
  promotion, or firmware semantic change. `v0.10.3` publication is a terminal
  LAR-00 operation only after owner review, merge, CI, package, provenance, and
  clean-Windows evidence pass; it is never part of an implementation slice.
- No change to firmware-family/map facts, Saved Rule/report wire compatibility,
  CLI observable behavior, user settings/files, or external processor protocol.
  A minimum versioned composition-profile/compiled-contract extension is in
  scope only where the canonical owner lacks a typed representation required to
  delete the old path—for example the existing optional A FlashCode delivery
  kind/range/naming declaration. It cannot change route admission, source or
  target ranges, output bytes, naming tokens, or processor behavior.
- No removal of a required legacy Combiner.exe protocol adapter merely because
  its name contains `Legacy`.
- No replacement broad facade, service locator, compatibility hierarchy,
  fallback route, or indefinite forwarding adapter.
- No code-size reduction by relocation, excluded paths, tests, generated code,
  documentation removal, line compaction, or weakening evidence.
- No attempt to reduce the complete runtime to 25,000 lines; the size
  assessment is descriptive, not an architecture cap.

## Canonical owners and affected layers

| Responsibility | Canonical owner | Retirement effect |
| --- | --- | --- |
| Bundle loading, schema/hash/trust | Infrastructure adapter | Remove Bootstrap materialization and fallback lookup. |
| Profile normalization, map selection, compilation, processor plan | Profiles | Remove runtime/Bootstrap plan reconstruction. |
| Catalog publication, reload, cache, fixed/dynamic resolution | Application `CanonicalCapabilityCatalog` | Remove migration source, projection, route caches, and Bootstrap resolution. |
| Session mutation and revision | `AuthoringSessionState` + `CompiledAuthoringWorkflowService` | Remove workflow planning/session adapters and grouping-only session wrappers. |
| Per-slot inspection and readiness | Canonical Application inspection publication | Remove path-backed inspection and repeated metadata/readiness evaluation. |
| Memory/slot semantics | Application `MemoryLayoutProjector` | Remove Bootstrap memory and slot projections. |
| Output naming | `CompositionRunService.ResolveOutputNameAsync` + `CompiledOutputNameResolver` | Remove client/Bootstrap auto-name preflight and path-backed naming. |
| Preview and Build | Shared Application execution port + `CompositionRunService` | Remove workflow-specific runners and result conversion. |
| Run result and report | `CompositionRunResult` + typed `CompositionRunReport` | Remove `WorkbenchRunResult` and in-process JSON transport. |
| Additional delivery | Compiled delivery declaration + Application Build stage | Remove AB-specific planning/export services. |
| External processor dispatch | Compiled processor plan + `IExternalProcessor` + router | Remove runtime postbuild planner and fallback; retain distinct required protocol adapters. |
| UI display and interaction | Presentation-local ViewModels | Remove Bootstrap dependency and semantic calculations. |
| CLI parsing/rendering | CLI assembly | Relocate client duties without claiming deletion. |
| Object construction/lifetime | Bootstrap | Reduce to wiring, lifetime/disposal, and platform adapter selection. |

The change affects all six workflows: Standard Merge, AB Merge, General Merge,
DP Replace, CtrlRAM Replace, and General Replace. It does not change any
workflow's supported IC, IC Count, topology, profile, processor, or evidence
classification.

## Functional requirements

1. Production Application, Bootstrap, CLI, and Presentation contain zero
   `Workbench*` symbols at terminal completion.
2. Zero-name evidence is paired with dependency and semantic-owner guards so
   the retired graph cannot be recreated under a new name.
3. Desktop owns six isolated `AuthoringSessionState` instances; CLI creates an
   ephemeral session per invocation.
4. One accepted mutation advances `AuthoringRevision` once and invalidates all
   downstream derived publications atomically.
5. One canonical inspection publication is bound to exact artifact identities,
   catalog token, typed draft, capability fingerprint, and compilation
   fingerprint for an authoring revision.
6. Naming, memory, readiness, Preview, and Build consume that publication and
   cannot reopen paths or reconstruct facts.
7. UI and CLI call the same typed Preview and Build operations. Firmware
   semantic options are accepted into the session/compiled plan before that
   boundary; host output destinations remain typed Build intent.
8. Preview publishes the typed output-name result and admission identity; Build
   reuses it and rejects stale identities rather than recalculating.
9. A disabled action returns typed readiness only. A diagnostic-plan-only
   Preview returns a typed diagnostic/report outcome and is never represented
   as a fabricated execution result.
10. Additional artifacts use compiled kind/range/naming declarations and the
    completed primary output bytes. No input reopen, recompilation, or processor
    rerun is permitted.
11. Application returns typed result/report data to both clients. JSON is
    emitted once only for an explicitly requested external report artifact.
12. A compiled processor operation selects exactly one protocol adapter through
    the router. Shared host staging/process/diff/range/assertion/cleanup/audit
    behavior has one implementation.
13. Bootstrap exports no callable workflow method, semantic DTO, cache, service
    locator, or policy-bearing adapter.

## Failure requirements

- A changed publication, capability, compilation, draft, revision, artifact
  identity, naming admission, or Preview token fails closed before Build.
- Missing, ambiguous, unsupported, contract-only, or evidence-incomplete routes
  retain their existing typed availability/publication/evidence distinctions.
- Failed catalog reload retains the last known good publication; a cold start
  without a valid publication disables Build.
- Missing required inspection or runtime dependency yields typed readiness and
  cannot trigger an alternate inspection or execution route.
- External processor resolution is exact; a missing/mismatched adapter or tool
  fails without fallback. Writes outside declared ranges remain rejected.
- Primary and optional delivery failures remain distinguishable and preserve
  the existing atomicity and operator-safe diagnostics.
- Any unexplained golden byte, hash, naming, mutation, processor, or report
  difference stops the retirement slice.

## Compatibility, firmware, support, security, and release impact

- Accidental-public Workbench/Bootstrap CLR APIs are removed without obsolete
  wrappers or type forwarding. An evidenced external consumer requires separate
  owner review.
- CLI commands/options/exit behavior/text, Saved Rule/report JSON schemas,
  existing profile/family document versions, external processor protocols, and
  user files/settings remain compatible. A new versioned composition-profile
  field is accepted only when required to express an already-executed behavior
  canonically; older persisted documents retain their declared compatibility
  policy and are never silently reinterpreted.
- Firmware maps, regions, half-open ranges, initialization, operation order,
  processor authority, padding, headers, CRC, hashes, and naming semantics are
  unchanged.
- Support/evidence/publication status is unchanged; this work cannot promote an
  IC, workflow, count, topology, or evidence class.
- Staging remains host-created, bounded, independently diffed, cleaned, and
  protected from arbitrary executable paths or undeclared writes.
- PR #352 remains the stable predecessor. The original draft authorized no
  merge, tag, release, package, or `main` mutation. The owner's subsequent
  2026-08-10 instruction authorizes the normal reviewed branch/PR/merge/release
  sequence for `v0.10.3`; it does not waive any release gate.

## Testing and evidence plan

Each vertical slice records the frozen base, exact live callers, gross removal,
required additions by owner, relocation, runtime/full net delta, lowered
ratchets, and residuals.

Required stable seams include:

- catalog cold-load/reload/last-known-good, fixed/dynamic route, exact-reference,
  token, capability-fingerprint, and compilation-fingerprint tests;
- six-workflow session isolation, one-edit/one-revision, invalidation, stale
  publication, slot lifecycle, and readiness tests;
- canonical inspection exact/short/warning/blocking, metadata dependency,
  reinspection, and immutable artifact identity tests;
- memory range/coverage/slot parity and output-naming token/admission parity;
- Preview-to-Build token/name/input parity, typed blocked/diagnostic outcomes,
  report/delivery behavior, and CLI/UI observable parity;
- processor router exact selection, staging, argv, mutation-range, assertion,
  cleanup, cancellation, and no-fallback tests;
- architecture guards for Presentation-to-Bootstrap absence, Bootstrap
  wiring-only shape, zero `Workbench*`, zero legacy callers, and zero renamed
  parallel owners;
- every available repository or owner-approved BIN golden, comparing full
  bytes, size, SHA-256, naming tokens, mutations, and processor outcomes to
  baseline `6ba7217299c3e2ddb1c38467e6f288d5710ffef1`;
- proportional scoped Polytail/R2 review for each slice and
  `python scripts/verify.py --all` on the terminal frozen diff.

Expected output/golden files cannot be edited to make the retirement pass.

## Size and completion accounting

The exact baseline and terminal implementation ledger are maintained in
[`0.10.x-legacy-architecture-retirement-size-assessment.md`](../governance/0.10.x-legacy-architecture-retirement-size-assessment.md).
The frozen direct legacy surface was 14,543 nonblank lines, but it was gross
retirement surface rather than promised net savings. The terminal
implementation is 67,433 runtime and 96,044 full-production nonblank lines,
respectively 1,334 and 1,454 below the predecessor. The former 7,800–10,200
planning estimate is superseded by that exact evidence; it overestimated how
much unique trust, route, admission, report, delivery, and processor behavior
could be deleted rather than relocated to its canonical owner.

A mergeable vertical slice must add only its minimum canonical contract,
migrate every named live caller, delete the displaced owner/forwarder, lower
ratchets in the same commit, and be net-negative for runtime and full
production. Temporary dual paths may exist only in unmerged intermediate
commits. A non-proportionate or non-negative candidate stops, records a
line-addressed residual, and yields to the next slice.

## Document consistency and supersession

This draft and its accepted decisions amend current authority without rewriting
historical evidence:

- `SPEC.md` and ADR 0015 own the terminal one-path, zero-Workbench architecture
  and full-byte golden invariant.
- ADR 0027 retains its performance/replay/evidence decisions, while its
  `WorkbenchRunResult` positional-ABI requirement is superseded.
- ADR 0040 retains exact metadata references and prerequisites, while its
  temporary Workbench inspection adapter allowance is superseded.
- ADR 0047 retains General admission/occupancy policy, while its shared client
  seam becomes direct typed Application consumption.
- `composition-report-v1` remains the durable external wire contract;
  `CompositionRunReport` is the typed Application projection rather than a
  Workbench transport.
- The #233/PR #352 ledger remains a frozen verified checkpoint. Its STOP rows
  are inputs to this new program, not failures to rewrite that historical PR.
- The approved LAR planning graph extends the existing numbered issue graph.
  Live GitHub state and its progress denominator remain unchanged until issue
  publication is explicitly authorized and the planning ids are mapped.
- Dated release notes, old measurements, historical roadmaps, test evidence,
  and migration records may retain Workbench terminology when they clearly
  describe the retired architecture. Current UI terminology uses workspace or
  memory-layout language.

No production status matrix, golden expectation, profile/schema, support, or
evidence class is changed by this retirement. Historical draft text remains
evidence of the earlier no-release boundary; LAR-00 now owns the CHANGELOG,
issue/PR state, package, and tag only after the terminal gates pass.
