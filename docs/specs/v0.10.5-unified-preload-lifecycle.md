# v0.10.5 Unified Preload Lifecycle

Status: Owner-approved specification and implementation intake
Decision date: 2026-08-13
Stable predecessor: `v0.10.4` / `8c3cc51dc95cea2fbae8ec5ac0287db730d1b37b`
Architecture authority: [ADR 0049](../adr/0049-unified-preload-lifecycle.md)

## Problem and intended outcome

The canonical firmware architecture has one execution path, but startup and
background preparation still use several unrelated cancellation flags,
generations, progress surfaces, caches, and failure policies. Catalog loading is
observable and retryable, while report/history restore, diagnostics refresh,
deferred view warm-up, selected-file inspection, and external-tool discovery
are only partly cancellable or invisible. One failure can suppress later
optional work, and some obsolete work continues after its result becomes stale.

`v0.10.5` makes every actual preload and named preparation path observable,
cancellable, bounded, and user-controllable without creating one untyped
semantic service. Presentation owns lifecycle only; the existing typed catalog,
report, inspection, diagnostics, and external-runtime owners remain final.
There is one production execution path for each operation and no indefinite
compatibility wrapper.

## Necessary user stories

1. As an operator, I can see the current startup/preparation stage, exact stage
   count, and truthful numeric progress instead of an unexplained spinner.
2. As an operator, I can retry a required failure, retry or skip an optional
   failure, and cancel remaining optional preload without canceling a Build.
3. As an operator, I can begin using the shell immediately after canonical
   catalog publication while history, diagnostics, and view warm-up continue
   safely in the background.
4. As an operator selecting firmware, I can replace or cancel a selection and
   know obsolete inspection work cannot publish or retain an unbounded cache.
5. As an operator using external tools, I can observe and explicitly refresh
   the reviewed tool environment without launching a processor or changing a
   run already holding a generation lease.
6. As a maintainer, I can trace each work item to one typed semantic owner and
   one lifecycle generation, with deterministic bounds and no parallel fallback.
7. As a firmware/release reviewer, I can compare all Golden outputs and report,
   CLI, package, and startup evidence and observe no semantic change.

## Scope

- One Presentation shell preload session for catalog, startup report/history,
  startup diagnostics, and deferred shell/view work.
- Required-versus-optional stage policy, closed ordering, concurrency budget,
  generation, linked cancellation, bounded close drain, retry, skip, and cancel.
- Reuse and extend `ForegroundLoadingState`; no second loading state model.
- One bounded cancellable report/history filesystem reader shared by startup and
  manual report load, retaining report parser/projection ownership.
- One Infrastructure external-tool environment loader with observable discovery
  and an explicit refresh path; Bootstrap retains composition and generation
  lease wiring only.
- One cancellable, observable selected-file inspection lifecycle per canonical
  workflow session, with coherent adapter-owned content identity and bounded
  cache behavior.
- Characterization, architecture, accessibility, performance, allocation,
  exact work-count, code-size, verifier, and Golden evidence.
- Deletion of displaced catalog-specific startup fields/coordinator, duplicate
  readers, Presentation filesystem probing/cache ownership, Bootstrap manifest
  parsing, and unused refresh seams after caller migration.

## Explicit non-goals

- No firmware range, operation, padding, CRC/header, external mutation, output
  naming, report wire, profile/schema, support, evidence, or availability change.
- No new IC, workflow, external tool, manifest format, network source, updater,
  persistence format, or support promotion.
- No global service locator, plugin stage registry, untyped result envelope,
  duration-prediction engine, timer-smoothed percentage, or second verifier.
- No preload execution of external tools and no early Preview/Build.
- No movement of first-frame preferences behind the loading surface.
- No inclusion of composition-run progress, CtrlRAM run metadata, or arbitrary
  demand-driven computations in the shell preload plan.
- No UI redesign beyond the loading/status/actions and accessibility changes
  required by this lifecycle.

## Canonical owners and affected layers

| Responsibility | Canonical owner | v0.10.5 effect |
| --- | --- | --- |
| Capability materialization/publication/LKG | Application catalog | Existing typed stream becomes required startup stage |
| Shell stage scheduling/control/presentation | Presentation preload session | New sole lifecycle owner; no feature semantics |
| Report JSON/history interpretation | Report Presentation model | Consume one bounded cancellable filesystem source |
| Filesystem reads and coherent identity | Infrastructure adapters | Own bounds, cancellation, content identity, stability |
| Selected-file readiness/metadata/inspection | Application authoring/inspection | Typed single-flight stream; no UI semantic cache |
| External manifest trust/environment generation | Infrastructure external-runtime adapter | Observable load/refresh; no executable launch |
| System information snapshot | Application diagnostics port | Optional startup stage; typed result unchanged |
| View materialization/focus/accessibility | Presentation | Optional serial UI stage |
| Dependency construction | Bootstrap | Wire typed ports/lifetimes only |

Domain and Profiles are behaviorally unaffected. CLI retains the same catalog,
inspection, readiness, Preview/Build, and report behavior; it does not consume
Presentation lifecycle state.

## Functional requirements

1. There is exactly one active shell preload generation. Starting a replacement
   or closing the window cancels the prior generation, and stale updates cannot
   mutate state or publish a feature result. The shell attempt generation is
   allocated when the attempt begins and is never reused. Report projection and
   inspection selection generations follow the same request-identity rule.
   External-environment load requests also allocate a never-reused request
   generation. Catalog and external-environment publication generations instead
   increment only when their typed owner atomically commits a validated candidate.
2. The catalog is the sole required startup stage and runs alone. Workflow
   selection stays disabled until its typed successful publication is applied.
3. After catalog success the shell is enabled. Optional stages use at most two
   non-UI workers; UI materialization remains serial at background dispatcher
   priority and yields to active operator work.
4. The admitted stage plan is closed and deterministic. It includes only stages
   applicable to current launch options and configured adapters.
   Post-catalog ordering is: apply the launch page; restore history before an
   explicit startup report; apply `--open-report` after that report chain.
   Diagnostics may run beside the report chain. Deferred views may run beside
   non-UI work but remain internally serial. External discovery is admitted only
   when the reviewed tools root exists.
5. Each stage exposes stable identity, localized title/detail, required/optional
   class, state, completed/total work when known, and exactly one terminal
   outcome through one immutable observable stage collection. Semantic result
   data remains in its typed owner.
6. The UI shows current stage and `index / admitted count`. A determinate stage
   shows a monotonic numeric percentage; an unknowable denominator is visibly
   indeterminate. Percentage is local to the named stage and represents work
   completion, not elapsed-time prediction. Heterogeneous stage units are not
   summed into an aggregate percentage. During optional concurrency, the compact
   summary selects the earliest incomplete stage in plan order and an expanded
   status view exposes every admitted stage and per-stage action.
7. Required failure blocks and offers Retry plus Cancel startup/exit. Optional
   failure records its typed diagnostic and permits Retry, Skip, or Continue.
   Cancel remaining optional work leaves completed results intact.
8. Optional-stage failure or skip cannot prevent independent later stages.
   Dependency successors do not run after a skipped prerequisite unless their
   typed owner declares that prerequisite optional.
9. Startup report-history restore, explicit startup report, and manual report
   picker share one bounded streaming read and the existing report parser.
   User-selected storage-provider inputs and `--load-report` paths remain valid
   outside application-managed roots. Each standalone raw report input is
   limited to 10 MiB (`10,485,760` bytes); the bound is checked before and
   during the read and cancellation is cooperative. An oversize input produces
   the typed report-input `TooLarge` failure on the existing report diagnostic
   surface and cannot parse, publish, or enter history. The default
   `System.Text.Json` encoder can expand a raw `<` byte to the six-byte `\u003C`
   escape. The 10 MiB ceiling reserves 60 MiB for that worst case and 4 MiB for
   the v1 envelope, maximum platform paths, and required entry fields. The
   history writer therefore guarantees that one maximum-size imported report
   can round-trip within the separate 64 MiB persisted-history-file bound by
   evicting older retained entries when the complete encoded history requires
   that space.
10. Report history keeps schema v1, its separate 64 MiB persisted-file admission,
    12 entries, ordering, metadata, and latest-generation publication. The
    16 MiB retained-payload limit is a soft budget: the newest valid entry is
    retained even when it alone exceeds 16 MiB, and only older entries are
    evicted to approach the budget. The 64 MiB complete encoded-envelope limit
    is independently hard. Before atomic save, the writer serializes and checks
    the complete v1 history. If it is too large, every retained entry whose UI
    summary is derivable from `ReportJson` uses the existing schema-v1 empty-
    metadata representation, and reload rematerializes the same summaries. If
    the envelope is still too large, the writer evicts oldest entries one at a
    time from the retained history and rechecks the complete serialization until
    it fits. It never evicts the newest report for either bound. If that newest
    in-process generated report still cannot fit the 64 MiB envelope by itself
    after the metadata fallback, persistence returns typed
    `EntryTooLargeToPersist`, leaves the previous persisted file intact, and
    keeps the report available for the current session.
11. External preload enumerates only the reviewed tools root in deterministic
    normalized-path order and never follows a reparse-point directory or accepts
    a candidate outside that root. One load visits at most 4,096 filesystem
    entries at depth 16, admits at most 256 manifests, reads at most 1 MiB
    (`1,048,576` bytes) per manifest and 16 MiB (`16,777,216` bytes) total, then
    validates schema, package identity, and trust before publishing one immutable
    generation. A bound violation is one typed load failure and publishes no
    candidate. Preload never starts an executable or stages firmware.
12. Explicit external refresh creates a new generation for future acquisitions;
    existing run leases remain coherent and stale-generation checks remain.
    The refresh generation increments only after the complete candidate commits;
    failure or cancellation retains the prior generation for future acquisitions.
    Startup discovery and explicit refresh are single-flight and ordered by an
    external request generation. A newer request cancels and supersedes the
    older request, waits for its drain, then materializes; commit also requires
    that request generation still be current, so an older load cannot publish
    after a newer refresh was admitted.
13. Selected-file inspection is per workflow session and single-flight. A new
    selection cancels obsolete work; terminal publication still requires exact
    authoring revision, resolution/compilation identity, file content identity,
    and current generation.
14. Infrastructure returns coherent bytes/content identity/stability from one
    read boundary. Presentation no longer performs before/after filesystem
    identity probing or owns a parallel semantic inspection cache.
15. Any retained compiled-artifact classification cache is bounded, clearable,
    and keyed by full canonical publication/capability identity; otherwise it is
    deleted and recomputed canonically.
16. Batch inspection dispatches only the typed authoring strategies required by
    the workflow roles declared on its inputs. It preserves one distinct-path
    read cache, input/result order, health, metadata, diagnostic order, and
    cache-off parity. Applicability is never inferred from filenames, bytes, or
    IC identity.
17. Shell preferences remain bounded and loaded before first-window creation so
    language, theme, and reduced motion are correct on the first frame. They
    contribute trace evidence only, not shell preload percentage.
18. Closing cancels active preload and waits at most five seconds to drain. It
    cannot trap the process or abandon a publishable partial feature result.
19. All compatibility transitions name their remaining callers and are deleted
    in the same ticket once the canonical path is live.

## Failure requirements

- Cold catalog failure publishes no capability and cannot be skipped. Reload
  failure retains the prior publication only under the existing typed LKG
  contract and does not present it as a new success.
- Missing, empty, decreasing, non-finite, duplicate-terminal, post-terminal, or
  out-of-range progress fails the owning stage contract or is rejected as stale.
- Cancellation observed before semantic commit publishes no result, increments
  no semantic publication generation, and does not enable an action. The shell,
  report, or inspection request generation already allocated to the cancelled
  attempt remains consumed and is never reused.
- File oversize, growth/truncation, replacement, read failure, malformed JSON,
  and stale content identity fail through the feature's stable diagnostic and
  never publish partial report/history/inspection state.
- Optional failure is isolated; the coordinator retains the failure and starts
  the next independent stage unless the operator cancels remaining work.
- External missing/malformed manifest, hash mismatch, protected path, staging
  failure, or unavailable executable remains fail-closed. No legacy fallback or
  alternate executable path is introduced.
- A run that already acquired an external generation is not rebound by refresh.
- A progress observer, UI dispatcher callback, or accessibility announcement
  cannot execute under an Application publication lock or turn its exception
  into a semantic source failure.
- Any unexplained CLI text/exit, report JSON, Golden byte/hash/name, operation
  trace, processor write-range, support, or evidence difference stops the slice.

## Compatibility, firmware, support, security, and release impact

- Existing public/serialized profile, Saved Rule, report, external protocol,
  settings, and report-history formats remain compatible.
- Accidental internal startup helpers may be removed after zero-caller proof;
  no compatibility facade is retained for repository-internal implementation
  shapes.
- Firmware bytes, ranges, operation order, initialization, processors, headers,
  CRC, padding, output names, and atomic publication are unchanged.
- Support and evidence remain unchanged. This release is support-neutral and
  cannot certify or promote an IC/workflow/topology.
- Automatically discovered or staged filesystem work stays under reviewed roots
  and size limits. Operator-selected report input retains existing arbitrary
  storage-provider/path compatibility, subject to the 10 MiB raw-byte bound,
  coherent identity, and stable-read checks. External tools retain manifest
  hash, host-created staging, timeout, output bounds, changed-range validation,
  cleanup, and no arbitrary path behavior.
- `v0.10.4`'s stable tag/assets are immutable. `v0.10.5` receives new package,
  startup, provenance, SBOM, smoke, and release evidence.

## Testing and evidence plan

### Behavioral seams

- Shell preload session: closed stage order, applicability, required/optional
  policy, two-worker cap, UI serialization, generation, retry/skip/cancel,
  failure isolation, close drain, and exactly-one terminal outcome.
- Catalog: cold success/failure, reload/LKG, full route progress, cancellation,
  retry, publication token, and no selection before publication.
- Report/history: empty, exact bound, one-byte-over, growth/truncation, malformed
  JSON, cancellation during read/parse, stale generation, startup/manual parity,
  arbitrary user-selected path, 12-entry/16 MiB soft-budget in-memory retention
  including one newest entry larger than 16 MiB, maximum-size imported-report
  round-trip within the 64 MiB file bound when older retained entries contain
  worst-case literal-`<` encoder expansion, deterministic oldest-first encoded-
  envelope pruning, derivable-metadata fallback parity, over-envelope
  preservation of the preceding persisted file, and no partial publication.
- Diagnostics and deferred views: independent failure, operator interaction
  priority, skip/cancel, deterministic count, and no hidden exception cascade.
- External environment: deterministic discovery, manifest bounds/hash, empty
  environment, reparse/escape/depth/entry/count/per-file/cumulative-byte limits,
  refresh generation, failed-refresh LKG, lease stability, cancellation, no
  process launch, stale rejection, and a delayed startup-load versus newer
  explicit-refresh race proving single-flight newer-request-wins behavior.
- Inspection: cancel-on-reselection, coherent one-read identity, exact terminal
  health/metadata, stale file/publication/revision/compilation, bounded cache,
  cache-off parity, selective strategy dispatch versus the characterized
  all-strategy baseline, diagnostic/result ordering, read count, and all six
  workflow projections.

### UI and accessibility

- Blocking focus for required startup, restored focus after success/cancel,
  keyboard actions, localized Retry/Skip/Cancel, dark/light/reduced-motion state,
  percent and stage count, indeterminate state, and no underlying shell action
  while required loading is active.
- Optional background work never disables the shell. Polite announcements are
  bounded to state/phase/decile changes and coherent in English/Traditional
  Chinese.

### Performance and source convergence

- Use the exact packaged `v0.10.4` stable artifact as predecessor and the exact
  candidate package on the same controlled machine.
- The fixed predecessor source measurements are 97,306 full-production and
  67,186 counted-runtime nonblank lines. Its two official-package observations
  measured 777.090 ms and 806.930 ms medians; the unchanged prior control
  package measured 782.368 ms in the same environment. These values and their
  exact package hashes remain owned by
  `docs/references/v0.10.4-startup-700ms-evidence.md` and
  `docs/governance/v0.10.4-simplification-and-ownership-audit.md`.
- Measure one warm-up plus at least five scored launches: process start to first
  handle, first handle to catalog-ready usable shell, all optional preload
  completion, peak working set/private bytes, and exact stage/work counts.
- Record median/range and environment identity. Do not claim the historical
  700 ms gate from a different package or environment; `v0.10.5` must improve or
  explain each interval and retain a truthful release limitation if the absolute
  gate remains unmet.
- Every ticket records gross removed, required additions, relocation, net
  production delta, current ratchets, and line-addressed retained residuals.
  Each merged implementation ticket must be net-negative across measured
  production by deleting its displaced path or a separately reviewed compatible
  duplicate in the same PR. Runtime/slice ratchets never rise. No minification,
  excluded-path relocation, or evidence deletion may manufacture the reduction.

### Final evidence

- Narrow project tests, Architecture tests, scoped Polytail/R2 contract review,
  `python scripts/verify.py --all`, all 17 Golden cases, full output hashes and
  names, coverage, package smoke, SBOM/provenance, clean-machine UI/accessibility
  review, and official CI within the accepted five-minute target.
- Expected Golden/BIN/report-wire data cannot be edited to make the change pass.
