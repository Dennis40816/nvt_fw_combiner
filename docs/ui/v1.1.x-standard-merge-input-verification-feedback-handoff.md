## Reuse inventory and current Verified contract

The verification path already has one semantic owner. The later correction
must explain that path; it must not add a UI-side firmware validator.

- Every built-in Standard Merge profile declares required, exactly-one DP and
  TP slots accepting `.bin`. `NT51928` also has one optional LDC slot.
- The selected IC must resolve through the canonical capability catalog to one
  exact Standard Merge profile/map/capability, and the slot must be applicable,
  selected, and `Ready`. For multi-map `NT51928`, and for the DP-perspective
  `NT51950`/`NT51951` routes, DP length resolves the exact map first; dependent
  TP/LDC inputs remain Pending rather than claiming terminal health until that
  compilation identity exists.
- `FileContentSnapshotInspector` reads one bounded complete snapshot, hashes it,
  and rejects an unreadable, oversized, or concurrently changing file. The
  accepted `FileStamp` and bytes then enter the canonical authoring inspection
  lease; a stale lease or changed selection is not accepted as current health.
- `CompiledInputArtifactInspectionService` applies the active IC profile's
  compiled length contract. `NT51917`, `NT51919`, `NT51923`, `NT51926`,
  `NT51927`, `NT51928`, `NT51929`, and `NT51932` require each DP/TP input to
  cover the furthest profile-declared source view or metadata read. `NT51950`
  and `NT51951` require DP to equal the resolved map capacity and require TP to
  cover its declared overlay/read span. These are compiled geometry rules, not
  filename guesses.
- All ten Standard Merge profiles declare warning-only
  `dp-content-plausibility` and `tp-content-plausibility` input-load checks.
  `CompiledInputLoadValidationEvaluator` reports the corresponding
  `DP_UNIFORM_CONTENT_WARNING` or `TP_UNIFORM_CONTENT_WARNING` when every byte
  in the exact profile-declared DP or TP range is the same value. This catches
  often-blank, erased, or placeholder content such as an all-`00` or all-`FF`
  region, although intentional repeated content remains possible; it is not a
  checksum or semantic firmware proof.
- A terminal inspection maps to **Verified** only when the compiled inspection
  severity is `Valid`. A uniform-content result maps to **Warning**, retains
  accepted bytes, and has `BlocksBuild=false`. Unreadable input, rejected
  extension, insufficient/excess length where the compiled contract forbids
  it, stale inspection, or other blocking compilation/readiness results map to
  **Error**.
- The existing `FirmwareSlotCard` status toggle already exposes
  `SemanticStateAutomationText` through both a focusable disclosure and
  `ToolTip.Tip`. `FirmwareInspectionProjection.ApplyInputSlotInspection` and
  `ShellTextResources.GetInputSlotInspectionStatus` are the existing typed
  projection and localization owners. The correction reuses them.

The **Verified** badge is deliberately narrower than “this firmware is known
good.” DP/TP version and Jira facts, PID, detected IC/Number suggestions,
filename text beyond the `.bin` extension, header/CRC integrity, DP-to-TP
compatibility, output-byte parity, and Golden comparison are not gates for this
input-card badge. Both required cards and overall action readiness remain a
separate Build-level contract; one card can be Verified while the other input
is still missing.

## Root cause of the unclear warning

Before this correction, `ShellTextResources.GetInputSlotInspectionStatus` had dedicated text for only a
small subset of issue codes. Every other warning falls through to a generic
sentence that prints the raw code and says only to review it before Build. The
existing status tooltip therefore works mechanically but repeats text such as
`TP_UNIFORM_CONTENT_WARNING` without explaining what was measured, why it may
matter, or whether Build is blocked.

Previously the evaluator knew the checked range and repeated byte, but the
terminal projection lost those facts. The approved extension now carries them
through immutable Application diagnostics, as accepted in
[ADR-0069](../adr/0069-input-diagnostic-evidence.md). Presentation does not reread
the file, duplicate range lookup, or infer facts from an IC, filename, PID,
version, or raw diagnostic text.

The run-report evaluator's original uniform-content message also says
`is a repeated-byte placeholder and cannot be used.` even when its typed
severity is `warning` and the accepted input does not block Build. Presentation
now explains that actual severity; the original message remains intact as
secondary diagnostic evidence, not as the leading instruction.

## Accepted compact-card contract (latest owner amendment)

1. Keep the compact badge states **Verified**, **Warning**, and **Error**. A
   uniform DP/TP result must never retain the green Verified treatment merely
   because Build remains available.
2. Error/Warning badge hover and keyboard focus use one noninteractive compact
   `IssueDetailsCard`, reusing the IC details card shell and shared tokens.
   Use concise facts: `TP BIN too short (≥ 256 KiB)` or
   `TP region contains only 0xFF`, followed by Build impact and a short next step.
   The displayed minimum/value comes from typed Application evidence, not a UI
   constant; 00/A5/FF and other measured byte values use the same projection.
3. The entire disabled Build region exposes the same card, including keyboard
   focus. Keep Application's canonical primary blocker and global-priority
   ordering. Enrich only an exactly matching blocked input slot; other blockers
   retain their canonical explanation. Do not invent a second resolver or an
   unprovided `+N` count. Corrected inputs restore Build and remove the overlay.
4. Report Summary starts with short human-readable findings. Issues retains
   actual/required/missing bytes, exact half-open source range, repeated byte,
   code, operation and original diagnostic when available. Live typed and
   reopened JSON reports use the same projection; Error/Warning/Info styling
   remains distinct. Missing or malformed optional diagnostics fall back without
   hiding or reclassifying the original issue.
5. The first failing declared range is the measured scope, not necessarily the
   whole BIN or every failed range. Optional report evidence is correlated to
   one final issue occurrence by index; duplicate issue values must not acquire
   another occurrence's facts. A pre-Build blocker does not create a Run Report;
   only an actual Preview/Build may do that. English and Traditional Chinese
   convey the same severity and action.
6. `NT51928`'s existing `LDC_UNIFORM_CONTENT_WARNING` uses the same shared copy
   pattern if the mapping is touched, while retaining its own LDC label. No new
   LDC validation or scope is introduced.
