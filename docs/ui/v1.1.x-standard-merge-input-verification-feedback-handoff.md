# v1.1.x Standard Merge input verification feedback handoff

Status: owner-requested `v1.1.x` UI correction; exact release unallocated.

The owner asked what the DP and TP cards actually verify before they show
**Verified**, and observed that feedback such as
`TP_UNIFORM_CONTENT_WARNING` is too implementation-oriented to be useful.
This handoff records the current contract and the smallest later copy/tooltip
correction. It is excluded from `v1.1.1` and changes no profile admission,
input range, validation severity, accepted bytes, Build availability, output
bytes, support claim, or Golden evidence.

## Reuse inventory and current Verified contract

The verification path already has one semantic owner. The later correction
must explain that path; it must not add a UI-side firmware validator.

- Every built-in Standard Merge profile declares required, exactly-one DP and
  TP slots accepting `.bin`. `NT51928` also has one optional LDC slot.
- The selected IC must resolve through the canonical capability catalog to one
  exact Standard Merge profile/map/capability, and the slot must be applicable,
  selected, and `Ready`. For multi-map `NT51928`, and for the DP-perspective
  `NT51950`/`NT51951` routes, DP length resolves the exact map first; dependent
  TP/LDC inputs remain Pending rather than claiming terminal health until that
  compilation identity exists.
- `FileContentSnapshotInspector` reads one bounded complete snapshot, hashes it,
  and rejects an unreadable, oversized, or concurrently changing file. The
  accepted `FileStamp` and bytes then enter the canonical authoring inspection
  lease; a stale lease or changed selection is not accepted as current health.
- `CompiledInputArtifactInspectionService` applies the active IC profile's
  compiled length contract. `NT51917`, `NT51919`, `NT51923`, `NT51926`,
  `NT51927`, `NT51928`, `NT51929`, and `NT51932` require each DP/TP input to
  cover the furthest profile-declared source view or metadata read. `NT51950`
  and `NT51951` require DP to equal the resolved map capacity and require TP to
  cover its declared overlay/read span. These are compiled geometry rules, not
  filename guesses.
- All ten Standard Merge profiles declare warning-only
  `dp-content-plausibility` and `tp-content-plausibility` input-load checks.
  `CompiledInputLoadValidationEvaluator` reports the corresponding
  `DP_UNIFORM_CONTENT_WARNING` or `TP_UNIFORM_CONTENT_WARNING` when every byte
  in the exact profile-declared DP or TP range is the same value. This catches
  often-blank, erased, or placeholder content such as an all-`00` or all-`FF`
  region, although intentional repeated content remains possible; it is not a
  checksum or semantic firmware proof.
- A terminal inspection maps to **Verified** only when the compiled inspection
  severity is `Valid`. A uniform-content result maps to **Warning**, retains
  accepted bytes, and has `BlocksBuild=false`. Unreadable input, rejected
  extension, insufficient/excess length where the compiled contract forbids
  it, stale inspection, or other blocking compilation/readiness results map to
  **Error**.
- The existing `FirmwareSlotCard` status toggle already exposes
  `SemanticStateAutomationText` through both a focusable disclosure and
  `ToolTip.Tip`. `FirmwareInspectionProjection.ApplyInputSlotInspection` and
  `ShellTextResources.GetInputSlotInspectionStatus` are the existing typed
  projection and localization owners. The correction reuses them.

The **Verified** badge is deliberately narrower than “this firmware is known
good.” DP/TP version and Jira facts, PID, detected IC/Number suggestions,
filename text beyond the `.bin` extension, header/CRC integrity, DP-to-TP
compatibility, output-byte parity, and Golden comparison are not gates for this
input-card badge. Both required cards and overall action readiness remain a
separate Build-level contract; one card can be Verified while the other input
is still missing.

## Root cause of the unclear warning

`ShellTextResources.GetInputSlotInspectionStatus` has dedicated text for only a
small subset of issue codes. Every other warning falls through to a generic
sentence that prints the raw code and says only to review it before Build. The
existing status tooltip therefore works mechanically but repeats text such as
`TP_UNIFORM_CONTENT_WARNING` without explaining what was measured, why it may
matter, or whether Build is blocked.

The evaluator currently knows the checked range and discovers that it contains
one repeated byte, while the terminal status projection retains only the issue
code. Static, truthful issue-code help can be added immediately through the
existing localization owner. If the approved design also shows the exact range
or repeated value, that data must first be carried by one typed Application
diagnostic; Presentation must not reread the file, duplicate range lookup, or
infer details from an IC, filename, PID, version, or warning-code string.

## Intended feedback contract

1. Keep the compact badge states **Verified**, **Warning**, and **Error**. A
   uniform DP/TP result must never retain the green Verified treatment merely
   because Build remains available.
2. Replace the raw-code-first fallback for the two uniform checks with concise
   language. Proposed Traditional Chinese TP detail:
   “TP 區段疑似為填充值：profile 指定的 TP 範圍全部是同一個 byte（不限
   於 00/FF）。這通常表示空白或佔位資料，但也可能是刻意內容。此警告
   不會阻擋 Build；請確認來源檔。” DP uses the same wording with DP.
   Proposed English TP detail: “The profile-declared TP range contains one
   repeated byte value throughout (not only 00/FF). This often indicates blank
   or placeholder data, but it may be intentional. This warning does not block
   Build; confirm the source.”
3. Reuse the existing status toggle's hover, keyboard-focus tooltip, disclosure,
   and automation text. The expanded/hover content explains, in this order:
   **what was checked**, **what was detected**, **why it may indicate a wrong or
   placeholder BIN**, **what the user should check next**, and **Build impact:
   warning only; Build remains available**.
4. The machine-readable issue code remains available as secondary diagnostic
   detail for reports/support, but it is not the leading user message. English
   and Traditional Chinese must convey the same severity and action.
5. If exact typed range/value details are approved, display the half-open range
   in hexadecimal and the repeated byte without claiming that `00`/`FF` are the
   only possible values. When those typed details are absent, omit them rather
   than fabricate them.
6. `NT51928`'s existing `LDC_UNIFORM_CONTENT_WARNING` uses the same shared copy
   pattern if the mapping is touched, while retaining its own LDC label. No new
   LDC validation or scope is introduced.

## Acceptance outline for the allocated release

- Headless inspection tests cover all-`00`, all-`FF`, and another repeated byte
  in the exact compiled DP and TP ranges. Each result is terminal **Warning**,
  keeps `BlocksBuild=false`, retains the accepted snapshot, and never projects
  Verified. A non-uniform compatible range projects **Verified**.
- Negative tests retain blocking behavior for unreadable/changing input,
  rejected extension, too-short source-view coverage, exact-capacity mismatch,
  stale lease, and authoring compilation/readiness failure.
- Profile-driven tests cover both the source-view-coverage families and the
  `NT51928`/`NT51950`/`NT51951` DP-first map-resolution variants without copying
  an IC/range table into Presentation. An `NT51950`/`NT51951` fixture makes only
  `tp-overlay` uniform while the rest of the file remains non-uniform, proving
  the copy says profile-declared range rather than whole file.
- Rendered `FirmwareSlotCard` tests in Light/Dark and English/Traditional
  Chinese activate the actual status control by pointer, keyboard, and focus.
  They prove the help is reachable, wraps at narrow width, names DP or TP,
  states that Build remains available, and does not lead with the raw issue
  code. Screen-reader automation text carries the same meaning.
- Contract tests prove version/PID/IC/Number facts, CRC/header inspection,
  Golden comparison, and the other required slot do not silently become new
  gates for the individual card badge.
- Existing Standard Merge build, output-name placeholder, input inspection,
  stale-file, memory projection, report, Golden, and CLI tests remain green.

## Version boundary

release is not assigned by this handoff. It is not part of the
verification-only `v1.1.1` release and grants no firmware-policy or runtime
