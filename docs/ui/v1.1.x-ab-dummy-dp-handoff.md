# v1.1.x AB Dummy DP handoff

Status: owner-requested behavior recorded for planning; implementation and
firmware evidence are not yet admitted. Version allocation is owned by the
[NFC roadmap `v1.1.4` milestone](../architecture/nfc_roadmap.md#114-ui-corrections-and-ab-dummy-dp).

## Retained owner requirement

Owner scope amendment (2026-09-06): implement and verify NT51919, NT51929,
NT51932 **and NT51950 / NT51951** in the same Dummy DP batch. The owner's
latest clarification includes both 51950 and 51951, not 51952; it supersedes
the earlier exclusion of 51950. This follows the shared AB execution direction:
initialize the complete output with 0xFF, omit DP input/seed, retain existing
TP overlays, relocation and declared header/integrity processing, and leave the
entire non-TP complement at 0xFF. Do not create a fake DP file or a second
executor. Scope authorization is not proof that any new Golden passed.

NT51950 verification includes its declared single and cascade maps, including
the non-TP container tail. NT51951 verification must separately cover the ordinary Off path, the Dummy On
path and the three TP B postbuild imports at output 0x8A100, 0x8A110 and
0x8A130 (four bytes each), across the complete 0x100000-byte output. The profile
still records missing direct NT51951 AB input/output Golden and firmware-owner
review; CtrlRAM Golden and NT51950 workflow-logic evidence do not close those
AB gates. Retain this limitation until independent expected output and the
required review are actually admitted.

- Add an AB Code **Dummy DP checkbox**, **unchecked by default**.
- When enabled, fill **all output sections that do not belong to TP** with
  `0xFF`. This preserves the owner's correction: the scope is not only the
  section named DP.
- Do not allow DP input while enabled. A visual-only disabled input is not
  sufficient; the accepted typed request must enforce the same rule.

The owner moved the checkbox and its complete firmware behavior into
`v1.1.4` on 2026-09-05; this is not merely a visual control change.
The feature was deferred past `v1.1.2` and is not a `v1.1.3` change. Scheduling
does not certify output bytes, admit a new IC/mode or promote support.

  an orange confirmation-button style or the generated preview's square focus

The generated image was a process preview, not implementation or byte evidence;
the owner subsequently corrected its button styling and checkbox arrangement.

## Acceptance outline

### Read-only implementation inventory (2026-09-06)

Existing AB authoring is owned by `AbMergeAuthoringExperience`, canonical
capability/profile compilation by `CanonicalCapabilityCompiler.AbMerge` and
`V2CompositionPlanCompiler`, execution by the shared `CompositionRunService`.
Current profiles require `dp-ab-input` and seed the output from DP. Dummy mode
therefore needs a typed, profile-compiled DP-free input/initializer selection;
it cannot be implemented by disabling Browse, creating a fake DP file or
overwriting the completed output afterward.

Canonical map inventory, half-open ranges in `output-image` projected from
`flash` (not an approval of new Dummy output):

| IC / map | TP A | TP B | Non-TP complement proposed for 0xFF |
| --- | --- | --- | --- |
| 51919 / 51929 / 51932; output ends 0x80000 | [0x7000,0x40000) | [0x47000,0x80000) | [0,0x7000), [0x40000,0x47000) |
| 51950 single; output ends 0x80000 | [0xA000,0x37000) | [0x4A000,0x77000) | [0,0xA000), [0x37000,0x4A000), [0x77000,0x80000) |
| 51950 cascade >=2; output ends 0x100000 | [0xA000,0x37000) | [0x4A000,0x77000) | [0,0xA000), [0x37000,0x4A000), [0x77000,0x100000) |
| 51951; output ends 0x100000 | [0xA000,0x37000) | [0x8A000,0xB7000) | [0,0xA000), [0x37000,0x8A000), [0xB7000,0x100000) |

Map sources: [919/929/932 family](../../profiles/built-in/nt51919-nt51929-nt51932-ab-merge/families/nt51919-nt51929-nt51932-ab-merge.json)
and [950/951 family](../../profiles/built-in/nt51950-ab-merge/families/nt51950-ab-merge.json).
The complement includes declared unknown/unmapped and container-tail regions;
filling only DP-owned regions is not equivalent to the owner's all-non-TP rule.

Existing TP B relocation must be distinguished from copying raw TP unchanged:
919/929/932 relocate ILM/DLM/DIFF address words; 950/951 retain DIFF relocation
and import three four-byte TP header results at B-relative 0x100, 0x110, 0x130.
The declared final postbuild imports are inside TP. The owner selected the
shared-execution direction above and added NT51950/NT51951 to its first verification
batch; independent expected outputs and exact-range certification remain open.

No certified AB Dummy output case was found. Existing AB Golden certifies the
ordinary DP-seeded mode, not this new contract. 950/951 retain their declared
candidate/evidence limitations; adding Dummy must not promote them. Without DP,
the current `AbCodeOutputNameResolver` would produce missing-DP metadata
placeholders/warnings; explicit Dummy naming/report provenance remains a product
decision, not a fabricated DP version. Independent expected outputs and exact
write-range review are still required before firmware implementation admission.

Separately, the preceding UI batch still has committed `design-active` records
and unresolved final integration/code-size evidence. The current capability
lifecycle does not let those records authorize a new production batch. No
record finalization, gate waiver or Dummy production edit is claimed here.

### Required checks

- Off preserves the existing AB behavior and its complete Golden outputs.
- On rejects DP input through the shared typed path, preserves the approved TP
  bytes, and fills every approved non-TP output range with `0xFF`.
- Boundary tests cover adjacent TP/non-TP sections, complete output length,
  invalid/incomplete requests and atomic failure without partial output.
- Toggle/retained-input/UI tests prove the switch cannot bypass Application
  admission or leave stale DP state participating in execution.
- Independent whole-output Golden comparisons and the exact write-range audit
  pass for each approved scope; aliases/topologies do not certify each other.

Use the existing profile compiler and shared planner/executor. Do not implement
the fill in a UI click handler, add an AB-only executor, or regenerate expected
bytes from the changed implementation to make tests pass.
