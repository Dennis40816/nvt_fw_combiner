# v1.1.x AB Dummy DP handoff

Status: owner-requested behavior recorded for planning; implementation and
firmware evidence are not yet admitted. Version allocation is owned by the
[NFC roadmap `v1.1.4` milestone](../architecture/nfc_roadmap.md#114-ui-corrections-and-ab-dummy-dp).

## Retained owner requirement

- Add an AB Code **Dummy DP checkbox**, **unchecked by default**.
- When enabled, fill **all output sections that do not belong to TP** with
  `0xFF`. This preserves the owner's correction: the scope is not only the
  section named DP.
- Do not allow DP input while enabled. A visual-only disabled input is not
  sufficient; the accepted typed request must enforce the same rule.

The owner moved the checkbox and its complete firmware behavior into
`v1.1.4` on 2026-09-05; this is not merely a visual control change.
The feature was deferred past `v1.1.2` and is not a `v1.1.3` change. Scheduling
does not certify output bytes, admit a new IC/mode or promote support.

## Decisions and evidence before implementation

### Accepted interaction contract (2026-09-06)

The owner authorized implementation after approving these interaction rules:

- Place `Dummy DP (0xFF)` beside `Use the same TP for A and B` in one horizontal
  checkbox row below the AB description and above the input cards. Reuse existing
  checkbox styling/spacing; wrap only when the supported narrow viewport needs it.
- The option starts off. Requesting On opens confirmation **before** changing
  the accepted selection. DP remains selected until confirmation is accepted.
- Explain that non-TP regions use Dummy Byte (`0xFF`), the current DP selection
  will be cleared and DP input disabled. Explicitly state that original files
  will not be deleted. Disabling later requires selecting DP again.
- Cancel/Escape leaves the option and selected inputs unchanged. Accept clears
  DP selection (never deletes the file), enables Dummy DP and disallows DP input
  through both UI and shared typed admission. Off restores input availability
  without restoring the previous file; TP selections are preserved.
- Reuse `semanticAction secondary` for Cancel and `semanticAction primary`
  for Enable Dummy DP, with the existing focus/hover/disabled states. Do not add
  an orange confirmation-button style or the generated preview's square focus
  frame. Initial keyboard focus stays on Cancel.

The generated image was a process preview, not implementation or byte evidence;
the owner subsequently corrected its button styling and checkbox arrangement.
The approved interaction does not settle the firmware questions below.

### Remaining firmware admission

1. Identify the existing AB request/profile/compiler/planner owners and each
   affected profile's explicit TP and non-TP sections, including address
   spaces, topology and complete output bounds. Do not infer them from a
   filename, observed Golden layout or UI state.
2. Obtain the firmware owner's exact treatment of headers, integrity and
   postbuild processing where it intersects the requested non-TP fill. Do not
   silently exempt non-TP bytes or invent new processor semantics.
3. Enforce the accepted toggle contract above through the existing accepted
   session owner. No stale DP input may affect a Dummy DP build.
4. Approve the complete output/write-range contract and independent expected
   outputs for the affected IC/topology cases before firmware-semantic changes.

## Acceptance outline

- Off preserves the existing AB behavior and its complete Golden outputs.
- On rejects DP input through the shared typed path, preserves the approved TP
  bytes, and fills every approved non-TP output range with `0xFF`.
- Boundary tests cover adjacent TP/non-TP sections, complete output length,
  invalid/incomplete requests and atomic failure without partial output.
- Toggle/retained-input/UI tests prove the switch cannot bypass Application
  admission or leave stale DP state participating in execution.
- Independent whole-output Golden comparisons and the exact write-range audit
  pass for each approved scope; aliases/topologies do not certify each other.

Use the existing profile compiler and shared planner/executor. Do not implement
the fill in a UI click handler, add an AB-only executor, or regenerate expected
bytes from the changed implementation to make tests pass.
