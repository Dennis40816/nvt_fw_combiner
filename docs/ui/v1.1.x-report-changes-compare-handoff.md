# v1.1.x Report Changes compare handoff

Status: handoff-only scope, acceptance, diagnosis, and evidence. Version
allocation is owned by the [NFC roadmap `v1.1.4` milestone](../architecture/nfc_roadmap.md#114-ui-corrections-and-ab-dummy-dp).

The owner observed four related problems in the Report **Changes** experience:
the changed-range scrollbar covers content, one physical CtrlRAM section is
presented as many small compare entries, the Light-theme Original rows have
drifted from pale pink/red to purple, and the localized Original address label
can overlap the first byte column. This handoff records a reuse-first later UI
correction only. It is excluded from `v1.1.1` and changes no firmware range,
mutation authority, `ByteDiff` result, report-wire schema, persisted hash or
replay evidence, acceptance verdict, output byte, Golden evidence, or release
content. The diagnosis below records the original defects; the local corrections
and still-pending physical-section grouping are distinguished below.

## Original reuse inventory and diagnosis

The four symptoms already have suitable owners. Implementation must begin
with red rendered reproductions and repair those owners; it must not add a
second Hex renderer, range diff algorithm, report projector, or scroll host.

- `MainWindowReportAuditTemplates.axaml` renders the right-hand changed-range
  navigator as `ListBox.reportHexDiffRanges`. Its existing
  `VirtualizingStackPanel` is required for bounded large-report behavior, but
  the ListBox's template-created `ScrollViewer` currently keeps the default
  overlay scrollbar treatment. The repository already owns the visible,
  non-auto-hiding 14-pixel vertical gutter and 6-pixel thumb treatment in the
  shared `contentScrollSurface` styles. The navigator should reuse that same
  behavior through its internal ScrollViewer rather than wrapping the ListBox
  in another ScrollViewer or replacing its items panel.
- Domain `ByteDiff.FindChangedRanges` deliberately returns contiguous runs of
  bytes that actually changed. `CompositionRunService` then preserves every
  run as an independent `OutputDifferenceSummary` with its exact range,
  before/output slice hashes, preview, aligned replay context, semantic
  classification, explanation, and acceptance verdict. Those raw rows are
  audit evidence and must remain intact.
- `ReportReviewViewModel.CreateOutputDifferenceProjection` already groups raw
  rows by their physical `SectionLabel`, publishes a compact group count and
  expected/review status, and lazily materializes the group's raw rows. The
  Changes navigator currently binds directly to the raw Hex Diff ranges, so a
  single physical CtrlRAM section can still appear as many primary cards. The
  existing physical-section group is the correct semantic and performance
  seam; no CtrlRAM-specific range merger or second grouping model is needed.
- Historical reports persist exact replay evidence per recorded range. They do
  not necessarily retain a complete before/output snapshot for every unchanged
  gap between two runs. A wider section envelope is therefore safe only when
  existing typed replay evidence proves complete coverage of that envelope.
  Neither Presentation nor a migration adapter may invent unchanged bytes,
  reread old source paths, or bridge gaps merely because two rows share a
  `SectionLabel`.
- `HexViewportControl` already owns both current and Original comparison rows.
  Commit `5c0ce710` routed Original row, changed-cell, text, marker, and border
  roles through the purple controller/reference-input resources. Before that
  regression, the approved Light treatment used pale pink/red (`#FDF2F8` row,
  `#FBCFE8` changed cell, `#9D174D` text, and `#DB2777` marker). Original is a
  Hex comparison semantic, not an error, controller input, or reference-file
  slot semantic, so it needs its own Light and Dark resource roles.
- `HexViewportControl` reserves a fixed `AddressWidth = 112`, while
  `FormatReferenceLabel` draws `0x{address:X6}  {ComparisonRowLabel}` from
  x=4 and the first byte cell starts immediately after that fixed gutter.
  At the production technical font and size, the English
  `0x123456  original` label is wider than the reserved area. The resulting
  overlap is a measured geometry defect, not a localization-string defect and
  must not be hidden by shortening or clipping the label.

## Intended interaction and visual contract

Owner clarification on 2026-09-08 keeps the English Light presentation as the
layout baseline and adds one bounded clarity pass. Current and Original address
labels share a 12-pixel text inset; the Original leading rail is three pixels
wide at x=2, leaving visible separation without breaking row alignment.
The first range-first card arrangement was subsequently rejected by the owner;
the approved reference below replaces that right-card hierarchy, not the
address-rail or navigation corrections.

The Report Summary's duplicate history icon is removed because it invokes the
same Run Reports list as the modal header. Report detail therefore has one
keyboard-accessible, localized breadcrumb-style chevron and `Run reports`
return action. This changes no history model, persistence, selection, report
schema, acceptance decision or evidence.

The earlier `54db97a1` candidate was rendered at 1440x900 in English Light and
Traditional Chinese Dark. Both frames confirm the shared address inset,
non-overlapping Original rail, complete top-right verdicts, selected-only
Why/Result details, one return breadcrumb and no duplicate history icon.
Focused verification passed 4/4 rendered layout cases, 11/11 report
presentation contracts, 9/9 Report Hex Diff data/replay cases, 1/1 shell
navigation architecture case, and 19/19 code-size policy cases. These are
local scoped results, not a full-suite or release claim.

Physical-section grouping below remains pending and is not implemented by this
visual correction. The next separate items remain in the roadmap's small-scope
first queue; no new firmware semantics or release certification is implied.

1. The changed-range navigator always reserves a non-overlay vertical
   scrollbar gutter. The thumb never covers range labels, values, focus rings,
   or card actions at rest or on hover. It reuses the existing
   `contentScrollSurface` width, thumb, theme, and non-auto-hide treatment on
   the ListBox's internal ScrollViewer while preserving the current
   `VirtualizingStackPanel`, keyboard selection, range selection, and scroll
   position. A nested ScrollViewer is forbidden.
2. The navigator's primary level contains one card for each existing physical
   `SectionLabel`. For example, multiple contiguous runs within Normal CtrlRAM
   are summarized as one card such as **Normal CtrlRAM — 37 changed runs**,
   with the existing expected/review counts and verdict. This is a presentation
   grouping only: it must not change `ByteDiff`, coalesce audit rows, recalculate
   acceptance, or make disjoint changed bytes appear contiguous in the report.
3. Expanding or activating a physical-section card exposes its original raw
   runs in address order. Each raw run remains individually selectable and
   retains its exact range, hashes, Why/Result evidence, replay bytes, and
   accepted/review state. A group with any review-required child cannot appear
   wholly expected.
4. When a current report contains a typed complete before/output snapshot for
   the whole physical section, the selected group may offer one continuous
   section-envelope comparison derived from those exact bytes. When complete
   coverage is absent, especially for historical per-range reports, the group
   remains the primary navigator card but comparison drills into the persisted
   raw runs. It must state that a continuous section preview is unavailable
   rather than synthesize bytes for gaps.
5. Original comparison rows use one dedicated Hex Original semantic resource
   family in both Light and Dark themes. Light restores the approved pale
   pink/red hierarchy; Dark supplies a contrast-safe counterpart with the same
   semantic hierarchy. The resources cover the row surface, changed-cell
   surface/border, text, and leading marker together. They must not alias error,
   caution, controller-input, or reference-slot tokens, and current output-row
   colors remain unchanged.
6. The Hex viewport measures or otherwise reserves the complete localized
   address-plus-Original label gutter before calculating byte-column geometry.
   The first current and Original byte cells remain vertically aligned, and
   the label's rendered right edge plus the shared minimum spacing never
   crosses the first byte cell. English and Traditional Chinese, Light/Dark,
   the largest supported address, font fallback, and display scaling must all
   use the same geometry rule; fixed English-only width guesses are forbidden.
7. These repairs preserve Report range selection, splitter behavior,
   virtualization, pointer and keyboard focus, screen-reader descriptions,
   high contrast, reduced motion, complete replay/hash evidence, and the
   existing read-only Hex viewport contract.

## Acceptance outline for the allocated release

- A rendered production Report regression first reproduces the owner-observed
  overlap with enough changed ranges to scroll. At desktop and supported narrow
  widths, the actual internal ListBox scrollbar reserves its gutter and never
  intersects the right edge of any card or focus visual in Light/Dark and both
  languages. A large fixture proves item virtualization remains active and no
  nested scroll host exists.
- A report fixture with many disjoint changes inside one physical CtrlRAM
  `SectionLabel` renders one primary group card with the exact child count and
  aggregate expected/review status. Expanding it exposes every original run in
  deterministic address order; selecting each run resolves the same exact
  range, hashes, replay, Why/Result, and acceptance evidence as before.
- The existing large-report projection regression remains bounded and lazy;
  grouping cannot eagerly materialize every raw row or replay segment merely
  to show the primary navigator.
- A complete-snapshot fixture may render a continuous section envelope and
  proves every gap byte comes from that exact typed snapshot. A legacy
  per-range fixture with uncovered gaps omits the continuous envelope, retains
  raw-run navigation, performs no path reread, and exposes a localized
  unavailable explanation.
- Rendered Hex viewport comparisons assert the Light Original row, changed
  cell, text, and marker match the approved pale pink/red semantic palette and
  are not resolved from controller/reference-input resources. Dark and high
  contrast meet the repository contrast policy while retaining a distinct
  Original hierarchy; current-row state colors do not regress.
- Rendered bounds tests use the actual technical font, production font size,
  localized `ComparisonRowLabel`, representative and maximum supported
  addresses, and supported scaling. They assert the label remains inside the
  reserved gutter with minimum spacing before the first byte cell, and that
  current/Original hex and ASCII columns stay aligned without clipping.
- Existing `ByteDiff`, output-difference classification, raw report JSON,
  history replay, hash, acceptance, Hex viewport interaction/performance, and
  Report accessibility tests remain green.
