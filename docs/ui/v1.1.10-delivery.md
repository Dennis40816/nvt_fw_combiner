### Info 模型與顯示規劃（版型已批准；完整 metadata 模型待補）

分為兩步，避免把「顯示用途」變成第二個 firmware 判斷來源：

1. **共用事實取得**：捕獲不可變輸入與當前 profile／宣告的 slot role／source view，
   由既有分類與 metadata owners 辨識適用類型並解析欄位。結果保留欄位 identity、
   A／B 所屬、原始值、來源範圍／snapshot，以及可讀／未知／不適用／錯誤狀態。
   完整 AB Base 的資訊範圍不隨替換 A／B 縮減；讀不到的 bank／欄位明示原因。
   顯示發現不自行授予 Build 支援，也不另訂或略過既有驗證門檻。
2. **共用顯示投影**：以「頁面用途 × typed slot 角色 × 已辨識的檔案類型」
   決定主資訊／Details 與分組；依欄位 identity 分類，不用文字 label、檔名、
   IC 型號 switch 或清單前四項決定意義。同一資訊不在各頁重寫解析邏輯。
   頁面只傳既有 typed context 並持有自己的 state；共用模型不依賴頁面 ViewModel。

候選顯示矩陣如下；實際讀取仍須有 profile 宣告，欄位不存在不推算、不假造。

| 當前頁面／slot | 輸入類型／來源 view | 主要資訊 | Details／界線 |
| --- | --- | --- | --- |
| Standard Merge／TP；AB Merge／TPA、TPB | TP Code，或可提供已宣告 TP view 的完整 FlashCode | 該 TP 的版本、PID、Common FW、Event Buffer；AB 保留 bank 標籤 | IC Count；DP 等額外資訊只在有可信 observation 時提供；完整檔案不等於切換 workflow |
| Standard Merge／DP；AB Merge／DP A／B | DP Code，或具有合法 DP source view 的容器 | 對應 DP Version、適用的 Jira／輸入健康狀態 | TP 額外資訊與地址；不把相同檔案放進 TP slot 時的優先次序直接沿用 |
| CtrlRAM Replace／Base | Standard TP Code／Standard FlashCode | TP Version、PID、Common FW、Event Buffer | IC Count；FlashCode 的 DP Version／Jira、地址、驗證細節；TP-only 不顯示虛假的 DP 欄位 |
| CtrlRAM Replace／Base | AB FlashCode | A／B 各自的 TP 欄位，含目前未選替換的 bank；相同 PID／Common／IC Count 合併標示 | A／B IC Count、DP A／B、bank／metadata 地址與技術細節；兩邊資料不互相補值 |
| CtrlRAM Replace／replacement slot | compact NF／Normal／VN 等宣告的 section payload | subtype／endpoint、檔案大小與允許範圍、來源健康狀態 | 不冒充完整 TP／FlashCode，不從任意 bytes 抓版本或 PID |
| Initial Code／LDC 等具名 slot | 宣告的 section source view | 該角色有權取得的資訊、大小／範圍／健康狀態 | 不套用通用 TP metadata 假設 |
| General Merge／Replace mapping source | 任意合法 mapping source；Base 另依其類型 | 檔案與 mapping 範圍、健康狀態；Base 顯示可信 firmware facts | 已有可信 observation 才顯示附加韌體資訊；辨識不到不把任意 payload 誤當完整韌體 |

主資訊欄數可隨空間換行，但語意分組不再依 `Take(4)`／`Skip(4)`。
未知 Event Buffer 保留 raw hex 並標明未知；讀到 0、讀不到、AB 不吻合等既有
阻擋原因不得折疊到 Details。資訊讀取成功不代表 CRC／Golden 已認證。
Output Settings／Report 消費同一 accepted snapshot 的適用 facts；歷史 Report
保留當時捕獲結果，不因新畫面而重讀目前檔案或設定。
