# v1.1.x bundle primary-output rename handoff

Status: owner-requested minor UI follow-up; exact `v1.1.x` release unallocated.

This handoff records the owner request that enabling **Bundle output and
sources** must not prevent the operator from renaming the generated primary
output file. It is not part of `v1.1.1`, changes no firmware bytes or naming
tokens, and does not authorize implementation until an exact later `v1.1.x`
release and its R2 host-delivery review are assigned.

## Current behavior and reuse inventory

The product already has the required loose-output naming path and most of the
bundle UI. The gap is an explicit bundle-only restriction, not a missing
naming subsystem:

- `ICompositionOutputNaming` and
  `CompositionOutputNamingExperience.ResolveAcceptedOutput` are the live
  Presentation/CLI naming boundary. They carry the accepted session through
  `AcceptedSessionOutputNameResolver` to `CompiledOutputNameResolver`; the
  bundle change must extend this owner rather than route through an unused
  naming entry point. `CompositionRunRequest.IsOutputFileNameOverride` and
  `OutputNamingSummary.IsExplicitOverride` remain the execution/report
  provenance for manual host Build intent.
- `OutputDeliveryConfirmationViewModel` and
  `OutputDeliveryConfirmationModal` already expose `OutputFileName`, the edit
  action, keyboard focus, and localized labels. Today
  `CanEditOutputFileName` is false while bundling is enabled and switching the
  bundle on resets an operator draft to the canonical automatic name.
- `CompositionOutputBundleProposal`, `CompositionOutputBundleAdmission`, and
  `CompositionOutputBundleIntent` already retain the exact accepted session,
  prepared output name, immutable sources, and proposed folder destination.
  Today admission intentionally rejects an explicit output-name override.
- `FileSystemCompositionOutputBundleDestinationValidator` and the atomic
  bundle writer already own Windows-name, path, protected-input, collision,
  staging, promotion, cancellation, and partial-output safety. They remain the
  only destination/materialization owners.

No implementation may add a Presentation-only filename resolver, parse
firmware facts from a filename, or copy files after the atomic bundle commit.

## Intended interaction contract

1. `Bundle output and sources` may be on or off while the same output-filename
   edit action remains available.
2. The **Bundle folder name** and **Output filename** are independent fields.
   Editing or toggling either one must not silently rewrite the other. The
   existing automatic suggestions remain the initial defaults.
3. The override applies to the generated primary output BIN inside the atomic
   bundle. Accepted source filenames remain their accepted source identities;
   this item does not add source renaming.
4. The final primary filename, report identity, commit receipt, hash evidence,
   and Explorer/recent-output actions must all use the same effective accepted
   override and record it as explicit host Build intent.
5. Loose-output behavior, output bytes, compiled operations, profile-owned
   automatic naming, additional-delivery semantics, and bundle folder
   collision suffixing remain unchanged.

Whether a separately generated additional delivery should gain its own rename
field is deliberately unresolved and outside this request. It must not be
silently coupled to the primary filename or inferred from its stem.

## Safety and validation boundary

The bundle path must apply the same accepted manual-filename validation as the
loose path plus the existing atomic bundle destination validation. A proposed
name cannot carry path syntax or escape the selected folder, alias a protected
input, bypass Windows reserved/invalid-name and path-length checks, overwrite
another bundle member, or cause a visible partial bundle. Existing deterministic
collision allocation, private sibling staging, atomic promotion, cancellation,
and stale-session rejection remain fail closed.

The manual override is host delivery intent only. It cannot alter IC/profile
selection, naming-token extraction, Preview/Build firmware semantics, output
bytes, Golden evidence, or support status.

## Acceptance outline for the allocated release

- Turning bundle mode on preserves an already edited valid primary filename;
  editing remains keyboard- and screen-reader-accessible in both supported
  languages.
- Confirming bundle delivery creates no loose primary file and places the
  generated primary output under the selected custom filename in the promoted
  folder.
- Folder-name edits and primary-filename edits remain independent across
  toggle, Cancel/reopen, validation failure, and retry.
- The run report's `OutputNaming` records the delivered `ActualFileName` and
  `IsExplicitOverride = true`; commit and bundle receipts record the same
  actual delivered primary filename, size, and SHA-256 without gaining a
  duplicate intent flag. Bytes and SHA-256 equal the automatic-name run.
- Invalid, colliding, protected-input, stale-session, cancelled, or failed
  requests leave no visible partial output and do not mutate any selected
  source.
- Source and optional additional-delivery names retain their existing typed
  behavior, including deterministic collision handling.
- Existing loose automatic/manual output tests remain green, and new
  Application, Infrastructure, UI-smoke, localization/accessibility, and
  packaged-Windows checks cover the bundle override end to end.

## Version boundary

This is a later `v1.1.x` product/UI-delivery change. It is explicitly excluded
from the verification-only `v1.1.1` release. The owner must assign its exact
release before implementation; this handoff does not silently append it to the
indivisible former-`v1.0.9` bundle already allocated to `v1.1.2`.
