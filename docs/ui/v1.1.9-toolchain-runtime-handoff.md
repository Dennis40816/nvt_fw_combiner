## Toolchain Runtime intake — 2026-09-16

Owner decision, 2026-09-19: an explicitly selected user Runtime that is
deleted, changed or incompatible must fail closed with an actionable reason
for workflows requiring it. Do not silently substitute the bundled Runtime.
The user can explicitly switch back to the bundled default in Settings.
This resolves invalid-override fallback only; deployment/trust design and
the preview remain separate implementation work.

Owner trust decision, 2026-09-19: selected runtimes require strict Microsoft
signature trust validation. If certificate revocation cannot be confirmed,
including offline/unavailable status, reject the selected runtime rather than
accepting an unverified status. The already approved bundled runtime remains
an explicit manual alternative. This does not authorize automatic downloads,
system changes or weakening the packaged-tool trust policy.

**User-installed selection is queued for `1.1.9`; not implemented or verified.**
The bundled/default runtime portion shipped in `1.1.8`; see the
[release closure](../references/verification-report.md#118-published-release-closure--2026-09-19).
Do not implement its packaging again. The historical size estimate below is
not the final published package size.
Add **Settings > Config > Toolchain** within the existing Settings modal.
The owner also confirms that the tool should **bundle the repo-approved
runtime and use it by default**. Selecting a validated user-installed runtime
is optional; detection must not silently replace the bundled/default selection.
Automatically detect available user-installed VC++ Runtime candidates and
let the user choose their own compatible runtime, including newer installed
versions. A clean Windows installation does not guarantee that the required
runtime is present: the current x64 Combiner directly imports `VCRUNTIME140.dll`.
This selection concerns that dependency, not a new Combiner/CRC worker,
arbitrary executable, profile, firmware algorithm or support route.

Implementation assessment and preview should cover:

- Show detected source/path, file version, architecture and availability;
  allow explicit user selection or browsing to a locally supplied runtime.
  Treat "latest" as the latest **compatible, validated available** candidate,
  not merely the highest version string or an automatic Internet update.
- Validate the required x64 architecture, trusted Microsoft source/signature,
  required exports and actual dependency loading. Expose missing, incompatible
  or unreadable candidates with actionable reasons; do not advertise readiness
  just because a DLL filename exists. The exact compatibility/admission rule
  remains to be designed through the existing external-tool owner.
- Reuse the Config draft/Save/Discard/Reset interaction and shared runtime
  readiness/invalidation owners. Applying a selection must refresh every
  affected workflow and invalidate stale readiness; only workflows requiring
  the unavailable dependency should be blocked. Record the effective runtime
  identity for diagnostics and reproducible execution.
- Verify that the selected DLL is the one Combiner actually loads. Windows
  executable-directory lookup can take precedence over another configured
  location; changing a Settings path or PATH alone is not proof. Resolve the
  deployment/search-order strategy before implementation, preserving immutable
  tool identity, staging isolation and declared firmware write boundaries.
- Cover no runtime, valid installed runtime, multiple/newer versions, x86 or
  incompatible runtime, invalid manual path, changed/deleted selected files,
  Save/Discard/Reset, shared readiness refresh and real clean-Windows Build.

Packaging-size observation, 2026-09-16: the current approved x64 runtime is
124544 bytes (121.625 KiB). An isolated ZIP `Optimal` compression measurement
produced 62240 bytes of compressed DLL data (about 60.8 KiB). Relative to the
original 116698716-byte `1.1.8` candidate ZIP, the runtime alone increases the
estimate from 111.2926 to about 111.3522 MiB including its ZIP entry overhead;
notices/manifest/SBOM changes and the final rebuild are not included in that
estimate. The main 75513019-byte EXE is unchanged by adding a separate DLL.
This is a size estimate, not a rebuilt or released package identity.

This intake does not authorize downloading/installing a runtime automatically,
overwriting system DLLs, silently changing the selected version, bypassing
package trust, or waiving redistribution terms. The default is now settled as
the bundled/repo runtime. Invalid explicit overrides follow the fail-closed
owner decision above; the exact UI preview and executable trust/deployment
design remain open. Existing `1.1.8` dependency-fix/release evidence remains separate; no production code or
release assets change in this planning update. The
[roadmap](../architecture/nfc_roadmap.md#current-release-sequence--2026-09-14)
owns priority and version allocation.

## Current design proposal — 2026-09-19

Read-only discovery at `d8269da3` recommends an isolated host-owned tool
execution directory with the unchanged manifest-verified Combiner executable
and selected validated DLL. Keep firmware staging as WorkingDirectory. Reuse
`ExternalStagingDirectory` ownership/cleanup; do not overwrite bundled/system
files or rely on PATH overriding executable-directory DLL lookup.

Extend the existing resolver, environment generation/readiness and both
Combiner processor consumers, not a Settings-only loader. Preserve source
path and accepted hash; revalidate changed/deleted selection before use.
PE architecture, imports/exports, Microsoft trust and proof of actual loaded
module identity need executable evidence. This is a reviewed proposal, not
an admitted implementation or security certification.

The generated Toolchain preview in the owner task reuses the Config sidebar,
Bundled/User selection rows, right-aligned Detect/Browse and aligned metadata.
Save/Discard/Restore defaults retain the existing Config transaction model.
Its separate invalid-state strip is illustrative: production puts that state
inside the same page and keeps the invalid selected radio visibly selected.
The version is real inspected data at runtime, not the preview's descriptive
text. No Internet update, auto-selection or automatic fallback is proposed.
Owner approved this layout and implementation in the subsequent task replies:
show invalid-selection feedback directly below the existing User runtime row,
update its Verification value and reuse the existing Bundled runtime selector.
Do not render the separate example strip or duplicate recovery controls.
Complete implementation admission remains required before production edits.

## First implementation component — 2026-09-19

`TOOLCHAIN-119-IMAGE-01` admits an internal immutable-snapshot header inspector
using framework PEReader. It observes Machine, DLL characteristic, optional
header magic and CLR-header presence; it neither executes the candidate nor
grants compatibility, trust or readiness. Browse integration must consume it
before this feature can be complete. Existing bundled readiness is unchanged.

Evidence in `D:/NvtFwCombiner-TestArea/evidence/v119-toolchain`:
`runtime-image-red.trx` had 5 expected failures/6 passes against the temporary
unimplemented body; `runtime-image-final.trx` has 14 passes, no failures/skips,
including existing runtime dependency tests. The initial unused-parameter
analyzer failure was corrected without suppression. A test initially treated
the executable test assembly as a DLL; it now uses the actual Infrastructure
DLL as its managed-image fixture. Synthetic native fixtures are PE/COFF header
bytes, not firmware or executed native code. No native loader is invoked.

Independent design admission: `name_validation_design`; fixed-head review and
integration record closure follow the implementation commit. This component
has no production caller until the next candidate-inspection/Browse slice;
no Toolchain UI, saved selection, signer/revocation/export checks, actual DLL
load evidence, full-suite, Golden or release completion is claimed here.
