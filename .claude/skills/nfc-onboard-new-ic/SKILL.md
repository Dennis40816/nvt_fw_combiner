# Onboard A New IC

This skill orders the work. The runbook [`adding-ic-merge-replace-workflow.md`](../../../docs/architecture/adding-ic-merge-replace-workflow.md) owns the file list, and skill `nfc-firmware-profile-authoring` owns the profile facts. An owner data drop is evidence, not support.

1. **Protect the drop first.** Store the original files in the private asset repository and record each SHA-256 and size. The public repository gets only the IC name, program support, address settings the owner approved for publication, and manifest identities. It gets no BIN, flash-map sheet, postbuild script, source file, or customer file name, unless the owner marks the drop public and free of firmware payload, secrets, and customer data. Then the runbook's reference flow applies, with provenance, hash, and owner review. Do not paste private content into a PR, issue, comment, or CI log.
2. **Inventory by role.** Sort the files into map or header, postbuild flow, source headers, sample images, Golden outputs, and tools. List what the runbook's evidence table still lacks.
3. **Stage, do not promote.** For a public drop, run `scripts/intake_ic_reference.py`. For a confidential drop, never use `--dry-run`, because it prints the source folder, file names, sizes, and hashes to the log. Point `--output-root` at a controlled folder in the private asset repository instead, and keep the console output out of PRs, issues, and CI logs. The script copies files and writes names, sizes, and hashes, so its output must never land in this repository for confidential files. Ignore its proposed tracked destinations for them. The script changes no profile and no code. It has no `ab-merge` mode. For an AB Merge drop, use `reference-only` and collect the AB processor and Golden evidence by hand from the runbook.
4. **Resolve layouts with the owner.** When the drop holds more than one layout or firmware version, do not pick one. Ask the owner which one is production. Compare the facts with the nearest family. Do not join a family without an official map that proves identical facts and an owner approval.
5. **Check the Combiner, only when the workflow needs it.** Do this only when the chosen workflow or profile declares an external processor stage. Examples are CtrlRAM Replace, AB Merge, and a General Replace that touches TP ranges. For a new IC that has no profile yet, create the unpublished candidate profile, binding, and command plan first (step 6), and run the check on them. Standard Merge needs no Combiner evidence. Check the profile's `toolBindingId` to be sure. Never run a delivered `Combiner.exe` that is not approved. First complete its exact identity, the execution approval, and the trust review through skill `nfc-change-legacy-combiner`. Until then it is evidence only. When it is approved, run it and the pinned one with the profile's exact command plan, on host-created staging copies of the samples, in the test area. Compare complete outputs byte by byte and list each difference range. Matching output is not support evidence, because the legacy Combiner does not check the chip.
6. **Declare a candidate, when the owner decides it.** First decide whether the canonical facts change. If a new firmware version stays inside an existing effective-version interval and brings no new map, command plan, or other canonical fact, it is evidence only: add the version to the evidence of the existing route and create no new candidate. Otherwise an owner decision or an ADR must approve an isolated map, family, and bundle first. Mark copied numbers as provisional. Register each route as `Candidate`, `ContractOnly`, with authoring unavailable. Hash-pin every changed fact, and keep the existing IC identities stable.
7. **Collect promotion evidence.** Every declared route needs the complete-output Golden that the runbook and skill `nfc-golden-regression` require for its workflow. This covers every active route type, for example Standard Merge, AB Merge, CtrlRAM Replace, and General Replace. DP Replace is retired from the canonical policy, so keep DP evidence as reference only, unless the owner approves a decision that restores that workflow and updates the schema, loader, and publication policy. For example, Standard Merge needs a single-chip direct Golden, and CtrlRAM Replace needs one Golden for each declared FW contract and each Single or Cascade topology. A General Replace that touches TP ranges also runs a postbuild, so it needs its own case. A missing case is unexecuted, never a pass.
8. **Write docs, tests, and the PR.** Update `supported-ic-matrix.md` and `ic-workflow-flowcharts.md`. Update the other matrices the runbook names when they apply. Use the runbook's PR notes checklist. For a confidential drop, file names and hashes stay in the private repository, and the PR names only the IC and the evidence kind. Ranges, command order, processor write ranges, and Golden promotion are R3 and need firmware-owner review.

Ask the owner about each risky decision on its own. Group related questions, at most three per round, and continue the independent work meanwhile.
